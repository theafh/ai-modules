# Scope append-only to settled entries, and consolidate a session's own log entry

## Goal

Every wiki generated from or maintained by this skill states that `log.md` is append-only with respect to *settled* entries — those from earlier sessions — and that a session writing about its own ongoing work keeps **one** entry recording the net effect of that work, rewriting it as the work churns rather than appending a new entry per commit or per refinement. The canonical `template_log.md` preamble and the base skill's append-a-log-entry guidance carry the rule, and it is worded as one coherent qualification of append-only alongside the repair carve-out. The outcome an owner sees: a page refined across several commits in one session, or edited and then reverted, leaves a single entry describing what actually shipped, not a running commentary of intermediate states nobody can see in the committed wiki — and no rule tells the agent that touching the entry it just wrote is forbidden.

This task owns the **content** of one default rule: what counts as append-only and how a session records its own multi-step work. It is a sibling of the subject-scope rule in [wiki_log-scope-wiki-changes-only.md](wiki_log-scope-wiki-changes-only.md) and shares the append-only region with the repair carve-out in [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md); all three co-edit the same preamble. [wiki_log-scope-wiki-changes-only.md](wiki_log-scope-wiki-changes-only.md) is order-independent, while [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) lands first because this task rewrites the absolute append-only phrasing it will author.

## Context

The append-only contract as written treats every dated entry as immutable and says nothing about the boundary between a settled entry and the one a session is still forming. Today's carriers: the `template_log.md` preamble opens `Chronological record of wiki changes. Append-only.`; its `Entries:` group still says an operation that creates or updates wiki files `appends one entry`; `template_schema.md` still carries a `must be appended` log-convention bullet; and the base skill's `<appending_to_log>` block (`skills/wiki/SKILL.md`) defines newest-at-bottom ordering and is silent on revising an already-written entry. The same absolute reading also lives outside `<appending_to_log>`: the architecture-diagram annotation `# Chronological action log (append-only, rotated yearly)`, the `<query>` step whose bold lead-in is `Append a \`query\` log entry when the query changed files` (body: a file-changing query `appends one entry`), and the`<update_navigation>` ingest write site that says `Append to \`log.md\`: \`## [YYYY-MM-DD] ingest | Source Title\``. Sibling [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) is still`checked`; it will add to the preamble region the substance rule`the log is append-only in substance, so never reword, reorder, or delete a past entry's recorded content` plus a repair carve-out. Read together, the short unconditional `Append-only.` / `appends one entry` surfaces plus that silence leave no settled-vs-in-progress boundary — and once the sibling's absolute substance sentence lands, a literal reading would forbid the consolidation this task wants: an agent that wrote an entry earlier in a session and then refined the same page across two more commits is told to append two more entries rather than fold the work into the one it already wrote.

That literal reading is the failure mode, and it is not hypothetical. In a downstream wiki a session refined one page across several commits and, in a later turn, deleted a block and restored it; each step drew its own log entry, including entries describing a delete-then-restore that no committed state reflects. The owner's correction: the log should record what the commit ships, not the transitions between commits that nobody will ever see, and making every edit its own entry is noise. The distinction the rule must draw is between a **settled** entry — one from a prior session, part of the history other readers depend on — which append-only protects absolutely, and the **current session's own** entry for work still in progress, which the session may rewrite because it is not yet settled history.

The subject-scope sibling [wiki_log-scope-wiki-changes-only.md](wiki_log-scope-wiki-changes-only.md) settles *what an entry is about*; this task settles *how many entries a session's work produces and whether it may revise its own*. The heading-repair sibling [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) will carve one exception into append-only — an entry may be edited to repair a structural or lint break it introduced, provided the repair preserves what the entry records. This task adds a second, adjacent qualification: the current session may consolidate its own entry, which *does* change what the entry records. The two must read as one coherent paragraph rather than two rules that appear to fight, so the wording is a genuine co-edit of the same preamble region and the same `<appending_to_log>` block (plus the diagram, query, and `<update_navigation>` absolute sites named above); this task lands after that sibling and supersedes the absolute "never reword, reorder, or delete a past entry's recorded content" phrasing that sibling will author with the settled-entry-scoped form, composing the two into one qualification.

Consolidation is an authoring judgement an agent makes while writing, not a property a linter can compute from the committed file — a log with one entry per commit is byte-valid and indistinguishable by rule from one an agent chose to write that way. So this task ships as canonical prose plus agent guidance, and does not add a lint check.

Propagation rides the channel the sibling log tasks already use: the rule lives in the `template_log.md` preamble above the first `## [` heading, so it reaches new wikis at init and existing wikis through the boilerplate-drift path that the `auto_shaper_wiki` agent's preamble-restore move (`<fix_log_preamble_drift>` in `agents/auto_shaper_wiki.md`) already runs. Keep the new lines inside that boilerplate-checked region or the propagation is lost.

## Approach

1. **Scope append-only in the canonical preamble, and rewrite `Entries:` for consolidation.** In the `template_log.md` preamble, reword the append-only statement so it binds *settled* entries — entries from earlier sessions — rather than every dated entry unconditionally. Rewrite the existing `Entries:` group in place (do not add a parallel granularity group beside it). Define once here: a **session** is the current agent conversation that authored the entry (that boundary is what makes a prior session's entries *settled*); **consolidation** is one current entry per coherent work unit — the same subject or change set — within that session, not one mega-entry for unrelated operations in the same conversation. Target `Entries:` form: an operation that creates or updates wiki files records into the session's current entry for that work unit — append when the session has none open for it, rewrite that entry while the session is still revising the same work unit (refining a page across commits, or deleting and restoring content); an operation that changes no file writes none; work that no committed state reflects, such as a delete later restored, leaves no entry; lint and audit runs remain the exception — each records its outcome, including a zero-change one, as a process record. Name the failure the rule prevents in one clause, so the agent applies a rule it understands: an entry per commit, or an entry narrating churn no committed state shows, turns the log into a transition record instead of a record of what shipped. Leave `Body:` untouched except as needed for adjacent preamble coherence. Word the append-only scoping so it and the repair carve-out from [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) read as one coherent qualification, not two competing ones.

2. **Mirror it across the base skill's append-facing sites.** In `skills/wiki/SKILL.md`, rewrite every greppable absolute append-only / unconditional “appends one entry” / create-or-update “Append to `log.md`” directive so one scoped reading remains, pointing at the preamble rather than restating the whole rule: (a) `<appending_to_log>` — rewrite the opening “An entry records a change” / unconditional append-one framing so append-only protects settled (prior-session) entries and the current work-unit entry consolidates as the work evolves (append when none open for that unit; rewrite when consolidating), pointing at the preamble rather than restating it; keep the standing newest-at-bottom, **Anchor on the previous entry's last body line**, cluster-ordering, and post-edit grep-verify directives as the mechanics for a genuine append; supersede the absolute one-entry-per-operation reading so one canonical create-or-rewrite directive remains, and do not retire those append mechanics when adding consolidation; (b) the architecture-diagram annotation that today reads `# Chronological action log (append-only, rotated yearly)` (including any repair-carve-out wording [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) will add) — supersede any absolute or repair-only reading with the settled-entry-scoped form, keeping yearly rotation; (c) the `<query>` step `Append a \`query\` log entry when the query changed files` — supersede “appends one entry” so a file-changing query records through the session's consolidating entry for that work unit (create or rewrite) rather than mandating a fresh append each time, still listing exactly the files that changed and still writing nothing when nothing changed; (d) the `<update_navigation>` ingest write site that today says `Append to \`log.md\`: \`## [YYYY-MM-DD] ingest | Source Title\`` — supersede that unconditional Append so an ingest that created or updated files records through the session's consolidating work-unit entry (append when none open; rewrite when consolidating), still listing only files actually created or updated and still writing nothing when nothing changed. Do not leave a second absolute copy beside the new text. Leave lint and audit process-record Append sites under the process-record exception already named in **Scope append-only in the canonical preamble, and rewrite `Entries:` for consolidation.**

3. **Mirror the convention in the schema template.** Rewrite the log convention bullet in `template_schema.md` (the bullet that currently opens `Every operation that creates or updates wiki files must be appended`) in place so it carries the same rewritten `Entries:` consolidation semantics from **Scope append-only in the canonical preamble, and rewrite `Entries:` for consolidation.** — create/update records into the session's current work-unit entry (append when none open; rewrite when consolidating); compose consolidation into whatever subject-scope wording is already present on that bullet, or leave a single bullet that will hold both when [wiki_log-scope-wiki-changes-only.md](wiki_log-scope-wiki-changes-only.md) lands; point at the preamble rather than restating; do not leave an absolute “must be appended” / one-entry-per-operation reading beside the scoped form.

4. **Reconcile the agent's append-only language.** Where `agents/auto_shaper_wiki.md` calls dated entries append-only and out of scope for its scaffold diff, confirm that language still reads correctly once "append-only" means "settled entries." The agent audits rather than authors session work, so it needs no consolidation move; the edit here is only ensuring its append-only wording does not re-assert the absolute form this task scopes down.

**Out of scope:** A linter check for consolidation, rejected because one-entry-per-commit is byte-valid and an agent's authoring judgement is not mechanically recoverable from the committed file. Rewriting historical entries in any existing wiki, which stays the owner's editorial call as [wiki_log-heading-uniqueness-and-repair.md](wiki_log-heading-uniqueness-and-repair.md) will establish for append-only history. A behavioural eval proving an agent consolidates rather than appends, which belongs to the wiki front-end behaviour suite in [tests_wiki-front-end-behavior-evals.md](tests_wiki-front-end-behavior-evals.md). Rewriting the post-approval “append a single … entry” steps in `wiki_import` / `wiki_wrapup`, since each front-end’s single action-typed entry after approval is already one coherent work unit and remains a genuine append under the settled-entry / consolidation rule this task ships in the preamble and base skill.
