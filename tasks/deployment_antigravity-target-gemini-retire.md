# Retire the Gemini CLI deploy target and correct the Antigravity target

## Goal

Update `deployment/deployment.sh` (and its `deployment.conf` and `deployment/README.md`) to (a) **retire the `gemini` deploy target** because consumer Gemini CLI is retired, and (b) **correct and expand the `antigravity` target** so it deploys into every directory Antigravity actually reads and supports **skills**, **(sub)agents**, and **hooks**.

The user-visible outcome is that one `./deployment/deployment.sh --target antigravity` run lands this repo's skills, agents, and hooks in every place Antigravity reads them, so the components work whichever Antigravity app the user happens to run — 2.0, the IDE, or the CLI — without the operator knowing which root belongs to which product. Concretely: each skill arrives as a real `SKILL.md` directory tree, each agent as a file whose frontmatter is transformed into Antigravity's schema, and the repo's hook as a declarative `hooks.json` plus its script. Alongside that, `gemini` is no longer an accepted target, its dead generators and config are gone, and the docs reflect both changes.

Reaching every product is achievable, and cheaper than the root split first suggests. Project mode needs nothing special: the workspace `.agents/` tree is uniform, so one deploy covers all three products. Globally, agents and hooks are single-rooted under `~/.gemini/config/` and so already reach every product from one write. **Only skills actually fan out**, to the three documented skill roots. So "works with whatever app the user uses" costs one extra copy per skill rather than triplicating the whole deploy.

## Context

The verified Antigravity facts, their sources, and the frontmatter-tolerance finding this task's agent transform depends on are owned by [ai-dev_harness-portability-antigravity-gemini-retire.md](archive/ai-dev_harness-portability-antigravity-gemini-retire.md); this task consumes them and should follow it, or re-verify the paths against official `antigravity.google` docs if built first. The deploy-relevant facts are restated here so this file stands alone.

**Why retire Gemini.** Consumer Gemini CLI was retired on 18 June 2026 (`410 Gone`; only paid/enterprise API-key access survives), and Google's live surface is Antigravity, which shares the `~/.gemini` tree. Deploying to live consumer Gemini CLI no longer reaches a working tool, so the `gemini` target is removed rather than maintained.

**What Antigravity actually reads.** Verified against official `antigravity.google/docs` pages during the linked skill task; the skill records the per-page sources. The workspace tree is uniform across products: `.agents/{skills,agents,rules,plugins}/` plus `.agents/{mcp_config.json,hooks.json}`. Globally the roots split **by artefact class, not by product**: agents (`agents/`), hooks (`hooks.json`), MCP (`mcp_config.json`), and sidecars (`sidecars/`) all sit under `~/.gemini/config/`, while **skills split three ways** — `~/.gemini/config/skills/<skill-folder>/` for 2.0, `~/.gemini/antigravity/skills/<skill-folder>/` for the IDE, `~/.gemini/antigravity-cli/skills/` for the CLI — and **plugins split two**, `~/.gemini/config/plugins/` for 2.0 and the IDE against `~/.gemini/antigravity-cli/plugins/<plugin_name>/` for the CLI. Skills are `skills/<name>/SKILL.md` directory trees under the Agent Skills open standard (near drop-in with this repo's skills); agents are `agents/<name>.md`; hooks are a declarative `hooks.json`.

Correcting an earlier premise of this task: `~/.gemini/antigravity` is **not** purely a transcript/artifact output path. It is the IDE's documented global **skills** root as well, so the directory serves both purposes and the script's current use of it is right for IDE skills and wrong for everything else. The breakage to fix is therefore not "stop pointing at `~/.gemini/antigravity`" but "stop treating one directory as the whole Antigravity target", which the skill-root fan-out in the Approach settles by writing every documented root instead of choosing between them.

**Current state in `deployment/deployment.sh`** (reference each site by its symbol, not a line number):

- `GEMINI_DIR` has a consumer that is **not** the Gemini target: `clear_backups_for_active_targets()` and the backup creation loop both special-case `app_id == "antigravity"` onto `backup_roots=("${GEMINI_DIR}|")`, so the variable already serves as the Antigravity tree root. Both sites take a `path|backup_name` pair where an empty name falls back to `basename(path)`, and `backup_app_dir` skips silently when the path does not exist — so an emptied `GEMINI_DIR` degrades to a no-op rather than an error. This is why retirement renames the variable instead of deleting it.
- The target-directories block (the `if [[ -n "$PROJECT_DIR" ]]` … `else` split) sets `GEMINI_DIR="${HOME_DIR}/.gemini"` and `ANTIGRAVITY_DIR="${HOME_DIR}/.gemini/antigravity"` globally, and leaves both empty in project mode with a comment that Gemini and Antigravity have no project convention. Antigravity **does** have a project convention (`.agents/`), so that assumption is wrong.
- `ALL_APP_TARGETS` carries `opencode`, `gemini|Gemini CLI|${GEMINI_DIR}`, and `antigravity|Antigravity|${ANTIGRAVITY_DIR}`.
- In `install_for_app()`, the `command` case has a `gemini` arm calling `generate_toml_command` (→ `${app_dir}/commands/<name>.toml`) and an `antigravity` arm calling `generate_antigravity_workflow` (→ `${app_dir}/workflows/<name>.md`); the `agent` case dispatches to `generate_gemini_agent` for `gemini` (and `generate_toml_agent` for `codex`), and its `antigravity` arm is a stub whose whole body is `info "skip" "[$name] Antigravity does not support agent definitions"` — so the generator is net-new while that false skip is an existing passage this task rewrites.
- Gemini-only helpers `generate_toml_command`, `generate_gemini_agent`, `map_gemini_tool_name`, and `GEMINI_AGENT_ALLOWED_KEYS` become dead once the `gemini` target is gone; confirm no other caller before deleting.
- `deployment/deployment.conf` has a `#gemini` and a `#antigravity` section (each `disallow:*legacy*`) and names both in its header comment; the script header comment and `--target` help text enumerate `opencode`, `gemini`, and `antigravity`; `deployment/README.md` carries Gemini/Antigravity rows in its Target Layout and Generated Formats tables, and its Target Layout Antigravity **Agents** cell reads `not supported (skipped)`.

**The Antigravity agent transform.** The repo's agents are Claude-style markdown; the script already generates target-specific variants (`generate_toml_agent` for Codex, `generate_gemini_agent` for Gemini) that first run `rewrite_agent_frontmatter` then emit the target's schema. A new `generate_antigravity_agent` follows that shape, mapping to Antigravity's native frontmatter: `name` and `description`, both **required** by Antigravity's documented agent frontmatter and so mandatory survivors of the whitelist, then a `tools` array of Antigravity tool names, `model` as a tier (`inherit`|`flash`|`pro`, defaulting to `inherit`, with an `inherit` sentinel or omission for session inheritance), `commandExecutionPolicy` (`off`|`auto`|`eager`|`sandbox`, default `sandbox`), and `mainAgent: false` on every agent it writes — `mainAgent` and `subagent` both default to `true`, so `subagent: true` restates the default while the default `mainAgent: true` would register the agent as user-invocable; `plugins/*/agents/` holds `auto_*`-named files exclusively, which the standing repo rule **Name skills and agents by invocation mode and collision risk** reserves for agents no user invokes, so the generator marks the spawn-only role unconditionally the way `generate_opencode_agent` already emits an unconditional `mode: subagent` in this script. A source carrying no `tools:` line at all — the state of three of the repo's six agent sources today — generates no `tools` key rather than an empty array, the same absent-field handling every agent generator in this script already applies. What Antigravity makes of that absence stays unverified: `harness_portability`'s `<agent_definition_surfaces>` records the field's documented default as `[]`, and no official page says whether an empty or absent array grants every tool or none, so this task records the gap rather than assuming a semantic in either direction. Read-only roles land on both Antigravity levers, the mapped `tools` array and `commandExecutionPolicy`, driven by the source `readonly:` field both sibling generators already read: `readonly: true` with a `Bash`-free `tools:` allowlist emits `commandExecutionPolicy: off`, `readonly: true` with `Bash` present emits `sandbox` because the role still needs contained command execution, and every other agent takes the `sandbox` default — the split `harness_portability`'s `<readonly_agent_enforcement>` prescribes, where `off` denies commands outright while `sandbox` denies only unsandboxed ones. Gate it on the same `Bash`-in-allowlist test `generate_opencode_agent` uses to drop its `bash: deny` clause, this target's counterpart to `generate_toml_agent`'s `sandbox_mode = "read-only"`.

Two tool-name corrections carried over from the linked skill task, because getting either wrong fails silently. The documented vocabulary is `view_file`, `grep_search`, `run_command` and the fuller hook-matcher list — **not** `read_file` or `edit_file`, which circulate widely but appear on no official page — and no canonical tool list is published anywhere in the docs. **The unmappable-tool rule:** the generator emits every source tool name it can map to a name copied verbatim from a documented list, and drops only the individual entry it cannot map, leaving the mapped names in the array. The repo's own agents are the worked case — `tools: Read, Grep, Glob` generates `tools: [view_file, grep_search]`, because `Read` and `Grep` have verbatim documented names while `Glob` has none, and `Bash` adds `run_command` where an agent carries it. An unmapped or misspelled tool name makes the subagent **hang at runtime** rather than fail at load, so a wrong mapping is worse than a missing entry. Likewise `flash_lite` is not a real tier: it appears in neither the subagents frontmatter table nor the model list, so emitting it risks the same silent failure.

**Hooks — the documented contract.** Antigravity hooks are declarative, closer to the Claude/Codex JSON-config arms the script already has than to OpenCode's code bridge in [deployment_opencode-hook-bridge.md](deployment_opencode-hook-bridge.md).

The config file keys by a **named hook first, then the event** — unlike Claude and Codex, which nest events under a top-level `hooks` key:

```json
{
  "charter_guardrail": {
    "PreToolUse": [
      { "matcher": "*", "hooks": [ { "type": "command", "command": "<deployed charter_guardrail.sh>", "timeout": 10 } ] }
    ]
  }
}
```

`matcher` takes an exact tool name, `""` or `"*"` for all tools, `"a|b"` alternatives, or a regex like `"browser_.*"`.

The `PreToolUse` stdin envelope addresses the tool at `toolCall.name` and its parameters at `toolCall.args`, and carries **two casings**: the envelope is camelCase (`toolCall`, `stepIdx`, `conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`) while the nested arguments are PascalCase — a shell call arrives as `toolCall.args.CommandLine` with `toolCall.args.Cwd`. There is no top-level `cwd`. On stdout the handler returns `{"decision": "deny", "reason": "…"}`, with `decision` one of `allow`/`deny`/`ask`/`force_ask` and an optional `permissionOverrides` array.

**What that means for `charter_guardrail.sh`.** The script reads its envelope through a handful of `jq` pulls (`.cwd`, `.tool_name`, `.tool_input.file_path`, `.tool_input.command`) and blocks through a single `block()` function that `exit 2`s — one input mapping and one output choke point, so the adaptation is contained rather than sprawling. Give it an Antigravity branch that reads `toolCall.name`, takes the shell command from `toolCall.args.CommandLine`, takes the directory from `toolCall.args.Cwd` or `workspacePaths[0]`, and makes `block()` print `{"decision":"deny","reason":"…"}` on stdout and exit 0 instead of exiting 2. Detect the shape rather than the harness — the presence of `toolCall` is the signal, which keeps the branch correct if Antigravity is renamed again and follows the skill's own capability-over-identity carve-out rule. Probe for it without `jq`, as a shell `case` on the captured `input_json` in the style of the script's existing `*CHARTER.md*` fast-path case and placed ahead of the `command -v jq` check, so the flag is set before the first `block()` call: the `jq is required to inspect hook input` and `hook input was not valid JSON` aborts both run where no `jq` pull can succeed, and a `jq`-computed flag would leave exactly those two exiting 2 — the fail-open **Hooks ship in this task — settled.** rejects.

Only `run_command`'s argument keys are documented, so do not guess a per-tool key for the file-writing tools (`write_to_file`, `replace_file_content`, `multi_replace_file_content`). Scan every string value under `toolCall.args` for a CHARTER.md path instead: it covers all three file-writing tools without knowing their key names, and stays correct when Antigravity adds another. The `apply_patch` arm simply never fires here, as Antigravity has no such tool.

**Shared surfaces.** The OpenCode target owned by [deployment_opencode-target.md](archive/deployment_opencode-target.md) has shipped, so its `VALID_TARGETS`, `ALL_APP_TARGETS`, target-directories, and `install_for_app()` edits are already in `deployment.sh`; this task lands second and reconciles those shared regions around the live `opencode` entries, leaving the archived record as written. The copy-based (non-symlink) deploy model this task's skill copy follows is established by [deployment_copy-not-symlink.md](archive/deployment_copy-not-symlink.md).

## Approach

**Retire Gemini — the target, not the string.** Retirement means no `gemini` deploy target and no Gemini-CLI-shaped generator survives, and that every remaining mention of the string serves Antigravity's needs. It does **not** mean purging `gemini` from the script: Antigravity's own tree is `~/.gemini`, because Google kept the legacy directory name when it ported the app, so the correct end state still contains `.gemini` paths throughout. A blanket "grep finds no gemini" check would therefore be wrong, and would push an implementer into renaming real paths.

Remove `gemini` from `VALID_TARGETS`; drop the `gemini|Gemini CLI|…` row from `ALL_APP_TARGETS`; delete the `gemini` arms from the `command` and `agent` cases in `install_for_app()`; delete the now-dead `generate_toml_command`, `generate_gemini_agent`, `map_gemini_tool_name`, and `GEMINI_AGENT_ALLOWED_KEYS` after confirming no other caller. Keep the parked `# GEMINI_MD="${GEMINI_DIR}/GEMINI.md"` declaration rather than deleting it, renaming it in place to `# ANTIGRAVITY_RULES_MD="${ANTIGRAVITY_TREE_DIR}/GEMINI.md"` and leaving it commented under its existing revival note: `~/.gemini/GEMINI.md` is Antigravity's global rules file, so the line is a remaining `.gemini` mention that serves Antigravity, and [deployment_park-managed-rules-scaffolding.md](archive/deployment_park-managed-rules-scaffolding.md) parked it to stay revivable — a byte-identical `${GEMINI_DIR}` stops resolving once the rename lands. Leave the other four parked declarations untouched; this is the only one the rename reaches. Remove the `#gemini` section from `deployment.conf` together with `gemini` in that file's own header-comment tool-identifier list; and strike Gemini CLI as a *target* from the script header comment, the `--target` help text, `deployment/README.md`, and the root `README.md` — while letting those same docs name `~/.gemini` paths where they describe Antigravity. `tests/deployment/script_tests/run.sh` carries no `gemini` scenarios, so retirement deletes no test there; the Claude- and Codex-shaped envelope scenarios the `charter_guardrail.sh` change must keep passing live in `tests/charter_guardrail/script_tests/run.sh`.

**Rename `GEMINI_DIR`, do not delete it — it has a live non-Gemini consumer.** Both backup sites special-case the Antigravity target onto `backup_roots=("${GEMINI_DIR}|")`, so `GEMINI_DIR` is already the Antigravity tree root rather than a Gemini-target variable. Deleting the assignment while leaving those two references would set the antigravity backup root to the empty string, and neither `backup_app_dir` nor `clear_old_backups_for_app_dir` errors on an empty path — backups would silently stop and `--clear-backups` would operate on nothing, with no failure surfaced. Rename it to `ANTIGRAVITY_TREE_DIR="${HOME_DIR}/.gemini"` and update both backup sites, so no `GEMINI_`-prefixed variable remains and every Antigravity path derives from an Antigravity-named one. Keep `ANTIGRAVITY_DIR` as the target's `ALL_APP_TARGETS` base dir — `${ANTIGRAVITY_TREE_DIR}/config` globally, `${PROJECT_DIR}/.agents` in project mode — so the existing base-dir contract that `install_for_app()` relies on is unchanged, and set `ANTIGRAVITY_TREE_DIR` to `${PROJECT_DIR}/.agents` in project mode where there is no `~/.gemini` tree.

**Make the retired flag say why.** `--target gemini` should abort with a message naming the retirement and the successor — that Gemini CLI support is retired because Google is removing that app and porting it to Antigravity, and that `--target antigravity` is the replacement — rather than falling through to the generic "Unknown deploy target" abort, which reads as a typo and leaves an operator with a working `gemini` deploy in their notes guessing.

**Correct and expand Antigravity.** Set `ANTIGRAVITY_DIR` to `${ANTIGRAVITY_TREE_DIR}/config` in the global branch and `${PROJECT_DIR}/.agents` in the project branch (stop skipping Antigravity in project mode, and rewrite the `# Build filtered target list...` skip comment to reflect Gemini is removed and Antigravity supported). `deployment/README.md` asserts the same skip in prose — the project-dir sentence under the **Target Layout** table reading `It skips Gemini and Antigravity (no documented project-level config convention)` — so rewrite it in place to name `<project>/.agents/` as Antigravity's project path beside OpenCode's `<project>/.opencode/`, rather than striking only the word Gemini and leaving the README claiming Antigravity is skipped. That base dir stays the single home for agents and hooks, which reach every product from there. In `install_for_app()`, rewrite the `antigravity` arms in place so: the `agent` case's existing `Antigravity does not support agent definitions` skip arm becomes a call to a new `generate_antigravity_agent` writing `${app_dir}/agents/<name>.md`, replacing that arm rather than adding a second one, since bash `case` takes the first match and an appended arm never fires; the `skill` case copies the directory tree (mirroring the copy-based `claude`/`opencode` skill branch) to **each** documented global skill root rather than to `${app_dir}/skills/<name>/` alone; and the `command` case loses its `antigravity` arm entirely, along with the `generate_antigravity_workflow` helper, per the settled no-workflow-deployment decision below. Refresh the Antigravity rows in the script header/help and in the `deployment/README.md` Target Layout and Generated Formats tables, and leave `deployment.conf`'s `#antigravity` section at its existing `disallow:*legacy*` line — Antigravity's per-source hook filtering lives in the basename gate under **Hooks.**, not in the conf.

**Fan skills out to every product's skill root.** Introduce an explicit list of Antigravity global skill roots — `${ANTIGRAVITY_TREE_DIR}/config/skills`, `${ANTIGRAVITY_TREE_DIR}/antigravity/skills`, and `${ANTIGRAVITY_TREE_DIR}/antigravity-cli/skills` — and have the global-mode `skill` arm copy each skill tree into every one of them, so the operator does not have to know which root their app reads. Project mode writes the single `${PROJECT_DIR}/.agents/skills/<name>/` and needs no fan-out. Two consequences follow from the global fan-out and each must be handled rather than assumed: every copied path is recorded in the uninstall log so `--uninstall --target antigravity` removes all of them and leaves no orphan skill behind; and every root the fan-out names is created before its copy, which the `skill` case's existing unconditional `ensure_dir "$dest_dir"` call supplies once the loop runs it per root.

**Open decision: who owns `.agents/skills` in project mode.** `${PROJECT_DIR}/.agents/skills` is byte-identical to the `CODEX_SKILLS_DIR` the `skill` case already redirects `codex` onto, because `.agents/` is Antigravity's native workspace root and Codex's project skill root at once — so a plain `--project-dir` run with no `--target` filter has both targets writing and logging one directory. The write is harmless (one source, the same `copy_path_with_replacements` call); the removal is not, because `append_deployed_artifact_log` records the path once per target id, `dedupe_deployed_artifact_log` keeps both lines since the ids differ, and target-filtered `uninstall_logged_artifacts` reaches `remove_logged_path`'s `rm -rf`, so `--uninstall --target antigravity` deletes the tree Codex still depends on and strands Codex's log entry on an absent path. The options are (1) one owner, with `${PROJECT_DIR}/.agents/skills` always logged under the `codex` target id whichever run writes it, while the `antigravity` branch skips the copy when `codex` is also active and performs it when `codex` is filtered out; (2) the mirror, with the `codex` redirect deferring to Antigravity's native root and `antigravity` the sole owner id; (3) both writing under their own ids, with `uninstall_logged_artifacts` taught to retain a path another target still claims. **Default without further input: option 1, with the owner pinned to the path rather than to the run** — extend the `skill` case's existing `app_id` branch, which already picks `CODEX_SKILLS_DIR`, to carry a log-owner id that defaults to `$app_id` and is pinned to `codex` when `antigravity` writes in project mode, and pass it as the `target_id` argument of `copy_path_with_replacements`. The pin is safe because that argument is log-only at this call site — the identically named parameter that derives vendor prefixes belongs to `rewrite_agent_frontmatter` on the `agent` path — and `uninstall_logged_artifacts` is the log's only reader, so deploys never consult it and repeated runs collapse to one line. `codex` owns the path because `CODEX_SKILLS_DIR` already holds it in the shipped script and `ALL_APP_TARGETS` lists `codex` ahead of `antigravity`. The accepted cost is that `--uninstall --target antigravity` leaves the shared tree for a `codex`-scoped or unfiltered uninstall to remove; option 3 instead changes uninstall semantics for every target.

**Backups need no change beyond the rename.** Every Antigravity write lands under `~/.gemini`, and both backup sites already point the antigravity target at that whole tree, so the single existing root covers all three skill roots, the config subtree, and any config location a future Antigravity version adds there — coverage an enumerated per-root list would silently lose. `backup_app_dir` derives the backup name from `basename`, so the root yields a self-describing `~/.gemini_<timestamp>` with no naming override needed; the bare-`config_<timestamp>` worry only applies if the backup root is narrowed to `~/.gemini/config`, so leave it at the tree. The only edit here is the `GEMINI_DIR` → `ANTIGRAVITY_TREE_DIR` rename at both sites. Resist narrowing the backup root to match the base dir: it would trade complete coverage for a longer, staleness-prone list. One residual risk to note in `deployment/README.md` rather than solve: no page states that a product reads *only* its own root, so if one app reads two of these roots the same skill id could register twice — benign here since every copy is byte-identical, but worth recording so a future duplicate-id report is diagnosable.

**Hooks.** Ship the Antigravity-shaped config as a source file rather than synthesizing it in the script: add `plugins/ai_dev/hooks/antigravity-hooks.json` beside the existing Claude and Codex hook configs, carrying the single top-level named-hook key `charter_guardrail` in the Context's JSON shape, with matcher `"*"` and the relative command `./hooks/charter_guardrail.sh`. Extend the `hook` case with an `antigravity` arm ahead of the trailing `*)` default: its JSON branch gates on that exact basename — as the `codex` arm gates on `codex-custom-deploy-hooks.json`, so the Claude-shaped `plugins/ai_dev/hooks/hooks.json` is skipped rather than deployed — and merges it into `${app_dir}/hooks.json` through `merge_json_key`, passing `${app_dir}/hooks` as `hooks_dir` globally and the project-root-relative `.agents/hooks` in project mode, exactly as the `claude` arm splits those two shapes so a committed config carries no machine path; its `.sh` branch copies `charter_guardrail.sh` into `${app_dir}/hooks/` and marks it executable. Keep the named-hook key a jq-safe identifier rather than the hyphenated form Antigravity's own docs illustrate, because `merge_json_key`'s `jq ".${key}"`, the deploy log's `path[key]` notation, and `strip_json_key`'s `del(.${key})` each interpolate it unquoted, and a hyphen aborts the merge and silently skips the uninstall. Then teach `charter_guardrail.sh` the Antigravity branch the Context specifies, keeping the guardrail policy itself in the one shared script. Three enumerations of the harness-specific hook-config set live outside `deployment/` and name only Claude and Codex, so the fourth config lands in each of them too, rewritten in place per the `CHARTER.md` invariant beginning `Plugin metadata, local marketplaces, and documentation`: `plugins/ai_dev/README.md`'s single `charter_guardrail` bullet extends its existing clause chain to Antigravity's `hooks/antigravity-hooks.json`; the root `README.md` layout-tree comment `# shared hook scripts plus Claude/Codex hook configs` becomes `# shared hook scripts plus Claude/Codex/Antigravity hook configs`; and the root `README.md` phrase `harness-specific hook configs for Claude and Codex` becomes `harness-specific hook configs for Claude, Codex, and Antigravity`. Ship this with the rest of the task, per **Hooks ship in this task — settled.**

**Hooks ship in this task — settled.** The question was whether the `charter_guardrail.sh` adaptation could be written from documentation or needed an observed envelope first. It can: `antigravity.google/docs/hooks` and `/docs/ide/hooks` publish the full `PreToolUse` stdin payload, the stdout `decision`/`reason`/`permissionOverrides` response, and the `hooks.json` matcher syntax, all reproduced in the Context above. The one genuinely undocumented corner — per-tool argument keys for the file-writing tools — is sidestepped by scanning every string under `toolCall.args` rather than naming a key, so it does not gate the work. The OpenCode target/hook-bridge split does not apply as precedent: that split existed because OpenCode needed a new TypeScript bridge plugin in a new runtime, whereas this is one JSON emit plus a branch in an existing 172-line script. Splitting would also be actively worse than waiting, since a `hooks.json` deployed against an unadapted script would leave Antigravity with no `decision` and **fail open** — a guardrail that looks active and is not.

**No Antigravity workflow deployment — settled, not deferred.** Three facts close this. The repo ships no commands at all, so the `command` case has nothing to deploy for any new target. `CHARTER.md` treats a standalone command as "a legacy, deprecated mechanism the deployer still installs but new work no longer adds", so building an Antigravity command path is work the charter points away from. And no official page names a workflow directory — the docs describe workflows as created through IDE controls that pick global or workspace scope — so the existing `generate_antigravity_workflow` helper's `${app_dir}/workflows/<name>.md` target is a guess. Delete that helper along with the `command`-case `antigravity` arm rather than carrying an unverified path for a deprecated mechanism with zero artefacts to move. This is a decision, not a gap: a future doc revision naming the directory would not by itself justify adding the case, since the charter's deprecation and the empty command set both still hold.

**Antigravity agent frontmatter uses the whitelist — settled.** The generator cannot be a passthrough regardless of tolerance, because Claude's capitalized comma-separated `tools:` string has to become Antigravity's lowercase array with each name mapped or dropped. Once a real transform exists, whitelisting the target's keys costs nothing beyond it, while a passthrough would additionally have to be *safe*, which the unconfirmed tolerance cannot promise. The whitelist is therefore correct whether the loader turns out strict or tolerant, and `generate_toml_agent` already demonstrates the shape in this script. Implement the whitelist and drop non-Antigravity keys; if someone later confirms tolerance empirically, record it in the skill as a fact rather than reopening this as a deployment choice.
