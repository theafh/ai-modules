# Autonomous tree-shaper — refine task_fix with an opt-in auto_shaper_task agent

## Goal

Grow the autonomous tree-shaping capability **inside `task_fix`** rather than shipping a second skill for it. `task_fix` stays the single user-facing entry point for whole-tree repair — the task-backlog twin of `wiki_fix` — and keeps its current inline four-phase pass (orient → assess → remediate → verify) as the fast default for the common small-tree case. On explicit opt-in — the user asks for autonomous judgement-call resolution, or the tree is large enough that inline iteration strains one context — `task_fix` escalates to one new spawned agent, `auto_shaper_task`, which becomes the single serialized writer for that run and drives a read-only assess fan-out of the existing `auto_*_task` agents over the judgement calls `task_fix` today only surfaces. The capability earns an **agent, not a skill**: there is no manual fix sibling for an `_auto_` skill to sit beside, and the standing naming rule keeps a sole entry point on its family-first name even when it delegates to agents (`wiki_fix`). Net change: no new skill, one new agent. The escalation is bounded to converge on the original tasks made sound, never a mutation of them, and `task_fix`'s familiar inline behavior is unchanged for anyone who does not opt in.

## Context

This reframes the earlier plan to build a separate `task_auto_shaper` skill. The deciding rule is the repo's naming convention: a skill that is the only entry point for its capability keeps the ordinary family-first name even when it delegates to agents (`wiki_fix`), and the `<family>_auto_<rest>` skill form is reserved for an automation skill that must sit beside a classical sibling of the same capability (`task_auto_check` beside read-only `task_check`). Whole-tree fix has exactly one entry point — `task_fix` — and no manual fix sibling, so a second `task_auto_shaper` skill would manufacture exactly the two-entry-points-for-one-job collision the rule guards against. `task_fix` is also already a writer-and-looper (it auto-fixes mechanical findings and re-lints), so the escalation adds **scale and one autonomy tier** (resolve the judgement calls instead of only surfacing them), not a new kind of action; that is why folding it in fits, where `task_check` → `task_auto_check` correctly forked because it crossed read-only into writing. `task_fix`'s own design note already named the safe shape and called it an *agent* — "a read-only assess fan-out feeding a single remediation writer, never per-file write agents (they would race on the shared link graph)" — so this realizes its lineage rather than rivaling it. The principled asymmetry against [`task_auto_implement`](task-family_autonomous-implement-loop.md) is worth stating: that sibling earns skill status by sitting beside the manual `task_implement`, whereas the shaper has no `task_shaper` to sit beside.

The gate stays `task_fix`/the linter (whole-tree health), distinct from `task_check` (per-task readiness). Driving one task to `ready` is the job of [`task_auto_check`](archive/task-family_autonomous-readiness-loop.md): it surfaces or routes the structural splits it cannot safely make, and the `task_fix` tree pass is precisely the actor that executes them. The two share one technique — generate-then-verify anchored on a frozen task `## Goal`, coverage from diverse generation and precision from refute-by-default verification, never counting agreement (on one model, agreement reflects shared priors, not truth). That technique already lives in the shared `auto_*_task` agents and the readiness-loop precedent, so it is **reused by citation, not redefined here**, and the shaper may invoke `task_auto_check` per task when a tree pass also wants the readiness dimension. `auto_shaper_task` follows the repo's [agent-naming convention](archive/cross-repo_convention-and-wiki-rename.md) — `auto_<role>_<family>`, the verbatim twin of `auto_shaper_wiki` with the family token swapped, role kept to the single word `shaper`.

Implementing this repoints the live references that named the old skill: `task_fix`'s design note (rewritten in place, since "no dedicated agent" becomes false), `task_auto_check`'s `<structural_split_boundary>` and `<output_contract>` (route stuck structural work to `task_fix` / `auto_shaper_task`), the [implement-loop](task-family_autonomous-implement-loop.md)'s auto-trio sentence (reworded so the fix member is `task_fix`'s escalation, not a peer skill), the [standing-doc framework](task-family_optional-standing-doc-conventions.md)'s charter-consumer set (cover `auto_shaper_task`), and both READMEs' `task_fix` bullets. Archived files that name the old skill stay as historical record.

## Approach

Realize the capability as a hybrid in `task_fix` plus one spawned agent, modeled on the proven `auto_shaper_wiki` shape — the same four named phases, task-first cold iteration that evaluates each task fresh to break the confirmation-bias cascade, the re-Read-after-`git mv` discipline before inbound-link edits, the contested protocol that surfaces contradictions without picking a winner, and the confirm-before-bulk gate for changes spanning many files.

- **Inline default, explicit escalation.** `task_fix` runs its current inline pass by default and surfaces the judgement calls exactly as today. It hands off to `auto_shaper_task` only on an explicit, user-visible signal — a request for autonomous resolution, or a scale trigger the user confirms — never a silent switch, so the everyday "clean up the backlog" stays cheap, predictable, and surface-only. This deliberate deviation from `wiki_fix` (which delegates with zero inline work) is justified: the fixed cost of spawning an agent and its read fan-out is not worth paying on a handful of files, consistent with the wiki cost lesson that kept parallelism optional. `task_fix`'s `description` and activation prose must advertise both modes so the router and human browsers can still find the autonomous capability.
- **One writer per run, across both paths.** Escalation is mutually exclusive with the inline remediate phase: either `task_fix` writes inline (small tree) or `auto_shaper_task` writes (escalated), never both, so the single-serialized-writer invariant holds and two writes never touch overlapping cross-references at once. The spawned assess agents only ever read.
- **Parallel assess fan-out, serial writes.** The agent applies generate-then-verify to the judgement calls on two read-side axes that may run in parallel: per-task cold reads (breadth, and the confirmation-bias break) and per-judgement-call diverse-lens stances from `auto_reviewer_task` (coverage, unioned). An independent refute-by-default `auto_verifier_task` is the **synthesis** — it decides what to do, gated on the frozen intent, and never counts agreement. Writes stay strictly serial through the single writer because tasks share a link graph; **parallel writers are an explicit non-goal**. File-creating splits and link-graph relocations — the most dangerous to parallelize — are executed only by the writer itself (as `auto_shaper_wiki` performs its own splits), informed by a reviewer's split summary rather than written by a sub-agent.
- **Bounded to defect-resolution, drift-guarded.** Where `task_fix` can only surface a split, a body-framing reframe, or a scope relocation, the agent resolves it — but only when the generate-then-verify pass returns a verified fix and the change clears two guards run before any write: the project [charter gate](task-family_charter-guardrail-for-autonomy.md) (consumed through the standing-doc framework's presence-gated mechanism, guarding against drifting the *project*) and a frozen-`Goal` snapshot per edited task (guarding against drifting an individual *task* from its own objective). Each applied fix also passes an adversarial fidelity pass charged solely with whether the change drifts a task from its frozen intent, able to veto or narrow it, and is a minimum change applied only when verified. The mandate is bounded to resolving the **defects** `task_fix` surfaces, not open-ended optimization, which is the engine of drift. The loop **stops** when a full round produces no change that survives verification, with a hard iteration cap as a backstop; genuine contradictions and contested calls are surfaced via the contested protocol, never auto-resolved. Because the mandate is defect-resolution and the intent is frozen, the fixed point is the original backlog made sound.

Non-goals: a second skill of any kind (the deliverable is `task_fix` refined plus one agent); per-task `open` → `ready` readiness promotion, which is `task_auto_check`'s job (the shaper may invoke it but does not redefine it); autonomous code implementation ([`task_auto_implement`](task-family_autonomous-implement-loop.md)); any spawned agent writing to the shared link graph or any parallel-writer path; and changing `task_fix`'s inline default for users who do not opt in.

## Acceptance

- The deliverable adds **no new skill and exactly one new agent**, `auto_shaper_task` (`auto_<role>_<family>`, role `shaper`); a grep confirms no `skills/` directory was added for this work and that `auto_shaper_task` exists under the plugin's `agents/`. The base `task` skill's `<family>` roster and the sibling family lists gain **no** new line, because agents are not roster members.
- `task_fix`'s inline default is unchanged: a plain "health-check my tasks" on a small tree runs the inline four-phase pass with no agent spawned and leaves the judgement calls surfaced rather than resolved (a check confirms this path still runs).
- On explicit opt-in over a staged messy backlog, `auto_shaper_task` is the single serialized writer and drives the linter to zero with no cross-reference corruption across fixes that touch overlapping links; a grep confirms the spawned **assess** agents (`auto_reviewer_task`, `auto_verifier_task`, and `auto_gate_task` when a pass wants readiness) carry the `auto_*_task` name and none writes, while `auto_shaper_task` is the lone writer.
- On a staged backlog the agent autonomously resolves at least the split, body-framing-reframe, and scope-relocation classes `task_fix` surfaces, applying each only when the generate-then-verify pass returns a verified fix and both the charter gate and the frozen-`Goal` fidelity gate pass; a planted charter violation blocks the corresponding write and that task is left untouched and surfaced.
- The loop freezes each edited task's original `## Goal` and gates every applied change on fidelity to it: on a staged task where a candidate "fix" would alter the objective, the adversarial fidelity pass rejects or narrows it and the original objective is preserved.
- The loop stops when a round surfaces no verified change, with a hard iteration cap as backstop: a staged already-clean tree applies zero changes and terminates in one round, and a staged defected tree converges and then stops once no verified defect remains.
- Genuine cross-task contradictions are marked and surfaced via the contested protocol, never auto-resolved, on a staged contradicting-pair fixture.
- Parallelism stays read-side only: cold reads may fan out per task and stances per judgement call, the refute-by-default verifier is the synthesis and never counts agreement, and a check confirms no parallel-writer path exists and that splits and relocations are executed only by the single writer.
- Reuse is by citation: a grep confirms `auto_shaper_task` and the reused assess agents cite the base `task` skill, `task_fix`, and the readiness-loop technique rather than copying their rules or restating the stance list.
- References are repointed: a grep for `task_auto_shaper` across live (non-archive) files returns zero; `task_fix`'s design note is rewritten in place with no surviving "no dedicated agent" claim; `task_auto_check`'s `<structural_split_boundary>` and `<output_contract>` and the implement-loop's auto-trio sentence name `task_fix` / `auto_shaper_task`; the standing-doc charter-consumer set covers `auto_shaper_task`; both READMEs' `task_fix` bullets reflect the inline-default-plus-escalation shape; and archived files are left unchanged.
- `make lint` passes and `auto_shaper_task` is registered in the plugin README, metadata, and both marketplaces.
