# Harden auto-loop stop conditions so the orchestrator cannot walk past them

## Goal

`git_auto_review` and the task-family loops stop where their rules say they stop. Only the invoking user's request raises a loop's round cap: the `round-cap-authority: user` attestation is a caller contract, and an orchestrator that writes it violates that contract, with the harness as the hard backstop. From round 2 the gate reviews the cumulative run change — the run's base ref diffed against the current tree, so the original change's lines plus every fixer write, with repository code the run never touched left out — instead of re-reading the whole repository. A finding on a line the change did not add or modify is a follow-up task proposal, not a fix. Each round records why it continues, and every stop the loop controls after the relay exists writes `report.txt` with the cap source, the per-round continue reasons, and the unapplied findings. The prior severity-floor decision stays in force: `inferred` and should-fix findings remain eligible for a fix while the loop is under its cap.

## Context

- **Observed run.** A recent `git_auto_review` run over a large change in a downstream repository completed 10 rounds plus an aborted 11th, raised 28 qualifying findings, every one `non_blocking`, and landed 25 regression reproductions. The user asked why 11 rounds ran when the default cap is 5.
- **The cap was overridden by the orchestrator.** `<inputs>` accepts the literal phrase `round cap <N>` "written anywhere in the prompt". The orchestrator composes the prompt it invokes `git_auto_review` with, so it wrote `round cap 8`, then `10`, then was on `11` without any user instruction; the gate and fixer prompts are never cap sources. The cap is the loop's designed brake; the override handed the brake to the party the brake exists to restrain.
- **The re-review was not a stated review subject.** The `<role>` says the loop "re-reviews the delta", but `<round_driver>` says round 2+ uses "the same target shape as round 1", and the gate's report rule orders every defect either evidence set carries. Nothing bounded the subject to the run's own change, so each round re-derived `inferred`/should-fix items from repository code the run never touched. That is the source of the long tail. The fix is the cumulative run change: the run baseline diffed against the current tree, which carries the original change plus the fixer's writes and nothing else.
- **The scope anchor is elastic.** `<scope_anchor>` admits a finding that concerns "lines the change added or modified, or behaviour the change's intent covers". The second clause admitted an unmodified documentation bullet, an unmodified watcher branch, and an unmodified warm-up function. Those were the findings that pulled the loop into adjacent cleanup.
- **The self-written stop did not fire.** It counts only two consecutive rounds whose findings all sit in code the loop wrote. Findings on the original commit's code never count, so a large first change can run indefinitely without meeting it. Keeping the original change's lines inside the review subject keeps those findings available, so the stop stays meaningful.
- **No round recorded why it continued.** The per-round record has `decision <continue|stop>` but no reason. A round could continue on a non-blocking nit without saying so.
- **`report.txt` was never written.** The run was stopped by the user, and the orchestrator ended without the terminal report the `<relay>` contract requires. The relay held gate, fixer, verifier, and round-diff files but no `report.txt`.
- **The severity-floor decision stays.** A prior repo decision deliberately removed a severity floor so `inferred` and "should be fixed" findings get fixed. This task does not re-introduce a floor, and it does not change `git_review`'s headings or labels.
- **Existing tests to extend.** `tests/git_auto_review/evals/` carries `honours_round_cap`, `stops_on_self_written_code`, `lists_preexisting_issue`, `lists_scope_extension`, and `fixes_inferred_and_should_fix_findings`; `tests/git_auto_review/script_tests/run.sh` carries `s4_convergence_labels_single_source` and `s5_carryover_blocks`; `plugins/ai_dev/skills/task_auto_check/SKILL.md` `<loop_bounds>` carries the same "unless the user prompt supplies a positive integer override" pattern. The shipped `honours_task_scope_anchor` eval expects an untouched-file finding to be fixed through the task file; it changes to expect a follow-up, because the task-file anchor no longer widens the line-level anchor, while its `honours_task_scope_anchor_no_task` twin already expects that follow-up. The `honours_round_cap` fixtures cite committed lines the change never modifies, so their cited lines move onto changed lines to keep the cap reachable.

## Approach

1. **Make cap authority user-only.** In `plugins/ai_dev/skills/git_auto_review/SKILL.md` `<inputs>`, rewrite the bullet that opens `**An optional round-cap override**`:
   - The phrase is read only from the invoking user's request, meaning the skill's own invocation prompt carrying the literal attestation line `round-cap-authority: user` that the invoking user's request supplies.
   - An orchestrator-composed gate or fixer prompt is never a cap source.
   - A positive-integer `round cap <N>` phrase in the invocation prompt with no attestation line — the observed orchestrator override — is the contract violation the run records while still using the default cap. That is the only case that records `round-cap-without-attestation`.
   - Keep the bullet's existing invalid-integer sentence verbatim, so its behaviour keeps a textual pin.
   - Record the two outcomes for a non-override phrase beside the kept sentence rather than inside it: a phrase whose integer is not a positive integer is not an override, records `contract-violations none`, and records `cap-source default`.
   - The named-target bullet's own "written anywhere in the prompt" wording stays as it is; only the round-cap bullet changes.
   - Absent the attestation the run uses the default cap and records `cap-source default`; when the attested phrase supplies the cap the run records `cap-source user`, and an attestation with no `round cap <N>` phrase records `cap-source default`. `cap-source` follows the cap actually used.
   - The attestation is a caller contract, not a security boundary: the loop trusts its invoking caller, and an orchestrator that writes the line violates the contract; the harness remains the hard backstop.
   - Extend the `final-state block` field list, in `<relay>`, to `stop <condition> | cap-source <user|default> | contract-violations <none|round-cap-without-attestation> | files-changed <path[,path]|none> | pending-decisions <wording|none>`. This is the one statement of both fields.
   - Apply the same authority rule to `plugins/ai_dev/skills/task_auto_check/SKILL.md` in that skill's own vocabulary, editing both its `<inputs>` max-round bullet and its `<loop_bounds>`: the override is read only from the invoking user's request and counts only when that request carries the same `round-cap-authority: user` attestation, so a max-round value carried in an orchestrator-composed helper prompt is not an override and the run keeps the default cap. Add no `cap-source` or `contract-violations` field to `task_auto_check`; those fields belong to `git_auto_review` alone.
2. **State the cap as a hard ceiling.** In `<stop_rule>`, at the sentence that already ends a round on the cap, add the `report.txt` obligation: the run stops and writes `report.txt`; no finding reopens a round. Keep the existing default of 5 and the user-supplied override as the only exception.
3. **Review the cumulative run change from round 2.** In `<round_driver>`, replace "with the same target shape as round 1" with: from round 2 the gate's review subject is the cumulative run change — the run's base ref diffed against the current tree — where the run's base ref is the base state round 1 reviewed against, distinct from the `baseline.patch`/`baseline.untracked.tar` authored pair. On a branch target it is the merge base of `<remote>/<default>` and `HEAD`; on a default-branch target it is the upstream ref that branch's `local-commits lane` is read against, so the local commits ahead of it stay inside the subject, and it falls back to `HEAD` when that branch has no upstream ref. That subject carries the original change's lines plus every fixer write since the baseline, with the current working tree supplying current line numbers only, and repository code outside that diff is outside the subject. On a branch target the subject is the union of the branch-mode evidence and the uncommitted evidence the gate already collects, so the existing two-collection rule stays the mechanism. On a default-branch target, add a third collection to the gate: branch mode with `--base <upstream> --head <checked-out branch>`, because `collect_uncommitted` writes the local commits as a `git log` listing with no diff, so without that set a defect in a local commit would sit inside the stated subject but stay invisible to the gate; the subject is then that set's union with the uncommitted set. `git_review` keeps its existing target resolution — a pull request, a branch, or nothing — so the subject is a scope the gate states, not a new `git_review` target shape. The prior gate return supplies the prior findings set. A prior finding outside the review subject is re-listed with its prior tag and no fix. A brand-new finding outside the review subject is listed under the existing `What should be fixed though it is not a clear bug` heading as a follow-up task proposal, carrying the `new` tag `git_review` gives a defect first seen in the delta, with no fix. This adds no heading and no new tag value. `round-r<round>.diff.txt` stays what `<relay>` says it is — the round's fixer-write diff for the verifier — and is not the gate's subject. A pre-seeded gate return supplies the gate's classification as written, and `<convergence>`'s qualification and subject filters still apply to it. Round 1 keeps the full-change review. The orchestrator computes the subject once per round from the gate's evidence sets — the branch-mode diff and the uncommitted set, whose `### untracked` section carries a created path's content — and names it in the gate prompt; `git diff <base-ref>` supplies only the tracked-path part, so an untracked created file stays inside the subject. Write the `<round_driver>` subject as one rule per sentence rather than one stacked sentence: the baseline per target shape, the subject's contents, the line-number convention, the outside-subject exclusion, and the per-target evidence mechanism each get their own sentence. In `plugins/ai_dev/agents/auto_gate_git.md`, replace the `<policy>` delta sentence "take the same target shape as round 1 as the review subject" with a sentence naming the cumulative run change as the round-2+ subject and stating both outside-subject dispositions; bound the report rule "Report every defect either set carries" to every defect inside that subject, rewording "either set" and the adjacent "When both sets carry the same defect" sentence so the default branch's third set is included, naming repository code the run never touched as outside it, and state the disposition once so the bound and the listing do not read as contradictory: a defect inside the subject is a finding, and a defect outside it is a follow-up line. **Out of scope:**

- Changing `git_review`'s review criteria or its own target shapes.

- Observing or reporting a hard user abort, meaning the harness or user killing the run outside the loop's own stop conditions; a kill the loop cannot observe carries no report requirement.
- The downstream change that exposed the run; this task hardens the loop, not that change.
