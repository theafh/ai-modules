# Add Antigravity coverage to harness_portability and drop Gemini CLI as a target

## Goal

Update the `harness_portability` skill so it covers **Google Antigravity** as a first-class target harness with verified current facts, rewrites the now-stale Gemini-CLI-derived claims so they describe Antigravity where the live Google surface is meant, and records one short note that Gemini CLI is dropped as a supported target because its consumer surface is retired.

The user-visible outcome is that an agent consulting the skill treats Antigravity — the live Google surface shared across its IDE, CLI, and 2.0 desktop app — as *the* Google target, with correct config paths and correct skill / agent / hook / plugin models, and no longer encodes the retired consumer Gemini CLI as a live deploy target or carries Gemini CLI's strict-frontmatter behaviour as if it were Antigravity's.

## Context

**Why this change.** Google's consumer Gemini CLI was retired on 18 June 2026 — AI Pro/Ultra and free usage now return `410 Gone`; only paid/enterprise API-key access survives ([transition blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/), [gemini-cli discussion #27274](https://github.com/google-gemini/gemini-cli/discussions/27274)). The `google-gemini/gemini-cli` repo stays active as a spec, but the surface a user actually runs is now **Antigravity** — a Go rewrite that shares the `~/.gemini` lineage and inherited Skills, Hooks, Subagents, and Extensions (renamed "plugins"). So the skill's Gemini coverage is both stale (it points agents at a retired serving target) and mis-scoped (Antigravity, not Gemini CLI, is the live surface). The skill's current treatment of Gemini CLI as an agent-definition-only, strict-schema surface is doubly out of date.

**Current skill passages that name Gemini CLI** (all in `plugins/ai_dev/skills/harness_portability/SKILL.md`), to rewrite in place: the `description:` frontmatter; the `<target_harnesses>` scope clause; and the `<agent_definition_surfaces>`, `<frontmatter_schema_tolerance>`, `<tool_name_namespaces>`, `<readonly_agent_enforcement>`, `<reasoning_effort_portability>`, and `<native_fields_and_deploy_bridges>` sections. Antigravity is absent from the skill entirely. The skill already models a diverging full target (OpenCode) through a `<cross_harness_artefact_discovery>` block, an `<opencode_plugin_hooks>` hook block, and per-surface agent coverage — that treatment is the template for Antigravity.

**Antigravity facts to encode.** Each carries a confidence flag; the skill's own `<policy>` rule — *"State the provider documentation source or the verification gap when a change depends on harness-specific execution, initialization, configuration, filesystem, environment, permission, or tool-discovery behavior"* — governs how an unconfirmed fact is written, so anything below marked *verify* is encoded with its source or as an explicit gap, never as settled fact.

- **Shared config tree across all Antigravity surfaces (IDE, CLI, 2.0)** *(well-corroborated; verify the exact `config/` level against official docs)*: global `~/.gemini/config/{skills,agents,plugins,sidecars}/` plus `~/.gemini/config/{mcp_config.json,hooks.json}`, with `~/.gemini/GEMINI.md` sitting one level up (not under `config/`); workspace `.agents/{skills,agents,rules,plugins}/` with `.agent/` and `_agents/` as back-compat. The per-product `~/.gemini/antigravity` (2.0) and `~/.gemini/antigravity-cli` (CLI) directories are **transcript / artifact output paths, not config** — one deploy into the shared tree reaches all surfaces.
- **Skills** *(confirmed, [antigravity.google/docs/skills](https://antigravity.google/docs/skills))*: `SKILL.md` + `name`/`description` frontmatter under the Agent Skills open standard, model-invoked with progressive disclosure; workspace `.agents/skills/<skill>/`, global `~/.gemini/config/skills/<skill>/`. The `.agents/skills/` alias is a foreign-directory convergence worth noting beside the existing OpenCode `<cross_harness_artefact_discovery>` coverage.
- **Subagents** *(confirmed schema, [antigravity.google/docs/subagents](https://antigravity.google/docs/subagents); re-verify the full field list)*: `.agents/agents/<name>.md` or `.agents/agents/<name>/agent.md`; global `~/.gemini/config/agents/…`; bundled `plugins/<plugin>/agents/`. Frontmatter: `name`, `description`, `tools[]` (native tool names; an unmapped/misspelled name causes a runtime **hang**, not a load rejection), `model` (`inherit`|`flash_lite`|`flash`|`pro`), `commandExecutionPolicy` (`off`|`auto`|`eager`|`sandbox`, default `sandbox`), `mainAgent`/`subagent` booleans, `mcpServers` (camelCase), `skills`/`plugins` dependency arrays, plus `hidden`/`inheritMcp` seen in community docs.
- **Tool namespace** *(confirmed)*: native identifiers `read_file`, `edit_file`, `invoke_subagent`, `define_subagent` — a distinct namespace from Claude/Codex/OpenCode/Gemini-CLI. Read-only enforcement = a `tools[]` allowlist plus `commandExecutionPolicy` (`off`/`sandbox`), the Antigravity equivalent of the levers `<readonly_agent_enforcement>` already lists per harness.
- **Hooks** *(confirmed, [antigravity.google/docs/hooks](https://antigravity.google/docs/hooks))*: declarative `hooks.json` in `.agents/` (workspace) or `~/.gemini/config/` (global); events `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`; stdin/stdout JSON with **camelCase** fields (`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`); `PreToolUse` returns a `decision` of `allow`|`deny`|`ask`|`force_ask`; works in both IDE and CLI; a Python SDK hooks module also exists. **Divergence trap:** Gemini CLI's own hooks used `BeforeTool`/`AfterTool` — Antigravity uses the Claude-style `PreToolUse`/`PostToolUse` names but with camelCase JSON, so equivalence between the two Google surfaces cannot be assumed. Unlike OpenCode's code-only bridge, Antigravity hooks are declarative, so they sit closer to the Claude/Codex JSON-config model.
- **Plugins (bundling unit)** *(confirmed bundle, [antigravity.google/docs/plugins](https://antigravity.google/docs/plugins); mapping undocumented)*: `plugin.json` under `.agents/plugins/` or `~/.gemini/config/plugins/`, bundling skills + rules + MCP + hooks (and agents via `plugins/<plugin>/agents/` per the subagents doc, though the plugins overview omits agents — a documented inconsistency). Gemini CLI Extensions migrate into Antigravity plugins, but how a `gemini-extension.json` maps onto `plugin.json` is undocumented.
- **Rules / workflows** *(partial)*: workspace rules `.agents/rules/*.md` (≈12,000-char cap, four activation modes), global rules `~/.gemini/GEMINI.md`, project-root `AGENTS.md` (precedence over `GEMINI.md` is secondary-sourced); workflows are markdown slash commands.

**Verification gaps to carry as gaps, not facts** — the highest-value one being frontmatter strictness: Gemini CLI's Node loader rejected a single unknown frontmatter key; whether Antigravity's Go loader does the same is **unconfirmed and the evidence leans tolerant** — official subagents/skills docs are silent, the only documented Antigravity validation gotcha is the bad-tool-name runtime hang, and the fixed-allowlist "unexpected fields" behaviour that circulates is VS Code's own SKILL.md editor linter ([microsoft/vscode #294520](https://github.com/microsoft/vscode/issues/294520)), which may surface cosmetic warnings inside Antigravity's editor but is not a runtime load rejection and never names Antigravity. Also verify: the exact `~/.gemini/config/` paths, the hook event names and camelCase envelope, the `plugin.json` layout, whether agents are officially part of plugin bundles, and the extension→plugin mapping.

**Shared surface.** [ai-dev_rename-harness-portability-to-plugin-portability.md](ai-dev_rename-harness-portability-to-plugin-portability.md) (status `ready`) renames this skill's directory and identifiers to `plugin_portability` and co-edits the same `SKILL.md`. Keep this task's edits name-agnostic — change section bodies and the frontmatter `description`, not the skill's identity — so whichever task lands second reconciles without conflict.

## Approach

Rewrite each affected passage of `plugins/ai_dev/skills/harness_portability/SKILL.md` in place rather than appending Antigravity beside stale Gemini text:

- In `<target_harnesses>`, add Antigravity as a full target (skills, agents, commands, hooks, plugins) alongside Codex/Claude/OpenCode, and replace the Gemini clause with one short note that Gemini CLI is dropped as a supported target because its consumer surface is retired (18 June 2026; paid/enterprise API-key access is the only survivor). Keep the retirement note to the one or two sentences the user asked for.
- Mirror the OpenCode treatment for Antigravity's diverging model: extend `<cross_harness_artefact_discovery>` with Antigravity's shared `~/.gemini/config/` global tree, `.agents/` workspace tree, the `.agents/skills/` foreign-directory alias, and the clarification that `~/.gemini/antigravity[-cli]` are transcript/output dirs rather than config; add an Antigravity hook block (declarative `hooks.json`, the five events, the camelCase envelope, the `allow`/`deny`/`ask`/`force_ask` decision, and the `BeforeTool`/`AfterTool`-vs-`PreToolUse`/`PostToolUse` divergence trap) beside `<opencode_plugin_hooks>`.
- Update the agent-surface sections to Antigravity's native facts where the live target is meant: agent paths and the fuller frontmatter field set in `<agent_definition_surfaces>`; the native `read_file`/`edit_file`/`invoke_subagent` tool namespace in `<tool_name_namespaces>`; the `tools[]` + `commandExecutionPolicy` read-only levers in `<readonly_agent_enforcement>`; the `inherit`/`flash_lite`/`flash`/`pro` model tiers in `<reasoning_effort_portability>` and `<native_fields_and_deploy_bridges>`.
- In `<frontmatter_schema_tolerance>`, attribute the strict-unknown-key-fails behaviour to the **retired Gemini CLI** loader and record Antigravity's tolerance as unconfirmed (evidence leans tolerant, verify against the Go loader or empirically), so the union-of-native-fields classification for the Google target is marked pending verification rather than stated as strict.
- Rewrite the `description:` frontmatter in place to name Antigravity and drop the implication that Gemini CLI is a live target, keeping one canonical line.
- Preserve Gemini CLI facts only where they still teach — as clearly-labelled history of the retired surface — never as live-target guidance. Apply the skill's own official-doc-or-explicit-gap rule to every Antigravity claim, carrying the verification-gap items above as gaps.

**Out of scope:**

- Deployment-script changes — retiring the Gemini deploy target and correcting the Antigravity target across `deployment/deployment.sh`, `deployment/deployment.conf`, and `deployment/README.md` — belong to a separate deployment-scope task and are not touched here; this task edits only the skill.
- Renaming the skill to `plugin_portability` stays owned by [ai-dev_rename-harness-portability-to-plugin-portability.md](ai-dev_rename-harness-portability-to-plugin-portability.md); this task edits content under whatever name is current.
