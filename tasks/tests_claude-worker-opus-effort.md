# Run Claude evals on Opus at high effort, with effort in commands, cache keys, and baselines

## Goal

Every harness that runs a Claude worker runs it on the latest Opus (the `opus` alias) at high effort in place of `sonnet`. The two harnesses with an LLM judge run that judge on `opus` at `xhigh` effort. Effort becomes a vendor setting with a command-line override. It reaches every Claude worker and judge command, joins the shared verdict cache key, is recorded beside the model in each run record, and takes part in the trigger-eval baseline check. A Claude verdict therefore always names the model and effort that produced it, and it never replays or compares across a different model or effort. Cursor keeps `auto` and gains no effort setting. The docs state how long a Claude eval runs at high effort and what a full Claude suite costs, and the evals README records the measurements these defaults rest on.

The switch matters because `sonnet` verdicts measure the model's shortcuts rather than the skill: on agent_spinner, `sonnet` reached the right answers while skipping the procedure the skill requires. Opus at high effort follows that procedure where Opus at low effort mostly did not, and high is the effort the operator's own Claude Code sessions run at, so high-effort verdicts reflect how the skills are used.

## Context

- **Vendor settings today.** `tests/lib/vendor.py` holds one `VendorConfig` per vendor in `_CONFIGS`. The Claude entry carries `worker_model="sonnet"` and `judge_model=""` (inherit the CLI default), and the Cursor entry carries `auto` for both. `add_vendor_arguments` offers `--model` and, when called with `with_judge`, `--judge-model`, and `resolve` builds a `Resolved` from them. No effort setting exists. The Claude branches of `build_print_cmd` and `build_stream_cmd` each append `--model` and nothing else.
- **The verdict cache.** `content_key` in `tests/lib/eval_cache.py` takes a `model=` keyword and stores `model` in the cache record. Every runner that imports the cache passes `model=resolved.worker_model`; `rg -l "content_key\(" tests --glob '**/evals/run.py'` finds them. The unit tests that call `content_key` directly, found by `rg -l "content_key\(" tests --glob 'test_*.py'`, pass a literal model.
- **The judges.** `tests/language_humanizer/evals/run.py` and `tests/natural_language/evals/run.py` pass `resolved.judge_model` to their judge calls, which `rg -n "judge_model" tests/language_humanizer tests/natural_language` finds. Neither harness imports the cache. [The language_humanizer shared-pool task](tests_language-humanizer-shared-pool.md) moves that harness's pass loop, judge call included, into the shared pool, so both tasks edit the judge call path in `tests/language_humanizer/evals/run.py`. Neither depends on the other, and whichever lands second carries the judge effort through the call as it then stands.
- **Trigger evals.** `tests/trigger_evals/run.py` resolves its deployed-mode worker through the vendor settings and writes `worker_model` into `results.json`. Its `--baseline` check refuses a baseline from another vendor and reports `baseline vendor mismatch`, but it compares no model, so a Claude run on `opus` would diff silently against a Claude baseline recorded on `sonnet`. Its `--force-uuid` path hands `--model` to skill-creator's own runner.
- **The CLI.** `claude` 2.1.289 accepts `--model opus`, which its stream-json init event resolves to the latest Opus id, and `--effort low|medium|high|xhigh|max`, which it also accepts in print mode. Neither the init event (`per_turn_effort_active` reads `true` with and without the flag) nor `--debug` output names the effective level, but the low-effort and high-effort probe runs below behaved differently on the same evals, which shows the flag takes effect. The binary also reads a `CLAUDE_CODE_EFFORT_LEVEL` environment variable and an `effortLevel` setting.
- **Measurements behind the defaults (2026-11-13).** Every run used `claude` 2.1.289 on agent_spinner at commit `c592b42`, and their run directories sit in local scratch space that no clone carries:
  - **`sonnet`, full suite.** 56 of 93 evals passed, 36 failed, and `checker_spawned_through_role` stayed inconclusive because it outran a 560-second wall-clock cap twice. Every runner-level check passed, and the recorded Cursor verdicts all pass.
  - **Opus at low effort.** On the 36 `sonnet` failures plus six `sonnet` passes, run with `--no-cache` through a wrapper that added `--effort low`, it fixed 8 of the 36, failed `blind_pass_by_prompt` where `sonnet` passed, and left `checker_spawned_through_role` inconclusive again. Most remaining failures hit the same checks `sonnet` failed. The median run took 89 seconds against 57 for `sonnet`.
  - **Opus at high effort.** On eight still-failing evals, two from each failure cluster (pre-dispatch plan, per-item fan-out, ledger records, report contract), failed checks fell from 28 at low effort to 6. `containment_one_path` and `placeholder_figure_held` passed. `documented_absence_stays_conditional` and `report_rederivation` each failed one check. `inline_floor`, `phase_plan_announcement`, `roster_partial_stop`, and `twelve_files_twelve_rows` hit the probe's 500-second worker timeout with every check passing except the final report's opening, which a killed run never writes. Runs took 182 to over 500 seconds, and the eight cost about nine points of the five-hour usage window.
- **Docs that state the Claude default.** The vendor table under `### Model policy` in `tests/CLAUDE.md` and its twin `tests/AGENTS.md` give the Claude worker model as `sonnet` and the judge as inherit. `TESTING.md`, `tests/README.md`, and the runner docstrings and usage lines (`--model sonnet|auto|''`) name `sonnet` as the Claude worker. Tables that record past runs name `sonnet` as history. The newest dated run heading in `tests/agent_spinner/evals/README.md` records the 2026-11-12 helper-role spawn-route run.

## Approach

1. **Vendor settings.** Give `VendorConfig` and `Resolved` a `worker_effort` and a `judge_effort`. Set the Claude entry to `worker_model="opus"`, `worker_effort="high"`, `judge_model="opus"`, and `judge_effort="xhigh"`, and give the Cursor entry empty efforts. `add_vendor_arguments` gains `--effort`, plus `--judge-effort` when called with `with_judge`, each overriding the vendor default the way `--model` does, with an empty string omitting the flag from the command. A non-empty effort on Cursor stops `resolve` with an error that names Claude as the vendor with an effort control.
2. **Commands.** The Claude branches of `build_print_cmd` and `build_stream_cmd` append `--effort <level>` after `--model` whenever the level is non-empty. Each judge call in the two judge harnesses passes `resolved.judge_effort` beside `resolved.judge_model`, so the judge command carries both.
3. **Cache key.** `content_key` takes a required keyword `effort`, hashes it beside `model`, and stores it in the cache record beside `model`. Every runner the Context selector finds passes `effort=resolved.worker_effort`, and every unit-test call passes a literal effort. Make the keyword required, so a caller that misses it fails on its first call.
4. **Run records.** Each run record that names the worker model names its effort beside it: the `"model"` entries in `tests/lib/eval_runner.py` and the runners, found by `rg -l '"model": ' tests/lib/eval_runner.py tests/*/evals/run.py tests/wiki/layer2/run.py`, plus `worker_model` in the trigger evals' `results.json`, which gains `worker_effort`.
5. **Trigger baselines.** Extend the trigger evals' baseline check so a baseline whose `worker_model` or `worker_effort` differs from the run's is handled like a vendor mismatch: the run writes its results without a comparison and exits non-zero, naming both values. A baseline with no `worker_effort` field reads as the empty effort.
6. **Docs.** Rewrite the Claude rows of the vendor table in `tests/CLAUDE.md` and `tests/AGENTS.md` to `opus` (latest alias) at high effort for the worker and `opus` at `xhigh` for the judge, and add `--effort` and `--judge-effort` to the override paragraph beside `--model` and `--judge-model`. Below the table in both files, add a runtime and cost paragraph: at high effort a Claude eval runs for minutes, 182 to over 500 seconds in the measurements, so an agent whose tool calls have a wall-clock limit runs few evals per call and reports an eval that outlasts one call as inconclusive; a full Claude suite costs about one point of the five-hour window per eval, so it spans more than one window, and a run that pauses at the operator's quota threshold resumes after the reset by re-running the same command, which replays the verdicts already cached. Rewrite each other statement of the current Claude default in `TESTING.md`, `tests/README.md`, and the runner docstrings and usage lines in place. Leave tables that record past runs as they stand.
7. **Measurement record.** In `tests/agent_spinner/evals/README.md`, add the heading `### 2026-11-13, Claude Code 2.1.289, worker model and effort probe` after the last recorded-results section, and record there the three measurements Context lists, with the commit, the eval sets, the method (the effort wrapper, `--no-cache`, and the wall-clock cap), each result, and the runtime and cost figures.

**Out of scope:**

- An effort setting for Cursor's worker or judge, since this task adds effort to Claude's commands only.
- Effort on the `--force-uuid` path, since that path hands its run to skill-creator's own runner.
- Raising any runner's timeouts, so the defaults and the per-eval `timeout` entries stay as they are.
- Re-running recorded measurements on the new default, beyond the confirmation run Acceptance names.

## Acceptance

- `python3 tests/lib/test_vendor.py` passes new cases: a default Claude resolve gives worker `opus` at `high` and judge `opus` at `xhigh`; the Claude print and stream commands carry `--model opus` and `--effort high`; `--effort ''` drops the flag; a Cursor command carries no `--effort`; and an explicit effort on Cursor stops with the error naming Claude.
- `python3 tests/lib/test_eval_cache.py` passes a case in which two keys that differ only in effort differ, and a case in which a `content_key` call without `effort` raises `TypeError`.
- Every file `rg -l "content_key\(" tests --glob '**/evals/run.py'` lists also matches `rg -l "effort=resolved.worker_effort"`, and `python3 tests/lib/test_eval_runner.py` and `python3 tests/agent_spinner/evals/test_run.py` pass with their `content_key` calls carrying an effort.
- For every file `rg -l '"model": ' tests/lib/eval_runner.py tests/*/evals/run.py tests/wiki/layer2/run.py` lists, `rg -c '"effort": '` on that file equals `rg -c '"model": '`.
- A hermetic test on the deterministic surface of each judge harness shows that its Claude judge command carries `--model opus` and `--effort xhigh`.
- `bash tests/trigger_evals/script_tests/run.sh` passes new scenarios: a baseline with another `worker_model` and a baseline with another `worker_effort` each produce results with no comparison, a non-zero exit, and a message naming both values, and `results.json` carries `worker_effort`.
- In `tests/CLAUDE.md` and `tests/AGENTS.md`, the vendor table's Claude worker row names `opus` and high effort, the judge row names `opus` and `xhigh`, the runtime and cost paragraph from Approach step 6 follows the table, and `rg -n "\bsonnet\b"` over both files, `TESTING.md`, `tests/README.md`, and the runner `.py` files under `tests/` finds only lines that record past runs.
- `tests/agent_spinner/evals/README.md` carries the heading from Approach step 7, and its section states the `sonnet` result (56 of 93), the low-effort result (8 of 36 fixed), and the high-effort result (28 failed checks down to 6), each with its commit, eval set, and method.
- `python3 tests/agent_spinner/evals/run.py --vendor claude smoke_inline_body` passes, and its `timing.json` and cache record name model `opus` and effort `high`. A second run with `--effort medium` reports no cache hit.
