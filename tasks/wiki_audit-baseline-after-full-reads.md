# Move the wiki audit baseline and checked dates forward only after full reads

## Goal

The wiki audit agent, `auto_shaper_wiki`, saves work by re-reading only the pages that changed since its last audit. It knows where the last audit stopped from the `Audit baseline:` line in that audit's `log.md` entry, which records a git commit. The agent treats every page unchanged since that commit as already checked and skips it.

Today the audit writes the current commit as the new baseline at the end of every run, even when it read only a few pages. The next audit then skips every page that changed before that commit, including the pages nobody read. A page's `checked:` date in its frontmatter has the same problem. It gets a new date even when the page was only partly read, or when only some of its claims were checked.

After this task, both records claim only what actually happened:

- The audit moves the baseline to the current commit only when it read every page that changed since the previous baseline, each one in full. Otherwise it keeps the previous baseline, so the next audit reads the pages this run skipped.
- A page's `checked:` date changes only after the whole page was read and every claim on it was checked against its source. A partial read leaves the date as it was.

The rule is written once in the wiki skill, and the audit agent follows it where it writes these two records.

## Context

- **How the audit picks pages today.** In `plugins/knowledge_management/agents/auto_shaper_wiki.md`, the block `<derive_page_audit_working_set>` reads in full only the pages that are new or changed since the newest usable `Audit baseline:`. Its text says that a page "unchanged since it last passed a cold walk stays out" of the pages to read, where a cold walk means a fresh full read of the file. The block `<append_audit_log_entry>` writes a new baseline after every completed audit, with the instruction ``Prefer `git rev-parse HEAD` for the baseline when the wiki lives in a git worktree.``. Nothing ties the new baseline to what the run actually read. The entry's `Cold page reads:` line lists the pages the run read, but nothing defines what counts as a full read.
- **How the checked date is set today.** In `plugins/knowledge_management/skills/wiki/SKILL.md`, the **Freshness** bullet in `<write_or_update_pages>` says to set `checked` "when you verify the claims". It requires neither reading the whole page nor checking every claim. The agent keeps `checked` unchanged when it rewrites frontmatter in `<fix_frontmatter_missing_or_malformed>`, and nothing tells it when it may set a new date. The agent's `<read_canonical_references>` reads only named blocks of the wiki skill, and those leave out both the **Freshness** bullet and `<operational_discipline>`. A rule placed only in the wiki skill might therefore never reach the agent.
- **What went wrong in practice.** One audit, given a broad review request, fully read only a small share of a wiki in which every page had changed since the previous baseline. Half of the pages it listed under `Cold page reads:` it had only seen as search excerpts. It still recorded the current commit as the new baseline, so the next audit would have skipped every page this run never read. A helper script in the same run set a new `checked` date on every page it touched, including one it had read only in part.
- **Why keeping the previous baseline is the right fix.** The audit promises that every page gets one fresh full read after each change. Keeping the previous baseline after a partial run keeps that promise. The cost is that the next audit re-reads some pages the partial run already read.
- **Tests that pin today's wording.** `tests/wiki/layer1/agent_contract.py` checks that several phrases stay in the two agent blocks, among them `unchanged since it last passed a cold walk stays out`, `Audit baseline:`, `Cold page reads:`, `on every completed audit`, and `zero-change outcome entry`. Its `derive_cold_reads` function re-implements the page-selection rule over a small example, so the test can compare the agent's text with the expected behaviour.
- **The log rotation task has shipped.** [The log rotation task](archive/wiki_log-rotation-and-retrieval.md) added the rule that the next audit after a rotation cold-walks once and records a fresh baseline in the new log, which `template_log.md` now carries. Under this task's rule that is true only when that audit reads every page in full, so this task lands second and rewrites that sentence to carry the condition. [The log consolidation task](wiki_log-session-entry-consolidation.md) keeps `<append_audit_log_entry>` and its baseline, but changes how the agent writes log entries inside that same block.

## Approach

1. **Write the rule once in the wiki skill.** Add one block, `<record_only_full_reads>`, inside `<operational_discipline>` in the wiki skill. It says that the audit baseline and a page's `checked` date move forward only over pages read in full during the same pass. A page counts as read in full only when the pass read every line of it, in one read or in several reads in chunks that together cover the whole file; the `<too_large_to_read_in_one_shot>` locate-then-`Read` path reads a range, not the page. A claim counts as checked only when the pass read the source that claim cites, as the page's `sources:` frontmatter lists it and its inline claim links cite it, so those reads are the record. A source counts as checkable when it lies inside the wiki or under a `Declared source root:` the wiki declares, because the **Provenance** bullet resolves a `sources:` value from the wiki root and lets a declared-root value point at a sibling of the wiki in the same repository; a claim whose source lies outside both locations, or that the pass read no source for, stays unchecked. Search hits, context excerpts, and partial line ranges read neither the page nor its claims. The block also says that the stamp refreshes a `checked` date the page already carries and adds the field to no page, keeping `checked` the optional signal `references/template_schema.md` defines and matching the no-add rule in `<fix_frontmatter_missing_or_malformed>`.
2. **Rewrite the Freshness bullet.** Change the **Freshness** bullet so a writer sets `checked` only after reading the whole page and checking every claim on it against its source. A partial read, or a check of only some claims, leaves the date unchanged. The bullet points at the new block.
3. **Change how the audit writes its baseline.** Rewrite the baseline paragraph of `<append_audit_log_entry>` in place:
   - The baseline moves to the current commit only when the run read in full every page that changed since the previous baseline and still exists. On a first audit, which has no previous baseline, that means every page in the wiki.
   - Otherwise the new entry repeats the previous usable baseline unchanged, or writes `unavailable` when there is none.
   - `Cold page reads:` lists only pages read in full.

   Point at the wiki-skill block by its tag instead of repeating the rule. Keep the phrases the layer-1 test checks, or update a pinned phrase where the rewrite changes it, following TESTING.md's Test Integrity rules.
4. **Carry the rule into every site that states the rotation rule.** Rewrite the rotation rule's closing sentence wherever it states the fresh baseline, so that baseline is conditional on that audit reading every changed page in full, matching Approach step 3. Two statements carry it: the `template_log.md` rotation line, and the wiki skill's `<rotate_log_at_500>` block in `plugins/knowledge_management/skills/wiki/SKILL.md`. Each currently says the next audit cold-walks once and records a fresh baseline in the new log. A rotation moves the prior baseline into the archive, so that audit is the first-audit branch of the **Change how the audit writes its baseline** rewrite: its condition is every page in the wiki read in full, never the changed subset. Each sentence becomes that conditional form, for example: "start fresh; the new log carries no baseline, so the next audit reads every page in the wiki in full and records a fresh baseline only when it does, otherwise writing `unavailable`." Two test sites pin that line, so move them with it: `stage_AS-16`'s `_assert_template_log_contains` argument in `tests/wiki/layer2/setup_scenarios.sh`, and the `A2_rotation_rule_present_at_template_text` regex in `tests/wiki/layer2/evals.json`. Both take the rewritten sentence verbatim, so the staging guard keeps passing and the grader keeps matching the inserted unit. Keep the rotation mechanics themselves unchanged.
5. **Make the agent load and follow the rule.** In `plugins/knowledge_management/agents/auto_shaper_wiki.md`, extend `<read_canonical_references>` so its wiki-skill read also covers the block step 1 adds and the **Freshness** bullet, read by contiguous semantic block like the two blocks it already names. Add one clause to the agent's `<policy>`: the agent sets a new `checked` date only as that block allows, and otherwise keeps the date the page already has. Give that clause its write site with a new block, `<advance_checked_dates>`, placed first in `<verify>` so the final relint covers the rewritten frontmatter: after the fixes, for every page this pass read in full and whose claims `<record_only_full_reads>` counts as checked, it sets `checked` to today's date in that page's frontmatter when the page already carries the field; a page read in part, a page whose claims are not all checked, and a page that carries no `checked` date keep the frontmatter they already have. The block also states that the stamp is a per-page metadata refresh rather than a fix, so `<confirm_large_bulk_changes>`, which gates fixes, does not apply to it, and the refresh leaves `updated` alone: a first audit of a 10+ page wiki stamps every fully read page without asking for bulk confirmation. This is a step in the ordinary pass rather than a fix move, because `<fix_moves>` dispatches by issue category and a page read in full that raises no issue enters no fix move, so a fix move would never stamp it. `<bump_updated>` keeps writing only `updated`, inside `<remediate>`, and `<fix_frontmatter_missing_or_malformed>` keeps carrying `checked` through a rewrite unchanged, so the stamp is the one site that moves the field. The `<policy>` clause and `<advance_checked_dates>` each point at the step-1 block by its tag and repeat no part of the full-read definition.
6. **Extend the layer-1 test.** In `tests/wiki/layer1/agent_contract.py`, pin the clause that keeps the previous baseline in `<append_audit_log_entry>`. The definition of a full read stays owned by the wiki-skill block and is pinned there once, through Acceptance 1. Add a helper beside it, `derive_recorded_baseline(previous_baseline, changed_pages, read_in_full, current_commit)`, which returns the value the entry records, and cover it with a small example: a complete read of every changed page advances to `current_commit`; a partial read repeats `previous_baseline`; a partial first audit with no previous baseline records `unavailable`; a complete first audit advances to `current_commit`. `derive_cold_reads` keeps returning the read set, and its three call sites stay unchanged. Scope the prefilter sentence in `<derive_page_audit_working_set>` so it names its own bullet — `A grep hit from this leakage prefilter adds the page to the full-read set; a grep miss removes nothing` — and move the layer-1 pin of that phrase with it, so an ordinary content search that returns a page for a cross-reference lookup adds nothing to the cold-read set; update `derive_cold_reads`'s `grep_hits` parameter comment to say it carries leakage-prefilter hits. Also pin the `<advance_checked_dates>` stamp sentence, so the write site cannot be dropped while both `checked` scenarios still pass, and pin its bulk-confirmation exemption sentence. Pin the narrower-scope sentence together with its **Contradiction peers** carve-out, so a build that drops the scope rule fails the layer-1 pin as well as the scoped-audit scenario, and a build that writes it as an unconditional restriction of the cold-read set fails the same pin.
7. **Add four layer-2 scenarios.** Give them the four next free `AS-` ids at implementation time in `tests/wiki/layer2/evals.json`. Stage each with a `stage_<id>` function in `tests/wiki/layer2/setup_scenarios.sh`, and add each id to its `ALL_SCENARIOS` list. In each sandbox, the wiki sits in a git repository whose `log.md` holds one earlier `audit` entry, which records the first staging commit as its baseline. A second commit then changes one `concepts/` page and one `procedures/` page.
   - `auto-shaper-holds-baseline-on-scoped-audit`: the request limits the audit to the `procedures/` directory. `<derive_page_audit_working_set>` states no scope rule today, and `wiki_fix`'s `<pass_through_user_scope>` forwards a narrower qualifier as an extra instruction, so a literal build would read the changed `concepts/` page in full. Add one sentence to that block, after the **Incremental audit** bullet: `When the request carries a narrower scope qualifier, restrict the changed-page part of the cold-read set to the pages under that scope, leaving the **Contradiction peers** rule to read both sides of a same-subject pair in full; the baseline condition stays wiki-wide, so a changed page outside the scope that stays unread holds the previous baseline.` Stage the two changed pages as different subjects, so neither is the other's **Contradiction peers** match and the peer rule adds no page, and stage both page bodies free of the lexical-leakage signals the **Lexical leakage prefilter** bullet names — no date, absolute or home-relative path, obvious person name, or command-output shape — so that prefilter adds neither page either, as the excerpt-only scenario stages its page. With that sentence and that staging the changed `concepts/` page stays unread, so the baseline must stay where it was.
   - `auto-shaper-advances-baseline-on-full-read`: the request asks for a full audit, so the baseline must move to the new commit. Stage one entity page in the second commit, carrying `checked: 2026-01-01`, whose every claim resolves to a source the run can read in full — one raw note inside the sandbox and one document under a `Declared source root:` beside the wiki that the sandbox `SCHEMA.md`'s `## Lint` section declares — so the full audit can legitimately check them all, and write the second commit's sha to a sidecar file outside the wiki tree, under the sandbox's existing `baseline/` directory beside the sidecars `setup_scenarios.sh` already writes, so the agent's wiki view never sees it and `log_baseline_equals_file` compares that sha to the new entry's `Audit baseline:` line without hard-coding a commit hash.
   - `auto-shaper-holds-checked-on-partial-claim-check`: an entity page carries `checked: 2026-01-01`, several claims whose sources lie outside the sandbox, and one figure that contradicts a staged raw note. The request asks the audit to check that figure against the note and fix it. The figure must be fixed while the `checked` date stays the same, because the page's other claims were not checked.
   - `auto-shaper-holds-checked-on-excerpt-only`: a page carries `checked: 2026-01-01`, stays unchanged since the baseline, and reaches the run only as a search excerpt: the request asks the audit to confirm one cross-reference from another page's fix, so the page is consulted for that excerpt and never opened for a full read. Its `checked` date must stay `2026-01-01` and its body must stay unchanged. Stage it so the only path to the page is that ordinary content search and never the lexical-leakage prefilter; an ordinary content search used to confirm a cross-reference yields an excerpt rather than a cold read, because `<derive_page_audit_working_set>` sends only a prefilter hit to the full-read set. Stage the fix page and the excerpt page on different subjects, so **Contradiction peers** finds no same-subject pair between them and adds no full read: neither page's title, index entry, nor links name the other's subject. A build that stamps every page it touches, or that sends any search hit to the cold-read set, fails this scenario while a build that stamps only full reads passes it.

   Write the graders under TESTING.md's `## Test Design Principles`, and run the scenarios under TESTING.md's vendor rule. Add one assertion type to `tests/wiki/layer2/grade.py`, `log_baseline_equals_file`: it reads the sha from the sidecar file the assertion names and compares it to the `Audit baseline:` value of the newest `audit` entry in the graded `log.md`. No existing type can make that comparison, because `glob_file_contains` applies one regex to the text of each file its `pattern` matches and never reads a second file, and `file_matches_baseline` compares one file byte-for-byte against its own sha256. That comparison is the regression guard against a build that over-holds the previous baseline, not a flip item: on a complete read the old and new behaviour agree, so it cannot fail before the work and the new condition is proven by the hold scenarios and the layer-1 clause pin.

**Out of scope:**

- Editing the `checked` paragraph of `references/template_schema.md`. It defines the field, and this task conforms to it rather than changing it: the stamp refreshes an existing date and never adds the field, so the paragraph's optional-signal rule still holds. Changing the template would make every wiki's scaffold differ from it on the next audit.

3. `<append_audit_log_entry>` moves the baseline only under the full-read condition, and otherwise repeats the previous baseline or writes `unavailable`. 5.
