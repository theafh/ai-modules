# Stamp ready→checked, split→open, and completed-work routing on any rewrite

## Goal

Each task file records its lifecycle stage in the `status` field of its frontmatter. `task_check`, the readiness gate of the `task_*` family, stamps a task `ready` when it finds no blocking issue. Several skills and agents in the family later rewrite task bodies. Today the hub states what a rewrite does to `status` for one kind of pass only, and that rule leaves a rewritten `ready` task at `ready`. In one batch repair, the owner had to set such tasks back to `checked` by hand.

After this task, the task hub states once, for every family skill or agent that edits a task body, what a rewrite does to `status`:

- A rewrite of a `ready` task that goes beyond the hub's mechanically fixable lint set returns the task to `checked` in the same edit. The report names the task. The mechanically fixable lint set is the hub's list of linter findings an agent may repair without judgement, such as a missing frontmatter value or a broken link.
- A task file that a split creates starts at `open`.
- A family repair skill or agent that finds a rewrite for an `implemented` or `audited` task reports the finding and routes it elsewhere instead of applying it.

**Settle the trigger** in Approach carries the rule, meaning what triggers the return to `checked`, and its exceptions.

## Context

- **Current state.** In the task hub, `plugins/ai_dev/skills/task/SKILL.md`, the **Status discipline** rule inside `<backlog_coherence>` says what a repair does to status. That block defines the coherence pass, in which `task_fix` judges a set of tasks read together. The rule opens with ``A coherence pass writes no `status` value at all, in either direction.`` A repair that leaves the meaning of Goal, Approach, and Acceptance unchanged keeps the task's status, `ready` included. A repair that changes that contract is flagged for re-check in the report, and the frontmatter stays as it was. The rule bans lowering `ready` to `open` and gives the reason. It closes by naming `task_check` and `task_auto_check` as the owners of every status value. It binds coherence passes only. Other skills and agents edit task bodies with no stated effect on status:
  - The hub's `<update>` workflow edits a task when the user asks for a change.
  - `task_fix` applies inline advisory repairs, small fixes outside the lint set such as dropping a duplicate cross-link. It also applies regroups. A regroup gathers what a body says about one link target into the section that owns it.
  - `auto_shaper_task` makes splits, reframes, and regroups.
  - `task_auto_check` runs a repeated-link round after a `ready` verdict. That round regroups a body in which the linter found one target linked more than once. Three standing directives still forbid writing `checked` on that regroup: `<authority>` says `task_check` owns the ready/checked status write; `<single_gate>` says the loop does not override `task_check`'s `ready` or `checked` stamp; `<apply_repairs>` says Preserve frontmatter except for the `updated` timestamp.
- **Copies and citations.** The **Gated coherence reconcile** step in `plugins/ai_dev/skills/task_fix/SKILL.md` applies the coherence repairs the user accepted. It restates the rule ("leave a semantics-preserving repair's `status` standing and flag a contract-altering repair for re-check, never stamping `ready`"). `plugins/ai_dev/agents/auto_shaper_task.md` is the agent that writes `task_fix`'s escalated repairs. It cites the rule as the `<backlog_coherence>` block's **Status discipline** rule in three places: the `<rule>` beginning `Resolve these five defect kinds`, its `<remediate>` step, and the `## Applied fixes` line of its report format. In `<remediate>`, the backlog-coherence path still says leave every `status:` value exactly as found and names a task needing re-check under **Status discipline**, never demoted in its frontmatter. The `## Applied fixes` line likewise names every task left flagged for re-check under **Status discipline**. Its split instruction in `<remediate>` says nothing about the status of the new file.
- **Pinned behaviour.** Two evals assert today's rule. In both evals, most of the staged tasks that the run edits start at `ready`. The `immediate_ready_citations_overturn` entry in `tests/task_auto_check/evals/evals.json` carries the expectation `No passage of the loop writes status, computes a second readiness score, or overrides the task_check stamp.`
- **Observed owner behaviour.** In one batch repair, a pass rewrote several `ready` tasks and widened the contracts of some. It left every stamp standing, as the written rule requires, and reported that the readiness verdicts still held. The owner then set each rewritten `ready` task back to `checked` by hand. That included one task whose rewrite changed no Goal, Approach, or Acceptance clause. In the same batch, a split wrote its new half as `ready`, because a helper argued that a strict narrowing keeps its stamp. A repair also rewrote the contract of an `implemented` task and left its stamp unchanged. The owner had that repair reverted, stating that implemented work is either left alone or was never implemented.

That round sits beside the trigger passage that [the deletion-and-regate task](task-family_readiness-loop-deletion-and-regate.md) rewrites, the passage that decides when the loop challenges a `ready` verdict. Whichever task lands second keeps that sentence true, and updates it in place where the flow changes.

## Approach

1. **Lift the rule to the family.** Rewrite **Status discipline** as its own block, `<status_discipline>`, so the passage moves out of `<backlog_coherence>` instead of being copied. Place the block after `<backward_move_guard>`, the hub block that guards against moving a status backward, and keep its bold lead-in. The block applies to every skill and agent in the family that edits a task body. A rewrite of an `open` or `checked` task leaves its status as it is. The ban on lowering `ready` to `open` carries over unchanged, with its reason. Leave a one-sentence pointer to the block in `<backlog_coherence>`, and point `<update>` at it too.
2. **Settle the new-file case.** A task file that a split creates starts at `open`, whatever status its parent carried. No gate verdict transfers to text the gate never read. Point the split instruction in `auto_shaper_task`'s `<remediate>` at this clause.
3. **Settle the completed-work case.** A family repair skill or agent never applies a rewrite beyond the mechanically fixable lint set to an `implemented` or `audited` task. It reports the finding and routes it to `task_audit`, to `task_finish`, or to a new follow-up task. The task's contract stays as delivered. When the user explicitly edits such a task through `<update>`, that edit stays the user's call.
4. **Settle the trigger.** `<status_discipline>` states the rule that decides when a rewrite changes status. Every rewrite of a `ready` task beyond the base `<lint>` mechanically fixable lint finding set returns the task to `checked` in the same edit. The report names the task and what changed. The one exception for a `ready` task is an edit that carries the user's readiness declaration through `<update>`'s apply-findings flow. That edit stamps `ready`. In the apply-findings flow, the user answers a `task_check` report issue by issue and may declare the task ready. The rule follows the owner's own practice: the owner applied this trigger by hand when the written rule left rewritten tasks stamped `ready`.
5. **Apply the settled trigger.** Make these edits so that the rest of the hub and the sibling skills agree with the rule:
   - Widen the `checked` entry in `<frontmatter>` so it also covers a body rewritten after its last clean verdict.
   - In `<lifecycle_responsibility>`, which names the skill that writes each status, name the skill or agent that writes this `checked`. In `<backward_move_guard>`, list this move from `ready` to `checked` among the moves that proceed without the guard.
   - Narrow the rule's closing ownership sentence, which names the owners of every status value, so it covers `ready` alone. Only `task_check`, `task_auto_check`, and the user's declaration write `ready`.
   - Make `task_auto_check`'s repeated-link round after a `ready` verdict follow the same rule, with no exception of its own. When the round rewrites the body, that edit writes `checked`. In the same skill, rewrite those three directives so the write is legal: `<authority>` keeps `task_check` as owner of the ready/checked verdict and the status write that verdict performs, and names this skill's body rewrite as a writer of `checked` under `<status_discipline>`; `<single_gate>` still forbids inventing a second readiness score, and treats writing `checked` on a rewrite beyond the mechanically fixable lint set as the settled trigger rather than an override of `task_check`'s stamp; `<apply_repairs>` may write `status: checked` when `<status_discipline>` requires it, not only the `updated` timestamp. One re-gate through `auto_gate_task` then runs before the loop's final mechanical lint step, and it counts against the round cap in `<loop_bounds>`. `task_check` writes the status its new assessment reaches. When the cap leaves no room for that re-gate, the task stays `checked` and the report names it. When the round surfaces every finding instead of regrouping one, or skips because the recorded set is empty or already dispositioned, the body stays byte-identical, the `ready` stamp stands, and no re-gate runs.
   - Rewrite in place the sentence in `plugins/ai_dev/skills/task_auto_check/SKILL.md` pinned under the label `immediate ready path routes the repeated-link round before finalize`, and update the matching assert in `tests/task_auto_check/script_tests/run.sh`, to post-re-gate wording: a body-rewriting round proceeds to re-gate then finalize; a non-regroup path that surfaces every finding, or skips because the recorded set is empty or already dispositioned, leaves `ready` standing and proceeds to finalize. Keep the label. This task owns that rewrite when its re-gate changes the flow; Shared surface already coordinates with the deletion-and-regate sibling.
   - Make the **Repeated-link react protocol**, the hub's procedure for repeated-link findings, and `task_fix`'s inline advisory repairs leave `implemented` and `audited` bodies alone. They report each finding on such a task instead.
6. **Repoint the copies.** In `task_fix`'s **Gated coherence reconcile**, replace the restated rule with a citation of `<status_discipline>`. Point `auto_shaper_task`'s three citations at the block. In the same edit of `auto_shaper_task`'s `<remediate>`, rewrite the backlog-coherence clauses that leave every `status:` value exactly as found and that forbid demotion in frontmatter so a rewrite beyond the mechanically fixable lint set writes `checked` in that edit per `<status_discipline>`. Keep report-flagging under **Status discipline** only for cases the block does not demote.

   - In `tests/task_auto_check/evals/`, rewrite the `regroup_immediate_ready` expectation "The task ends status: ready, written only by task_check." in `evals.json`, and the grader check labelled `task ends status: ready, written only by task_check` in `grade.sh`.
