# Backlog-coherence assessment for task_fix: assess by default, reconcile on accept

## Goal

`task_fix` gains a backlog-coherence capability: on every everyday invocation it jointly reads the selected live tasks (a scope filter, an explicit list, or the whole live tree by default) and the target artifacts those tasks point at, judges the tasks against each other and against the code as it stands, and reports per-task verdicts — ship as-is, alter with concrete minimum edits, or defer candidate — plus a coherent ship order. Reconcile stays gated: on the user's acceptance, or through the existing escalate path, it applies the minimum, intent-preserving repairs and surfaces only what context cannot settle. The assessment catches the defect class every per-task surface structurally misses: two tasks that are each individually ready can still contradict each other, double-own one edit, reintroduce a hazard a sibling fixes, or sit stale against work that shipped after they were written. User-facing activation language is ordinary backlog phrasing (coherence, consistency, "do these ship together"); no special jargon is required because everyday `task_fix` already runs the assessment. The capability is written entirely against the base `task` skill's own conventions — `scope` frontmatter, body links, statuses, `<dependency_signals>` — and derives the target-artifact set from each task's own scope and links, so it works on any repo's tasks tree with no repo-specific assumptions.

## Context

The family's existing surfaces each look at the wrong granularity for this class. `task_check` and `task_auto_check` judge one task at a time (the base `<readiness_checklist>`), so a cross-task finding is outside their structural reach. `task_fix`'s assess phase walks every task with format-level advisory checks and never reads the target artifacts; its `<surface_for_review>` carries one bare cross-task bullet — "Contradictions between tasks — mirror `wiki_fix`'s contested protocol" — that names an output shape but no detection procedure. `auto_shaper_task` resolves escalated defects but only receives what task_fix's assess produces. No surface reads a selected live set plus its shared target artifacts in one head.

The motivating session, generalized: a 17-task live set sharing one scope was assessed jointly against the plugin it targets, on the prompt "should these all ship, or do some need altering or deferring to stay coherent with each other and the current code?". The joint read surfaced, with greppable evidence: one task introducing a warn-severity finding that recreated exactly the unreachable-clean-bar hazard a sibling task existed to fix; one edit double-owned by two tasks while a third assumed one of them owned it; a task enumerating one of the five sites its own rule implied; four sibling-file sites missing from another task's sweep; sibling tasks answering the same surface-versus-auto-repair question oppositely — one distinction principled, one accidental; quoted anchors invalidated by siblings that had shipped since; and references to finished archived tasks phrased as still pending. None of this is visible from any single task file, and each would have degraded the target artifacts if shipped blindly. The subsequent reconcile pass repaired ten task files with minimum edits, left every status standing, and surfaced nothing — every call settled from task intent, sibling tasks, archived precedent, or the code.

Placement follows the shipped precedent in [task-family_autonomous-tree-shaper.md](task-family_autonomous-tree-shaper.md): whole-tree capability grows inside `task_fix` rather than as a second skill, heavy judgement routes through the existing `auto_shaper_task` escalation with `auto_verifier_task` gating, and a family rule is authored once in the base `task` skill (the `<readiness_checklist>` precedent) and cited by its consumers.

This task composes with, and does not replace, [task-family_count-stable-references.md](task-family_count-stable-references.md): both edit the base `task` skill and `task_fix`, so when that sibling has landed, preserve its count-stable `<markdown_policy>` rule, Ambiguity flag, **Assess** advisory, and `<surface_for_review>` entry while this task adds `<backlog_coherence>` and rewrites only the "Contradictions between tasks" bullet.

The Pattern A task-family behavioural suite at `tests/tasks/evals/` inventories every scenario id in the table under `## The eval set (every \`id\` in \`evals.json\`)` in `tests/tasks/evals/README.md`; family peers already listed there include`fix` and the hub scenarios. ## Approach

1. **Author the lens set once in the base `task` skill**, under the greppable tag `<backlog_coherence>`, defined over a selected live set C (the live tasks in scope for this run) and the shared target-artifact set T (the union of C's `scope` directories and the files C's bodies link). When adding `<backlog_coherence>`, leave any landed count-stable `<markdown_policy>` rule and Ambiguity flag byte-stable:
   - **Joint orientation.** Read every task in C in full and read T once; every later lens runs against that shared context — the shared read is what makes N premise checks affordable and is the precondition for every cross-task lens.
   - **Premise freshness against shipped state.** The base premise check applied set-cheap, per task: quoted anchors that no longer grep in T, references to archived tasks phrased as pending, described gaps the code has since closed. An invalidated premise makes the task a defer candidate with disposition handed to the user, per the base rule; drifted details are ordinary repair findings.
   - **Shared-surface ownership.** Map each task's claimed edits onto T; flag an edit claimed by two or more tasks, and an edit the selected set's own rules imply that no task owns. Repair shape: one owner, a verify-only step in the other task, reciprocal coordination links.
   - **Emergent contradiction.** Derive each task's post-state and check pairwise compatibility on shared surfaces and against invariants other selected tasks establish or repair. Canonical case: task A carves an exception so an autonomous loop can terminate cleanly, and task B adds a finding at the severity that re-blocks that loop with no handling. Repair shape: change the offending parameter with its rationale recorded once, or couple the change to the sibling that owns its precondition.
   - **Posture consistency.** The same design question answered differently across siblings (severity tier, auto-fix versus on-demand, naming): reconcile an accidental divergence; record a principled one on the task that carries it.
   - **Sweep completeness.** When a task states a rule and enumerates its edit sites, search T for the rule's actual site set and flag the un-enumerated remainder.
   - **Ship-order coherence.** Derive waves from the base `<dependency_signals>` plus shared surfaces; name the tasks that stay coherent only when landed together or in a stated order.
2. **Wire backlog-coherence assessment into everyday `task_fix`.** Every everyday invocation runs the mechanical pass and the `<backlog_coherence>` assessment over the selected live set in the same report — assessment is default-on, not a separate mode. Selector defaults to the whole live tree when the user names no filter; a scope filter or explicit list narrows C. User phrasing such as "check backlog coherence", "backlog consistency", or "do these ship together" may emphasize or narrow the run but is not required to trigger assessment. Assessment is propose-then-act for the write half: the report is the phase-one deliverable for coherence findings; the pass writes no coherence repair until the user accepts findings or opts into the existing escalate path. Rewrite `task_fix`'s frontmatter `description`, `<role>`, and `<when_to_activate>` in place so ordinary backlog phrasing for coherence, consistency, or whether selected tasks ship together routes here beside the existing health-check, clean-up, audit, and lint entries, without requiring special jargon — `<role>` names default-on `<backlog_coherence>` joint assessment beside the existing mechanical repair and escalation narration. Leave `<output_contract>`'s mode used (`inline` or `escalated`) as the two-value writer mode — backlog coherence is an assess-phase section, not a third mode token. Rewrite the `<surface_for_review>` opening preamble in place so user-accepted backlog-coherence findings from the assess-phase report reconcile under **Decide or label** per **Reconcile on acceptance or escalate**, while findings outside the selected live set stay human-owned and surfaced; rewrite only the "Contradictions between tasks" bullet in place to that same dual disposition. Leave any landed count-stable **Assess** advisory and other `<surface_for_review>` entries untouched.
3. **Reconcile on acceptance or escalate.** Backlog-coherence reconcile picks exactly one writer for the accepted set, matching task_fix's mutual-exclusion rule: when every accepted repair is anchor refresh, premise-drift staleness, or a semantics-preserving additive out-of-scope note per **Status discipline — the change-significance rule** (the (b) and (k) class), apply them inline; when any accepted repair is a judgement reconciliation, hand the full accepted set to the existing `auto_shaper_task` escalation (verifier-gated, single writer) so staleness items ride that same escalated write rather than a parallel inline path. Rewrite `<workflow>` **Remediate** in place so backlog-coherence findings from assess never enter the inline mechanical auto-fix set — **Remediate** continues to auto-fix only lint and other mechanical findings until the user accepts coherence findings or opts into escalate; backlog-coherence reconcile then runs on a follow-up invocation that carries the accepted finding set, or in the same invocation when the user accepts findings before **Remediate** begins. Rewrite task_fix's `<design_note>` mutual-exclusion clause in place so coherence reconcile is assess-then-one-writer under that exclusive-writer rule. User-accepted backlog-coherence findings reconcile under the base **Decide or label** procedure (reconcile from task intent, then guardrails, then sibling and archived tasks, then the code; surface what that evidence leaves open); findings outside the selected live set, and any fork Decide or label leaves open, stay human-owned and surfaced. Rewrite `auto_shaper_task`'s three always-human contested sites — contested-protocol `<rule>`, `<objective>` contradiction-surfacing clause, `<output_contract>` contested-contradictions line — to that dual disposition. Widen `auto_shaper_task`'s resolve-types rule (`Resolve split, body-framing-reframe, and scope-relocation defects only`) and its `## Applied fixes` grouping so backlog-coherence repairs are admitted alongside those types. Widen the matching auto_shaper-scoped rules in `auto_reviewer_task` (`propose the split or relocation shape for the single writer to execute`) and `auto_verifier_task` (`approve only writer-executed split or relocation plans`) so those helpers can propose and approve backlog-coherence repair shapes for the single writer, without adding a new agent. Rewrite the root and plugin README `task_fix` / `auto_shaper_task` bullets and `auto_shaper_task`'s frontmatter `description` in place so each names default backlog-coherence assessment and gated reconcile beside the current inline/escalated tree-repair narration. Repairs preserve each task's frozen `## Goal`, bump `updated`, and re-lint archive-inclusive.
4. **Status discipline — the change-significance rule.** A repair that leaves a task's Goal, Approach, and Acceptance semantics unchanged leaves its status standing, `ready` included; a repair that alters the implementation contract flags the task for re-check in the report. Stamps stay owned by `task_check` / `task_auto_check`; the pass never writes `ready`. The shared `fix_coherence` fixture plants (k) and (l) for this rule: (k) a `ready` task receiving only an additive out-of-scope note; (l) a task whose accepted repair alters Acceptance semantics.
5. **Extend the existing task-family harness rather than standing up a new one.** Fixture scripts live on disk at `tests/tasks/evals/fixtures/<id>/setup.sh`; `evals.json` `files` entries use the `evals/fixtures/<id>/setup.sh` prefix the live Pattern A harness expects — state both forms wherever fixture paths appear. Add primary assess eval `fix_coherence` in `tests/tasks/evals/` as a full Pattern A suite entry: `tests/tasks/evals/fixtures/fix_coherence/setup.sh` (`evals/fixtures/fix_coherence/setup.sh` in `evals.json`) stages the combined (a)–(l) fixture backlog **Primary eval `fix_coherence`** plants; a matching `stage.sh` case whose prompt runs assess only; `grade.sh` programmatic checks for that assess path plus `note_agent_attest` notes where needed; and an `evals.json` entry — reusing the Pattern A runner and deterministic grader rather than introducing a second `task_fix` harness. Add two reconcile companion evals that reuse the same fixture tree but carry distinct prompts and `grade.sh` cases, matching the `update` / `update_contract` precedent: `fix_coherence_reconcile_escalated` (prompt accepts (a)–(e) and runs reconcile through `auto_shaper_task`) and `fix_coherence_reconcile_inline_staleness` (prompt accepts the staleness-only set {(b), (k)} for inline anchor-refresh and out-of-scope-note repairs, and accepts (l) only to flag for re-check without applying the Acceptance-altering repair). Selector coverage is three additional eval entries, not three prompts inside one entry: `fix_coherence_selector_scope` (prompt names a scope filter), `fix_coherence_selector_explicit_list` (prompt names an explicit live-task list), and `fix_coherence_selector_whole_tree` (no selector named — whole live tree default); each carries its own `tests/tasks/evals/fixtures/<id>/setup.sh` (`evals/fixtures/<id>/setup.sh` in `evals.json`), `stage.sh` case, and `grade.sh` checks staging a minimal live set sized for that selector form. Rewrite the inventory table under `## The eval set (every \`id\` in \`evals.json\`)` in `tests/tasks/evals/README.md` in place so `fix_coherence`, the two reconcile companion ids, and the three selector ids appear beside existing family peers. Update the existing whole-tree`task_fix`eval (`id: "fix"`) — including any`grade.sh` checks that assertion needs — so a default invocation expects a backlog-coherence assessment section in the report (including the clean/no-finding case) while keeping its mechanical-pass coverage.

**Out of scope:**

- Implementing any live backlog task — `task_implement` owns builds; this capability only makes the backlog coherent to build from.
- Readiness promotion — the pass flags re-checks and never stamps `ready`; promotion stays with `task_check` / `task_auto_check`.
- A new user-facing skill or a new agent — the archived tree-shaper decision holds: `task_fix` stays the sole whole-tree entry point and the existing agents carry escalation.
- Auto-applying judgement reconciliations without user acceptance or escalate opt-in — assessment always reports; coherence writes stay gated.
