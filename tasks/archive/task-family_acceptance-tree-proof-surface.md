# Judge every Acceptance item against the pre-commit tree, never against commit or pull-request content

## Goal

Refine the base `task` skill's Acceptance contract in place so every item is judged against the working tree as it stands before any commit, making a tree artifact the only proof surface and barring the commit message and the pull-request description. State the constraint once by rewriting the existing `**Deliverable items flip.**` bullet in `plugins/ai_dev/skills/task/SKILL.md` `<body>`, bring the `**Measured, with a fail branch.**` bullet and the contract intro into line with it, add a readiness finding that flags a violation, pair a `task_fix` advisory that surfaces one, confirm the two `auto_*_task` agents inherit through their existing citation, and prove the readiness finding with one eval pair. The reader knows the work is done when a grep of each surface returns the new wording and the eval grades the violation task as surfaced and the control as clean.

## Context

An Acceptance item today may name the commit message or the pull-request description as the surface its proof lives on, and two forces let that happen. The `**Acceptance**:` definition lists "a measurement to record" and the `**Measured, with a fail branch.**` bullet says "the recorded measurement is the deliverable", yet neither names where the record lands. The `<body>` positive-framing paragraph then routes rejected-option rationale to "the change's commit or pull-request description", and `**Decide or label**` tier (b) reconciles a vague pointer against "the standing repo rules, comprising the harness-loaded rule files", where a downstream repo rule names the commit message as where non-wiki work "is recorded". A "record the numbers" pointer with no home therefore reconciles deterministically onto the commit message.

That surface is unverifiable at the moment acceptance is judged. The manual chain checks acceptance at `task_check` before implementation, at `task_implement`, and at `task_audit`, each before the commit exists, so an item proven only by commit content is a tautology: nothing verifies it before the commit, and nothing re-reads the commit after. It is also machine-dependent whenever it asks for recorded numbers, because a run count or a timing depends on the host. This was observed twice in a downstream repository in September 2026: one task draft and one readiness pass each wrote an Acceptance item whose proof surface was the commit message, and the shipping commit then carried none of the promised record.

The existing `**Implementer-runnable.**` bullet already keeps a user-gated action out of acceptance, but it speaks to who runs the step, not to when the surface exists, so it does not catch a commit-time proof surface. No `<readiness_checklist>` item, no `task_fix` advisory, no linter check, and no eval names commit-time content as out of bounds, which is why the class shipped unflagged.

One interaction constrains the Measured edit. The `<markdown_policy>` `**Reference a mutable set by its defining property: the count-stable rule.**` cites the `**Measured, with a fail branch.**` clause as the home for a legitimate "measurement protocol's run count and fixed denominator", so the Measured rewrite keeps run count, fixed denominator, and baseline as legal subject matter and changes only where the record lands and when the number is itself the deliverable. The two `auto_*_task` agents already cite the base contract: `auto_reviewer_task` reports a `base_rule_cited` naming a base `<body>` rule, and `auto_verifier_task` judges an Acceptance-coverage repair by the base gate's written-pairing method, so both inherit a strengthened contract without a copied rule. The eval runner discovers ids through `DEFAULT_IDS = _all_eval_ids()` in `tests/task/evals/run.py`, so a new fixture pair needs `evals.json`, a fixture `setup.sh`, a `grade.sh` case, and a `stage.sh` registration (Valid eval ids header plus a case arm per new id that hard-lists the dispatcher); `run.py` itself needs no edit.

Files this touches: `plugins/ai_dev/skills/task/SKILL.md` (`<body>` Acceptance contract and `<readiness_checklist>` content lens), `plugins/ai_dev/skills/task_fix/SKILL.md` (assess-phase advisories), and `tests/task/evals/` (`evals.json`, two fixtures, `grade.sh`, `stage.sh`). The contract and the `**Measured, with a fail branch.**` bullet this task narrows were introduced by [task-family_acceptance-contract.md](task-family_acceptance-contract.md).

## Approach

1. **Refine the deliverable-flip rule to fix the surface, before any commit.** In `plugins/ai_dev/skills/task/SKILL.md` `<body>`, rewrite the `**Deliverable items flip.**` bullet in place so it states that each item's proof surface exists in the working tree before any commit, a tree artifact (a command's output, a file state, a fixture, a test, or a committed results or notes file), so the commit message and the pull-request description are never proof surfaces. This is the single canonical statement the other bullets point at, and it rides on the bullet that already lists the mechanically verifiable surfaces rather than adding a seventh bullet beside them.

2. **Bring Measured and the contract intro into line.** Rewrite the `**Measured, with a fail branch.**` bullet in place so "the recorded measurement is the deliverable" reads for work whose deliverable is the number, and so the recorded measurement lands in a tree artifact rather than in the commit message, pointing at the canonical statement in **Refine the deliverable-flip rule to fix the surface, before any commit.** for the surface. Rewrite the `**Acceptance**:` intro's "a measurement to record" phrase the same way, so it names the tree home rather than leaving the record homeless. Preserve the run-count, fixed-denominator, and baseline protocol wording the count-stable rule depends on, and confirm the `**Reference a mutable set by its defining property: the count-stable rule.**` cross-reference to this clause still reads coherently after the rewrite.

3. **Add the readiness finding.** In the `<readiness_checklist>` `**Content lens**`, add a finding immediately before `**Restated standing rules**` that flags an Acceptance item whose verification depends on the commit message or the pull-request description, citing the `**Deliverable items flip.**` bullet as the surface rule. Route its disposition through `**Decide or label**` as the neighbouring lenses do, with the fix moving the proof onto a tree artifact or dropping the item, and keep it distinct from `**Implementer-runnable**`, which bars a user-gated action rather than a commit-time surface.

4. **Pair the task_fix advisory at both parallel edit sites.** In `plugins/ai_dev/skills/task_fix/SKILL.md`, add an assess-phase surface-and-propose advisory at both parallel sites — the Assess-walk italic best-effort list and the matching `<surface_for_review>` bold entry beside `**Restated standing rules**` and `**Artifact-edit placement**` — that surfaces an Acceptance item resting on a commit or pull-request proof surface, cites the base `<body>` `**Deliverable items flip.**` bullet rather than restating it, and proposes moving the proof onto a tree artifact or dropping the item.

5. **Author the violation-and-control eval pair.** In `tests/task/evals/`, add `check_commit_proof_surface` and `check_commit_proof_surface_control` as a full pair: entries in `evals.json`, fixture directories each with a `setup.sh` that stages its sandbox task, a `grade.sh` case for each id, and `stage.sh` registration that adds both ids to the Valid eval ids header, the `${1:?...}` usage line, and a case arm for each that stages its fixture and prompts `task_check`, so the hard-listed dispatcher arms the pair; leave `run.py`'s `DEFAULT_IDS = _all_eval_ids()` unchanged.

**Out of scope:**

- The downstream standing-rule sentence that names the commit message as where non-wiki work "is recorded", in a repository's standing rule files and in the wiki log template preamble, stays as written; it correctly tells a wiki log where a non-wiki record belongs, and this task changes only the task family's Acceptance contract.
- Rewriting the `<body>` positive-framing paragraph that routes rejected-option rationale to "the change's commit or pull-request description" is rejected: that sentence governs where rejected-option debate lives, not Acceptance proof surfaces; this task leaves it as written and changes only the Acceptance contract's tree proof surface.
- A parallel commit-proof-surface rule copied into `auto_reviewer_task` or `auto_verifier_task` is rejected: both inherit through their existing base-contract citation, and a copy would drift against the family's author-once rule. Acceptance verifies the inheritance rather than adding a copy.
- Backfilling further Acceptance-contract eval coverage beyond the one violation-and-control pair this change needs stays out, per the repo's ship-the-tests-a-change-needs rule; unbounded harness growth belongs to its own session.
