# Deploy the output style to VS Code Copilot

## Goal

GitHub Copilot in VS Code receives the repository's output style as a generated instructions file, deployed at whichever scope the run selects and needing no activation key at either. Under `--global` it lands in Copilot's own user-profile instructions root and applies across every workspace. Under `--project-dir` it lands in that project's own instructions directory and applies to work in that repository. This is the cheapest of the non-Claude targets, since deployment and activation are the same act in both scopes.

## Context

This builds on [the Claude groundwork task](archive/deployment_output-style-claude-groundwork.md), which shipped the repo-root source directory, the `style` artefact type, and the deploy-log restore behaviour. This task adds one target.

The wiki records the mechanism in [system prompt substitution across harnesses](../wiki/comparisons/system-prompt-substitution-across-harnesses.md). The essentials: instructions files combine rather than compete, the user-profile instructions root applies across every workspace and sits above repository and organization instructions in the documented precedence, and nothing has to be switched on for a file placed there to take effect. VS Code is append-only, so the deployed prose competes with default guidance rather than displacing it, which the docs should say plainly.

One trap belongs in the implementation. Copilot also reads a rules folder and a `CLAUDE.md` from the Claude configuration tree, and the documentation presents that path alongside its own. Those are adoption roots, and the standing rule in the harness portability skill's policy is to deliver a per-harness variant into the target's own native root and treat adoption as contamination. Writing the variant into the Claude tree would put one file in front of two harnesses and hand VS Code a Claude-shaped artefact, so the deploy writes only into Copilot's own instructions root.

## Approach

Generate a VS Code variant of the style and write it as a single Markdown file, resolving the destination from the script's existing Copilot directory variable rather than a hardcoded path so the same code serves both scopes. Under `--global` that is Copilot's user-profile instructions root, `~/.copilot/instructions`. Under `--project-dir` it is that project's own instructions directory, `${VSCODE_COPILOT_DIR}/instructions`, which resolves to `<project>/.github/instructions` because `deployment/deployment.sh` sets `VSCODE_COPILOT_DIR="${PROJECT_DIR}/.github"` in project mode.

The wiki's [GitHub Copilot in VS Code](../wiki/entities/github-copilot-vs-code.md) page records the mechanism today. Both scopes take the `*.instructions.md` form: VS Code's custom instructions reference documents `~/.copilot/instructions/**/*.instructions.md` for user modular instructions and `.github/instructions/**/*.instructions.md` for project targeted instructions, and the entity page records the same form. Write `${VSCODE_COPILOT_DIR}/instructions/${name}.instructions.md` at either scope, and record that filename at both scopes on the entity page, dated to the verification, so the next reader does not repeat the check. Where the project-scoped file supports an `applyTo` glob, write the value that scopes it to every file rather than leaving the field out, so the rule is unambiguously always-on.

Generate rather than copy. Strip the Claude frontmatter, which this target does not implement, and rewrite the `<engineering_behavior>` element that names Claude's `keep-coding-instructions` mechanism, following `generate_cursor_style_rule` in `deployment/deployment.sh`, which replaces that element wholesale. The style source carries no `$VAR$` token, so no `replace:` rule applies to it.

Narrow the editor-side adoption of the Claude tree on `--global` alone, as hygiene rather than a closed route. VS Code reads user-level instructions from `~/.claude/rules` as well as its own root, and `chat.instructionsFilesLocations` maps a path to a boolean where a `false` disables it even when it is a documented default. This merge closes no route for this style: Copilot's adoption list excludes `~/.claude/output-styles`, so a Claude style never arrived this way, and whether the map reaches Copilot's own instruction discovery is unverified, since the wiki records the switches as configuring only the Local harness, which that same record marks deprecated for removal in February 2027. The cost it carries is that the user's own Claude rules stop loading in the Local harness, accepted in exchange for keeping Claude-tree instructions out of that harness's view. Merge `{"~/.claude/rules": false}` into the user's VS Code settings through `merge_settings_map_entries`, the entry-grain settings-map helper already defined in `deployment/deployment.sh` and already exercised with this exact key in `tests/deployment/script_tests/vscode_hook_run.sh`; `merge_json_key` supplies only the prior capture and restore log shape, since it writes the whole key. That helper captures the prior value on first write and restores it on uninstall, and narrows the merge to that one path so every other entry the user set survives. A `--project-dir` run writes no settings key and leaves that route as it found it, since the file it would touch is the user's own VS Code settings outside the project. The hook half of the same adoption landed without a settings write in [deployment_vscode-hook-routing.md](archive/deployment_vscode-hook-routing.md), because no editor setting is documented to close that route, so this style merge is the first deploy-path caller of that helper.

Rewrite [Output style delivery design](../wiki/concepts/output-style-delivery-design.md)'s `### What the deploy writes per target` in place so its `Copilot in VS Code` row states both destinations and the settled filename (`~/.copilot/instructions/natural-language.instructions.md` at `--global`, `.github/instructions/natural-language.instructions.md` at `--project-dir`, body only), records the `chat.instructionsFilesLocations` key as a `--global` settings write beside the style's own no-activation-key delivery, and carries the shape `file plus key at --global; file only at project scope`; and so the built-rows paragraph beneath that table (opening `Claude and Cursor are the built rows` and closing `Every other row stays per-target delivery work`) names Copilot in VS Code among the shipped rows. That paragraph is shared with [the Antigravity style task](deployment_output-style-antigravity.md), which rewrites it to name Antigravity among the shipped rows: read the paragraph as it stands before rewriting and keep every row already named there, so whichever task lands second does not drop the other's built row. Replace the existing text at each site rather than adding a second account beside it.

**Out of scope:**

- Delivering the style through a Copilot agent plugin, which has no instructions component, so its only routes are a selectable agent or an on-demand skill and neither is standing.
- Writing anything into the Claude configuration tree to reach this target, which the **Context** rejects as adoption rather than delivery.

## Acceptance

- A dry run under `--global` restricted to the style type and the VS Code target reports exactly one style-file write, into Copilot's own user-profile instructions root and nowhere in the Claude configuration tree; the settings-map merge that run also reports is a separate action, proven by the settings-merge item.
- A dry run under `--project-dir` reports exactly one file write, into that project's `.github/instructions/` directory, and it touches nothing under the home directory and reports no `chat.instructionsFilesLocations` merge.
- A real deploy at each scope, under a scratch `HOME` and a scratch `--project-dir` and driven from a case in `tests/deployment/script_tests/style_run.sh`, writes exactly `~/.copilot/instructions/natural-language.instructions.md` under the global scope and `<project>/.github/instructions/natural-language.instructions.md` under the project scope, and the wiki's GitHub Copilot in VS Code page records that filename at both scopes as the supported form, dated to the verification.
- The project-scoped file carries an `applyTo` value scoping it to every file, so it is always-on rather than pattern-limited.
- The deployed file contains no Claude output-style frontmatter keys, verified by searching it for `keep-coding-instructions` and `force-for-plugin` and finding neither.
- The deployed body contains no reference to Claude's keep-coding-instructions mechanism, and the clause that named it reads correctly for a harness that only appends.
- Uninstalling removes the deployed file and leaves any other instructions files in the same root untouched.
- A global dry run reports a `chat.instructionsFilesLocations` merge setting `~/.claude/rules` to `false`, a real deploy under a scratch `HOME` records the key's prior value for uninstall, and an unrelated entry placed in that key beforehand survives the deploy. Uninstalling from that same `tests/deployment/script_tests/style_run.sh` case restores the key's prior value, and removes the key when the prior was `@absent`. The `deployment/README.md` VS Code row and the wiki's GitHub Copilot in VS Code page describe that merge as a `--global` Local-harness setting, and a search of both for `only route` and `route closed` finds neither.
- `deployment/README.md`'s existing VS Code Copilot row stops reading `not yet` in its Styles cell, and that cell becomes the single canonical statement of the style destination: it names the instructions root, states that no activation key is needed, and states that this target appends rather than replaces, so adherence is weaker than on Claude.
- `wiki/concepts/output-style-delivery-design.md`'s `### What the deploy writes per target` Copilot in VS Code row names both destinations, the settled `.instructions.md` filename, and the `--global` `chat.instructionsFilesLocations` write, and its built-rows paragraph beneath that table names Copilot in VS Code among the shipped rows, checked by reading those two passages beside the shipped arm's write path and generator call and finding no Copilot row left stated as `file only` or as a global path only.
