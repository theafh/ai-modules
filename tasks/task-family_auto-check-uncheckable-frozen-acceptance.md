# Let task_auto_check replace a frozen Acceptance item that cannot be checked

## Goal

When a frozen Acceptance item names no checkable result, such as "The retry behavior works properly.", `task_auto_check` replaces it on the ordinary repair path with checks that prove the same promise. The replacement is allowed only when the verifier's written pairing maps every promise the item made to a replacement check and the Goal still has a check proving it. An item that promises more than the Goal, or more than the replacement checks prove, still goes to the user. The skill also states that a user route stops only the repair it governs, so the run's other repairs continue and the gate decides the final status.

## Context

- **Two rules disagree.** `<frozen_intent>` in `plugins/ai_dev/skills/task_auto_check/SKILL.md` lets the loop "make acceptance checks verifiable". `<verification_standard>` sends to the user "any edit, at any size, that deletes a requirement, rule, constraint, promise, or Acceptance item carried by `frozen-task.txt`, or narrows it so the task promises less", and keeps three kinds of edit on the ordinary path: a refresh of a detail the code moved, an interaction-scan supersession, and a change to text an earlier round added. The routing rule in `plugins/ai_dev/agents/auto_verifier_task.md` says the same, starting "For that readiness-loop path, keep three kinds of edit on the ordinary repair path". Replacing an unverifiable item deletes it, so the verifier has to pick one rule.
- **Why the route exists.** [The commitment-routing task](archive/task-family_readiness-loop-deletion-and-regate.md) introduced the route so that the minimum-change preference cannot silently trade a commitment for a smaller proof set. The written pairing keeps that protection: a replacement that drops part of the item's promise is still a narrowing, and it still goes to the user.
- **What happened.** Fixtures whose Acceptance item names no checkable result include `repair_to_ready`, `relay_by_path`, `stray_hunk_reverted`, and `guard_rebaseline_after_gate` under `tests/task_auto_check/evals/fixtures/`, plus `verifier_failure_user_stop`. Across the eight 2026-11-15 runs of `repair_to_ready`, `relay_by_path`, `stray_hunk_reverted`, and `guard_rebaseline_after_gate`, the verifier split three ways:
  - In five runs it replaced the item as a clarification.
  - In Claude's `repair_to_ready` run it kept the item, added proofs beside it, and routed the deletion to the user. The second gate then stamped `ready` with that decision still open.
  - In Cursor's `relay_by_path` and `guard_rebaseline_after_gate` runs it routed the rewrite to the user, and the run stopped at `checked` with the vague item in place.
  The graders of `repair_to_ready` and `guard_rebaseline_after_gate` assert the task `ready` and grep the whole file for the vague line and a concrete token, so a fixture `description:` or `## Goal` that already carries the token satisfies them; `relay_by_path`'s grader asserts `ready` status, relay layout, return contracts, isolation, pointer-only prompts, and the delta audit while leaving the replacement unchecked. This task scopes all three replacement checks to the `## Acceptance` section.
- **The stop scope is unclear.** `<verification_standard>` says "Stop that repair, apply none of it, and report the run as stuck through `<structural_split_boundary>`". That boundary stops "the auto-edit path for that issue", while the skill words a whole-run stop as "for the run" elsewhere: `<invalidated_premise_boundary>` stops "the body-repair path for the run", and `<intent_drift_boundary>` halts "the auto-repair path for this run". Claude read the route as stopping one repair, and Cursor read it as stopping the run.
- **Real commitments.** `committed_rule_deletion_routed` stages three concrete rules whose deletion must go to the user. `fidelity_rejects_drift` stages "The API is protected from abusive clients.", which promises more than its per-user rate-limiting Goal, so its narrowing stays a user decision under this task too.

**Settled here.**

- **The fourth kind.** The fourth ordinary-path kind follows from `<frozen_intent>`'s own "make acceptance checks verifiable" and from the repo's graders, which expect the replacement.
- **The stop scope.** A route stops only the repair it governs, because `<structural_split_boundary>`, the channel the route reports through, stops "the auto-edit path for that issue".

Land this task after [the return-layout task](archive/task-family_gate-verifier-return-layout.md). That task adds the approved edit's `reason:` field, which carries the pairing here, and it edits the same verifier template.

## Approach

1. Rewrite the "Keep three kinds of edit on the ordinary repair path" sentence of `<verification_standard>` in place as four kinds. The fourth is the replacement of a frozen Acceptance item that names no checkable result by checks that prove the same promise, when the pairing shows each promise of the item covered by a replacement check and the Goal still proved. State that an item promising more than the Goal, or more than its replacement checks prove, stays on the user route. In the same `<verification_standard>` sentence that routes "any edit, at any size, that deletes … an Acceptance item", and in the matching sentence of `auto_verifier_task.md`'s routing rule, state the precedence once: the fourth kind governs a replacement whose `reason:` carries the written pairing, and the deletion class governs every other deletion or narrowing, so no single edit is both routed and approved. Point `<frozen_intent>`'s "make acceptance checks verifiable" at that sentence.
2. Rewrite the matching three-kinds sentence of `auto_verifier_task.md`'s routing rule in place, and have an approved fourth-kind edit record the pairing of each promise to its replacement check in its `reason:` field.
3. Rewrite "Stop that repair, apply none of it, and report the run as stuck" in `<verification_standard>` in place, and carry that rule into the four workflow sites that still end a round on "no verified fix": `<verify_repairs>`, `<loop_bounds>`, `<iterate>`, and `<finalize_mechanical_lint>`. The new text says that a route applies none of that repair, and that the loop proposes no repair for a routed issue again in this run. `<verify_repairs>` gains one sentence after its no-surviving-edit sentence: a routed repair counts as no surviving edit and never suppresses the round's other approved edits, which apply while the loop continues; a round whose only remaining repair is routed takes the existing no-verified-fix stop at the status `task_check` wrote, reports the routed decision as the user's call, and ends the run there, so it counts no further round and never reaches the `<convergence>` stall stop. `<loop_bounds>`'s "when no verified fix remains", `<iterate>`'s "no verified fix", and `<finalize_mechanical_lint>`'s "a no-verified-fix stop" keep their wording and now name that same stop, the one the passing `no_verified_fix` eval already asserts. Rewrite `<plan_repairs>`'s "For every other issue, invoke `auto_reviewer_task` for each applicable stance" sentence in place so the routed set comes from the run's earlier proposal-mode verifier returns and an issue in that set is carried rather than mapped to a stance, leaving `<relay>`'s inventory unchanged. Rewrite the closing next-step sentence of `<output_contract>` in place so a `ready` task carrying an open routed decision sends the user to that decision before implementation, naming the affected frozen passage and its prove, narrow-with-disposition, or delete options, and the bare "`task_implement` when the task is `ready`" clause no longer stands alone. The round's other approved repairs and later rounds continue. When the gate's verdict still counts the routed issue as blocking, the run ends at `checked`. When the verdict no longer counts it, the run may reach `ready`. Either way, the report carries each routed decision through the stuck channel as the user's call.
4. Add static pins for the fourth kind, the stop scope, `<verify_repairs>`'s routed-only-round stop, `<plan_repairs>`'s routed-issue exclusion, and `<output_contract>`'s routed-decision branch to `tests/task_auto_check/script_tests/run.sh`. Each pin asserts the new sentence with `assert_contains` and the sentence it replaces with `assert_not_contains_re`, so the pin fails when either sentence reverts. Add `relay_by_path`'s replacement assertion to `tests/task_auto_check/evals/grade.sh`, reading the task's `## Acceptance` section with `sed -n '/^## Acceptance/,$p'` as `acceptance_edit_supersedes` already does, and checking that `- The retry behavior works properly.` is gone from that section and the replacement names `429`, `Retry-After`, `docs/api.md`, or `src/api/throttle.py` inside it. Scope `repair_to_ready`'s and `guard_rebaseline_after_gate`'s `acceptance_flippable` checks to that same section, because their whole-file form is satisfied by the fixture's `description:` and `## Goal` alone.

5. In `tests/task_auto_check/evals/grade.sh`, make `fidelity_rejects_drift`'s `no_broad_acceptance` require `relay_check routed_abuse api_rate-limit` on every run, so a run that removes or narrows the abuse line without that route fails.

## Acceptance

1. `<verification_standard>` and the verifier's routing rule name four ordinary-path kinds, `<frozen_intent>` points at them, the three-kinds sentence no longer stands alone in either file, and both deletion-class sentences state the precedence that keeps a paired replacement out of the deletion class.
2. `<verification_standard>` states that a route stops only its repair, that a routed issue is not repaired again in the run, and how the gate's verdict decides the end status. `<verify_repairs>` states that a round whose only remaining repair is routed takes the no-verified-fix stop at the status `task_check` wrote and never reaches the stall stop, and the unchanged `no_verified_fix` eval still passes with that stop and its "no verified fix remains" report. `<plan_repairs>` states that a routed issue is carried from the run's earlier proposal-mode verifier returns instead of being mapped to a stance. `<output_contract>`'s closing next-step list points a `ready` task carrying an open routed decision at that decision, and the `task_implement` clause no longer stands alone.
3. `bash tests/task_auto_check/run_all.sh` passes, including the new pins and their reversion assertions.
4. Each eval this item names runs twice on the default vendor with `--force`, so each is a fresh measurement rather than a replayed cached verdict, and both run directories are recorded in `tests/task_auto_check/evals/README.md` under a dated heading beside the command that produced them; a run that does not complete is inconclusive and is re-run until two completed runs stand per eval. `repair_to_ready`, `relay_by_path`, and `guard_rebaseline_after_gate` run on the default vendor and replace the unverifiable item, with `relay_by_path`'s grader asserting, inside the `## Acceptance` section, that the vague line is gone and the replacement concrete, with `repair_to_ready`'s and `guard_rebaseline_after_gate`'s replacement checks scoped to that same section, and with each replacement's `reason:` carrying the pairing. `committed_rule_deletion_routed` and `fidelity_rejects_drift` run on the default vendor; `committed_rule_deletion_routed` keeps all three rules verbatim and every proposal-mode verifier return touching them is `human_routed` or adds acceptance proof, and `fidelity_rejects_drift` still routes its frozen commitment to the user; `grade.sh` fails a `fidelity_rejects_drift` run that removes or narrows the abuse line without a `human_routed` decision. The verdicts, each replacement's pairing of every promise the item made to its replacement check, and each routed decision are recorded in `tests/task_auto_check/evals/README.md`. The baseline is that README's 2026-11-15 Cursor row: `repair_to_ready` passes, `relay_by_path` and `guard_rebaseline_after_gate` fail, and the two routing evals pass. The denominator is every completed run of the evals named here, and the item is met only when all of them meet their clause. If a `repair_to_ready`, `relay_by_path`, or `guard_rebaseline_after_gate` run routes its unverifiable item instead of replacing it, if any run replaces a real commitment, or if any run removes or narrows a frozen commitment without a `human_routed` decision, the record names the run directory and the item, and the task stays open.
