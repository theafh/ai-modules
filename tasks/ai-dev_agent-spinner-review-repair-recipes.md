# Ship agent_spinner's review and repair recipes, with run.sh checks for every recipe file

## Goal

agent_spinner is the skill an orchestrating agent, the orchestrator, reads before it runs helper agents. Its body describes general shapes, such as one helper per file or a panel of reviewers. A recipe adds the step-by-step procedure for one common kind of job. It is a reference file under `plugins/ai_dev/skills/agent_spinner/references/recipes/` that lists the job's helper phases, the steps the orchestrator runs itself, and its checks.

After this task, an orchestrator whose ask is a source-fidelity review, a drift repair across many artifacts, or a read-only audit sweep finds a matching recipe. It reads that recipe in full, names it in the run's opening sentence, and follows its phases, orchestrator steps, and checks.

This task ships three recipe files, `fidelity-review.md`, `artifact-repair.md`, and `check-only-audit.md`. It adds their rows to the `<selector>` recipe table, which maps each kind of ask to its recipe file. It also ships the per-recipe static checks in `run.sh`, the skill's static test script, which hold every recipe file to one layout and one set of shared lines. It ships one eval per recipe, each a behavioural test on a staged fixture. One more eval proves that an orchestrator working from an attached skill body reads and names the recipe its ask matches. An attached body is the `SKILL.md` text a user attached by hand, which arrives in the conversation without its reference files.

- **Terms the recipes use.** The run protocol and the checks define these terms:
  - The run ledger is the program `scripts/run_ledger.py`, bundled with the skill, which keeps a run's records under `.agent_spinner/`. Its commands are verbs. `init` opens a run over an enumerated list and records the baseline, and `close` ends the run. A clean `close` exits 0, which it does only when nothing is left open.
  - The baseline is the state of the files, and the output of each named gate, when the run opens. The net diff is every change between the baseline and the final tree, which `diff` measures and writes per file under `diffs/`.
  - A gate is either a deterministic command, such as a linter, or a user gate, a question the user must answer before the run goes on. `gate` runs a command gate and compares its result with the baseline run. A positive control is a known positive that a count or search must find before its empty result counts (C4).
  - The roster lists the run's rows. A row is mostly one helper's work on one unit, such as one page, and it carries a bound, the time after which the orchestrator stops waiting for it. `rows` creates the rows of a later phase from accepted records, one row per record.
  - A return is what a helper hands back. `accept` checks a return against the return contract and imports its records, such as findings and forks, before the return counts. A beyond-brief find is a defect a helper noticed outside its brief, and an incident is something that went wrong during its work.
  - A wave is a group of helpers sent out together. A barrier is the point where the orchestrator waits for every return of a phase before it goes on.
  - The tiers are the ways a run can execute. At the inline floor the host offers no way to spawn helpers, so the orchestrator runs every pass itself, one after another. Under batch delivery, a batch of spawned helpers returns together inside the turn. Under notice delivery, a spawn returns at once and a notice reports its completion later.
  - A fork is a real decision that belongs to the user. A decision packet puts one fork to the user, with its options, their costs, and a recommendation.
  - A stamp is a status field that a separate gate owns, such as a task's readiness status. A marker records what an earlier pass examined, such as a capture hash, an audit baseline, or an index or log entry. The family skill that owns a stamp or marker updates it through its own gate (C9).
  - A refute-by-default checker starts from the position that the work is wrong, and it clears the work only with a cited span. A lens is one angle a checker reads from.
  - A finding is recall-confirmed when a checking pass was shown it and did not refute it. It is independently surfaced when a pass found it without being shown it.
  - A read receipt is a helper's claim that it read a file, carrying one verbatim line from it. Tool evidence of a full read is a record, such as the helper's tool log, showing that it read the whole file (C8).
  - Depth is the model and effort a helper runs at. A narrowing is any cut to what the run checks, which the run names aloud and puts to the user when it drops a check.
- **Approved decisions these recipes apply.** The owner approved each on 2026-10-03.

## Approach

### Recipe file layout

Write each recipe as one file under `references/recipes/`, in pseudo-XML with positive, action-oriented wording, as the standing repo rules require.

- Open with an H1 that names the recipe id and title, such as `# J1. Source-fidelity review and fix`, so a cross-reference by id resolves by search.
- Wrap the body in one outer tag named after the file stem with hyphens turned into underscores, such as `<fidelity_review>`. Inside it, place thirteen field tags in this order: `<trigger>`, `<ledger_steps>`, `<phases>`, `<width>`, `<roles_and_returns>`, `<adversarial_checks>`, `<orchestrator_gates>`, `<failure_handling>`, `<stop_and_ask>`, `<report>`, `<cost_profile>`, `<tier_notes>`, `<post_run_checks>`. A variant ships as its own tag inside the same outer tag.
- The fields hold these parts of the procedure. `<trigger>` says when the recipe applies, and `<ledger_steps>` names the ledger commands the run makes. `<phases>` lists the helper phases, and `<width>` says how many helpers each phase gets. `<roles_and_returns>` says what each helper role returns, and `<adversarial_checks>` says how checkers try to refute the work. `<orchestrator_gates>` lists the steps the orchestrator runs itself. `<failure_handling>` covers helpers that fail, and `<stop_and_ask>` says when the run asks the user. `<report>` says what the report carries, and `<cost_profile>` holds the cost estimate and the cuts the user may choose. `<tier_notes>` says what changes at each tier, and `<post_run_checks>` lists the checks after the run.
- List two to four numbered helper phases in `<phases>`. Each phase is one verb plus one clause naming what a helper does over which unit, and it names the earlier returns it reads.
- List the orchestrator steps under `<orchestrator_gates>` in run order. Scouting, calibration with the user, deterministic gates, merges by script, validation, and reporting are orchestrator steps. So is a single helper dispatched at a barrier, such as a critic, a planner, or a validator. The one repair round re-enters the write and check phases, so it adds no phase.
- Cite run-protocol steps and checks by their labels, P1 to P6 and C1 to C10. Name ledger verbs and flags only from the frozen set in run-protocol.md's command reference.
- Keep each recipe file at most 12,288 bytes. The orchestrator reads a matched recipe in full, and the recipe must carry every rule. The context estimate that P1 requires already counts that load. No standing repo rule caps a reference file, so this one limit covers every recipe. Each planned recipe fits it with all its fields.
- Register each recipe's severity names at `init`. `init` records the ladder `blocker`, `major`, and `minor` unless `--severity` names others, and `accept` rejects any finding whose severity sits off that ladder. Each recipe therefore passes the names its roles use with `--severity` at `init` whenever they differ from that default.
- Name the ledger's finding keys in every `<roles_and_returns>`: each finding carries `claim`, `severity`, `quote`, and `anchor`, and each examined entry carries its `receipt`, matched against the input version its row recorded (P3). `accept` rejects a return that omits any of them.
- Write rules only. Leave out session figures, cost observations, case evidence, harness product names, tool identifiers, harness paths, instruction-file names, and precedence phrases such as "takes precedence".

In each recipe section below, the bold label of a field bullet names its field, such as **Trigger.** for `<trigger>` and **Cost profile cuts.** for `<cost_profile>`. A variant bullet names its own tag, and the **Gates beside the steps.** bullet lists gates that run beside the ordered steps.

### Lines every recipe carries

Every recipe carries the shared lines quoted below. Each quoted line stands as a paragraph of its own inside its field, so a later recipe can copy it whole. The per-recipe checks find each one by the phrase `RECIPE_SHARED_LINES` or `RECIPE_REPAIR_LINES` holds for it. A plain note follows some lines, and only the quoted text goes into the recipe.

- `<trigger>`: "It runs under {shape} and applies only after the selector matched that shape." Each recipe writes its own shape in place of `{shape}`.
- `<width>`: "A run whose context estimate crosses half the host's window spans sessions at wave ends (P1)." A run expected to fill more than half the host's context window therefore continues in a fresh session at the end of a wave.
- `<roles_and_returns>`: "A role barred from file writes returns in its final message, which you relay verbatim to `accept --stdin`, never through a shell (P3)." A helper that may not write files thus hands back its return as its final message, and the orchestrator passes that message to the ledger unchanged.
- `<orchestrator_gates>` opens with "These orchestrator steps run in this order, and the announcement lists them as checks. Its first step runs the gate-scope check from run-protocol.md's run-directory section before dispatch. A report step builds the report from the ledger after a clean `close` (P6)." The announcement is the run's opening statement to the user.
- `<failure_handling>`: "At a turn end with rows out, send the interim report. Any later turn runs `status`, then `attach` when a run is open, and accepts every pending return before it continues (P4)." Rows out are rows whose helpers have not returned yet. The interim report names each open row and each open gate, `status` shows the run's state, and `attach` re-enters an open run.
- `<stop_and_ask>`: "Ask about scope and the estimate before dispatch, with the estimate beside any size guideline the host or user states, and ask before any widening past the enumerated list. An answer the request states is the user's answer. On a host with no later turn, an unanswered gate ends the run with its decision packet (P1). Create the stop file with `stop` the moment a pause request arrives, before any question (P4)." The stop file halts new dispatch while running helpers finish.
- `<cost_profile>` opens with "Keep these whatever else is cut: coverage by construction, a review of every landed write, and baseline-differential gates. Offer each cut only as a narrowing the user chooses, with the checks it drops. Estimate the cost as rows per phase, times the per-row cost the pilot measured, plus the checking share." The recipe's own cuts follow. Coverage by construction means one row for every enumerated item, so no item is skipped. Baseline-differential gates compare each gate's final result with its baseline run. The pilot runs two or three items to price one row.
- `<tier_notes>` holds one note per row of run-protocol.md's tier table: the inline floor, batch delivery, and notice delivery. Each note says only what the orchestrator does differently there and states no host behaviour and no measurement.
- A recipe with a repair round also carries three lines. `<orchestrator_gates>` says "The one repair round (C5) re-enters the write and check phases for the failing rows." `<report>` says "Report each repaired item as re-checked once, recall-limited, and unverified end to end, or as failed after repair (C5)." `<post_run_checks>` says "Each repaired item has exactly one re-check row, at no lower depth than its first check."

### `fidelity-review.md`: J1, source-fidelity review and fix

- **Trigger.** The shape is per-artifact fan-out. The ask checks derived documents against the sources they cite. It looks for dropped details, misreadings, overcompression, invented forks, wrong connections, and missed integration. The run fixes what the sources settle and puts the rest to the user. These signals mark the ask: pages with a source-lineage field that names their sources, source captures with recorded content hashes, an index and a log, and live originals behind the captures. A source capture is a stored copy of a source, and its live original is the source it was copied from.
- **Ledger steps.** `init` takes the lineage inventory, meaning the pages listed from their source-lineage fields, with its exclusions. It also takes the pages and captures the owning family reports as marked, meaning they carry a marker (C9). `accept` checks each finder's coverage list against the inputs its unit recorded. `rows --from-records` creates the Verify rows, `--from-gaps` the gap-unit rows, and `--from-repair-list` the repair rows. Accept the plan against every target path the surviving findings name. The linter differential, which compares the lint output at the baseline and at the end, runs last as a `gate`. Before `close`, each changed marked path has a hand-off or fork row. A hand-off row passes the marker update to the owning family's gate, and a fork row puts it to the user.
- **Phases.** **Find**: a read-only finder reads each unit against its cited sources and reads no earlier return. **Verify**: two refute-by-default lenses test each write-bound finding, meaning each finding that would lead to an edit, and each lens reads the Find return that raised it. **Write**: a writer applies each target path's confirmed block, the confirmed findings for that path, reading the findings file. **Review**: a read-only reviewer reads each changed path's diff against the baseline, with its Write return.
- **Width.** Find gets one finder per unit row. Verify takes the write-bound findings plus a fixed sample of each unverified band, times two lenses, in batches of at most five (C7). An unverified band is a severity band left out of full verification. Write gets one writer per target path. Review gets one reviewer per changed path in the net diff, the orchestrator's own edits and the index included (C1). The repair round gets one repairer and one re-checker per failing path. The plan caps the gap units, the extra units the completeness critic proposes for ground the earlier passes missed (C6). Verify, gap-unit, and repair rows come from accepted records (P4). Lenses and reviewers run no shallower than the passes they check.
- **Roles and returns.** Writers, repairers, and the validator, the roles that may write files, write return files.
  - The finder returns its label, its unit, and findings. Each finding carries an id, a kind (dropped detail, misread, overcompressed, false fork, integration hole, or wrong connection), a severity, a class (fix or decide), the page path and quote, the source path, anchor, and quote, and a suggested fix. A fix-class finding is one the sources settle, and a decide-class finding goes to the user. The finder also returns its coverage per path (read in full, searched, or unreachable), what it examined and cleared, beyond-brief finds, and incidents.
  - The source lens re-reads the source in context, and the page lens re-reads the page and searches the corpus. Each lens returns, per finding, a verdict (confirmed, partly, or refuted), a corrected statement for partly, the settling span, and a confidence.
  - The writer re-reads the cited source and applies exactly its block. It returns applied, rejected, or routed per finding, with the span it re-read. It also returns contradictions between its instructions and the source, the recorded decisions it touched, and incidents.
  - The reviewer returns issues with a kind (instruction unapplied, unsupported, lost qualifier, dropped content, misquote, decision changed, or prose), a severity, the hunk, the source span, and a fix. A hunk is one changed block of a diff. It also returns the hunks it cleared.
  - The repairer re-derives each issue and returns applied, refuted with its span, or routed (C5).
  - The validator returns the invariants held, the invariants broken with path and anchor, and the proposals it left unapplied.
- **Adversarial checks.** Both lenses open from "refuted unless the evidence confirms". A partly verdict's corrected statement replaces the finding downstream. A finding survives when no lens refutes it and at least one lens returns, and it takes the lower severity. When both lenses saw it, its label is "survived both lenses, recall-confirmed". Each batch set carries one known-false control, a planted finding that its quoted source contradicts, so a verifier that confirms it has failed (C7). The reviewer opens from the position that the edit dropped, distorted, or skipped something. It reads the diff, the writer's block, and the cited sources. It clears a hunk only with a hunk citation plus a source citation.
- **Orchestrator gates, in run order.**
  - **Scout**, before Find: build the inventory by script from the lineage fields, and exclude each page with no resolvable source, with its reason. Cut units one helper can read in full. Add the cross-cutting sweeps the corpus needs: a fact ledger, the open questions the sources settle, and sources no capture holds. Run the gate-scope check, record the baseline and the roster (P1), and put the scope forks, the verification scope, and the estimate to the user (C7). When no family owns the corpus, the scout records the corpus's own markers (capture hashes, audit baselines, index and log entries) at `init` as marked targets.
  - **Critic**, at the Find barrier: the completeness critic reads the coverage records, and its gap units become Find and Verify rows (C6).
  - **Findings file**, before Write: build it by script, with one block per target path. Use a planner only where root-cause clustering, grouping findings by their shared cause, needs judgement. Take its plan as a manifest, and treat any canonical statement it writes as a produced artifact (P3).
  - **Repair round**, after Review, for the paths with a blocking or should-fix issue.
  - **Terminal validation**: the validator checks the index, log, and schema invariants.
  - **Hand-offs**: capture hashes, the audit baseline, and index and log upkeep go to the owning family's gate by name, naming as examined only rows read in full (C9). On a corpus no family owns, each marker update goes to the user as a fork.
  - **Report**: the report step that `### Lines every recipe carries` describes.
- **Gates beside the steps.** These gates run beside the ordered steps. Inventory arithmetic: every inventory path belongs to a unit or a named exclusion. Coverage: count a path as read only where tool evidence shows a full read, and `accept` checks each receipt against the input version its row recorded (C8). Positive controls run on every numeric scan (C4). A decision guard checks that no edit dropped or reopened a recorded decision. It searches the removed lines under `diffs/` for decision markers with the ledger's `search`, and it searches the edited pages for any decided item still stated as open. The closing checks are the linter differential and a net-diff audit that finds a review row for every changed path.
- **Failure handling.** A plan whose tasks cover fewer target paths than the findings name stops the run before Write. The planner gets one re-invocation with the gap listed, and a second miss fails the phase, which the report states. The terminal validator writes only its named set, and it returns a shortfall report when an upstream phase produced nothing. A dead finder earns one re-invocation, and then its unit is reported unreviewed. A finding whose lenses both failed stays unverified. An aborted writer's paths are reconciled from the diff before any re-dispatch (P4).
- **Stop and ask.** Put the verification scope to the user with the scope and the estimate. Before dispatch, route every write to a marked page or capture to the owning family's gate or to the user, whatever the write changes (C9). A widening from review to fix goes to the user. So does a marker advance past the rows read in full, meaning a marker that would claim more than the run read, and so does an item that fails its re-check. Every decide-class finding and every writer contradiction goes out as a decision packet (P6). Writers keep every recorded decision. Where a source undercuts a decision's premise, the writer adds one sentence saying the premise is worth revisiting.
- **Report.** Build it from the tally block, the counts `close` prints (P6). The opening sentence counts the helpers dispatched, returned, and accepted in each phase. Coverage splits into read in full by tool evidence, claimed by receipt only, only searched, and unexamined, and each unexamined class names the check that would cover it. Findings are counted raised, verified, narrowed, and refuted per lens, split into recall-confirmed and independently surfaced. Each unverified band carries its sample rate, and a zero refutation rate is named as a calibration question. List the paths written, reviewed, repaired, and re-checked, the open items by id, and each hand-off with the rows it names as examined.
- **Cost profile cuts.** The cuts are a narrower verification scope, a smaller sample of each unverified band, and a lower cap on gap units.
- **Tier notes.** Inline floor: Find and Verify run as separate passes, each closing on its return file, and Review reads the per-file diffs that `diff` wrote. Batch delivery: each wave's lenses go out in the batch after its finders, and a row that returns late is marked as over its bound (P4). Notice delivery: send a unit's Verify rows once its Find return is accepted, and hold page writes until the readers return (P5). Where the notice carries no result, batch the read-only roles (P3) and poll the Review wave inside the turn (P4).
- **Family-owned variant**, in `<family_owned_variant>`. When the user names agent_spinner for a knowledge base the wiki family owns, the family writer stays the only writer. The orchestrator runs the scout, Find, the critic, and Verify at its own level. It then hands `wiki_fix` the confirmed findings as its scope, once the user approves the list. After the writer returns, the orchestrator runs Review and sends every repair back to `wiki_fix` as a findings list the user approves. It relays the family agent's report as that family's contract requires. The family agent keeps its own checks, and the variant restates none of them.
- **Post-run checks.** Unit rows equal the inventory minus exclusions, and each unit has an accepted return with a coverage list. Every write-bound finding has two lens verdicts or an unverified label. Writers equal the distinct target paths, and every changed path has a review row. Every changed marked path has a hand-off or fork row, and each hand-off names as examined only rows read in full (C9). Every premise sentence the plan routed exists in its landed page. A premise sentence is the sentence a writer adds to say that a decision's premise is worth revisiting.

### `artifact-repair.md`: J4, drift repair across many artifacts

- **Trigger.** The shape is per-artifact fan-out. The ask finds which of many specification artifacts drifted from the repository, fixes them, and checks the fixes. Such artifacts are tasks, specs, or procedure pages, and one has drifted when what it says no longer matches the code. These signals mark the ask: items with anchors into the code, status stamps that separate gates own, and completed items beside live ones. Where a shipped family owns the backlog, its contract governs, and every stamp consequence goes to that family's gate by name. That family's contract states what the gate does.
- **Ledger steps.** `init` takes the drift table's drifted rows, with each row's stamps as the owning family reports them. The scout writes the drift table, its verdict on every artifact. An item fails its check when that check raised a blocking or should-fix finding, whatever verdict word the checker used. A nit-only item goes to the report. `rows --phase write --from-repair-list` creates one row per item on the repair list (C5). `rows --phase write --from-records` creates one write row per critic finding that needs a repair or a new artifact, and `diff --add-checks` adds its check row. The link-graph validator, which checks the links between artifacts, runs before `close`. The roster shows a routing or fork row for every changed path recorded as stamped, sending the change to the owning gate or to the user (C9).
- **Phases.** **Write**: a writer repairs each drifted artifact and reads no earlier helper return. Its brief has four parts: what is stale, the tree state to verify, the fix, and what to verify without assuming it is stale. **Check**: a checker reads each repair's diff against its brief, with the writer's return, and goes out as soon as its writer returns. **Critique**: three critics each test the scout's work under one lens (C6), reading the drift table and the net diff and no helper return. One refutes every item the scout called current, one reads recent commits for landed work no item accounts for, and one scans outward from the touched code.
- **Width.** Write gets one writer per drifted row, and Check gets one checker per repair. The repair round gets one remediator per item on the repair list (C5). Critique gets three to five critics. Each critic repair and each new artifact gets one write-and-check pair. Each trade-off proposal, such as a merge or a split, gets one advocate per side.
- **Roles and returns.**
  - The writer returns its label and path, what it applied and skipped, brief corrections, judgement calls, the contract clauses its changes touched, a statement that it left the stamp alone, and incidents. A brief correction is a place where the writer found its brief wrong.
  - The checker returns a verdict (`pass` or `fail`, the ledger's only verdict values) and issues with a severity (blocking, should-fix, or nit). The finding list decides the item's fate, so a `fail` verdict carrying only nits leaves the item out of the repair list. It also reports the anchors checked and those that miss, whether intent was preserved, the stamp consequence, and the fate of each input finding: resolved, refuted with its re-derivation, or silently dropped.
  - The critic returns its lens, findings with evidence, and items confirmed clean with citations.
  - The remediator returns applied, refuted with its span, or routed per finding, plus the minimum edit it made.
- **Adversarial checks.** A trade-off question gets a symmetric stance, which argues each side at full strength: one challenger per side, the user's objective in the user's own words, and a status-quo cost beside every proposal (C2). The repair checker opens from the position that the repair is incomplete or wrong. It runs a closed checklist of seven to nine lines, which check these points:
  - The diff matches the writer's report, with unrequested and missing changes listed.
  - Every quoted anchor is re-derived.
  - No new defect of the repository's banned classes appears.
  - Intent is unchanged.
  - Stamps are unchanged, and the stamp consequence is stated.
  - The named staleness is gone.
  - Every input finding is accounted for.
- **Orchestrator gates, in run order.**
  - **Scout**, before Write: read every artifact and test its anchors, run the gate-scope check, and write a drift table. The table names the method behind each verdict and lists the items judged current, marking those judged on anchors alone.
  - **Lifecycle triage**, before Write: route each completed item to its audit or close-out, or to a new follow-up item, and leave its contract as delivered. Route every write to a stamped target to its owning gate by name, or to the user as a fork, whatever the write changes (C9).
  - **Sibling-surface enumerator**, at the barrier before any contract repair: one helper lists every surface that carries the same contract, such as a sibling file or block that states the same rule.
  - **Critic rows and new artifacts**, after Critique: every critic repair and every new artifact (a filing, merge, split half, or repoint) gets its own write-and-check pair. A filing is a newly filed item, and a repoint moves links to a new target. A new artifact starts at its initial lifecycle state, with its inbound-reference map, the list of links that point at it, built from the repository root.
  - **Repair round**, after the critic rows and new artifacts.
  - **Terminal validation**, last: one terminal writer runs the linter last and the link-graph validator from the root, and status fields go to the owning family's gate by name (C9).
  - **Report**: the report step that `### Lines every recipe carries` describes.
- **Gates beside the steps.** These gates run beside the ordered steps. Net-diff attribution maps each changed path to a write row or marks it out-of-band, meaning changed outside the run, so the user's concurrent edits are recognised as the user's. Each writer's diff touches only its own path.
- **Failure handling.** Return templates put the verdict first and allow at most one long free-text field. The limit exists because a return with two overlapping fields can oscillate between them until its retries run out. A failed slot, meaning one helper's row, is attributed by its label and re-invoked once. The synthesis, the pass that merges the returns, receives the full item list with states, so it names any missing slugs, the stable per-item ids.
- **Stop and ask.** Surface completed items, stamp consequences, every labelled fork, every deletion of committed content, and every trade-off answer. Quote the governing skill's writer rule in the plan. State any departure from it in the same sentence as the work, together with the user's permission.
- **Report.** Keep brief corrections, checker findings, and critic findings apart. Give verdict counts from records, and each stamp consequence with the gate or user it went to. Compare the forks returned with the forks relayed, and list each filing with its check row. Close with open items by id and yield, the helpers dispatched set against the decisions or edits they produced.
- **Cost profile cuts.** The cuts are critics beyond three and single-artifact panel lenses beyond three. Each cut drops extra looks at the same work.
- **Tier notes.** Inline floor: write and check run back to back, and the critics share the scout's context, so their confirmations are recall-limited. Batch delivery: the run goes in waves, with the returned batch as the barrier before the critics. Notice delivery: checks wait on accepted writer returns, the orchestrator follows the run by reading the roster through `status`, and the final wave is polled inside the turn with `accept --wait` (P4).
- **Single-artifact variant**, in `<single_artifact_variant>`, for one artifact repaired over several rounds when no family loop governs it. A panel of three to five lenses over the identical artifact replaces a single first readiness draw, meaning one run of a readiness check. The panel includes an interaction lens that derives touch points, the names and files the change touches, and searches the code for them. The issue-by-stance list goes to the roster, with each row keyed by a slug of the issue text. Each issue gets one reviewer per stance: one adds proof and one trims. The sibling-surface enumerator runs before any proposal. The verifier reads the gate verdict and every reviewer return by file, with no preference stated, and it quotes the issue sentence each decision rests on (C3). Anchored replacements keyed by approved-edit id are applied, and then the post-apply delta audit checks the applied change against the approved edits (C1). Every deletion of behaviour-bearing content waits for the user. One re-gate, a fresh run of the readiness gate, runs in isolation with the transcript store off limits. One refute pass, with external-evidence clears, tests the final clean result (C2). A further round waits for the user.
- **Post-run checks.** First-pass writers equal the drifted rows, each writer's diff touches only its path, and every repair has a check row. The repair list equals the failing items plus the class-sweep instances, the instances a sweep for a confirmed class of defect found. Every changed path recorded as stamped has a routing or fork row, and every new artifact has a check row. Forks returned equal forks relayed plus forks listed as the orchestrator's own decisions.

### `check-only-audit.md`: J7, check-only audit sweep

- **Trigger.** The shape is per-artifact fan-out. The ask sweeps a set of artifacts with an audit and reports what to fix, read-only. Any fix runs later and only on the user's word.
- **Ledger steps.** `init` takes the resolver's artifact list, the list the repository's own resolver produces. Every deterministic checker runs through `gate` before dispatch. Findings become ledger records, and `rows --phase verify --from-records` creates one verifier row per finding before any verifier brief exists.
- **Phases.** **Review**: a reviewer reads each artifact, and one reads each comparison cluster, a group of related artifacts compared with each other. Each reads no earlier helper return. Per-artifact reviewers carry the depth checks, which read one artifact closely, and cluster reviewers carry only cross-member comparisons. The union of clusters equals the artifact list, singletons, the artifacts alone in a cluster, receive their neighbours' text, and a cluster above about five members hands its depth checks to per-artifact helpers. **Verify**: a refute-by-default verifier tests each finding, reading that finding's record from the review returns. It works on atomic claims, which are findings split into single claims, and each refutation cites its span. It gives a real but low-value finding its own verdict, and it runs at no lower depth than the reviewer.
- **Width.** Review gets one reviewer per artifact plus one per comparison cluster, and Verify gets one verifier per finding.
- **Roles and returns.** The reviewer returns findings as atomic claims, a read receipt for every mandated rubric, and what it examined and cleared per criterion. The verifier returns a verdict per atomic claim with its settling span, including the direction of the recommendation, such as whether to add or remove text.
- **Adversarial checks.** `accept` checks each read receipt against the input version its row recorded, never against the live file. Count a path as read only where tool evidence shows a full read, and report a path claimed by receipt alone as unverified by tool evidence (C8). Pair receipts with the class re-sweep, which is the recall check: it searches every unit again for each confirmed class of defect. A clean result without citations routes back once, and the join keeps dead and clean apart, so a helper that died never counts as clean (P3).
- **Orchestrator gates, in run order.**
  - **Scout and deterministic checkers**, before Review: enumerate the artifacts with the repository's own resolver, and run the gate-scope check and every deterministic checker over the whole set. Read the repository's test and coverage model before judging any gap. Write the settled results into the preamble, the shared opening every helper brief carries, as measured facts, and share them with the user while the helpers run.
  - **Class sweep and recall probe**, after Verify and before any unit is called clean: `rows --phase review --from-records` creates one sweep row per confirmed class, from one of its confirmed findings, and that row covers every unit. A confirmed class is a kind of defect a verifier confirmed at least once. Each clean unit chosen for the recall probe gets one probe row from its review record, so a second reviewer re-checks a unit the first review called clean (C8).
  - **Report**: per-unit status lists with counts computed from them, and the fix-or-file fork, which asks the user whether to fix the findings or file them as follow-up tasks.
  - **Fix**, in a later run on the user's word: a single writer re-derives each finding and checks each recommendation's direction against the standing rules and the user's latest preference. It re-runs the deterministic checkers, accounts for every removed line, and gets the paired check over the diff. A prior-art check, which looks for the same work already filed or built, runs before any follow-up task is filed.
- **Gates beside the steps.** These gates run beside the ordered steps. The resolver's count equals the inventory. Deterministic checkers run on the full set before dispatch and on the edited files after a fix, and the lint passes after a fix.
- **Failure handling.** A null review, one that returned nothing, leaves its unit unreviewed. A verifier that threw an error leaves its finding unverified. Neither counts as clean or refuted.
- **Stop and ask.** The fix-or-file fork and every direction conflict go to the user. A direction conflict is a recommendation whose direction clashes with the standing rules or the user's preference. Commits and version bumps wait for the user's explicit request.
- **Report.** Count units as clean with citation, clean after the probe, or unreviewed, and findings as refuted, narrowed, or downgraded. Label each survivor from its ledger tag: "survived its verifier, recall-confirmed" where the verifier's brief relayed it. Reserve "confirmed" for a finding surfaced independently or re-derived against the source. Split the confirmations into recall-confirmed and independently surfaced, and close with the fork.
- **Cost profile cuts.** Two cuts are possible. Dropping comparison clusters drops the cross-member comparisons. Dropping the recall probe on clean units drops the direct recall measure beside the class sweep.
- **Tier notes.** Inline floor: reviewers run as separate passes, and the report says verification is recall-limited. Batch delivery: the reviewers go out in one batch and the verifiers in the next. Notice delivery: each finding's verifier row comes from `rows` as its review is accepted, and its verifier goes out then. Poll the final wave inside the turn with `accept --wait` (P4).
- **Post-run checks.** Every unit has a state, every clean unit carries citations, and the counts match the lists. Every receipt matched the input version its row recorded, every path counted as read has tool evidence of a full read, and every finding record has a verifier row.
