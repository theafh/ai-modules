# Add git_auto_review, an automated review-and-fix loop around git_review

## Goal

Add `git_auto_review`, an opt-in loop beside `git_review` that does for a finished change what `task_auto_check` does for a task. It runs `git_review` as its only gate under the Approach's `auto_gate_git` contract, fixes the findings that qualify through a single writer agent, verifies each round's fixes refute-by-default, re-reviews the delta, and repeats until no qualifying finding remains under the **Stop rule.**, or another of that rule's stop conditions fires. Every fix stays in the working tree, uncommitted. The loop carries five convergence rules from the start, which the Approach defines: a scope anchor, a severity floor, a regression ledger, routing of owner decisions, and a stop rule.

## Context

The user ran `git_review` by hand in rounds with fixes in between throughout October 2026. One change, the git_review secret scan, took nine review rounds and eleven fix rounds in one day. Each round surfaced defects earlier rounds had missed, defects the previous fix had introduced, and requests to extend scope to new input shapes and pre-existing configuration behaviour. Across 34 tasks studied from 2026-09-24 to 2026-10-24, fix rounds introduced about 40 of the 280 findings raised after readiness. Reviews also found what audits had passed, because a review builds adversarial inputs, which is the value this loop automates and the reason it needs explicit convergence rules. The review findings that drove those rounds came from a frontier-model review; the new agents inherit the orchestrator's model like the task family's agents.

The gate is `plugins/ai_dev/skills/git_review/SKILL.md`. Its report sorts findings under "What is critical", "Bugs it may introduce", and "What should be fixed though it is not a clear bug", labels each `verified` or `inferred` and marks the non-blocking ones, and keeps "Decisions the implementer must make before fixing" in a section of its own. On a delta re-review its `<tags>` rule tags every prior finding closed, open, open and not acknowledged, settled by a decision, or regressed, and tags a defect first seen in the delta `new`. When this loop runs `git_review` as the gate, the Approach's `auto_gate_git` contract keeps that skill's review criteria, headings, labels, and `<tags>` as written and forbids its mutation paths, so only `auto_fixer_git` edits the working tree.

The shape to mirror is `plugins/ai_dev/skills/task_auto_check/SKILL.md`: `<single_gate>`, `<relay>`, `<verification_standard>`, `<audit_delta>`, `<concurrent_modification_guard>`, `<agent_failure_policy>`, and `<loop_bounds>`, with its agents under `plugins/ai_dev/agents/` and the doctrine in `wiki/concepts/agent-delegated-automation.md`.

The boundary with [the autonomous implement loop](task-family_autonomous-implement-loop.md): its `task_auto_implement` runs implement, audit, re-implement on findings, and finish, and its audit answers whether the task was built. `git_auto_review` answers whether the change is correct and mergeable. It runs after a clean audit, or on any change the user names with no task at all, and neither loop re-runs the other's gate.

## Approach

1. **Write the front end** at `plugins/ai_dev/skills/git_auto_review/SKILL.md`, named `<family>_auto_<rest>` beside the manual `git_review` per the standing repo rules. It accepts only the default-branch target `git_review` already uses for uncommitted work: the staged, unstaged, and untracked changes together with local commits ahead of upstream, reported under the lane labels `working-tree lane` and `local-commits lane` taken from `collect_uncommitted` in `plugins/ai_dev/skills/git_review/scripts/collect_review_evidence.sh` (its step strings `working-tree lane:` and `local-commits lane:`), which this loop's gate verdict reuses as its `lane` vocabulary. The front end carries these sub-rules:

   - **Orient.** On start, resolve the default branch from the remote `HEAD`; when the current branch is not that default branch, decline the run there, before any gate call, with no working-tree write.
   - **Lane classification.** When `auto_gate_git` builds the structured verdict, it numbers every finding's `location` (`path:start` or `path:start-end`) 1-based inclusive on the working-tree file, the version the fixer edits, so a location, the fixer's anchor, and the Stop rule's authored-hunk parse read the same lines. Case by case:
     - A finding the report cites under a `(staged)` marker names the line `git_review`'s `<evidence_set>` passage defines as "the index line of content only the index holds". The working-tree file therefore carries no line to match, so the gate assigns every such finding `local-commits lane`, lists it as a follow-up task proposal, and gives it no fix.
     - The gate re-cites a report citation taken from `worktree_diff.txt`'s `### staged` hunk numbering, whose added lines the working-tree file still holds, by matching those lines in the working-tree file at that path and numbering `path:start` or `path:start-end` from the lines found there; when those added lines no longer appear in the working-tree file, the same fallback assigns `local-commits lane`.
     - When the staged hunk's added lines appear more than once in the working-tree file at that path, the location anchors the occurrence that sits at the cited index-world numbers there; when no occurrence sits at those numbers while more than one content match remains, the finding keeps its cited location and is listed in the report as a follow-up task proposal with no fix.
     - `worktree_diff.txt` numbers its hunk sections in two worlds: `### staged` is `git diff --cached`, whose hunk line numbers count the staged (index) content, and `### unstaged` and `### untracked` count the working-tree file; the gate assigns `working-tree lane` when the finding's path and range fall inside a hunk, matching each section in its own world — the `### unstaged` and `### untracked` hunks directly at the working-tree lines the location names, and the `### staged` hunks by finding the hunk's added lines in the working-tree file at that path, so a file staged and then edited again still classifies by content rather than by coincident numbers; every other finding gets `local-commits lane`.
   - Its `<path_resolution>` block resolves `git_review` as a same-plugin sibling skill under the skills-tree sibling form `git_review/` — the perspective [the skill-relative sibling-path task](ai-dev_harness-portability-skill-relative-sibling-paths.md) establishes — and the three agents `auto_gate_git`, `auto_fixer_git`, and `auto_verifier_git` by their published names through the harness's normal agent mechanism, using `../../agents/` relative to this skill directory when the harness exposes only file paths.
   - It takes two optional inputs: a task file path that anchors scope, and a positive integer that overrides the round cap.
2. **Write three agents** under `plugins/ai_dev/agents/`, named `auto_<role>_git`:
   - `auto_gate_git` runs `git_review` as a first review and then delta re-reviews, keeping that skill's review criteria, headings, labels, and `<tags>` verbatim, except that the run's reporting obligation stated under **State the convergence rules once** overrides `<non_findings>`, `<lint_baseline>`, and `<only_what_is_open>`, while forbidding `<fast_forward_when_clean>`, `<publishing>`, `<reviewer_side_edits>`, `<pin_commit>`'s `<scratch_worktree>`, and `<fetch_first>`, and requiring every `scripts/collect_review_evidence.sh` invocation to carry `--no-fetch`, so the gate never moves a ref, remote-tracking refs included, and never creates or removes a worktree, and the user's `HEAD` and committed history stay fixed. After round 1, the orchestrator passes `auto_gate_git` the path of the prior gate return already saved under the relay; `auto_gate_git`'s prompt explicitly directs a `<re_review>` / `<tags>` pass that takes that return as the prior findings set and the same target shape as round 1 as the review subject, without editing `git_review`; round 1 is a first review and receives no prior-return path. Its agent file carries an `<output_contract>` that pins this return shape as the sole verdict template: the `git_review` report, then a structured verdict listing every finding with id, heading, `verified` or `inferred` label, non-blocking mark, location as a greppable `path:start` or `path:start-end` form (1-based inclusive line numbers on the reviewed subject), `lane` under **Lane classification.**, `Fix:` sentence, and re-review tag, plus the decisions list. Because `git_review`'s `<finding_shape>` carries no id, the gate assigns each finding's id when it builds that verdict: consecutive positive integers in the order findings appear in the report, unique within that gate return. Cross-round identity stays with the re-review tag `git_review` already emits. It may write only the evidence-scratch files `git_review` already writes (collect scratch and `report.md`). It carries no `readonly: true`. Working-tree product edits stay with `auto_fixer_git` alone under the mutation forbids.
   - `auto_fixer_git` is the single serialized writer. For each approved finding it makes the fix in the working tree and adds or extends a reproduction, a test or a command that fails before the fix and passes after, and appends that reproduction to the run's regression ledger. It writes only the paths the finding's `Fix:` requires (anchored at that finding's location), the reproduction, and the ledger.
   - `auto_verifier_git` is read-only and refute-by-default. Its frontmatter carries `readonly: true` and `tools: Read, Grep, Glob`, matching `auto_verifier_task`. Its agent file carries two `<output_contract>` templates pinned to these field lists: triage mode returns each finding as approved or not-approved, with a reason on every not-approved finding under the convergence rules; delta mode returns every hunk of the round's diff mapped to an approved finding id or its reproduction, marking any other hunk `unmapped`.
3. **State the convergence rules once** in a `<convergence>` block of the skill:
   A finding qualifies for auto-fix — and is a qualifying finding for the **Stop rule.** and `auto_verifier_git` triage — only when it meets the **Scope anchor.**, meets the **Severity floor.**, has `lane` `working-tree lane` under **Lane classification.**, and is not held under **Decisions.** Every finding the gate lists that does not qualify is reported once, here: the run lists the finding with its `lane` and no fix, naming it a follow-up task proposal where it is a pre-existing issue or a scope extension under **Scope anchor.**, or a lane-excluded finding under **Lane classification.** This reporting obligation overrides `git_review`'s `<non_findings>`, `<lint_baseline>`, and `<only_what_is_open>` suppression rules for the run's report.
   - **Scope anchor.** A finding meets the Scope anchor when it concerns lines the change added or modified, or behaviour the change's intent covers, read from the anchoring task's Goal and Acceptance when a task file is given. A reproduction `auto_fixer_git` adds is not part of the change under review: a file reproduction lives at the path its `ledger.txt` line names, and the gate and verifier label a location as reproduction lines when its path matches a path named in `ledger.txt`, so a finding whose location sits only in reproduction lines never meets the Scope anchor, is listed in the report, and receives no fix; the reproduction's own correctness is enforced by the **Regression ledger.** restore-and-retry, not by gate qualification. A pre-existing issue and a scope extension go to the report as follow-up task proposals.
   - **Severity floor.** Findings under "What is critical" meet the Severity floor regardless of `verified` or `inferred` label. `verified` findings under "Bugs it may introduce" also meet the Severity floor. `inferred` findings under "Bugs it may introduce" and every finding under "What should be fixed though it is not a clear bug" are listed in the report.
   - **Regression ledger.** The ledger is `ledger.txt` in the run's relay directory, one reproduction command per line. A bundled script, `scripts/run_ledger.sh`, runs every line and reports each line's pass or fail, and the orchestrator runs it after every fix round. A failing line restores the round's pre-fix state and repeats the round once with the failing line named to the fixer; a second failure restores the pre-fix state and the **Stop rule.**'s second-ledger-failure condition stops the run.
   - **Decisions.** Every entry under "Decisions the implementer must make before fixing", and every finding whose fix depends on one, goes to the user and receives no fix. When a task file anchors the run, the report gives the wording to record in that task, applied through the base `task` skill's `<update>` workflow on the user's answer, with the base `<status_discipline>` rule deciding the status.
   - **Stop rule.** A round is one gate cycle, the unit the cap, the consecutive-round stop, and the authored-hunk append all count: it opens with one `auto_gate_git` call — the first review, then each delta re-review — and closes when the loop has finished that verdict's response, `auto_fixer_git`'s fix plus the **Regression ledger.** check and `<audit_delta>` each with their own one restore-and-retry, at the point the loop returns to the gate for the next round or stops; a restore-and-retry stays inside its round and never starts or counts a new one, and "fix round" and the ledger's "repeats the round once" name this same unit. The run stops when any of these conditions holds:
     - no qualifying finding remains;
     - a decision is pending;
     - a cap of 5 rounds unless overridden;
     - two consecutive rounds whose qualifying findings all sit in code the loop wrote in an earlier round;
     - a helper failure;
     - a second **Regression ledger.** failure after that rule's one restore-and-retry;
     - a second `<audit_delta>` unmapped-hunk result after its one restore-and-retry;
     - `<concurrent_modification_guard>` finds the working tree diverging from that round's pre-fix snapshot for a reason other than this run's fixer.
     After each fix round the orchestrator appends that round's authored hunks — each a path plus the line range `auto_fixer_git` changed on that path — to `authored.txt` in the run's relay directory. For the self-written stop, parse each gate finding's `location` for a path and a line or line range; a finding sits in loop-authored code when that path matches an earlier-round hunk's path and the parsed line or range intersects that hunk's range; the stop rule reads only that file.

The **Restore** procedure that every restore-and-retry in this task runs returns the working tree to that state solely from those two files, never touching committed history: reverse-apply `pre-fix.patch`, copy each file in `pre-fix.untracked.tar` back over its working-tree path, and delete the untracked files the fixer added that the copy does not contain.
