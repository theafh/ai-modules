# task_auto_check: a drift gate that halts only on broadened intent, judged against the last commit

## Goal

`auto_drift_task` returns `drift` only when the working-tree `# Title` or `## Goal` broadens what the task is for compared with the version in the last commit: it promises a deliverable, a goal, an edit surface, or a user-visible outcome that the committed title, Goal, and body do not, or it replaces the task's subject with a different one. Every other change classifies `clean`, however large the wording delta: narrowing (dropped scope, an added carve-out, a deferral to a sibling or into `**Out of scope:**`), refinement (clarification, precision, rewording, restructuring, added cross-references, a title widened to name deliverables the body already carries), bug fixes (a corrected path, command, name, or claim about current state), and resolved labeled open decisions. `task_auto_check` keeps human-routing a `drift` verdict through `<intent_drift_boundary>` and runs through on everything else. The user-visible outcome: the loop stops for a human only when unattended editing has widened what the task is for, and the ordinary shaping a task accumulates between commits no longer halts it.

## Context

The gate shipped through the archived [intent-drift detection task](task-family_intent-drift-detection.md) with a symmetric definition. The `<policy>` in `plugins/ai_dev/agents/auto_drift_task.md` reads "Return a drift finding only when the current title or Goal changes what the task is about, narrows away the original aim, or contradicts the recovered original aim", so a narrowing is drift by specification, and its `<compare_meaning>` step compares "scope boundaries", so a tightened boundary reads as a change. The gate exists to catch unattended drift, and unattended drift in an autonomous repair loop runs one way: toward scope creep. A human shaping a task narrows it, sharpens it, and corrects it, and none of that is a reason to stop a readiness loop.

The baseline compounds this. The same `<policy>` treats "the earliest committed baseline as the origin" and compares "against the full followed history, not merely the previous commit, so intent narrowed across several commits still remains detectable". That rationale exists only to catch narrowing, so it falls with the symmetric definition. It also leaves the human no way to attest a changed intent: a task broadened deliberately and committed weeks ago is compared against its first commit on every later run, so one legitimate expansion becomes a halt on every run for the rest of the task's life. In this repository a commit is the checkpoint the user owns (standing repo rules), so the version in the last commit is the human-attested intent, and the working-tree delta since then is exactly what an unattended run may have produced.

Three smaller defects ride along. The agent's `<policy>` returns `unassessable` when "the working-tree title and Goal no longer match the freeze-time inputs", so a freeze snapshot that differs from the file by whitespace, quoting, or an excerpted Goal ends the run through `<agent_failure_policy>` as well. The classification vocabulary has drifted between the two files: `<intent_drift_boundary>` in `plugins/ai_dev/skills/task_auto_check/SKILL.md` speaks of "Clean, meaning-preserving, and `low_confidence_clean` results" as though three classes existed, the agent's `<classify_result>` returns clean for meaning-preserving evolution, and the agent's `<output_contract>` enumerates `clean|drift|low_confidence_clean|unassessable`. One recorded run returned the off-contract value `meaning_preserving`, which `<agent_failure_policy>` counts as a contract violation that can end a run as a helper-failure stop. And the test harness pins the boundary only at its extreme: `intent_drift_human_route` in `tests/task_auto_check/evals/evals.json` stages a wholesale subject swap, no fixture stages a changed title or Goal that must classify `clean`, and the `s9_intent_drift_boundary` scenario in `tests/task_auto_check/script_tests/run.sh` asserts the literals "earliest committed" and "not merely the previous commit", so the harness enforces the design this task replaces.

In practice the gate fires on nearly every title or Goal change, in Cursor and OpenCode runs especially: a renamed title or a tightened Goal halts the loop with the intention check. The rule text mandates that outcome. Its trigger is worded as a change predicate, "changes what the task is about", and a title is what a task is about, so a rename satisfies it literally; the deployed OpenCode copy of the agent also carries no model or reasoning-effort fields, so the harness default decides how the rule is read. The fix therefore lands in the rule text and the baseline, and the negative fixtures below make the boundary visible instead of leaving it to the model's judgement. One interaction the new rule must survive: the base `task` skill's `<readiness_checklist>` **Title/description coverage** lens repairs an under-naming title by widening it in place, so the loop's own repair widens titles, and a broadening test that read the title alone would trip on the loop's previous run.

## Approach

Rewrite `plugins/ai_dev/agents/auto_drift_task.md` in place:

- **Agent surfaces.** Rewrite the frontmatter `description`, `<role>`, `<objective>`, and `<workflow>` to the broadening-only / last-commit rule: drop earliest-commit, full-history, meaning-preserving, recovered-origin, and freeze-time-match language; the workflow reads the working-tree title and Goal, recovers the last-commit baseline (with rename follow), compares for broadening, and classifies under exactly the four enum values. Keep the read-only and human-route posture.
- **Baseline.** Recover the committed file content from the last commit (`git show HEAD:<path>` or an equivalent) — `# Title`, `## Goal`, and body — following a staged or uncommitted rename: detect the rename with `git diff HEAD -M --name-status`, recover the prior path with `git log --follow` (the agent text names `git log --follow`), then fetch committed content with `git show` at that path, before giving up on the path. A file with no committed version returns `low_confidence_clean` as today. A title and Goal byte-identical to the committed version return `clean` at high confidence with no further reasoning. The earliest-commit walk and the full-history comparison go away.
- **Direction.** Apply the Goal's broadening-only rule in the agent text. A contradiction is drift only when it replaces the aim with a different or wider one; a caveat that carves part of the aim out is narrowing.
- **Evidence bar.** A `drift` verdict quotes, in `## Classification evidence`, the current passage that carries the added promise beside the committed passage that lacks it, and names the promise in one sentence. When no added promise can be named, the classification is `clean`. `confidence` and `drifted_fields` stay as they are.
- **Attestation.** Add an optional `attested_intent` input: the user's own statement from the run prompt that a change to the title or Goal is deliberate. A broadening the attestation covers is human-owned and returns `clean`, and the report names the attestation it relied on.
- **Working tree as authority.** Read the title and Goal from the working tree and treat the freeze-time inputs as a cross-check: a difference in whitespace, quoting, or an excerpted Goal is noted in the report and the working-tree text is judged. `unassessable` stays for a task file that cannot be read.
- **Contract.** Keep the classification enum exactly `clean|drift|low_confidence_clean|unassessable`, redefine `baseline_commit` as the commit whose version served as the baseline, and keep `history_followed` for the rename follow.

Rewrite `plugins/ai_dev/skills/task_auto_check/SKILL.md` in place: `<intent_drift_boundary>` states the broadening-only rule by citing the agent and names exactly the agent's four classifications, `<inputs>` admits the optional attestation from the run prompt, `<freeze>` passes it to the agent and names the same four classifications, and the `<output_contract>` drift bullet reports the baseline commit, the juxtaposition, and any attestation relied on. `<frozen_intent>`, the human-routing, the never-auto-repair rule, and `auto_verifier_task`'s fidelity check stay as they are: they guard the loop's own edits, while this gate covers what happened before the run.

Refresh the three descriptions of the mechanism: the `**auto_drift_task**` bullet in `plugins/ai_dev/README.md`; the sentence in `wiki/concepts/agent-delegated-automation.md` that says the drift agent catches intent that "moved away from the first" committed goal, edited through the wiki skill family; and the clause in `plugins/ai_dev/skills/task/SKILL.md` `<archive>` that ends "recover a task's committed origin", rewritten in place so rename detection still justifies `git mv` and the protected `git log --follow` walk recovers the last-commit baseline. Exact superseding sentence for that clause's final part: "Recreating the file at the archive path with a file-writing tool and then deleting the original is the superseded pattern here, because git records that as a delete plus an unrelated add, which drops rename detection and breaks the `git log --follow` walk `auto_drift_task` runs on the archived path to recover the task's last-commit baseline."

Update the tests with the change. In `tests/task_auto_check/script_tests/run.sh`, rewrite the five `s9_intent_drift_boundary` assert literals that pin the old design in place: `earliest committed` → last-commit baseline; `not merely the previous commit` → rename-follow / last-commit-only; `changes what the task is about` → broadening-only; `Clean accretion` → narrowing-as-clean; `intent-preserving clarifications` → refinement-as-clean. Keep the remaining s9 asserts that still match the new rule text. In `tests/task_auto_check/evals/`, add four fixtures on the `_common.sh` pattern (`init_proj`, `commit_proj`, then an uncommitted rewrite) with their `evals.json` entries, `grade.sh` cases, `stage.sh` registration rewritten in place (Valid eval ids header plus a case arm per new id, mirroring `intent_drift_human_route`), and the four new ids appended to `DEFAULT_IDS` in `tests/task_auto_check/evals/run.py` (every current `stage.sh` id already lives there):

- `drift_gate_narrowing_clean`: the rewrite drops one deliverable into `**Out of scope:**` and renames the title to the narrower scope; expected `clean`, the gate runs, no intention check.
- `drift_gate_refinement_clean`: the rewrite rewords the Goal, corrects a wrong path it cited, and widens the title to name a deliverable the body already carried; expected `clean`.
- `drift_gate_broadening_drift`: the rewrite adds a second deliverable on a new surface to the Goal; expected `drift` with `drifted_fields: goal`, the Goal intention check, a halt before the gate, and an unchanged body.
- `drift_gate_committed_broadening_clean`: a second commit broadens the Goal and an uncommitted refinement follows; expected `clean`, because the committed broadening is attested.

Keep `intent_drift_human_route` as the subject-replacement case and refresh its `expected_output` where it names the earliest committed Goal. Run each new fixture once with the change; a fixture that classifies against expectation sends the rule text back for tightening before the change lands.

**Out of scope:** Renaming the premise check's `drifted` staleness label in `task_check` and `auto_gate_task`; the word it shares with this gate is a reporting concern outside the freeze-time check. Any automatic repair toward the baseline; the gate detects and the human reconciles.
