# Define agent_spinner's read-only diagnostic, task, and registered role

## Goal

Three terms that steer an orchestrator's first moves get a definition the skill states once. A request to find something across many artifacts while changing nothing routes the same way on every draw. A "task" in the multi-file recipe row means a tracked item with its own acceptance list. A registered role means a role the host's own spawn surface lists, so an orchestrator probes roles through that surface and never goes looking for agent definition files on disk.

## Context

The three terms sit near the top of `plugins/ai_dev/skills/agent_spinner/SKILL.md` and in its recipe table:

- **Read-only diagnostic.** `<selector>` says "A read-only diagnostic, or a single judgement question about a mechanism not yet built, is answered inline from your own reads before any helper is spent, takes no recipe". The recipe table in the same block routes "Audit many artifacts, changing nothing" to `check-only-audit.md`. The skill never defines "read-only diagnostic", so an ask like "find the drift across these eight pages, change no file" fits both. On the identical `inline_floor` and `phase_plan_announcement` prompts, `sonnet` (2026-11-13) answered inline as a read-only diagnostic with no phase plan, no item count, and no bound, while `opus` (2026-11-14) ran the check-only-audit recipe. Neither eval asserts a recipe today: `inline_floor`'s branch checks the floor tier, the two-to-four-phase plan, the item count, the bound, the exclusions and the checking pass, and `phase_plan_announcement`'s checks the phase sequence, the five-in/three-out arithmetic, the bound and the exclusion reasons; only `attached_body_reads_recipe` checks `announcement_has 'check-only-audit\.md'` (`tests/agent_spinner/evals/grade.sh`).
- **Task.** The recipe row "Implement one task spanning many files" never says what a task is; only `references/recipes/multi-file-task.md`'s trigger ties it to "the task's written acceptance list". On 2026-11-14 the Cursor worker matched that recipe in seven announcements of the suite, once by writing its own `acceptance.md` to fit (`shape_matched_no_recipe`), while Claude matched no recipe on the same prompts. In the same evening's Claude run, `wide_run_plans_session_boundary` routed a hundred-page audit inline as a read-only diagnostic and planned no session boundary.
- **Registered role.** `<capability_probe>` says "A role definition on disk is evidence that the file deployed, not evidence that it can be called". That keeps disk files from proving callability, but it still names them as deployment evidence, which invites a search for them, and no sentence says where a registered role comes from. `<degradation>` says "Where the probe finds `auto_checker_spinner` or `auto_writer_spinner` callable, spawn through it". `references/run-protocol.md` P1 probes "once through each registered role the host lists". In the 2026-11-14 Claude run, the `depth_one_level` worker listed the operator's own agent directory under the home directory, read both role definitions there, and recorded role-route probe rows for roles its host could not spawn. A skill meant to work in any repository and on any host should not lead a worker to read another installation's files. The eval harness is tightening its isolation separately, in [the Claude worker scratch-home task](../tests_claude-worker-scratch-home.md); this task fixes the wording that sent the worker looking.

## Approach

1. In `<selector>`, rewrite the read-only-diagnostic sentence in place so it defines that term by what it reads: one artifact or one mechanism, answered from the orchestrator's own reads. Widen the per-artifact fan-out trigger in place at both of its sites — the `<selector>` bullet `An enumerated imperative over many artifacts: per-artifact fan-out.` and `<per_artifact_fan_out>`'s `**Trigger** an enumerated imperative over many artifacts, each judged on its own.` — to read `many artifacts each judged on its own, enumerated by the ask or by the resolver and in any mood, read-only included`, so a read-only ask over many artifacts whose findings are per-artifact matches that shape and reaches the "Audit many artifacts, changing nothing" row whatever verb it uses. Write a read-only ask that combines rows as an explicit exception to that rule: it keeps the smallest-covering-shape route `<selector>` already states. Add `check "selector defines a read-only diagnostic by what it reads" section_has_collapsed "$SKILL" selector 'one artifact or one mechanism, answered from the orchestrator'` to `tests/agent_spinner/script_tests/run.sh`, so the definition is pinned to its new wording rather than to a phrase already present. Name `references/recipes/check-only-audit.md` as an edit site: its `<trigger>` admits a read-only sweep whose artifact set the resolver enumerates even where the ask enumerates no items, and keeps the `applies only after the selector matched that shape` line the recipe check pins. Confirm `references/recipes/disputed-claim.md`'s "A disagreement the ask only asks about is a read-only diagnostic" still reads true under the bounded rule. Add `check "the announcement names check-only-audit.md" announcement_has 'check-only-audit\.md'` to the `inline_floor`, `phase_plan_announcement`, and `wide_run_plans_session_boundary` branches of `tests/agent_spinner/evals/grade.sh`, and the matching expectation line ("The announcement names check-only-audit.md.") to all three evals in `tests/agent_spinner/evals/evals.json`, so the new check is a declared expectation rather than an undeclared assertion.
2. In the recipe table row "Implement one task spanning many files" and in `references/recipes/multi-file-task.md`'s trigger, define a task as a tracked item that carries its own acceptance list, and send a per-artifact job without one to the shape that fits it with no recipe. Add `check "multi-file trigger defines a task by its own acceptance list" section_has_collapsed "$REFS/recipes/multi-file-task.md" trigger 'tracked item that carries its own acceptance list'` to `tests/agent_spinner/script_tests/run.sh`, so the definition is pinned to its new wording.
3. In `<capability_probe>` and `<degradation>`, and in `references/run-protocol.md`'s P1 probe step, define a registered role as one the host's spawn surface lists or accepts by name. Say that the probe tries each one through that surface and never searches home or configuration directories for definition files. Rewrite the "A role definition on disk is evidence that the file deployed" sentence in place so it no longer names disk files as evidence of anything the run needs. In the same change, reword `probe_definitions_no_spawn`'s expectation, `expected_output`, check label, and first grader alternative in `tests/agent_spinner/evals/` from "definitions as deployment rather than callability" to "on-disk definitions as no evidence of callability, which only the spawn surface establishes", so the eval checks the rewritten rule. The `capability_probe separates deployment from callability` check in `tests/agent_spinner/script_tests/run.sh` pins a substring of the sentence this step removes, so rewrite that check in place — relabel it for the spawn-surface rule and repoint it at the new `<capability_probe>` wording — rather than adding a second check beside it. Add `check "capability_probe forbids searching home or configuration directories for definition files" section_has_collapsed "$SKILL" capability_probe 'never (searches|reads|looks)[^.]{0,60}(home|configuration)'` to the same file beside the rewritten check.

## Acceptance

- SKILL.md `<selector>` carries the read-only-diagnostic definition beside a bounded many-artifacts routing rule: a read-only sweep whose findings are per-artifact routes to the audit row, and a read-only ask combining rows keeps the smallest-covering-shape route. The `<selector>` bullet and `<per_artifact_fan_out>`'s trigger both carry `each judged on its own, enumerated by the ask or by the resolver and in any mood, read-only included`, and `rg -n 'enumerated imperative over many artifacts' plugins/ai_dev/skills/agent_spinner/SKILL.md` finds nothing. A grep for the old undefined sentence alone finds it rewritten.
- `references/recipes/check-only-audit.md`'s `<trigger>` admits a read-only sweep over many artifacts whose findings are per-artifact even where the ask enumerates no items, because the selector's per-artifact fan-out trigger admits such an ask in any mood, and keeps the `applies only after the selector matched that shape` line the recipe check pins.
- `<capability_probe>`, `<degradation>`, and the P1 probe step define a registered role through the host's spawn surface, and a grep for "A role definition on disk is evidence" finds nothing. `tests/agent_spinner/script_tests/run.sh` carries `check "capability_probe forbids searching home or configuration directories for definition files" section_has_collapsed "$SKILL" capability_probe 'never (searches|reads|looks)[^.]{0,60}(home|configuration)'`, and `bash tests/agent_spinner/script_tests/run.sh` passes it.
- `tests/agent_spinner/script_tests/run.sh` carries one static check per definition — the selector pin named in Approach 1, the multi-file task-definition pin named in Approach 2, and the existing `capability_probe separates deployment from callability` pin rewritten in place from the retired `evidence that the file deployed, not evidence that it can be called` substring to a pin on the spawn-surface rule rather than left beside it — and `bash tests/agent_spinner/script_tests/run.sh` passes.
- The recipe row and the multi-file recipe's trigger define a task by its own acceptance list.
- `inline_floor`, `phase_plan_announcement`, `wide_run_plans_session_boundary`, `residual_selector`, `shape_matched_no_recipe`, and `probe_definitions_no_spawn` run on the default vendor, and their verdicts are recorded in `tests/agent_spinner/evals/README.md`. The `inline_floor`, `phase_plan_announcement`, and `wide_run_plans_session_boundary` branches of `tests/agent_spinner/evals/grade.sh` each carry `check "the announcement names check-only-audit.md" announcement_has 'check-only-audit\.md'`, mirroring `attached_body_reads_recipe`, and all three pass, so the first three taking the recipe path is proven rather than inferred from a pass that also holds when the run calls itself a read-only diagnostic. `residual_selector` labels its choice the smallest covering shape, `shape_matched_no_recipe` matches no recipe, and the probe eval checks the reworded rule. If any still routes the old way, the record says so and the wording gets another pass.
