# Make agent_spinner briefs carry the return contract the ledger enforces

## Goal

A helper that follows its rendered brief literally writes a return that `accept` takes, because the brief names every value and object shape `accept` checks. A reading helper that reads several committed files can carry a valid receipt for each one. When `accept` rejects a return because the brief itself left the helper unable to comply, the orchestrator re-invokes on a corrected brief rather than an identical one, so the retry can succeed. Today the brief leaves out part of the contract `accept` checks, and the skill's retry rule repeats any violation the brief caused.

## Context

Everything here lives under `plugins/ai_dev/skills/agent_spinner/`:

- **The brief token is unlabelled.** `cmd_brief` in `scripts/run_ledger.py` ends the rendered brief with a closing block that lists the return template's keys ("Return template: fenced json block with label, brief, status, verdict, ...") and then appends the bare token as its last line. `references/role-prompts.md` documents that line as "Repeat the brief token: [token].", and nothing in the rendered brief says that the return's `brief` key must repeat it or which `status` and `verdict` values `accept` allows. `validate_return` rejects a mismatch with "brief token disagrees with the roster". Across the eval suite's recorded runs, token mismatches are about a fifth of all `accept_reject` records, and in the 2026-11-14 Claude run a lighter-model triage helper put its label in `brief` and lost both of its tries (`triage_pass_routes_missed_hit`). The brief also lists the return's keys by name only, while `references/run-protocol.md` alone, which a helper never reads, gives their shapes ("`forks` is a list of objects with `issue`, two to four `options`, and `preferred`"). In the evening Claude run, both sweepers in `snapshot_search_positive_control` answered `status: "complete"` twice, the role checker in `checker_spawned_through_role` returned string-valued forks twice, and `clean_corpus` lost two rows to a `spans` list and plain-string objections; each row ended `failed` after its identical retry.
- **A reader can record only one input version.** `brief --target` takes a single path. `snapshot` writes its copies to `snapshots/<label>/<path>`, while `recorded_input_path`, which `validate_return` consults for each examined path, reads `snapshots/inputs/<label>/<path>` and two `baseline/` locations. A judge or lens reading several committed files therefore cannot carry a valid receipt for more than one of them, and the documented `snapshot` verb never satisfies the check. That conflicts with `references/checks.md` C8 ("Take a read receipt of its path and one verbatim line for every mandated input") and with `references/run-protocol.md`'s "Every reading pass reads a snapshot, a file copy under `snapshots/` made by `snapshot`". The `judge_flaws_capped` fixture reads a single candidate per judge, so it records that one input through `brief --target` and needs no multi-input support.
- **The retry rule repeats a brief-caused violation.** SKILL.md `<helper_failure>` gives "a **contract violation**, meaning a return `accept` rejects" one "identical-prompt re-invocation". When the brief caused the violation, the identical prompt reproduces it. Workers handled this three ways in the 2026-11-14 run: they applied the rule literally and lost the row, they hand-repaired the return JSON, or they re-briefed and then rebuilt the overwritten first brief by hand, because `brief` overwrites `briefs/<label>.txt` on a second call. The same block's "inline redo only after the user chooses it" also leaves open whether the one re-invocation may itself run inline at the inline floor; one run read it each way.

This task, [the terminal-states task](ai-dev_agent-spinner-ledger-terminal-states.md), and [the report-and-packet task](ai-dev_agent-spinner-report-packet-enforcement.md) all edit `run_ledger.py`, `references/run-protocol.md`, and `tests/agent_spinner/script_tests/ledger_run.sh`. Land the terminal-states task first and this one second.

## Approach

1. Rewrite `cmd_brief`'s closing block so it labels the token line "Repeat the brief token: <token>", says the return's `brief` key carries that token verbatim, lists every value `validate_return` rejects on — the `status` and `verdict` sets, the `how` set (`full`, `searched`, `unreachable`), the checklist verdict set (`pass`, `fail`), the run's `severity_ladder` read from `run.json`, and the two-to-four fork option bound — and renders the object shape of the five list keys `validate_return` inspects (`examined`, `checklist`, `findings`, `forks`, `objections`), with those sets and key lists shared between the validator and the closing block and the ladder rendered from `run.json` so the two cannot drift. `confirmations` and `gaps` stay out of the rendered template because `accept` imports them from `RECORD_LISTS` when a return carries them. Bring `references/role-prompts.md`'s `## Closing block` and its pass templates' ordered key lists into line with the rendered text, keeping `confirmations` and `gaps` in the prose that tells a pass when to use them rather than in the ordered key lists. Update `tests/agent_spinner/script_tests/ledger_run.sh`'s `token_of()` in the same step: read the token from `run.json`'s `brief_tokens` for run rows, as `tests/agent_spinner/evals/fixtures/_common.sh`'s `ledger_token` already does, and keep its `tail -1` read of `briefs/<label>.txt` for probe rows, whose `probe_brief` output still ends in the bare token.
2. Let a reading row record every mandated input by making `cmd_snapshot` write its copies to `snapshots/inputs/<label>/<path>`, the location `brief --target` already writes for a reader row and `recorded_input_path` already reads. One location then holds every recorded input, and `snapshot <label> <path>...` records several inputs for one row, while `brief --target` keeps its single path. Move the `snapshot --base` copies the same way, and update the `close` cleanup loop that removes `snapshots/` subdirectories if the move changes what it has to remove. Move the tests that pin the old path in the same edit: `tests/agent_spinner/script_tests/ledger_run.sh`'s `scenario_snapshot` compares against `snapshots/inputs/check:b/a.txt` for the changed file, the unchanged file, and the `--base` copy, and its `close empties snapshots` check keeps passing unchanged because it counts files under the whole `snapshots/` tree; `tests/agent_spinner/evals/grade.sh`'s `sweeper_briefs_name_control` greps `snapshots/inputs/sources` instead of `snapshots/sources`, which `fixtures/snapshot_search_positive_control/setup.sh` produces by running `snapshot sources docs/guide.md src/config.ini`. Document the result once in `references/run-protocol.md`'s `snapshot` section and in the reading-pass sentence quoted above.
3. Make a second `brief` call for the same label keep the first: move the earlier `briefs/<label>.txt` to `attempts/<label>.<n>.txt`, a directory beside `briefs/` under the run directory, outside that tree, and created on the first re-brief, and record the re-brief in the ledger, so a corrected re-brief is a ledger event rather than a hand reconstruction. That location keeps the shipped graders counting briefed rows: `grade.sh`'s `brief_files` finds every file under `briefs/` recursively and `writer_brief_files`/`checker_brief_files` fall back to filename-prefix matches for a label with no roster row, so an attempt file anywhere under `briefs/` would add a row to those counts.
4. Rewrite SKILL.md `<helper_failure>`'s contract-violation rule in place as the one statement of the retry policy. A rejection the brief caused, because the brief lacked or misstated what `accept` checks, earns one re-invocation on a brief corrected through `brief`, recorded as such. Every other contract violation keeps the identical-prompt re-invocation. State in the same edit that this one re-invocation carries no user gate, on the same footing as the spawn-glitch and spawn-failure re-invocations, so it may run inline at the inline floor without a user choice, distinct from the degraded inline redo after a failed re-invocation, which still waits for the user's choice. In the same pass, replace `references/run-protocol.md` P3's "A rejected return gets one identical-prompt re-invocation; a second rejection marks the row failed." with a pointer to `<helper_failure>` for the retry policy, keeping only the status value `inability` there.

## Acceptance

- A `ledger_run.sh` scenario renders a brief and checks that its closing block carries the labelled token line, names the `brief` key, lists the accepted `status` and `verdict` values, the accepted `how` set, the accepted checklist verdict set, the run's `severity_ladder`, and the two-to-four fork option bound, and states the required fields of each object in the five list keys `examined`, `checklist`, `findings`, `forks`, and `objections`; a return built only from that rendered text is accepted, including a finding whose severity is on the ladder and a fork with two options.
- The whole `ledger_run.sh` suite passes against the labelled closing block: every run-row return the harness builds through `token_of` still carries the token `run.json` records for its label, and the probe scenarios still read the bare last line.
- A `ledger_run.sh` scenario briefs one reading row over two committed files and accepts a return whose two examined paths each carry a matching receipt; with one receipt's verbatim line altered, `accept` rejects that return.
- A `ledger_run.sh` scenario runs `snapshot` for a reading row and then accepts a return whose receipt matches the snapshot copy.
- The `ledger_run.sh` suite stays green with its `scenario_snapshot` assertions reading `snapshots/inputs/check:b/` for the changed file, the unchanged file, and the `--base` copy and its `close empties snapshots` check still passing, and `grade.sh`'s `sweeper_briefs_name_control` reads the `snapshot_search_positive_control` sandbox's copies under `snapshots/inputs/sources`, so that eval still passes.
- A `ledger_run.sh` scenario calls `brief` twice for one label. The first text survives at `attempts/<label>.1.txt`, outside the `briefs/` tree, the live brief stays at `briefs/<label>.txt`, and the ledger holds a record of the re-brief; the same scenario asserts that the files selected by `find .agent_spinner/briefs -type f ! -name 'probe:*'` and by the `briefs/sweep:*.txt`, `briefs/writer:*.txt`, and `briefs/check:*.txt` globs are the same set before and after the second call, which is what `sweeper_briefs_name_control`, `writer_brief_files`, `checker_brief_files`, and `repair_brief_files` count.
- SKILL.md `<helper_failure>` is the only statement of the retry policy, carrying the brief-caused re-invocation rule and the inline-floor answer that this re-invocation carries no user gate and may run inline at the inline floor, distinct from the degraded inline redo after a failed re-invocation; `references/run-protocol.md` P3 points at it instead of restating the blanket identical-prompt retry.
