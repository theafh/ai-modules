# Add a verification-economy rule to the base task skill, consumed by implement, audit, and finish

## Goal

The task family re-runs linters, test suites, and other verifications more often than the evidence requires: a stage runs a check whose inputs have not changed since a run whose output is already in hand. Within one stage this wastes a little; across stages — and especially with slow, expensive LLM evals — it is dramatic, since an eval'd task can pay the full eval bill two or three times (implement, then audit, then a finish-time re-verify) for one unchanged artifact.

Add one canonical rule to the base `task` skill — a `<verification_economy>` section that every family component already consumes through its `<authority>` read of the base `SKILL.md`: run each linter, test suite, or named check to produce evidence about the current state of what it inspects, once per state, and re-run only when the tool or what it inspects has changed since the last run whose output is in hand. Keep running the default and make a skip the exception that must cite its grounds, so the rule trims waste without discouraging the runs the family depends on. Then point task_implement, task_audit, and task_finish — the three stages that re-run things unnecessarily today — at that rule at their point of use.

The user-visible outcome: the same verification discipline and coverage, at markedly lower cost and latency on repeated-state runs, with no stage skipping a check whose inputs actually changed.

## Context

- The unconditional re-run imperatives sit in two stages. task_implement's **Cross-check, then run the verifications the acceptance names** step says "Run every verification the task and repo name — `make lint`, the relevant bundled `lint.py`, the matching `tests/<skill>/script_tests` …"; task_audit's **Run the suite and attribute every failure** step says "Execute the verifications the task and repo name …" and its `<authority>` says "run what the task and repo name." Neither conditions the run on state having changed, so a stage re-runs a green suite it — or the prior stage — already ran on the identical tree.
- Most other family runs are already state-triggered and stay correct: the base `<update>` re-lints once "at the end" of an edit round, `<lint_after_create>` and `<archive>`'s final step lint after a write, and the `task_fix` / `task_auto_check` loops re-lint or re-gate after each repair round (inputs change each round). The new rule generalizes what these already do and must not contradict them.
- The family already carries two point instances of the same principle, which the base rule generalizes: task_auto_check's mechanical-lint path ("do **not** re-run `task_check` after applying them because lint cleanliness does not change the readiness verdict") and task_finish's **Verify before a `finished` close when needed** step's trust-the-`audited`-stamp gate ("when it is `audited`, treat the codebase-verification gate as already satisfied … when you have concrete evidence the code changed since that audit, re-verify"). task_finish's **Verify before a `finished` close when needed** step is the lifecycle-scale exemplar of the rule.
- The base skill is the consumption vector. Every sibling reads the whole base `SKILL.md` through its `<authority>` step and applies named sections, and every sibling already cites `<path_resolution>` inside `<workflows>`. A new operational rule placed beside `<path_resolution>` is consumed the same way, so the family inherits it rather than each sibling carrying a divergent copy.
- Governing guardrail: the repo `CHARTER.md` invariant that an autonomous component "keeps its audit, detection, and coverage scope intact when it optimizes for cost or speed … surfaces the tradeoff for human review rather than taking it silently." The rule stays on the right side of it because skipping a re-run on unchanged inputs surfaces every finding the skipped run would have — the prior run on the identical state already did — so it narrows no coverage, gates no check behind a shortcut, and skips no check whose inputs changed. Cite the charter as a standing repo rule; do not restate it.
- Motivating episode, as illustration only: a task_implement run in this repo re-ran the `git_commit` script suite a third time at phase end after a 25/25 pass, when only unrelated `SKILL.md` prose and the task frontmatter had changed since — nothing the script suite exercises. The general rule, not this one case, is the deliverable.
- Coordination — shared edit surface: [honor-task-dependencies](task-family_honor-task-dependencies.md) and [out-of-scope-boundary-convention](task-family_out-of-scope-boundary-convention.md) both add sections to the base `SKILL.md` and steps to task_implement, and [presentation-reframe](../task-family_presentation-reframe.md) reshapes the family docs' step spine. Place the new base section and the pointers to coexist with theirs, and anchor every pointer by the step's verbatim bold label (per the base `<markdown_policy>` soft-pointer rule), never by an ordinal step number a reframe would shift.
- Interaction: [autonomous-implement-loop](../task-family_autonomous-implement-loop.md), a future opt-in skill that runs implement → audit → finish, is the largest beneficiary of cross-stage economy and the sharpest test of the audit-independence clause — its build step runs in a separate worktree-isolated agent context, so the loop's audit holds no citable prior run from its own context and the rule requires a fresh run there. Read it before wording the cross-stage clause so the two stay consistent.

## Approach

Author the rule once in the base skill, then add point-of-use pointers to the three named stages. Keep the edit small and within the one family, per the charter's preference for small reviewable changes.

1. **Base rule.** Add a `<verification_economy>` section to the base `task` skill's `SKILL.md`, inside `<workflows>` immediately after `<path_resolution>` — the operational-preamble slot every sibling already consumes. State it positive and run-first: each linter, test suite, or named check is run to produce evidence about the current state of what it inspects, once per state rather than once per workflow step. Name the three always-sound runs — the first run in a session (a deliberate pre-edit baseline included), a re-run after any change to the tool or to anything it inspects, and a standing repo gate at its standing moment (a lint-before-commit rule fires at commit time regardless of earlier runs). Permit a skip only on citable grounds: the prior run's output is visible in the current session and neither the tool nor anything it inspects changed since — name the relied-on run, and run when either half is uncertain. Add the expensive/stochastic clause: for costly or sampling-noisy surfaces such as LLM evals and long integration runs, repetition on unchanged inputs adds cost and noise rather than assurance, so record the graded result where the project's testing conventions keep it and let a later stage accept that recorded result as evidence when it postdates every artifact under test, re-running only when it does not; note that `TESTING.md`, when present, names which surfaces count as expensive and where their results live.
2. **task_implement pointer.** In the **Cross-check, then run the verifications the acceptance names** step, qualify the run imperative to run each named verification once per the base `<verification_economy>` rule and to name the run each "done" conclusion relies on — while keeping the existing instruction to run every verification the task and repo name and to report the suite's actual state. Supersede the unconditional phrasing in place; one canonical instruction remains.
3. **task_audit pointer.** In the **Run the suite and attribute every failure** step and the `<authority>` run-line, qualify the run to be fresh wherever this session holds no citable prior run, and to accept a recorded expensive-surface result under `<verification_economy>` when it postdates every artifact under test. Preserve audit's evidence-not-prose stance and its independence by stating that a cross-session audit holds no citable prior run and therefore runs fresh. Supersede the unconditional phrasing in place.
4. **task_finish pointer.** Connect the **Verify before a `finished` close when needed** step's trust-the-`audited`-stamp gate to the base rule as its lifecycle-scale instance — a trailing clause, not a rewrite of the correct trust-the-stamp / re-verify-on-evidence logic — and state that the close-out re-lint runs once after the archive move rather than repeatedly.
5. **Consistency pass.** Confirm the new rule contradicts none of the already-correct state-triggered runs (base `<update>` re-lint-once-at-end, `<lint_after_create>`, `<archive>`'s final re-lint, the `task_fix` / `task_auto_check` re-gate-after-repair loops) and reads as the generalization the task_auto_check mechanical-lint and task_finish trust-the-stamp instances already follow.

**Out of scope:**

- Editing task_auto_check, task_check, task_select, task_fix, or the agents here — this task is scoped to the base skill plus implement, audit, and finish, and those siblings' runs are already state-triggered or already instance the rule. A later task may add pointers there for symmetry.
- The mechanical eval-runner cache backstop — a content-hash short-circuit in `tests/*/evals/run.py` with a `--force` override — which is separate, machine-local `tests/` work belonging in its own task; this task ships the prose rule only.
- Weakening any standing repo gate or lowering any coverage bar: the rule preserves every check and removes only re-runs on provably unchanged inputs.
- Deleting the existing run imperatives: they are qualified, not removed, so a model still runs by default.

## Acceptance

- **Base rule exists and is consumed.** The base `task` skill's `SKILL.md` carries a `<verification_economy>` section inside `<workflows>` adjacent to `<path_resolution>`. It states the run-once-per-state principle, the three always-sound runs (first-run/pre-edit baseline, post-change re-run, standing gate at its moment), the citable-grounds skip condition, and the expensive/stochastic recorded-result clause naming `TESTING.md`. Grep finds the section and its `TESTING.md` reference.
- **Skipping carries the burden, not running.** The section makes running the default and a skip the cited exception whose two grounds are the prior run visible in the session and inputs unchanged, with "run when either is uncertain" stated. Reading the section confirms no clause instructs skipping a check whose inputs changed or skipping a standing gate, so the rule cannot read as "avoid running."
- **task_implement points at it without losing its run duty.** The **Cross-check, then run the verifications the acceptance names** step cites `<verification_economy>` and asks the implementer to name the relied-on run, while still instructing it to run every verification the task and repo name and to report the suite's actual state. The prior unconditional phrasing is superseded by the qualified one — one canonical instruction remains, not two.
- **task_audit points at it, preserving independence and evidence.** The **Run the suite and attribute every failure** step and the `<authority>` run-line cite `<verification_economy>`: run fresh where the session holds no citable prior run, and accept a recorded expensive-surface result only when it postdates every artifact under test. The edit keeps audit's never-on-prose-alone stance and states that a cross-session audit runs fresh. Superseded phrasing is gone; one canonical instruction remains.
- **task_finish connects its trust-the-stamp gate to the rule.** The **Verify before a `finished` close when needed** step's trust-the-`audited`-stamp gate names `<verification_economy>` as its lifecycle-scale instance, added as a clause that leaves the existing trust-the-stamp and re-verify-on-evidence logic unchanged, and the close-out re-lint is stated to run once after the archive move.
- **No contradiction with existing runs.** A pass over the family confirms the rule agrees with every already-state-triggered run — base `<update>` re-lint-once-at-end, `<lint_after_create>`, `<archive>`'s final re-lint, and the `task_fix` / `task_auto_check` re-gate-after-repair loops — and reads as the generalization of the task_auto_check mechanical-lint and task_finish trust-the-stamp instances. No existing run imperative is deleted; each either already conditions on change or is the standing gate the rule exempts.
