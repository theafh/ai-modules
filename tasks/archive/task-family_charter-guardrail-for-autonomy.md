# Charter contract and cross-harness protect hook for the task family

## Goal

Give the task family the artifact half of its charter guardrail: a falsifiable root `CHARTER.md` project-identity contract — Core Purpose, DOES / DOES NOT domain boundaries, Key Invariants, Intentional Constraints — a reusable starter template for other projects, and a branch-gated protect hook that hard-blocks edits to `CHARTER.md` itself so an autonomous agent cannot quietly rewrite the contract to license its own drift. One canonical fence governs the whole task: a single shared POSIX script blocks any edit to root `CHARTER.md` unless a human is on a `guardrail/charter-*` branch, and it fires genuinely live on both Anthropic Claude and OpenAI Codex today. That hard block is the one guard reading-and-respecting the document cannot provide; how skills and agents actually consult the charter and validate their proposed work against it is the consumption half, owned by the standing-doc framework. The guardrail is coupled to autonomy and fully opt-in: with no `CHARTER.md` present the hook is inert and the task family behaves exactly as it does today.

## Context

By the filing rule that task-system material lives in `tasks/` while project-wide material lives in a root `UPPERCASE.md` doc (see [standing-doc framework](task-family_optional-standing-doc-conventions.md)), the charter is project identity beyond the task system, so it lives at repo root as `CHARTER.md`, a peer of the standing repo rules — not under `tasks/`, which the agents must be free to write. The base `task` skill already treats standing project instructions as a substrate that tasks cite rather than copy, and `CHARTER.md` is exactly such a standing doc.

This task ships only the charter's artifact and its tamper-protection. The consumption — how `task_check`, `auto_gate_task`, and the autonomous writing agents validate their proposed work against the charter and stop on a violation — is the standing-doc framework's unified, presence-gated doc-consumption model, not a bespoke validator here. That split is deliberate: charter validation is an agent reading the contract and refusing to violate it, the same mechanism by which it applies any standing rule, so the only thing this task adds beyond the document is the canonical fence the Goal names — the protect hook.

Both target harnesses expose a real blocking pre-edit hook, so the fence is live on each (harness_portability requires verifying provider behavior against official docs before encoding it):

- Claude Code auto-discovers a plugin-root `hooks/hooks.json` with no `plugin.json` entry, runs `PreToolUse` matched on `Edit|Write`, and delivers the edited path at `tool_input.file_path` (code.claude.com/docs/en/hooks, /plugins-reference).
- Codex has a real blocking hooks system whose `PreToolUse` can deny a tool call before it runs; for file edits the tool is `apply_patch` (matcher `apply_patch`, `Edit`, or `Write`; hook input always reports `tool_name` `apply_patch`) and the edited content/path arrives via `tool_input.command`, not `tool_input.file_path` (developers.openai.com/codex/hooks).
- Both harnesses honor exit code 2 with the reason on stderr as a block signal, so that is the portable common denominator a single script can use; Codex additionally accepts a stdout `permissionDecision` `deny` and Claude a stdout `hookSpecificOutput.permissionDecision` `deny`, but exit 2 + stderr is the one path both share.

Codex current documentation makes the wiring two-layer rather than dormant: trusted plugin-bundled hooks load from a plugin-root `hooks/hooks.json` by default or from the `.codex-plugin/plugin.json` `hooks` path when present, and config-layer hooks still load from `~/.codex/hooks.json`, `<repo>/.codex/hooks.json`, or `[hooks]` in `config.toml`. The live Codex path for this repo therefore uses both surfaces: the plugin manifest path covers sessions that install, enable, and trust the plugin hook, while config-layer `hooks.json` covers immediate repo-local activation and deployed global/project activation. A config-layer hook receives no plugin-root environment variable and runs with the session cwd as its working directory (also the stdin `cwd` field), so its command must resolve the shared script by an explicit path — repo-relative for the committed `<repo>/.codex/hooks.json`, deploy-resolved absolute for the installed `hooks.json`. A plugin-bundled hook gets plugin-root environment variables; Codex sets `PLUGIN_ROOT` and also `CLAUDE_PLUGIN_ROOT` for compatibility, so the shared plugin hook config can reference `${CLAUDE_PLUGIN_ROOT}` alongside Claude.

The repo and deployment facts that the wiring reuses: `deployment.sh` derives the `hook` artifact type from a `hooks/` directory; the `claude` arm splits its hooks dir on `PROJECT_DIR` (`<repo>/.claude/hooks` for a project deploy versus `${app_dir}/hooks` for a global deploy); `merge_json_key` with a `hooks_dir` argument rewrites command paths that literally begin with `./hooks/` to absolute (the `walk(... startswith("./hooks/") ...)` block), leaving any non-`./hooks/` command untouched; `CODEX_DIR` is already defined as `~/.codex` (global) or `<repo>/.codex` (project); and `deployment.conf`'s `#codex` section disallows only `*legacy*`, so a non-legacy Codex hook source under `plugins/ai_dev/hooks/` deploys through the script. The current `codex` case in the `hook` artifact branch falls through to the `*)` "Hook deployment not implemented" skip.

## Approach

Create this repo's real, activating project contract at root path `CHARTER.md`, populated for `ai-modules` rather than left as a placeholder, with the falsifiable structure: Core Purpose, DOES / DOES NOT domain boundaries, Key Invariants, Intentional Constraints. Ship an inert reusable starter at `plugins/ai_dev/hooks/CHARTER.template.md` carrying the same structure for other projects to copy or adapt; the template never activates anything by itself.

Write one shared POSIX hook script at `plugins/ai_dev/hooks/charter_guardrail.sh`, `chmod +x`, that both harnesses invoke. Its portable behaviour: read the single hook JSON object from stdin; feature-detect the edited path by taking `tool_input.file_path` when present (Claude `Edit`/`Write`) and otherwise parsing the target path out of `tool_input.command` (Codex `apply_patch`); resolve the target repo root from the stdin `cwd` field; treat the edit as a charter mutation only when the resolved path is the repo-root `CHARTER.md`; and, for such a mutation, allow it when the current branch matches `guardrail/charter-*` and otherwise block via exit code 2 with the reason on stderr — the common denominator both harnesses honor. When no `CHARTER.md` is present the script resolves no charter mutation and exits 0, keeping the hook inert. Frame the script around reading-and-respecting the contract branch: the human-only `guardrail/charter-*` branch is where the contract itself changes under review, and the hook permits exactly that path while fencing every other.

Wire Claude through plugin-root auto-discovery: add `plugins/ai_dev/hooks/hooks.json` defining a `PreToolUse` hook with matcher `Edit|Write` whose command invokes `${CLAUDE_PLUGIN_ROOT}/hooks/charter_guardrail.sh`, and add no `hooks` key to `.claude-plugin/plugin.json` (auto-discovery needs none). Leave the legacy `hooks/claude-code-hooks*.json` symlink-deployment config and `deployment.conf`'s Claude `disallow:**` rule frozen and unchanged — Claude is served via the native plugin marketplace, so the Claude branch in `deployment.sh` (which merges into `settings.json`) is not used by this task.

Wire Codex live by combining two delivery paths plus a forward-compat manifest key, all pointing at the same shared script. These two delivery artifacts are distinct files because their command forms differ: the committed config carries a repo-relative command that resolves from the session cwd, while the deploy source carries a `./hooks/`-prefixed command so the existing rewrite can fire.

- Commit a repo-local `<repo>/.codex/hooks.json` in ai-modules that registers the same `PreToolUse`/`apply_patch` hook at the config layer, with its command resolving `charter_guardrail.sh` by a repo-relative path that works from the session cwd at the repo root. This fires for Codex sessions in this repo immediately.
- Extend the `codex` arm of the `hook` artifact branch in `deployment.sh` so deploying ai_dev installs the hook through `CODEX_DIR`, mirroring the `claude` arm's `PROJECT_DIR` split: copy `charter_guardrail.sh` into the Codex hooks dir and `chmod +x` it, then merge the codex-format hook config JSON into the config-layer `hooks.json` (never `settings.json`) via `merge_json_key` with the matching `hooks_dir` argument — so a project deploy writes into `<repo>/.codex/hooks.json` (`CODEX_DIR` = project) and a global deploy into `~/.codex/hooks.json` (`CODEX_DIR` = global). The shipped codex-format source must declare its command as the relative `./hooks/charter_guardrail.sh` so the `hooks_dir` rewrite converts it to the deployed absolute path; a bare or already-absolute command would silently skip the rewrite. Ship that source as a non-legacy file under `plugins/ai_dev/hooks/` so it deploys through the existing `#codex` `disallow:*legacy*` filter.
- Add a `hooks` key to `.codex-plugin/plugin.json` pointing at the in-plugin hook path. Document in the shipped prose that Codex plugin-bundled hooks load after the user reviews and trusts the current hook definition, while the config-layer paths remain the immediate repo-local and deploy-time activation path for sessions that have not enabled or trusted the plugin hook.

Non-goals: a separate `task_charter` validation skill or a wired-in validation step — the standing-doc framework owns consumption, with `task_check`, `auto_gate_task`, and the autonomous writing agents reading and respecting the contract; any charter requirement on the manual chain or on a project that has no `CHARTER.md`; and any change to the frozen legacy Claude hook config or the Claude `disallow:**` rule. The `hooks`-key edit touches both `plugin.json` files, so the commit will bump ai_dev plugin meta in lockstep per the repo's versioning rule — handled at commit time, not a step here.

## Acceptance

- This repo has a real root `CHARTER.md` populated as the `ai-modules` project contract, and an inert reusable template ships at `plugins/ai_dev/hooks/CHARTER.template.md`; both carry falsifiable Core Purpose, DOES / DOES NOT, Key Invariants, and Intentional Constraints sections.
- A single executable shared script exists at `plugins/ai_dev/hooks/charter_guardrail.sh`; piping a Claude-shaped stdin JSON (`tool_input.file_path` = repo-root `CHARTER.md`, `cwd` = repo root) and a Codex-shaped stdin JSON (`apply_patch` with the same target encoded in `tool_input.command`) each exits 2 with a reason on stderr on a normal branch and exits 0 on a `guardrail/charter-*` branch, proving one script blocks both harnesses via the common-denominator signal.
- A `plugins/ai_dev/hooks/hooks.json` `PreToolUse` `Edit|Write` hook invoking `${CLAUDE_PLUGIN_ROOT}/hooks/charter_guardrail.sh` now exists.
- A regression check confirms no `hooks` key was added to `.claude-plugin/plugin.json`, and the legacy `hooks/claude-code-hooks*.json` config and `deployment.conf`'s Claude `disallow:**` rule are unchanged from before this task.
- A committed `<repo>/.codex/hooks.json` parses as valid JSON and registers a `PreToolUse` hook matching `apply_patch` whose `command` resolves `charter_guardrail.sh` by a repo-relative path (verified by reading or `jq`-querying the file); the block/allow flip itself is proven by the direct script invocation above.
- The `codex` arm of the `hook` artifact branch in `deployment.sh` installs the hook through `CODEX_DIR` with the same `PROJECT_DIR` split as the `claude` arm — copying `charter_guardrail.sh` into the Codex hooks dir with `chmod +x` and merging the codex-format hook config into the config-layer `hooks.json` (`<repo>/.codex/hooks.json` for a project deploy, `~/.codex/hooks.json` for a global deploy) via `merge_json_key`'s `hooks_dir` rewrite — and supersedes the prior fall-through to the `*)` "Hook deployment not implemented" skip. The shipped codex-format source declares its command as `./hooks/charter_guardrail.sh`, and a deploy dry-run targeting codex reports the copy and the merge with the command resolved to the deployed absolute path instead of the skip.
- `.codex-plugin/plugin.json` carries a `hooks` key pointing at the in-plugin hook path, and the shipped prose documents current Codex behavior: plugin-bundled hooks load after hook trust review, while config-layer `.codex/hooks.json` / deployed `hooks.json` remains the immediate repo-local and global/project activation path.
- With no `CHARTER.md` present, the script resolves no charter mutation and a staged `Edit`/`Write` anywhere exits 0 through every wired harness path, and a separate check confirms the manual create/check/implement chain gains no new requirement and emits no error.
- A check confirms no `task_charter` skill was created.
