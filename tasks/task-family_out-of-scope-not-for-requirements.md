# Clarify the Out-of-scope rule: exclusions are work the task does not do, never in-scope requirements and never rule waivers

## Goal

The base `task` skill's **Declare exclusions as an Out of scope boundary** rule reads as a self-contained block that states what the `**Out of scope:**` block records, the two tests that separate an exclusion from a requirement and from a rule waiver, and the three cases an author never writes there — so an in-scope requirement, a bare "this is not excluded" note, and an entry exempting the task's own work from a standing rule each stop landing in the block. The readiness checklist gains the two matching findings, so `task_check` catches a miscategorized requirement and a rule-waiving exclusion when either slips past authoring. Both rule and findings stay authored once in the base skill, so every family surface that reads it — authoring, checking, auto-repair, implementation, audit — inherits them.

## Context

The rule exists today in [SKILL.md](../plugins/ai_dev/skills/task/SKILL.md) as **Declare exclusions as an Out of scope boundary**, shipped via [task-family_out-of-scope-boundary-convention.md](archive/task-family_out-of-scope-boundary-convention.md). It defines the two entry kinds well — a **rejection** (work the task never does) and a **deferral** (work owned by a named sibling) — but it states only what the block *is*, never what it is *not for*, so nothing steers an author away from filing an in-scope item there.

That gap produced a concrete slip while shaping a task: a runtime guardrail the task actively builds — "the agent never fabricates a value; it never silently resolves a conflict" — was written into the `**Out of scope:**` block, when a guardrail the task delivers is an in-scope requirement that belongs in Goal, Approach, or Acceptance. A follow-up "fix" then added a meta line noting the guardrail "is not an exclusion", which is itself noise: a block for work-not-done never explains what is not excluded. Both slips trace to the rule omitting its not-for side and a distinguishing test. The episode is the illustration; the deliverable is the general rule.

The same omission leaves a second, sharper hole: nothing stops an exclusion from waiving a rule rather than narrowing work. The rule mentions standing authority only in the supporting direction — a rejection may cite the standing repo rule or `CHARTER.md` boundary "that motivates it" — so rule-motivates-exclusion is covered while exclusion-waives-rule is unaddressed. The block is executable rather than decorative: [task_implement](../plugins/ai_dev/skills/task_implement/SKILL.md) builds everything in scope while "skipping everything the task marks out of scope", and [task_audit](../plugins/ai_dev/skills/task_audit/SKILL.md) audits against the contract that block belongs to, so an entry reading "out of scope: the repo's lint gate for this change" is honoured by the builder and then ratified by the auditor. The readiness lenses that would otherwise catch it are suppressed by the same entry: **Acceptance coverage** measures the proof set against the promise set the body makes, and an exclusion removes the promise, while **Contradictions** flags an Acceptance item that proves excluded work — so deleting the waived gate reads as conformance repair rather than as the hole it opens. Existing coverage falls short of the case: **Charter check** sees `CHARTER.md` alone while most project rules live in the harness-loaded standing-instruction baseline, and **Restated standing rules** catches the mirror case of a rule copied into a body but not a rule opted out of.

The readiness checklist's **Contradictions** lens already guards the boundary in one direction — it flags a Goal, Approach, or Acceptance element that delivers work the block excludes, and an entry ambiguous between rejection and deferral. It does not yet flag the reverse: an in-scope requirement miscategorized as an exclusion, or a meta not-an-exclusion note.

Standing repo rules this task follows: author the refined rule in positive, action-oriented language per `ai_instruction_writing`; keep both the rule and its findings in the base skill so the front-end siblings inherit them through their `<authority>` reference rather than each carrying a copy.

Edit surface: [SKILL.md](../plugins/ai_dev/skills/task/SKILL.md) — the **Declare exclusions as an Out of scope boundary** rule, the readiness checklist **Contradictions** lens, and the checklist's **Restated standing rules** item, whose neighbourhood the waiver finding joins. Check that the nearby "Negatives earn their place … a guardrail" sentence stays consistent, since a guardrail earns its place as a positive requirement rather than as an out-of-scope entry.

## Approach

1. **Rewrite the rule in place into a self-contained block.** Lead with its purpose — the `**Out of scope:**` block records the work this task does not do — keep the rejection and deferral kinds as they stand, and add the not-for side:
   - **State the two tests that bound the block.** The requirement test: when the task does work to make a statement true, that statement is a requirement and belongs in Goal, Approach, or Acceptance; the block holds only statements of work the task does not do. The waiver test: an entry removes work from the task, never a rule from the work that remains, so the standing repo rules, guardrail-doc boundaries, and project gates governing whatever does get built keep applying untouched. An entry that tracks a carve-out its governing rule already provides stays legitimate, since it narrows work the rule itself leaves out.
   - **Name the three cases to keep out:** a requirement, guardrail, invariant, or feature behavior the task builds (state it as a positive requirement in its own section); a note asserting that something is not excluded (state the in-scope item where it belongs and leave the block to exclusions alone); and an entry exempting the task's own work from a standing repo rule, a guardrail-doc boundary, or a project gate (a rule that should not apply is a decision the user owns, so route it through **Decide or label** as a surfaced labeled decision rather than a self-granted exclusion).

   Keep the block compact and positive-voiced per `ai_instruction_writing`, and keep it in the base skill as the single family source.
2. **Pair the miscategorization enforcement in the readiness checklist.** Extend the **Contradictions** lens so an `**Out of scope:**` entry stating an in-scope requirement, guardrail, or feature behavior the task builds, and a meta note asserting that something is not excluded, are contradiction-rank findings, routed through **Decide or label** like the existing boundary findings — relocate the item to its proper section, or drop the meta note.
3. **Add the waiver finding beside its mirror in the content lens.** Give the checklist a finding for an `**Out of scope:**` entry that exempts the task's own work from a standing repo rule, a guardrail-doc boundary, or a project gate, placed next to **Restated standing rules** so the two directions of the task-versus-standing-rule relationship read together. Set its severity by the waived authority through a reference rather than a restated disposition: a waived `CHARTER.md` boundary escalates to the **Charter check** disposition already defined — surface it, leave the body unchanged, hold the task out of `ready` — while any other waived standing rule is an ordinary readiness issue routed through **Decide or label**. Keep the legitimate case clean: an entry that narrows work, including one tracking a carve-out its governing rule provides, produces no finding.

**Out of scope:**

- Migrating or re-editing existing task files onto the clarified rule — the convention converges opportunistically through update, check, and auto-repair, so this task ships the rule and its checks rather than a backlog sweep.
