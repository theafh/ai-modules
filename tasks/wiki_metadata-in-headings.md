# Stop stuffing metadata into wiki headings and bold labels

## Goal

Markdown headings and bold-prefix labels in wiki pages stay *structural*: each names the section's own subject, and where a wiki's `SCHEMA.md` declares a label vocabulary the labels match it verbatim, so readers navigate by skim and `grep`. Metadata such as date, source, session ID, audience, qualifier, mandate level, or scope tag is *semantic content* and belongs in a separate channel (frontmatter, per-claim inline link, `raw/` sidecar, audit-log entry). After this task, the `auto_shaper_wiki` agent and `SKILL.md` `<write_or_update_pages>` refuse to augment headings or labels with parenthesised metadata, and `lint.py` surfaces both Approach `heading-label` heuristics as info-level findings.

## Context

This is one of a family of **generalisable refinements** to the wiki skills + `auto_shaper_wiki` agent. The trigger was a concrete friction point surfaced while auditing a real wiki, but the rule is stated globally so it applies to every user of the wiki skills, not just the originating case.

During that audit the auto-shaper normalised eight section labels and produced strings like:

- `**What the canon says (2026-01-15 triage session):**`
- `**What the canon says (2026-01-15 design review session):**`

The user called this "overcompression beyond recognition": the label vocabulary is structural, while the parenthesised attribution is content that belongs elsewhere.

- [plugins/knowledge_management/skills/wiki/SKILL.md](../plugins/knowledge_management/skills/wiki/SKILL.md): `<write_or_update_pages>` and `<narrow_inline_checks>` severity summary.

This task is the heading-specific surface that extends the shipped rule and adds `<fix_heading_label>` under `<fix_moves>`. This task depends on that task shipping first: the `## Custom Types` section of `template_schema.md` does not exist yet, so the label-vocabulary shape has no anchor until it lands.

## Approach

1. **`plugins/knowledge_management/agents/auto_shaper_wiki.md` `<remediate>` section**: extend the shipped `<two_pass_remediation>` rule, which already names heading vocabulary and bold-prefix labels, with the heading-specific half: take the label vocabulary from the target wiki's SCHEMA where it defines one rather than inventing terms. **SCHEMA label vocabulary (stated once here):** a wiki declares a label vocabulary when its SCHEMA page-type anatomy sections name the structural labels entries must use (bold-prefix / section label strings), not merely describe section content. The shipped `template_schema.md` declarative-type anatomies describe content rather than fixing verbatim labels; the `procedure` anatomy does fix its bold labels, so treat those scaffold labels as a default vocabulary only where a wiki's SCHEMA adopts them. **Adopts (stated once here):** a wiki adopts the scaffold procedure labels when its `## Frontmatter` `type:` enum still lists `procedure` and its SCHEMA retains the `## Procedure Pages` section; a wiki whose enum omits `procedure` or whose SCHEMA drops that section declares no label vocabulary. Because `init_wiki.sh` copies `template_schema.md` verbatim, an untouched scaffolded wiki declares a vocabulary — the no-vocabulary case is a wiki that has edited its enum or schema, which is what AS-7's fixture stages. **Vocabulary binding (decided here):** a declared vocabulary binds only the labels on pages of the type whose anatomy declares it — the scaffold procedure vocabulary binds `procedure` pages — and every other page type receives metadata routing alone: its labels keep that page type's own anatomy wording and are never rewritten to the procedure vocabulary. This task reads that named-label shape as the vocabulary signal and does not invent a separate SCHEMA `## Label Vocabulary` channel. Without a declared vocabulary, leave the label wording alone and route only the displaced metadata. **`<fix_heading_label>` (stated once here):** under `<fix_moves>`, add `<fix_heading_label>` keyed to lint category `heading-label`. Parenthesised / ISO-date-suffix findings on an H2-or-deeper heading or on a bold label are remediative, so cite the "two-pass remediation" rule by that verbatim name and apply **SCHEMA label vocabulary (stated once here):**. An H1 date-suffix finding is decided review-only rather than remediative: `<fix_heading_label>` surfaces it as an info finding and leaves the title unchanged, because an H1 follows its page-type anatomy rather than a label vocabulary (a `query` page carries its question verbatim as the title, per the "Page anatomy" table in `SKILL.md` and `template_schema.md` `## Query Pages`). Length-only findings are acceptable info and may remain without remediative clearing. Each new info finding carries its heading's line number, matching every comparable per-heading check (for example `check_markdown_style`), so it is recorded with the accepted-info store's four-field form `- Accepted finding: heading-label — <path> — <line> — <message>`, where the line and the message together pin one finding out of several sharing a path.
2. **`plugins/knowledge_management/skills/wiki/SKILL.md`**: rewrite `<write_or_update_pages>` so it refuses parenthesised metadata on headings and bold-prefix labels, mirroring the agent rule without restating the family's "two-pass remediation" routing steps; rewrite `<narrow_inline_checks>` so its info-bucket summary names the new heading/label checks in lockstep with the matrix.
3. **`plugins/knowledge_management/skills/wiki/references/lint_checks.md`**: add a matrix row for the new heading/label checks and list them under the **info** severity bucket so the reference remains the structural source of truth for what `lint.py` emits.
4. **`plugins/knowledge_management/skills/wiki/scripts/lint.py`**: add info-level heuristics under category `heading-label` (both checks share that category). **Check scope (decided here):** the checks walk `iter_wiki_pages` only, matching `check_page_size`, so `SCHEMA.md`, `index.md`, and `log.md` stay outside the walk. `log.md` is append-only and `references/template_log.md` fixes its entry headings as `## [{{NOW}}] …`, so a finding there is unrepairable and would flood the log on every run; `index.md` is a generated catalog and `SCHEMA.md` is configuration rather than a page. The checks flag either of:
   - A heading line at H2 or deeper (`^#{2,6}\s`), or a bold-label line in **Label shape (stated once here):**, whose **structural text** is longer than 60 characters. **Label shape (stated once here):** a line whose whole content is one bold span forming a label — the bold content ends with `:` (`**What the canon says:**`) or the line ends with `**:` (`**What the canon says**:`). A whole-line emphasised prose sentence that is not in that shape, its bold content closing on sentence punctuation rather than `:`, is body prose rather than a label and draws no `heading-label` finding. Structural text is the visible label after stripping leading markdown heading markers (`#{2,6}` + following space) or bold wrappers (`**` … `**`) and an optional trailing `:`, not the full raw line. **H1 is exempt from the length rule**, because a page title follows its type anatomy rather than a section-label vocabulary: a `query` page carries its question verbatim as the title, required by both the "Page anatomy" table in `SKILL.md` and the `## Query Pages` section of `template_schema.md`, so a correctly written query title routinely runs past 60 characters and the rule would flag it. Length is also not what catches the labels in Context (those run ~52 characters of structural text); the date-suffix rule is, which is why the length rule can narrow without weakening the task.
   - A heading at any level, or a bold-label line in **Label shape (stated once here):**, carrying a parenthesised ISO-date suffix matching the regex `\([0-9]{4}-[0-9]{2}-[0-9]{2}.*?\)`. The check covers H1 as well, but an H1 hit takes the review-only disposition from step 1: the linter reports it and `<fix_heading_label>` performs no rewrite of the title. This is the lint half only: ISO-date-parenthetical detection, not a general parenthesised-metadata detector; broader refusal stays in the agent and `<write_or_update_pages>`.

   Surface both checks as `info`-level, not blocking. The script exits 0 when only info findings remain, so the wider workflow can land an edit that contains a violation while warning the author.
5. **Harness placement**: stage `lint.py` proofs under `tests/wiki/layer1` as new `l*_lint_*` scenarios driven by `layer1/run.sh`. Stage the two `wiki_fix` / `auto_shaper_wiki` behavioural fixtures as Layer-2 scenarios **AS-6** (SCHEMA declares a label vocabulary) and **AS-7** (SCHEMA declares none): register each in `tests/wiki/layer2/evals.json` and add matching `stage_AS-6` / `stage_AS-7` blocks in `tests/wiki/layer2/setup_scenarios.sh` following the existing AS-* registration pattern, so `tests/wiki/run_all.sh --layer2` exercises both new scenarios.

## Acceptance

- The agent `<remediate>` text and `SKILL.md` `<write_or_update_pages>` refuse parenthesised metadata on headings and bold-prefix labels; the agent's `<fix_moves>` carries `<fix_heading_label>` for category `heading-label` with dispositions per Approach **`<fix_heading_label>` (stated once here):**; the agent's heading-normalisation text extends the shipped `<two_pass_remediation>` rule rather than restating its routing steps. `lint.py` implements the Approach heuristics (H2+/bold-label length on structural text; ISO-date parenthetical) under category `heading-label`. Full refusal stays in agent/`<write_or_update_pages>`; the lint half covers both heuristics, with the ISO-date check as the parenthesised-metadata proxy.
- `references/lint_checks.md` carries a matrix row for the new checks (category `heading-label`) and names them under the info severity bucket; `SKILL.md` `<narrow_inline_checks>` names the same checks in its info summary (prior passages that omit them are superseded).
- Layer-1 (`l*_lint_*`): a fixture `query` page whose verbatim-question H1 exceeds 60 characters of structural text draws no `heading-label` length finding, while an H2 on the same page whose structural text exceeds 60 characters does (info `heading-label`).
- Layer-1 (`l*_lint_*`): a bold-label line whose structural text is longer than 60 characters draws an info `heading-label` length finding.
- Layer-1 (`l*_lint_*`): a `log.md` carrying `## [YYYY-MM-DD] …` entry headings whose structural text exceeds 60 characters draws no `heading-label` finding, proving both heuristics walk `iter_wiki_pages` only.
- Layer-1 (`l*_lint_*`): an H1, an H2-or-deeper heading, and a bold-label line each carrying a parenthesised ISO-date suffix (`(YYYY-MM-DD…)`) draw the info `heading-label` date-suffix finding.
- Layer-1 (`a*` agent-contract): the new `a4_heading_label_h1_review_only` check, added to `tests/wiki/layer1/agent_contract.py` and registered in `tests/wiki/layer1/run.sh` beside `a1`–`a3`, requires the agent's `<fix_heading_label>` block to carry the H1 review-only disposition and to state no rewrite of an H1, so the disposition the Approach decides is pinned on the prompt surface the `l*` scenarios cannot observe.
- Layer-1 (`l*_lint_*`): a whole-line emphasised prose sentence whose bold content closes on sentence punctuation rather than `:` (such as `**Two variables circulate that nothing authoritative supports.**`) draws no `heading-label` finding from either heuristic, including when it carries a parenthesised ISO-date suffix.
- Layer-1 (`l*_lint_*`): a wiki whose only findings are those info `heading-label` hits exits 0.
- Layer-1 (`l*_lint_*`): an info `heading-label` finding, reported with its heading's line number, is accepted by an `- Accepted finding: heading-label — <path> — <line> — <message>` bullet, proving the new category fits the accepted-info store.
- Layer-2 **AS-6** (registered in `evals.json` + `setup_scenarios.sh`): fixture wiki staging at least one `procedure` page and at least one page of another type, each with mixed-source entries carrying parenthesised attribution suffixes, and a SCHEMA that declares a label vocabulary per Approach **SCHEMA label vocabulary (stated once here):** → after `wiki_fix`:
  - On the staged `procedure` pages, labels match the SCHEMA vocabulary verbatim (no parenthetical attribution), and the staged non-procedure page keeps its own anatomy's labels while its parenthesised attribution is routed away.
  - Displaced metadata appears in `sources:` or a `raw/` sidecar.
  - The audit report names the routing as part of the per-file change list.
  - Remediative clearing of parenthesised attribution used `<fix_heading_label>` per Approach **`<fix_heading_label>` (stated once here):**; length-only `heading-label` info findings may remain.
- Layer-2 **AS-7** (registered in `evals.json` + `setup_scenarios.sh`): fixture wiki whose SCHEMA declares no label vocabulary per Approach **Adopts (stated once here):** — its `## Frontmatter` `type:` enum omits `procedure` and its SCHEMA carries no `## Procedure Pages` section — and whose existing labels already match the page-type anatomy → after `wiki_fix`, label wording is left alone aside from routing displaced metadata (no invented vocabulary) and anatomy-driven section renames, which `<fix_section_order_or_gaps>` may perform.
- `tests/wiki/layer1/run.sh` covers the new `l*_lint_*` scenarios; `tests/wiki/run_all.sh --layer2` exercises AS-6 and AS-7, and each scenario reaches the all-passes result across the top-level `passes` denominator in `tests/wiki/layer2/evals.json` (the count `tests/wiki/README.md` says the runner takes, running those passes sequentially with a restage between them), with the graded run recorded under `tests/wiki/layer2/workspace/run-<ts>/`. When a scenario misses that bar, the report records the measured rate and the diverging assertions and hands the disposition to the user.
