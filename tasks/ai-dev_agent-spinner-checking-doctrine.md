# Rewrite how agent_spinner checks helper work: five SKILL.md blocks, checks.md, edit-mechanics.md, the role prompts, and evals

## Goal

agent_spinner is the skill an orchestrating agent, the orchestrator, follows when it runs helper agents. Five blocks of its `SKILL.md` say how the orchestrator checks helper work. `<shapes>` defines the six standard ways to arrange helpers, `<prompt_assembly>` says how each helper's prompt is built, and `<checking>` says how a checker tests a result. `<confirmation_provenance>` says how to label the way a finding survived, and `<remediation>` says how failed items get repaired. These blocks predate the run ledger, the program `scripts/run_ledger.py` that a prerequisite task bundles into the skill. The ledger keeps a run's records on disk and refuses to close a run while anything is unaccounted for. The owner has also approved three changes to the checking rules, which Context lists.

After this task, the orchestrator checks every write that lands in the tree, whoever made it. It builds each checker from the artifact's own acceptance contract, the list of conditions the artifact must meet. It keeps weak claims conditional, meaning claims backed only by documentation, a placeholder, or inference. It repairs failed items once, re-checks each repair once, and labels how every finding survived. The five blocks read as the target text below and cite the run ledger.

Three reference files carry the procedure behind those rules. A new `references/checks.md` holds ten numbered checks, C1 to C10. A new `references/edit-mechanics.md` holds the kind notes, which decide how each class of text may change. A rewritten `references/role-prompts.md` holds every template the shapes name, and each template ends in the ledger's return contract, the fixed format every helper return follows. New behavioural evals prove each checking rule on a staged fixture, and three existing evals change to follow the rules that changed.

## Approach

### SKILL.md

Rewrite the five blocks in place to this target text:

```markdown
<shapes>
Each shape's skeleton and return are templates in `references/role-prompts.md`.

<per_artifact_fan_out>
**Trigger** an enumerated imperative over many artifacts, each judged on its own. **Width** one helper per ledger row, one path per row. **Prompt skeleton** the producing template with the item's kind note. **Return** the producing return.
</per_artifact_fan_out>

<lens_panel>
**Trigger** one corpus that needs several angles. **Width** three to five named lenses over the identical corpus. **Prompt skeleton** the lens template. **Return** the lens return.
</lens_panel>

<paired_refute_check>
**Trigger** every write that lands, whoever wrote it, you included. **Width** one check per written file against the recorded baseline: gates clear pointer-only hunks, and one checker reads each file whose diff changes a claim. **Prompt skeleton** the checking template with its two standing lines. **Return** the checking return.
</paired_refute_check>

<judge_panel>
**Trigger** a closed comparison among candidates that already exist. **Width** one judge per criterion over the identical candidate set. **Prompt skeleton** the judge template, one criterion on a defined scale. **Return** the judge return, with at most three cited fatal flaws.
</judge_panel>

<completeness_critic>
**Trigger** a finished body that needs a what-is-missing read, and every check scoped to raised findings or changed files. **Width** one critic per body, paired with one surplus read. **Prompt skeleton** the critic template. **Return** the critic return, with gap units as full briefs.
</completeness_critic>

<single_writer_validator>
**Trigger** a tree of writes that share a link graph or an index. **Width** exactly one, alone, after every writer and checker has returned. **Prompt skeleton** the validator template, with a grant naming its paths. **Return** the validator return, with repairs proposed rather than applied. On an upstream shortfall it reports the gap and writes nothing.
</single_writer_validator>
</shapes>

<prompt_assembly>
Render every brief with `brief` from files in the run directory: the invariant preamble, the phase's access block, the item brief, its kind note from `references/edit-mechanics.md`, the hashed intent, and the paths of upstream returns to read in full. The preamble holds the hard rules, the vocabulary, the severity ladder, and settled facts. Settle only a fact measured against the primary system, or read in finished content of the artifact the claim is about, and tag each settled fact with its provenance class. A fact from documentation, a wiki, another project's guide, a placeholder, a to-do note, or a later phase stays conditional. It goes in the unverified-premises block, checking passes test it, and a deliverable states it with the probe that would settle it. A producer and its checker include the same rules file byte for byte, and a writer applies only text its checker saw. Scripted replacement touches pointers only, and every claim, quotation, and hard-wrapped sentence changes through a writer that edits whole sentences.

Write every role contract as text the pass reads inside its own turn. Open with its first concrete action, state each prohibition as something the pass does, and restate a load-bearing prohibition at the point of use. A role body can arrive inside the user turn with no authority over the conversation around it.
</prompt_assembly>

<checking>
Refute by default, cite to clear. The checker reads the producer's return, the governing contract, and the artifact from their paths, opens from the position that the work is incomplete or wrong, and concedes only after a closed numbered checklist. Name the cost that sets that default, so the checker weighs it. Build the checklist from the artifact's acceptance contract, one line per item, testing the required form present and the old form absent. Keep expected verdicts, preferences, and prior-round digests out of the brief. When the claim is your own, one pass derives it blind from the question and the sources first.

Each atomic finding carries a verdict, a confidence, a verbatim quote, an anchored path, and a severity, from the sets `references/checks.md` defines. A clean line cites its settling span, and an uncited or self-cited clear routes back once. A check clears only claims of its own type, and a probe fires on a known positive before its empty result counts. A read receipt is a claim that `accept` checks against the input version the row recorded. The checker changes nothing, uses the read-only operations its brief names, and stays off the shell where a read-only mode gates commands behind approval. Narrowed wording propagates. Every reviewing pass reports what it examined and cleared, and an empty finding list is a valid outcome.
</checking>

<confirmation_provenance>
Record how a finding survived. One a pass was shown and did not refute is **recall-confirmed**, and one a pass surfaced unprompted is **independently surfaced**. The ledger tags each confirmation recall-confirmed when the checker's brief relayed that record, and independently surfaced otherwise. A recall-confirmed finding carries less weight, and a decision resting only on such findings says so. Label a finding that no lens refuted after both lenses saw it "survived both lenses, recall-confirmed", and reserve "confirmed" for a finding surfaced independently or re-derived against the source.
</confirmation_provenance>

<remediation>
One round, never loop until pass. The repair list holds every item that failed verification, including each instance a confirmed class sweep found, whatever verdict word the checker used, and each enters repair once. A remediator re-derives each finding first and returns applied, refuted with its span, or routed. Re-check each repaired item once, at no lower depth than its first check. Report a pass as re-checked once, recall-limited, and unverified end to end, and report a fail as failed after repair, with no second round. Repeating a stochastic check until it passes selects its most lenient draw. Guard a follow-up fan-out on its count, so an empty list dispatches nothing and says so.
</remediation>
```

- **Budget.** Measured from opening tag through closing tag, the five target blocks hold 6,172 bytes, 121 fewer than today. `SKILL.md` stays under 25,000 bytes, measured with `wc -c` at implementation time, so run.sh's check "SKILL.md under 25000 bytes" passes.
- **What moves out.** The return fields each shape lists today move to the role-prompts templates. Today's `<checking>` sentence on re-deriving each finding before acting on it moves into `<remediation>`. The verdict set, the claim types, and the read-receipt detail move to C2 and C8.

### references/checks.md

This file holds the procedure behind the checking rules, as ten numbered checks. Write one section per check, headed `## C1. Check every landed write.` through `## C10. Tier the evidence and keep weak claims conditional.`. Each section holds a trigger where the check has one, which says when the check runs, and then numbered steps. It ends with a **Checks** line, which lists facts a reviewer can verify against the ledger's files. Cite run-protocol steps by their P label alone, never by a step number. Name ledger verbs and flags only from run-protocol.md's command reference, and name the ledger by its verbs rather than by its file. Write rules only, with no session figure, case evidence, product name, or harness path.

A few terms recur below. `init` opens a run and records the baseline, the state of the tree at the start. A row is one helper job in the ledger, such as a writer row or a check row, and the roster lists every row. A producer is the helper whose work a checker tests. A refute-by-default check starts from the position that the work is wrong and concedes only after its checklist. A gate is a deterministic command, such as a linter, that `gate` runs and records. A narrowing is any reduction in what the run checks, and the report names every narrowing. The checks hold these rules:

- **C1. Check every landed write.** Every file change that reaches the tree gets its own check. Trigger: any write lands, whether a helper's file, the orchestrator's merge or inline edit, a remediation, a filing, a split, a repoint, a regeneration, or an outbound draft under `outbound/`.
  - `diff` measures every path's net change against the baseline, untracked files included. It attributes each change to a writer row, the orchestrator, or an outside source, and `diff --add-checks` gives each changed path a check row. A diff that changes a claim gets one read-only checker, and gates cover pointer-only hunks, which change only paths, identifiers, link targets, or slugs. A set whose every hunk is a glyph-for-glyph substitution takes a sampled checker set only on the user's word.
  - The checker reads by path the producer's return, the brief or approved-edit list or acceptance list, its per-file diff under `diffs/`, and its snapshot copy. Its checklist always carries two standing lines. First, every hunk maps to a brief line or an approved-edit id, and every approved id maps to at least one hunk. Second, no hunk introduces a defect the repository's rules ban, such as a lost claim, hedge, contrast, number, link, or attribution, or a format violation.
  - An approved edit set lands as anchored replacements keyed by edit id, with a whole-file regeneration only where an edit needs one. An unmapped hunk is reverted or routed as a new issue, and the check runs once more. The orchestrator's own writes get check rows, and an append-only record gets a post-write assertion. The orchestrator never certifies its own inline work.
  - Checks: `close` refuses while a changed path lacks a check row from a pass other than its writer, a covering gate, or an unverified label with its reason.
- **C2. Build a clean checker.** A checker's brief carries nothing that could steer its verdict.
  - Aim the check at the artifact or edit that will ship. Copy the checklist verbatim from the artifact's acceptance contract, one line per item. Each line tests that the required form is present on every governed surface and that the old form is absent. Split compound findings into atomic claims, and treat a recommendation's direction as a claim.
  - Use the closed verdict set: confirmed; narrowed, with corrected wording that propagates; refuted, with its settling span, the quoted text that settles it; and right diagnosis with a different fix. Give every alternatives entry a disposition.
  - Keep out of the brief any expected verdict, preference, prior-round digest, or orchestrator-authored repair rule, so an idea of the orchestrator's enters as a labelled proposal. For the orchestrator's own claim or a pivotal number, one pass derives the answer blind from the question and the sources, and the claim stays out of the workspace until that pass returns.
  - Report a blind or isolated pass as "blind by prompt", the label for a pass kept blind by withholding text from its brief. Report it as blind only when the host's helper logs, read at a path the caller supplies, show no read outside its admitted inputs. A helper that runs the ledger breaches containment, and the same log reading catches it.
  - A trade-off gets one challenger per side under a symmetric stance. Each challenger is tested against the user's objective in the user's own words, with a status-quo cost beside each proposal. A re-gate, a repeated run of a gate, reads only its admitted inputs, with transcript and state directories off limits.
  - A verdict that read an earlier verdict counts as recall-confirmed and is re-run once in isolation. That re-run's brief names none of the earlier verdicts, and the re-run carries the blind-by-prompt label unless the logs show no read of them. The last clean draw of a repeated gate, meaning its last passing run, gets one refute pass whose clears rest on external evidence.
  - Checks: checklist lines at least match the acceptance items in number, the brief lint finds no steering phrase, every orchestrator claim has a blind pass, every return carries an alternatives list that may be explicitly empty, every alternatives entry has a disposition, and every blind or isolated pass carries its label.
- **C3. Hand off verbatim and unsteered.** Each checker reads the producer's own words.
  - Producers' returns and gate verdicts live in their files, and checkers read them in full by path. A checker brief holds no paraphrase. A routing summary may head it only when labelled as routing, with the verbatim material following. A pasted payload has a stated cap, a truncation notice, and its trimmed identifiers, and the pass re-reads load-bearing detail from the source.
  - The checker quotes the issue sentence each approval resolves and the sentence each rejection was measured against. The writer applies only bytes the checker saw, keyed by edit id. The orchestrator reads returns by P6's reading rule, which reads every record that needs judgement in full, and never cuts them by character offset.
  - Checks: every producer return appears in its checker's brief by path or verbatim, a spot diff of one proposal against the checker's input shows no loss, and the applied text equals the approved text.
- **C4. Run deterministic gates against the baseline, with positive controls.** Every gate result is a measured comparison between the baseline and the final tree. A positive control is a known positive, a planted case the gate must report, so that an empty result means something. At `init` the ledger plants one such file per file type the gates read.
  - Run every named gate on the baseline and on the final tree, and report baseline-to-final deltas per category, warnings included. For a gate, the baseline is a snapshot copy of the base commit overlaid with the baseline copies of files modified at the start. A baseline gate runs with the snapshot copy as its root. The path filter, which drops findings under the run directory, applies only outside that root. A gate that did not report the planted file at `init` keeps its `init` run as its baseline.
  - Run each command as `gate NAME -- ARGV` with an expectation: `exit0` records a silent pass as silent, `nonempty` fails on empty output, and `count` needs a counter whose positive control passed. An executable that does not resolve makes its gate unavailable, which the report names as a narrowing. Where a gate the recipe relies on is unavailable, widen checker coverage to every changed file or ask the user.
  - Every self-written count first fires on a known positive and records that it did. Patterns come from a file and are counted in Python, with no shell-quoted alternation, and shell constructs follow the shell floor harness_portability states. A comparison prints both sides' exit status and summary line, and equality stands only where both sides met their expectation.
  - For prose, count per file the modal and requirement words, hedges, numbers, links, quoted strings, negation and contrast markers, dashes, and character growth. Judge each count against the direction the rule explains, and run a wrap-seam detector. Gate exclusions mirror the writers' preserve list, the text writers must leave unchanged, and filters keep the change's own vocabulary visible. A sample states its size and supports only a claim about the sample.
  - The change-specific gates are move integrity with status and similarity, the anchor re-grep, append-only assertions, and date-only change detection. Capture hashes go to the owning family's gate (C9).
  - Checks: every gate line carries its expectation, resolved executable, exit status, and baseline and final values, every zero has a passing control, and every gate that sees the run directory carries the path filter or a narrowing.
- **C5. One repair round with one re-check.**
  - The repair list holds every item that failed verification, whatever verdict word the checker used, including each instance a confirmed class sweep found (C8). Each enters repair once. Findings bound for a writer pass a refute-by-default check first. A remediator, the helper that makes repairs, re-derives each finding and returns applied, refuted with its span, or routed. A repair pass that refutes none of many findings gets a spot re-derivation.
  - Re-check each repaired item once, at no lower depth than its first check, against a snapshot copy taken before the repair. Report a pass as re-checked once, recall-limited, and unverified end to end, and a fail as failed after repair. A second round waits for the user's word. A follow-up fan-out is guarded on its count, so it dispatches only when its list holds items.
  - Checks: the repair list equals the failed items plus the confirmed class-sweep instances, each repaired item has one re-check row at no lower depth than its first check, and at most one round runs without the user's word.
- **C6. Aim critics at the run's own conclusions.**
  - A completeness critic reads the earlier passes' coverage records and proposes a capped number of gap units, which run through find and verify. A gap unit is one missing item, written as a full brief. Every completeness critic is paired with a surplus read that names what to remove, turning restated rules into citations. A contested removal of load-bearing content goes to the user.
  - A scout is the pass that surveys the items before dispatch, and scout critics divide three ways. One refutes every item the scout called current, one reads recent commits for landed work no item accounts for, and one scans outward from the touched code.
  - Before any contract repair, a sibling-surface enumerator lists every surface that carries the same contract. A design gets a repository-grounded critic with read access and a charge list of named mechanisms, platform limits, collisions with shipped siblings, required test surfaces, and cost. Every disqualifying gap it names is re-derived.
  - Checks: every retained item maps to the brief and to an acceptance check, gap units have rows, and disqualifying gaps were re-derived.
- **C7. Set verification scope, depth, and calibration.** The run states how much it verifies, and controls show whether its verifiers can catch a false finding.
  - Before dispatch, state the verification scope, its estimate, and any narrowing, and verify every finding that drives a write. A band is a group of findings, such as one severity level. Each band left unverified gets a small random sample fixed before dispatch, and the report states that sample's refutation and re-tiering rates. Widening goes to the user with its cost.
  - Report each stage's refutation and narrowing rates. A stage over more than a handful of items that sits at 0 or 100 percent is non-discriminating. Call it that, with its information in its narrowings and surviving forms.
  - Each verifying stage carries one known-false control, a planted finding that its quoted source contradicts. A verifier that confirms the control fails, and its batch is re-verified under a different framing.
  - Checker depth is at least the producer's. Where no depth control exists, state rigour as behaviour in the brief: read each rule's full text, cite a span per line, and name the minimum reads. The roster holds requested model and effort from `dispatch` and observed values from `accept`. `close` flags every checker below its producer's depth, and the report names each flag as a narrowing and lists both values per role. Choose a checker role whose contract is review.
  - Reserve "independent" for passes that shared neither the claim nor its framing. Report replicated draws unreduced, so each run of a repeated prompt keeps its own result. Apply the survival labels `<confirmation_provenance>` states, with the tally splitting confirmations by the tags `accept` recorded.
  - Checks: rates are reported per stage, every row records requested and observed model and effort with each checker below its producer flagged, and unverified counts and the confirmation split come from the roster.
- **C8. Sweep residuals and classes, and check receipts.** These rules find what a diff-scoped check missed, and they test whether helpers read what they claim to have read.
  - After a diff-scoped check, which looks only at the changed hunks, sweep the target class across every in-scope item on the final tree, edited or not, under the writers' exclusions. The target class is the kind of text the change targets, such as an old term. Classify each residual, each instance the sweep still finds, as kept, citing its rule or class, or as missed. A confirmed finding class, or a ruling on a borderline class, triggers an enumeration of every instance of that class across the scope, each with a disposition.
  - Every mandated input returns a read receipt of its path and one verbatim line. `accept` checks each receipt against the input version its row recorded, never against the live file. That version is the baseline copy for a writer's target and the snapshot for a reader. A mismatch earns one re-invocation, and then the unit is reported unreviewed. An empty return states, criterion by criterion, what it examined and the span that cleared it.
  - A settling span quotes the text that settles the line, with its anchor. A heading or an anchor alone therefore cites no span, and its clear routes back once like an uncited one. Where the stakes justify it, an isolated second reviewer probes some clean units, and units are reported as clean with citation, clean after the probe, or unreviewed.
  - Count a path as read only where tool evidence shows a full read. Tool evidence is a full read of that path in the helper's log, at a path the caller supplies, or your own full read at the inline floor, where one context runs every pass. Where no log is reachable, the path is claimed by receipt and unverified by tool evidence, which is a narrowing. Pair receipts with the class re-sweep, which is the recall check.
  - A claim-type table states which claims each check clears:
    - A presence check clears the required form at the surfaces it searched.
    - A count with a passing control clears the count.
    - A header or structure check clears the structure.
    - A sample clears claims about the sampled items.
    - A reader comparing a diff with its source clears meaning for the hunks it read.
    - A class sweep clears a universal claim over its scope.
    - An external clear, a measurement against the primary system, clears a claim about the world outside the repository.
  - A presence, count, header, or sample check never clears a meaning or universal claim.
  - Checks: every in-scope item has a residual entry, no class grep finds an instance ruled against its class, every receipt is found in its row's recorded input version, and every path counted as read has tool evidence or appears as claimed by receipt.
- **C9. Hand stamps, completed artifacts, and markers to their owners.** A stamp is a status that a skill family's gate writes, such as a task's `ready`. A marker is a persistent record of progress, such as a wiki audit baseline. The owning gate is the step of the owning family that writes the stamp or marker.
  - Record at `init` which targets carry a stamp or marker, as the owning family reports them. A completed artifact is read-only to the run, and it goes to its audit, its close-out, or a follow-up item. Route every write to such a target to the owning gate by name, or to the user as a fork, a decision the user makes. Do so before dispatch, whatever the write changes. An artifact the run creates starts at its initial state, and no pass writes a post-gate status on it.
  - A persistent marker advances only over what the run examined. Hand each stamp, capture hash, audit baseline, and index or log entry to the owning family's gate by name. Pass that gate the paths tool evidence shows read in full (C8), and list beside them each path claimed only by receipt, marked unverified. The ledger checks only its own rows, and family file formats stay with the family.
  - Checks: every changed path recorded as stamped has a routing or fork row, whatever the write changed, and every marker hand-off counts as read only paths with tool evidence of a full read.
- **C10. Tier the evidence and keep weak claims conditional.** Every fact carries a label for where it came from.
  - Tag every fact in a brief, a deliverable, and an outbound draft with its tier. The five tiers are measured (a command run against the primary system), read (finished content of the artifact the claim is about), documented (docs, wikis, notes, other projects' guides, and declarations such as a retention setting), placeholder (to-do notes, templates, and future-phase outputs), and inferred.
  - Only measured and read facts enter the preamble as settled, and every number carries its tier. A documented, placeholder, or inferred fact goes in the unverified-premises block, the preamble's list of unconfirmed claims.   - A negative or availability claim below the read tier stays conditional with its probe, or that probe runs first through a vetted read-only script.   - A premise about how people or systems currently work carries its source and scope, and an unconfirmed one is labelled assumed. Helper-derived material in a later brief is a hypothesis the helper verifies, with a brief-corrections slot. The report lint flags an absolute claim whose backing fact sits below the read tier.

### references/edit-mechanics.md

This file holds the kind notes. A kind note is a short note that `brief` attaches to an item brief, and it tells the helper how one class of text changes. Write one section per class of text:

- **Pointer and claim classes.** Pointers are paths, identifiers, link targets, and slugs, and scripted replacement may touch them. Every other occurrence is a claim, and a claim changes only through a writer, a helper that edits whole sentences.
- **Hard-wrapped prose.** Hard-wrapped prose carries line breaks inside its paragraphs, so one sentence can span several lines. Each edit spans the whole sentence across line breaks, then the writer reflows the paragraph and re-reads it. A wrap-seam check finds sentences an edit split or joined at a wrap.
- **Verbatim text.** Quotations, archived records, and pinned commands and anchors stay byte-identical, and each is re-grepped after the run.
- **Append-only records.** After each write the record grew by exactly its entry, and the diff only adds lines.
- **Moves.** A move listing gives each moved path with its rename status and similarity, as git reports them, and an add-plus-delete pair counts as a finding.
