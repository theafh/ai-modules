# Limit a scoped `--uninstall` to the scope it names

## Goal

`deployment.sh --uninstall --global` removes only artefacts deployed into the global scope, and `deployment.sh --uninstall --project-dir DIR` removes only artefacts deployed into that project. Entries from every other scope stay deployed and stay in the deploy log. A scopeless `--uninstall`, which `make uninstall` runs, keeps removing matching entries from every scope. This task is the point-fix for uninstall: it adds a helper that derives a logged entry's scope from its deployed path and applies it to uninstall's selection.

## Context

`uninstall_logged_artifacts` in `deployment/deployment.sh` walks every line of the deploy log and selects an entry when `logged_path_matches_active_targets` accepts its target and `logged_type_matches_filter` accepts its type. Neither check looks at where the entry was deployed, so `--global` and `--project-dir` change nothing about which entries are removed. A project uninstall therefore deletes global copies as well, without a backup, because the main flow skips backups whenever `PROJECT_DIR` is set. A global uninstall likewise deletes every project's copies. On 7 October 2026, `--project-dir <empty scratch directory> --target claude --type skill --uninstall --dry-run` listed every logged global Claude skill and every Claude skill entry of a second project for removal, while the named project had no entries at all.

The log records no scope, but each deployed path implies it under the derivation rule in **Approach**. A JSON-merge entry appends its key to the settings file's path as a `[key]` suffix. The run's own target-directory variables follow its scope flag, so under `--project-dir` they point into the project and cannot place a global entry.

The scopeless form is a deliberate maintenance mode, which the explicit-scope check marks with `NO_SCOPE_UNINSTALL`. The `style_run.sh` scenario under the comment `# --- Legacy four-field path[key] still strips ---` relies on it removing an entry whose settings file lies outside every target directory.

[The `make update` task](deployment_update-from-deploy-log.md) groups every log entry by this same derived scope and reuses the helper, which is why the helper serves any logged entry rather than only the entries of the run's own scope. [Merging hook entries into shared hook files](deployment_merge-hook-entries.md) also edits `uninstall_logged_artifacts`, where it adds a `path[key]` uninstall-by-manifest step; whichever of the two tasks lands second rebases onto the other's edit of that function.

`tests/deployment/script_tests/run.sh` stages a scratch home through `HOME` and a scratch project, copies the deploy log aside and restores it on exit, and already runs project-scoped uninstalls for OpenCode, Antigravity, and Codex. Each of those runs while the log holds only that project's entries, so their assertions hold after the fix.

## Approach

Add one helper, `logged_path_scope`, to `deployment/deployment.sh` that returns the scope of any logged entry from its deployed path and target id, after stripping a `[key]` suffix from the path. Write it at the bash 3.2 floor the script already targets: represent each target's two sets as indexed arrays in the `ASSET_FOLDERS` form, and name no `declare -A` map, so the helper runs wherever the script runs. For each target, global-form roots are the roots `backup_roots` would back up for that target in global mode plus, for `vscode`, the user-settings directory that holds that target's `settings.json` key merges — the directory the OS branch places the VS Code prompts root inside, one level above the prompts root itself; `backup_roots` never covers that directory, because a merge writes one key into a file rather than copying a tree, so without the extra root every logged `settings.json[key]` entry for that target derives the empty string and outlives every scoped uninstall. That root is a forward provision: no `vscode` merge writes a `path[key]` entry today, so the log holds no such entry yet, and the two live siblings that will write one merge into that same user settings file — [the VS Code output-style task](deployment_output-style-vscode.md) through `chat.instructionsFilesLocations` and [the VS Code hook-routing task](deployment_vscode-hook-routing.md) through `chat.hookFilesLocations` — so the root derives from the prompts root's parent directory rather than from either key's name, and the sibling that lands first fixes the settings file path this provision assumes. Project-form matchers are the project-relative path suffixes the `# Target directories` block appends under `--project-dir` for that target. The table below states both sets per target id:

| target id | global-form roots | project-form suffixes |
| --- | --- | --- |
| `claude` | `${HOME_DIR}/.claude` | `.claude` |
| `cursor` | `${HOME_DIR}/.cursor` | `.cursor` |
| `codex` | `${HOME_DIR}/.codex` — the `CODEX_DIR` form | `.codex`, `.agents/skills` |
| `antigravity` | `${HOME_DIR}/.gemini` — the `ANTIGRAVITY_TREE_DIR` root | `.agents` |
| `opencode` | `${HOME_DIR}/.config/opencode` | `.opencode` |
| `vscode` | `${HOME_DIR}/.copilot`, the OS-selected prompts root, and the settings directory that holds that prompts root | `.github`, `.github/prompts` |

Return the literal `global` when the path lies under one of that target's global-form roots, the recovered project directory as an absolute path — the path prefix before the last occurrence of the matched suffix — when the path lies under `{recovered_project}/{suffix}` (or equals that directory) for any of that target's project-form suffixes, and an empty string when the path fits neither form. Both branches match with one comparison shape: a path lies under a directory when it equals that directory or begins with that directory followed by `/`, so a path equal to a global-form root derives `global` and a `$HOME`-sibling whose name extends a root's name, such as `${HOME_DIR}/.claudex` beside `${HOME_DIR}/.claude`, derives the empty string. Test the global-form roots before the project-form suffixes, so a path that matches both forms — as `--project-dir "$HOME"` produces — derives `global`. `logged_path_scope` returns status 0 on every path, its three outcomes being carried by the returned string alone and the empty string meaning "no derivable scope". When the target id has no row in the table — an unknown or retired id — treat both the global-form roots and the project-form suffixes as empty, so the path fits neither form and the helper returns the empty string at status 0. Read the table's two sets by target id, recomputing the global-form roots from `HOME_DIR` and the OS branch that selects the VS Code prompts root with the same expressions the `# Target directories` block's non-project branch uses — the target's own `${HOME_DIR}`-based root, `codex`'s global root being the `CODEX_DIR` form rather than its project-only `CODEX_SKILLS_DIR`, plus the antigravity, opencode, and VS Code special cases — rather than from the run's scope flags, rather than by reading the `*_DIR` variables the project branch reassigns, and rather than from the scope-dependent `ALL_APP_TARGETS` base-directory field. Keep that derivation inside `logged_path_scope`: the two inline `backup_roots` builders, in `clear_backups_for_active_targets` and in the main backup loop, keep their current form, no shared roots helper is extracted, and the table above is the one statement of each target's root set. Because the helper takes only the logged path and target id — and does not read scope flags, `PROJECT_DIR`, or source-prior log fields — it works on every line the log already holds, four-field and five-field alike, and the log format stays as it is.

In `uninstall_logged_artifacts`, **immediately after the existing target and type filters and ahead of the per-entry `if $DRY_RUN` reporting block**, select only entries whose derived scope is the literal `global` when `--global` is set, and only entries whose derived scope equals that project directory when `--project-dir DIR` is set, comparing by plain string equality against the already-resolved `PROJECT_DIR` value, with the helper returning the logged path's prefix unchanged, so a project deployed under a raw path such as `$(mktemp -d)` matches. Leave every unselected entry deployed and in the log, the way entries outside the target and type filters stay today. The scope-selection branch reports every entry it leaves unselected through the script's existing `skip` label as the line `out-of-scope for this uninstall: <logged path>`, leaving the entry in the deploy log; that covers the entry whose derived scope is the empty string and the derivable-but-mismatched entry alike. Without a scope flag, keep today's selection, so a scopeless uninstall still reaches every scope, empty-string derived scopes included. The scope test therefore applies to every entry the target filter leaves selected, including one whose target the repo has dropped: when no `--target` filter is set, the target-filter arm reports its `stale` label and falls through, and the scope test then applies to that entry like any other, so under a scope flag an entry whose deployed path derives no scope is reported `out-of-scope for this uninstall: <logged path>` and stays in the log, while a scopeless run keeps removing it.

Rewrite in place every uninstall description that presents the removal set as unscoped, so it states that a scope flag limits removal to that scope and that a scopeless run covers every scope. A surface that names the action or its log source without presenting a removal set keeps its wording; the two `--uninstall` Usage example comments in `deployment/deployment.sh` — the header example's `# uninstall logged artifacts only` and the `print_usage` Examples line `./deployment/deployment.sh --uninstall` — name the action alone. **Out of scope:**

- Separating, under a `--project-dir` run, a project-scoped entry whose project directory overlaps a global root from the global entries beside it, most plainly `--project-dir "$HOME"`, which writes entries at the global form's own path; no `--project-dir` run can single such an entry out, because the helper derives it as `global`, so `--global --uninstall` removes it alongside genuine global entries.

## Acceptance

Unless an item names its own fixture, each scenario runs in `run.sh` with the shared fixture's target and skill type as the `--target` and `--type` filters, after the shared fixture's singular language_humanizer skill is deployed globally into the scratch home and into two scratch projects via --only language_humanizer. `lists` and `lists only` name the paths a dry run reports on its `would-rm`, `would-strip`, and `would-restore` lines, so a path the run leaves unselected stays out of that listing whether or not the run also reports it as out-of-scope.

- `--project-dir <first project> --uninstall` removes the first project's copies and log entries, and leaves the global copies, the second project's copies, and their log entries in place.
