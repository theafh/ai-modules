# Ledger doctrine for agent_spinner: `<start_here>`, the run-state blocks, run-protocol.md, report shapes, and the ledger evals

## Goal

Today agent_spinner's `SKILL.md` tells the orchestrator to write its roster to a scratch file and to do a run's counting and joining itself. The run-ledger task ships a program, the run ledger, that keeps a run's records on disk and refuses to close a run while anything is unaccounted for. This task rewrites the skill's body so every helper run goes through that ledger, and it moves the procedure behind each rule into one reference.

After this task, a run opens through a new `<start_here>` block and keeps its state in `.agent_spinner/` through ledger verbs, the ledger's subcommands. It sends every return through `accept`, the verb that checks and imports a helper's answer. It reads the records that need judgement through `show`. Any turn that finds the run open re-enters it. The run reports from the tally block, the block of counts that `close` prints when it ends the run.

A new `references/run-protocol.md` carries the run protocol P1 to P6, the six numbered parts of the run procedure. It also carries the capability tier table, the run-directory rules, and the ledger's command reference. `references/report-shapes.md` carries the report shapes these blocks name. New behavioural evals prove each rewritten block on a staged fixture. The fixtures that stage helper returns move to the return contract, the return format `accept` requires, so they keep testing what they test once every return passes through `accept`.

## Approach

### SKILL.md

`<start_here>` is a new block that gives the orchestrator its first steps: find the ledger, resume an open run, match the ask, probe the host, open the run, and announce the plan. Insert it directly after `<role>`. Rewrite the other seven blocks in place. Each of the eight blocks then reads as this target text:

```markdown
<start_here>
Build every path to `scripts/` and `references/` from the directory of the loaded SKILL.md, and invoke the ledger by that absolute path. On a missing-file error, re-resolve the path once before treating the ledger as unavailable. The command is `python3 -B <skill dir>/scripts/run_ledger.py <verb>`. Then, in order:

1. Run the ledger's `status`. Where it reports an open run, run `attach` and continue that run from its status.
2. Match the ask's shape, then its recipe, per `<selector>`, and read a matched recipe in full. A job a governing skill owns follows `<invocation_boundary>`, and an ask answered inline stops here.
3. Run `init --probe` per `<capability_probe>`, then `init` over the validated inventory.
4. Announce the tier, the capabilities, the recipe, and the plan `<phase_plan>` specifies.
</start_here>

<run_state>
Keep the run in `.agent_spinner/` through the ledger, and query it only through the verbs `references/run-protocol.md` documents. `init` records the baseline: the commit, in-scope hashes with untracked files, and each named gate's output. Change rows only through the ledger. Derive the check set, the changed and untouched lists, and attribution from the net diff against the baseline, never from a helper's changed flag. State tool results as baseline-to-final deltas. Any turn that finds an open run, whether a completion notice, a user message, or a fresh session, runs `status`, accepts every pending return, and continues the run until a user gate opens or `close` exits 0. End a turn with the closing report after a clean `close`, or with the interim report while helpers are out or a gate is open. Where the session offers a goal tool, arm one goal per run, with the run directory in its objective and `close` exiting 0 as its completion condition. Where it offers none, re-entry through `status` and `attach` carries the run. After a stop, pause, abort, or resume, mark in-flight rows unknown, and settle them by reading the files and the diff before re-dispatching. Report the modified, untouched, and unknown rows, and reuse a return only when its brief hash matches. On a stop or pause request, run `stop` at once. Its STOP file halts new dispatch and lets running helpers finish. Before the report, run `close`, which prints the tally block the report carries verbatim and exits non-zero while any row, record, fork, or written path is open. The ledger's refusals bind only when you call `init` and `close`, so a report on a run with no clean `close` says so in its opening sentence. Where the host cannot run python3, or asks approval for each command, keep the same files by hand, perform the same checks against the roster, and report each check as unenforced.
</run_state>

<width>
Derive breadth from the ledger: one row per enumerated unit (a file, source, page, or issue-and-stance pair) written before dispatch, and one helper per row, never a round number and never a merge of rows taken to save calls. Rows for a later phase come from accepted records: `rows` creates one per finding, repair, or gap unit, so a finding-sized phase keeps its width equal to its rows. Replicate one identical prompt only for a single indivisible factual or arithmetic claim, stating the count first. A declared shape binds, and a mid-run switch is a ledger event naming the checks it drops, reported as a narrowing and put to the user when it removes a check.
</width>

<aggregation>
Merge cited findings, never count agreement. The ledger imports every return in full. Read through `show`, in full, every record that needs your judgement: forks, decide-class findings, contradictions, beyond-brief finds, incidents, and own-authority calls. Dispose of the rest by id pattern, and never read a return through slices or keyword searches. Give each record one disposition: applied, refuted with its reason, surfaced to the user, or deferred with a durable pointer. Two helpers raising the same item is shared priors, so union the proposals and check each. Join by the echoed identifier and stop the merge when one is missing. Every number the report states comes from the ledger. Cap any payload pasted downstream at a stated size, tell that pass its material may be cut and that load-bearing detail gets re-read from the source, and list every trimmed identifier.
</aggregation>

<helper_failure>
Classify a non-result before acting on it, and record the class on its ledger row.

- A **deliberate self-reported inability** is a completed result: record its reason, spend no retry, and route it to the user.
- A **spawn glitch** (a near-instant return with no tool use and only host boilerplate), a **spawn failure or mid-run death**, and a **contract violation**, meaning a return `accept` rejects, each earn one identical-prompt re-invocation.
- A helper the user aborted, or one past its bound that may have written, has its paths settled from the diff before anything is re-dispatched over them.

A helper that may write files writes its return file, and its final message is its END line. A helper whose read-only lever or brief withholds file writes ends with its return block and END line as its final message, and never writes through a shell. Relay that message verbatim to `accept --stdin`, which records the return as relayed.

Completion is an accepted return. A notice, a quiet interval, or a tree predicate is only a hint to run `status`. Wait inside the turn in bounded `accept --wait` polls until every row of the wave is terminal or past its bound. While a foreground batch blocks you, record each bound and mark a row that returned late as over its bound. A row past its bound is unreturned, earns the same single re-invocation, and then stays unreturned, distinct from a helper that found nothing. When a re-invocation fails again, mark the item failed and report it, and take a degraded path such as an inline redo only after the user chooses it. Guard every step against a dead or rejected upstream.
</helper_failure>

<reporting>
Put the verdict first, and keep three things apart. The opening sentence gives the answer, the tier, helpers dispatched against returned, and whether `close` exited 0. The body separates what the run established, what a helper found beyond its brief, and what a helper or you decided on your own authority for the user to review, with `none` under an empty part. A sentence in a report, reply, or log entry that asserts verification, independence, completion, or coverage cites its ledger row or check output and says whether it was measured, re-derived, or taken on a helper's word. Read repository state from version control at report time. Check the single claim the verdict rests on against the artifact, and report a verdict that resisted re-derivation as the helpers' finding. Re-read an earlier deliverable before conceding it lacks something, and fix a conceded false premise in every open draft. Helper return shapes stay internal.
</reporting>

<coverage_tradeoff>
Name every narrowing out loud, printed from the ledger. Every planned read, check, and step a governing skill mandates is a row before dispatch, and a row left unrun is marked skipped with its reason. Count a path as read only where tool evidence shows a full read. When the run answers inline, verifies a subset, or drops a phase, state in the same reply which checks go unrun and what would surface them. Proceed on the user's word where the narrowing removes a check the fuller shape would make. A repository's `CHARTER.md` coverage invariant is the authority this rule applies to the skill's own economy rules.
</coverage_tradeoff>

<run_economy>
Close every run with its yield: helpers dispatched against the decisions or edits they produced, the estimate beside the actual count, and per checking stage what it surfaced that the gates had not. Say plainly when a run or a stage cost more than it returned.
</run_economy>
```

### references/run-protocol.md

Write the reference as procedure for the orchestrator, in the skill's positive, action-first register. It names no product, no harness path, and no session figure, so the existing greps over the skill directory keep passing. Give it these sections:

- **Capability tier table.** Write one table, keyed by rung and by the delivery property the probe records. Batch delivery means a batch of spawns returns together inside the turn. Notice delivery means a spawn returns at once, and completion arrives later as a notice, with or without its result. harness_portability records which host shows which property. Batch and notice delivery spawn through the host's own sub-agent surface, the only route a helper runs on. For each table row, state what the orchestrator does and which ledger calls it makes:
  - At the inline floor, run each pass from its brief file to its return file before the next brief, through `brief` and `accept`. Label every check recall-limited, since the one context has already seen what it checks. Cross sessions at wave ends with `attach`.
  - Under batch delivery, send one wave per batch. For each helper row, run `brief` and `dispatch` with a one-line pointer prompt, then `accept` or `accept --stdin`. Then run `diff --add-checks` and the checker wave. The batch is the barrier, so the next step waits for the whole batch, and the gates close the wave.
  - Under notice delivery, dispatch in the background with `--helper-id`, and wait inside the turn in bounded `accept --wait` polls. A late notice re-runs `accept`, which changes nothing on an accepted row. Where the notice carries no result, send read-only helpers as a foreground batch.
- **Run directory.** Describe the layout as the shipped ledger writes it, with one open run per working root, since `init` refuses while a run is open and names `attach`. Every brief keeps its helper out of the directory, apart from the helper's own brief, start marker, and return, and the inputs its brief names, snapshot copies included. No brief lets a helper run the ledger. The gate-scope check works like this. At `init` the ledger plants a known positive and runs each named gate at the baseline, recording whether the gate reported the planted file. For a gate that sees the directory, `gate` drops findings under its path and says so on the gate line. A gate the filter cannot handle is named as a narrowing, a check the run drops or shrinks. `init` refuses to register an auto-fix gate while run state exists. Every recipe's orient step, where the orchestrator reads the governing documents, runs this check before dispatch. Host search tools may skip the directory, so query it only through `status`, `show <label>`, and `search`, whose Python pattern search carries its own positive control.
- **Ledger floor.** The ledger needs Python 3.9 or newer and checks its version at start. If the ledger itself errors, record the error as a run event, continue by hand, and name each check left unenforced.
- **P1, open the run.** The section holds a trigger, numbered steps, and a checks line. The trigger is every new run, before its first item brief, and an open run re-enters through P4 instead. P1 also carries two reasons the body leaves out. A label comes from a stable per-item slug, because a repeated label leaves a dead helper unattributable. A nested entry returns as a finding, because a helper handed it edits a generated surface or fans out on its own. The steps are these:
  - Probe the four capabilities by observation through `init --probe`, which renders the fixed probe brief and opens no run. Spawn that brief through the host's own sub-agent surface, once through the cheapest route it offers and once through each registered role the host lists.
  - Count the read-only lever, a host setting that blocks a helper's writes, as enforced only when the probe's write attempt inside the run directory left no file. Count model and depth as observed only where the host exposes the helper's settings, and otherwise state rigour as behaviour.
  - Establish concurrency from the first real wave, through the filesystem times of each file-writing helper's `returns/<label>.start` marker and its return file. Cap the wave size at the largest batch harness_portability records for the host until the run's waves show more.
  - Record the delivery property, whether a notice carries its result, whether the session offers a goal tool, and whether the host gives a later turn. Record each capability as established, assumed absent, or unverified.
  - Next, write orient rows for the governing documents and the requirement sources, each read in full. The governing documents are `CHARTER.md` in full, the procedure pages, and the owning skill of each touched artifact class.
  - Scout and validate the inventory: no blank or repeated entries, category counts that sum, and every exclusion counted with a reason.
  - Then run `init` over the validated inventory, orient rows included. It opens the run and records the baseline and each gate's gate-scope result. Every git call passes `--no-optional-locks`, status reads pass `--porcelain -z --untracked-files=all`, and diff reads pass `--no-ext-diff --no-textconv --no-color`.
  - Split the user's hypothesis into its readings.
  - Read the request for each pre-dispatch gate's answer, proceed on a stated answer, and quote it in the announcement. A pre-dispatch gate is a question for the user that the run settles before it sends helpers. On a host with no later turn, an unanswered gate stops the run before dispatch, with its decision packet and `close --stopped`. A run on such a host uses the inline floor or batch delivery only.
  - Pilot two or three items to price the per-item cost.
  - Put every unanswered gate to the user: forks, widening, and the verification scope with its estimate beside any size guideline the host or user states.
  - Write the plan before any item brief. It holds two to four helper phases, each one verb plus one clause naming the earlier returns it reads. Scouting, calibration, deterministic gates, scripted merges, validation, and reporting are listed as orchestrator steps. The plan holds a model and an effort per role, recorded with `dispatch --model M --effort E`. It holds the wave size, the bound, and the exclusions. It also holds a context estimate against the host window harness_portability records, with a session boundary at the first wave end past half the window. Where the reference records no batch or window for the host, or omits the host, use a fallback figure: the figure the request states, otherwise the smallest figure the reference records for any host. Name that figure as unverified in the announcement.
  - Announce all of it.
- **P2, render every brief from files.** The run directory keeps the inputs every brief is built from: `request.txt` verbatim, `intent.md` with its hash, and a preamble with tiered settled facts and an unverified-premises block (checks.md C10). Each settled fact carries its evidence tier, and the unverified-premises block lists the claims nobody has verified yet. The directory also keeps one access file per phase, one rules file a producer and its checker share, kind notes for classes of item that need different treatment, and item briefs. `brief` renders each brief from those blocks and appends the closing block. That block carries the role's return template, the return channel P3 assigns, the END line, the no-delegation clause, the capabilities as facts, the bound, and a brief token as the last line. The brief token is a short code the return must repeat. A file-writing helper's closing block adds the start-marker instruction and an END-line-only final message. Relay upstream material, meaning earlier returns, by path with a read-in-full instruction, or paste it below a stated cap listing the trimmed identifiers. A relay refuses until its upstream row is accepted. The spawn prompt is one line pointing at the brief file. Lint every brief for byte-identical shared blocks within a phase, and for no path or command both forbidden and permitted. Keep text a blind pass must not see out of the workspace until that pass returns, with only its hash on the roster.
- **P3, return files and the acceptance gate.** A return holds optional prose, one fenced JSON block that echoes the label first and repeats the brief token, and the line `END <label>`. A helper whose brief grants writes writes `returns/<label>.md` as its last act. A helper whose lever or brief withholds writes ends with the block and END line as its final message. The orchestrator pipes that message verbatim into `accept --stdin <label>`, and the report names every relayed return. The template puts the verdict first and lists its fields as the shipped ledger requires them. List every rejection rule `accept` applies, the single re-invocation after the first rejection, and the inability path for a helper that reports it cannot do its item. Also list `accept --classify` for a free-text return, manifests for large outputs, joins by identifier only, recall tagging from recorded relays, and `accept --observed-model M --observed-effort E`.
- **P4, completion, waves, stop, and resume.** Completion is an accepted return, and anything else is a hint to run `status`. Before waiting on a predicate, such as a file appearing, confirm it can become true. Poll with `accept --wait`, at most 90 seconds per call. Work in waves, the batches of helpers sent together: writers first, then checkers and gates, with pending checks ahead of queued writes. A phase sized by earlier returns gets its rows from `rows` before dispatch. The verdict, each stamp hand-off (checks.md C9), and the report wait for every checker row they rest on. Create the stop file the moment a stop or pause request arrives. On a host with no later turn, a stop file planted before a wave pauses the run the same way. After a stop, abort, or resume, settle in-flight rows from the net diff before re-dispatch. Re-entry from a completion notice, a user message, or a fresh session runs `status`, then `attach`. A turn ends with the closing report or the interim report. A reply claiming nothing is left while rows or gates are open is a reporting error. Where the session offers a goal tool, the continuation step arms one goal per run, with the run directory in its objective and `close` exiting 0 as its completion condition. Where the session offers none, re-entry through `status` and `attach` carries the run.
- **P5, keep shared state still.** No pass runs a whole-tree version-control state command: stash, reset, clean, commit, bulk staging, a branch switch, or a checkout or restore of other paths. Every reading pass reads a snapshot, a file copy under `snapshots/` made by `snapshot`, and a blind pass reads `snapshot --base`. The run writes no ref, tree, commit, or object into the user's repository. A reading brief names its files and reads each in full or searches it by explicit path. It never searches a directory under the run directory. It forbids scripts, network access, credentials, other helpers' transcripts, the ledger, and any write beyond its return channel. The orchestrator holds its own writes while a reader is out. Every pass is guarded by the baseline git reads, and a change outside the write set stops the run.
- **P6, the findings ledger, decision packets, and the report.** P6 holds the reading rule `<aggregation>` states, one disposition per record, a decision packet per fork, and the report built from the tally block. Coverage comes from tool evidence (checks.md C8), and verification and confirmations are split by provenance (checks.md C7). The report lint flags an assertion word, such as verified or complete, that carries no ledger citation. A report on a run with no clean `close` says so in its opening sentence.
- **Command reference.** It lists what each verb and flag does, the roster columns, and the return contract with its channels, source tags, rejection rules, and start marker. It also lists the close conditions. Write every entry from the shipped ledger and its script tests, and let the program's behaviour govern wherever the two differ.

Give P1 to P6 each a checks line that a reviewer can verify against the ledger's files. Point at the C-checks by their numbers in `references/checks.md`, which the checking-doctrine task creates.
