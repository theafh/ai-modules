# Retire the Gemini CLI deploy target and correct the Antigravity target

## Goal

Update `deployment/deployment.sh` (and its `deployment.conf` and `deployment/README.md`) to (a) **retire the `gemini` deploy target** because consumer Gemini CLI is retired, and (b) **correct and expand the `antigravity` target** so it deploys into every directory Antigravity actually reads and supports **skills**, **(sub)agents**, and **hooks**.

The user-visible outcome is that one `./deployment/deployment.sh --target antigravity` run lands this repo's skills, agents, and hooks in every place Antigravity reads them, so the components work whichever Antigravity app the user happens to run — 2.0, the IDE, or the CLI — without the operator knowing which root belongs to which product. Concretely: each skill arrives as a real `SKILL.md` directory tree, each agent as a file whose frontmatter is transformed into Antigravity's schema, and the repo's hook as a declarative `hooks.json` plus its script. Alongside that, `gemini` is no longer an accepted target, its dead generators and config are gone, and the docs reflect both changes.

Reaching every product is achievable, and cheaper than the root split first suggests. Project mode needs nothing special: the workspace `.agents/` tree is uniform, so one deploy covers all three products. Globally, agents and hooks are single-rooted under `~/.gemini/config/` and so already reach every product from one write. **Only skills actually fan out**, to the three documented skill roots. So "works with whatever app the user uses" costs one extra copy per skill rather than triplicating the whole deploy.

## Context

The verified Antigravity facts, their sources, and the frontmatter-tolerance finding this task's agent transform depends on are owned by the shipped `harness_portability` skill — `<antigravity_config_tree>` for the roots, `<antigravity_hooks>` for the hook contract, and `<frontmatter_schema_tolerance>` for that pending tolerance state — which this task consumes rather than re-derives. The deploy-relevant facts are restated here so this file stands alone.

**Why retire Gemini.** Consumer Gemini CLI was retired on 18 June 2026 (`410 Gone`; only paid/enterprise API-key access survives), and Google's live surface is Antigravity, which shares the `~/.gemini` tree. Deploying to live consumer Gemini CLI no longer reaches a working tool, so the `gemini` target is removed rather than maintained.

**What Antigravity actually reads.** Verified against official `antigravity.google/docs` pages when that skill was authored; the skill records the per-page sources. The workspace tree is uniform across products: `.agents/{skills,agents,rules,plugins}/` plus `.agents/{mcp_config.json,hooks.json}`. Globally the roots split **by artefact class, not by product**: agents (`agents/`), hooks (`hooks.json`), MCP (`mcp_config.json`), and sidecars (`sidecars/`) all sit under `~/.gemini/config/`, while **skills split three ways** — `~/.gemini/config/skills/<skill-folder>/` for 2.0, `~/.gemini/antigravity/skills/<skill-folder>/` for the IDE, `~/.gemini/antigravity-cli/skills/` for the CLI — and **plugins split two**, `~/.gemini/config/plugins/` for 2.0 and the IDE against `~/.gemini/antigravity-cli/plugins/<plugin_name>/` for the CLI. Skills are `skills/<name>/SKILL.md` directory trees under the Agent Skills open standard (near drop-in with this repo's skills); agents are `agents/<name>.md`; hooks are a declarative `hooks.json`.

Correcting an earlier premise of this task: `~/.gemini/antigravity` is **not** purely a transcript/artifact output path. It is the IDE's documented global **skills** root as well, so the directory serves both purposes and the script's current use of it is right for IDE skills and wrong for everything else. The breakage to fix is therefore not "stop pointing at `~/.gemini/antigravity`" but "stop treating one directory as the whole Antigravity target", which the skill-root fan-out in the Approach settles by writing every documented root instead of choosing between them.

**The Antigravity agent transform.** The repo's agents are Claude-style markdown; the script already generates target-specific variants (`generate_toml_agent` for Codex, `generate_gemini_agent` for Gemini) that first run `rewrite_agent_frontmatter` then emit the target's schema. A new `generate_antigravity_agent` follows that shape, mapping to Antigravity's native frontmatter: `name` and `description`, both **required** by Antigravity's documented agent frontmatter and so mandatory survivors of the whitelist, then a `tools` array of Antigravity tool names, `model` as a tier (`inherit`|`flash`|`pro`), `commandExecutionPolicy` (`off`|`auto`|`eager`|`sandbox`, default `sandbox`), and `mainAgent: false` on every agent it writes — `mainAgent` and `subagent` both default to `true`, so `subagent: true` restates the default while the default `mainAgent: true` would register the agent as user-invocable; `plugins/*/agents/` holds `auto_*`-named files exclusively, which the standing repo rule **Name skills and agents by invocation mode and collision risk** reserves for agents no user invokes, so the generator marks the spawn-only role unconditionally the way `generate_opencode_agent` already emits an unconditional `mode: subagent` in this script. The `model` tier resolves through the script's existing `is_model_inherit_value`: the `inherit` sentinel all six repo agent sources carry today — Antigravity's own documented default for the field — generates no `model` line, while a source pinning `flash` or `pro` passes that tier through verbatim, the same sentinel-to-omission translation `generate_toml_agent` and `generate_opencode_agent` already apply. A source carrying no `tools:` line at all — the state of three of the repo's six agent sources today — generates no `tools` key rather than an empty array, the same absent-field handling every agent generator in this script already applies. What Antigravity makes of that absence stays unverified, and the verification gap is already on record in the shipped artefact rather than owed by this task: `harness_portability`'s `<agent_definition_surfaces>` records the field's documented default as `[]`, and its `<native_fields_and_deploy_bridges>` states that Antigravity documents that default without saying what an empty array grants — the default an omitted key falls back to. This task consumes that record rather than assuming a semantic in either direction and writes no second copy, the same routing **Antigravity agent frontmatter uses the whitelist — settled.** already applies when it sends a later empirical tolerance finding to the skill. Read-only roles land on both Antigravity levers, the mapped `tools` array and `commandExecutionPolicy`, driven by the source `readonly:` field both sibling generators already read: `readonly: true` with a `Bash`-free `tools:` allowlist emits `commandExecutionPolicy: off`, `readonly: true` with `Bash` present emits `sandbox` because the role still needs contained command execution, and every other agent emits the literal line `commandExecutionPolicy: sandbox`, so every generated agent carries its policy explicitly — the split `harness_portability`'s `<readonly_agent_enforcement>` prescribes, where `off` denies commands outright while `sandbox` denies only unsandboxed ones. Gate it on the same `Bash`-in-allowlist test `generate_opencode_agent` uses to drop its `bash: deny` clause, this target's counterpart to `generate_toml_agent`'s `sandbox_mode = "read-only"`.

Two tool-name corrections carried over from `harness_portability`'s own verification, because getting either wrong fails silently. The documented vocabulary is `view_file`, `grep_search`, `run_command` and the fuller hook-matcher list — **not** `read_file` or `edit_file`, which circulate widely but appear on no official page — and no canonical tool list is published anywhere in the docs. **The unmappable-tool rule:** the generator emits every source tool name it can map to a name copied verbatim from a documented list, and drops only the individual entry it cannot map, leaving the mapped names in the array. The repo's own agents are the worked case — `tools: Read, Grep, Glob` generates `tools: [view_file, grep_search]`, and `Bash` adds `run_command` where an agent carries it. `Read` and `Grep` pair with documented names, while `Glob` drops by decision rather than for want of a candidate: `harness_portability`'s `<tool_name_namespaces>` publishes `find_by_name` among the hook-matcher names it treats as one vocabulary with the allowlist, yet no page states what that tool matches, so pairing the two would ship an inferred equivalence into the read-only agents whose `tools` array is half the lever `<readonly_agent_enforcement>` defines — where `view_file` and `grep_search` are the read-only pair it names. Add the mapping once a documented source states the match; until then the entry drops. An unmapped or misspelled tool name makes the subagent **hang at runtime** rather than fail at load, so a wrong mapping is worse than a missing entry. Likewise `flash_lite` is not a real tier: it appears in neither the subagents frontmatter table nor the model list, so emitting it risks the same silent failure.

**Hooks — the documented contract.** Antigravity hooks are declarative, closer to the Claude/Codex JSON-config arms the script already has than to OpenCode's code bridge in [deployment_opencode-hook-bridge.md](deployment_opencode-hook-bridge.md).

The config file keys by a **named hook first, then the event** — unlike Claude and Codex, which nest events under a top-level `hooks` key:

```json
{
  "charter_guardrail": {
    "PreToolUse": [
      { "matcher": "*", "hooks": [ { "type": "command", "command": "<deployed charter_guardrail.sh>", "timeout": 10 } ] }
    ]
  }
}
```

`matcher` takes an exact tool name, `""` or `"*"` for all tools, `"a|b"` alternatives, or a regex like `"browser_.*"`.

The `PreToolUse` stdin envelope addresses the tool at `toolCall.name` and its parameters at `toolCall.args`, and carries **two casings**: the envelope is camelCase (`toolCall`, `stepIdx`, `conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`) while the nested arguments are PascalCase — a shell call arrives as `toolCall.args.CommandLine` with `toolCall.args.Cwd`. There is no top-level `cwd`. On stdout the handler returns `{"decision": "deny", "reason": "…"}`, with `decision` one of `allow`/`deny`/`ask`/`force_ask` and an optional `permissionOverrides` array.

**What that means for `charter_guardrail.sh`.** The script reads its envelope through a handful of `jq` pulls (`.cwd`, `.tool_name`, `.tool_input.file_path`, `.tool_input.command`) and blocks through a single `block()` function that `exit 2`s — one input mapping and one output choke point, so the adaptation is contained rather than sprawling. Give it an Antigravity branch that reads `toolCall.name`, takes the shell command from `toolCall.args.CommandLine`, takes the directory from `toolCall.args.Cwd` or `workspacePaths[0]`, and makes `block()` print `{"decision":"deny","reason":"…"}` on stdout and exit 0 instead of exiting 2. Detect the shape rather than the harness — the presence of `toolCall` is the signal, which keeps the branch correct if Antigravity is renamed again and follows `harness_portability`'s `<behavior_carveouts>` rule. Derive the signal once, structurally: past the JSON guard set it with `jq -e 'has("toolCall")'`, and let that one value pick the field pulls, the `toolCall.args` scan, and the `block()` output shape, so `block()` stays the single choke point for the Antigravity deny at exit 0. Let no text `case` glob on the captured `input_json` pick a contract anywhere in the script: a glob answers by where the marker sits rather than by the envelope's shape, and both of its wrong answers fail open — a Claude payload carrying the quoted `"toolCall"` takes the Antigravity shape and hands Claude a stdout `decision` at exit 0, which Claude reads as allow, while an Antigravity payload without it takes the Claude shape and hands Antigravity a bare `exit 2`, the silent fail-open `harness_portability`'s `<shared_hook_scripts>` records for that harness and the outcome **Hooks ship in this task — settled.** rejects. The two aborts that run where no `jq` pull can succeed — `jq is required to inspect hook input` and `hook input was not valid JSON` — therefore answer in every contract at once instead of choosing one: give them their own emit shape beside `block()` that prints the reason on stderr, prints `{"decision":"deny","reason":"…"}` on stdout, and exits 2, so Claude and Codex block on the non-zero exit `<shared_hook_scripts>` names as their mechanism while Antigravity reads the `decision` value it wants rather than the exit code it ignores. Rewrite `charter_guardrail.sh`'s own header comment in place rather than appending to it, since the Antigravity branch falsifies three of its statements. Its opening `The guard runs as a PreToolUse hook on both Anthropic Claude and OpenAI Codex and inspects three mutation surfaces` becomes a three-harness sentence naming Google Antigravity beside them and naming both signalling contracts, the `exit 2` Claude and Codex read against the stdout `decision` Antigravity reads. The numbered list below it stays at three surfaces — one per mutation shape, not one per harness — with the direct-edit item gaining the key-agnostic `toolCall.args` scan, the shell item gaining `run_command` with its `CommandLine` and `Cwd` keys beside the `tool_name "Bash"` and `tool_input.command` it already names, and the `apply_patch` item standing as written since it is already Codex-scoped. The third stale statement, its `Read-only references (cat, grep, test -f, git show/log/diff) emit no candidate and are never blocked` promise, is scoped by the tool-name gate below, which owns what stays a read on Antigravity. The header keeps its record of the one corner no page settles, per `CHARTER.md`'s constraint beginning `Verify harness-specific behavior`: Antigravity's handling of a stdout `decision` beside a non-zero exit is undocumented, and every branch lands at least as safe as the shipped script — it denies if it reads the decision, still stops the write if it treats the exit as an error and blocks or asks, and fails open exactly as today's `exit 2` already does if it discards the output.

Only `run_command`'s argument keys are documented, so the file-writing tools (`write_to_file`, `replace_file_content`, `multi_replace_file_content`) reach the guard through a key-agnostic scan instead of a guessed key name: take each string value under `toolCall.args` **as one whole path candidate** and append it to `paths_file`, exactly as the shipped `.tool_input.file_path` pull already does, so all three are covered without their key names and a fourth is covered when Antigravity adds one. ## Approach

**Retire Gemini — the target, not the string.** Retirement means no `gemini` deploy target and no Gemini-CLI-shaped generator survives, and that every remaining mention of the string serves Antigravity's needs. It does **not** mean purging `gemini` from the script: Antigravity's own tree is `~/.gemini`, because Google kept the legacy directory name when it ported the app, so the correct end state still contains `.gemini` paths throughout. A blanket "grep finds no gemini" check would therefore be wrong, and would push an implementer into renaming real paths.

Remove `gemini` from `VALID_TARGETS`; drop the `gemini|Gemini CLI|…` row from `ALL_APP_TARGETS`; delete the `gemini` arms from the `command` and `agent` cases in `install_for_app()`; delete the now-dead `generate_toml_command`, `generate_gemini_agent`, `map_gemini_tool_name`, and `GEMINI_AGENT_ALLOWED_KEYS` after confirming no other caller. Keep the parked `# GEMINI_MD="${GEMINI_DIR}/GEMINI.md"` declaration rather than deleting it, renaming it in place to `# ANTIGRAVITY_RULES_MD="${ANTIGRAVITY_TREE_DIR}/GEMINI.md"` and leaving it commented under its existing revival note: `~/.gemini/GEMINI.md` is Antigravity's global rules file, so the line is a remaining `.gemini` mention that serves Antigravity, and [deployment_park-managed-rules-scaffolding.md](archive/deployment_park-managed-rules-scaffolding.md) parked it to stay revivable — a byte-identical `${GEMINI_DIR}` stops resolving once the rename lands. Leave the other four parked declarations untouched; this is the only one the rename reaches. Remove the `#gemini` section from `deployment.conf` together with `gemini` in that file's own header-comment tool-identifier list; and strike Gemini CLI as a *target* from the script header comment, the `--target` help text, `deployment/README.md`, and the root `README.md` — while letting those same docs name `~/.gemini` paths where they describe Antigravity. `tests/deployment/script_tests/run.sh` carries no `gemini` scenarios, so retirement deletes no test there; the Claude- and Codex-shaped envelope scenarios the `charter_guardrail.sh` change must keep passing live in `tests/charter_guardrail/script_tests/run.sh`.

**Rename `GEMINI_DIR`, do not delete it — it has a live non-Gemini consumer.** Both backup sites special-case the Antigravity target onto `backup_roots=("${GEMINI_DIR}|")`, so `GEMINI_DIR` is already the Antigravity tree root rather than a Gemini-target variable. Deleting the assignment while leaving those two references would set the antigravity backup root to the empty string, and neither `backup_app_dir` nor `clear_old_backups_for_app_dir` errors on an empty path — backups would silently stop and `--clear-backups` would operate on nothing, with no failure surfaced. Rename it to `ANTIGRAVITY_TREE_DIR="${HOME_DIR}/.gemini"` and update both backup sites, so no `GEMINI_`-prefixed variable remains and every Antigravity path derives from an Antigravity-named one. Keep `ANTIGRAVITY_DIR` as the target's `ALL_APP_TARGETS` base dir — `${ANTIGRAVITY_TREE_DIR}/config` globally, `${PROJECT_DIR}/.agents` in project mode — so the existing base-dir contract that `install_for_app()` relies on is unchanged, and set `ANTIGRAVITY_TREE_DIR` to `${PROJECT_DIR}/.agents` in project mode where there is no `~/.gemini` tree.

**Make the retired flag say why.** `--target gemini` should abort with a message naming the retirement and the successor — that Gemini CLI support is retired because Google is removing that app and porting it to Antigravity, and that `--target antigravity` is the replacement — rather than falling through to the generic "Unknown deploy target" abort, which reads as a typo and leaves an operator with a working `gemini` deploy in their notes guessing.

**Correct and expand Antigravity.** Set `ANTIGRAVITY_DIR` to `${ANTIGRAVITY_TREE_DIR}/config` in the global branch and `${PROJECT_DIR}/.agents` in the project branch (stop skipping Antigravity in project mode, and rewrite the `# Build filtered target list...` skip comment to reflect Gemini is removed and Antigravity supported). The target-directories block asserts the same skip in a comment of its own — the two lines `# Gemini and Antigravity have no documented project-level config convention.` and `# Set to empty so the filter logic can skip them with a warning.`, standing immediately above the project-branch `ANTIGRAVITY_TREE_DIR` and `ANTIGRAVITY_DIR` assignments this task gives real `.agents` paths — so rewrite that pair in place to the single line `# Antigravity's native project-level convention is the workspace .agents/ tree.`, rather than leaving prose that contradicts the assignments beneath it and invites a later maintainer to re-empty the variables. `deployment/README.md` asserts the same skip in prose — the project-dir sentence under the **Target Layout** table reading `It skips Gemini and Antigravity (no documented project-level config convention)` — so rewrite it in place to name `<project>/.agents/` as Antigravity's project path beside OpenCode's `<project>/.opencode/`, rather than striking only the word Gemini and leaving the README claiming Antigravity is skipped. That base dir stays the single home for agents and hooks, which reach every product from there. In `install_for_app()`, rewrite the `antigravity` arms in place so: the `agent` case's existing `Antigravity does not support agent definitions` skip arm becomes a call to a new `generate_antigravity_agent` writing `${app_dir}/agents/<name>.md`, replacing that arm rather than adding a second one, since bash `case` takes the first match and an appended arm never fires; the `skill` case copies the directory tree (mirroring the copy-based `claude`/`opencode` skill branch) to **each** documented global skill root rather than to `${app_dir}/skills/<name>/` alone; and the `command` case's `antigravity` arm is rewritten in place so its whole body is an explicit skip, while the `generate_antigravity_workflow` helper goes, per the settled no-workflow-deployment decision below. In that Target Layout refresh, the Antigravity **Commands** cell drops today's `~/.gemini/antigravity/workflows/<name>.md` generated from command source and reads `not deployed — the repo ships no commands`, per **No Antigravity workflow deployment — settled, not deferred.** below — deliberately outside the table's `not implemented` register, which would promise pending work that settled decision rules out. Refresh the Antigravity rows in the `deployment/README.md` Target Layout and Generated Formats tables, and leave `deployment.conf`'s `#antigravity` section at its existing `disallow:*legacy*` line — Antigravity's per-source hook filtering lives in the basename gate under **Hooks.**, not in the conf.

**Fan skills out to every product's skill root.** Introduce an explicit list of Antigravity global skill roots — `${ANTIGRAVITY_TREE_DIR}/config/skills`, `${ANTIGRAVITY_TREE_DIR}/antigravity/skills`, and `${ANTIGRAVITY_TREE_DIR}/antigravity-cli/skills` — and have the global-mode `skill` arm copy each skill tree into every one of them, so the operator does not have to know which root their app reads. Project mode writes the single `${PROJECT_DIR}/.agents/skills/<name>/` and needs no fan-out. Two consequences follow from the global fan-out and each must be handled rather than assumed: every copied path is recorded in the uninstall log so `--uninstall --target antigravity` removes all of them and leaves no orphan skill behind; and every root the fan-out names is created before its copy, which the `skill` case's existing unconditional `ensure_dir "$dest_dir"` call supplies once the loop runs it per root.

**Open decision: who owns `.agents/skills` in project mode.** `${PROJECT_DIR}/.agents/skills` is byte-identical to the `CODEX_SKILLS_DIR` the `skill` case already redirects `codex` onto, because `.agents/` is Antigravity's native workspace root and Codex's project skill root at once — so a plain `--project-dir` run with no `--target` filter has both targets writing and logging one directory. The write is harmless (one source, the same `copy_path_with_replacements` call); the removal is not, because `append_deployed_artifact_log` records the path once per target id, `dedupe_deployed_artifact_log` keeps both lines since the ids differ, and target-filtered `uninstall_logged_artifacts` reaches `remove_logged_path`'s `rm -rf`, so `--uninstall --target antigravity` deletes the tree Codex still depends on and strands Codex's log entry on an absent path. The options are (1) one owner, with `${PROJECT_DIR}/.agents/skills` always logged under the `codex` target id whichever run writes it, while the `antigravity` branch skips the copy when `codex` is also active and performs it when `codex` is filtered out; (2) the mirror, with the `codex` redirect deferring to Antigravity's native root and `antigravity` the sole owner id; (3) both writing under their own ids, with `uninstall_logged_artifacts` taught to retain a path another target still claims. **Default without further input: option 1, with the owner pinned to the path rather than to the run** — extend the `skill` case's existing `app_id` branch, which already picks `CODEX_SKILLS_DIR`, to carry a log-owner id that defaults to `$app_id` and is pinned to `codex` when `antigravity` writes in project mode, and pass it as the `target_id` argument of `copy_path_with_replacements`. The pin is safe because that argument is log-only at this call site — the identically named parameter that derives vendor prefixes belongs to `rewrite_agent_frontmatter` on the `agent` path — and `uninstall_logged_artifacts` is the log's only reader, so deploys never consult it and repeated runs collapse to one line. `codex` owns the path because `CODEX_SKILLS_DIR` already holds it in the shipped script and `ALL_APP_TARGETS` lists `codex` ahead of `antigravity`. The accepted cost is that `--uninstall --target antigravity` leaves the shared tree for a `codex`-scoped or unfiltered uninstall to remove; option 3 instead changes uninstall semantics for every target.

**Uninstall checks run against a copied-aside deploy log.** Every `## Acceptance` item that invokes `--uninstall` runs with `deployment/deployed_artefacts.log` copied aside and removed first, then restored afterwards. `uninstall_logged_artifacts` reads the single fixed `DEPLOYED_ARTIFACTS_LOG` and narrows its selection only through `logged_path_matches_active_targets` (target id) and `logged_type_matches_filter` (type) — `--project-dir` narrows nothing — so an unisolated `--uninstall --target codex` or `--target antigravity` deletes the live deployments already recorded there and leaves the surviving log unreadable as evidence about the scratch tree.
