# Owner statements on re-opening audited tasks, 2026-10-13

This note records what the repository owner stated on 2026-10-13 about gaps that a re-audit finds in an `audited` task. The statements were made in a working session whose transcript is a local file outside the repository, so they are excerpted below verbatim as the authoritative copy. No machine path or session id is given.

## Statements

A re-audit of an `audited` task had found a gap in its test harness, and the agent had routed the fix to a new follow-up task, as the family's rules then required. The owner replied:

> No, I didn't say file follow-up tasks, but run a loop of implement and audit. If the task status bothers you, set it to implemented until the audit is truly done. Follow-up tasks result in task inflation and should only be filed if the audit/implement loop stalls and starts to repeat, or if a genuinely different issue or bug is found with no real overlap with the implemented task. Re-run the loop again!

In a later message the owner stated the status rule directly:

> it is NOT forbidden to set audited back to implemented when an (re) audit of an audited task finds something. This is totally fine!

When the agent then filed a task to change the family's rule rather than changing it, the owner restated the preference:

> i thought i was clear i want you to fix now and dont file new tasks

## Context

These statements revise one point the owner confirmed on 2026-10-10: that gaps a re-audit finds in audited or archived work go to a new follow-up task. They cover `audited` tasks. The 2026-10-10 statement that archived `finished` and `deferred` tasks never change status was not revisited.
