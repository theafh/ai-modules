# Win back agent_spinner's two drifted trigger queries

## Goal

The agent_spinner trigger set holds its 18/18 precise baseline on the default vendor again, or each query that keeps failing carries a recorded disposition. Two queries regressed on the same `description:` text:

- "merge what the helper agents reported into one answer without just counting how many of them agreed" should load agent_spinner, and loaded no skill.
- "which tool names do I need for a read-only subagent on each harness we target?" should load no family skill (it belongs to harness_portability), and loaded agent_spinner.

## Context

- **The measurement.** The baseline is the 2026-11-10 Cursor `auto` run of the set (3 runs per query, 18/18), recorded in `tests/agent_spinner/RUNBOOK.md` and taken on the trimmed description that commit `1174815` shipped. On 2026-11-14, three runs of the same set against that baseline each failed one or both queries at 0/3: 17/18, 17/18, and 16/18. Each query failed in two of the three runs, as the RUNBOOK's "Recorded measurements" table records. The deployed copy under the Cursor skills root matched the source description throughout, so the description did not change; the router behind Cursor's `auto` did. Trigger-run output stays local, so re-measure rather than assume a prior result on another machine.
- **The text in play.** agent_spinner's description in `plugins/ai_dev/skills/agent_spinner/SKILL.md` already lists "aggregating helper reports" and ends with "Per-harness facts stay with harness_portability". harness_portability's description claims "agent definitions, agent frontmatter, tool allowlists, read-only agent enforcement".
- **Prior art.** [The deferred description-recall task](ai-dev_agent-spinner-description-recall.md) found that adding keyword surface does not raise agent_spinner's recall, and it was parked when no tested rewrite beat the description of its day. That finding constrains this task: a fix that only adds trigger phrases is the approach already known not to work. `tests/CLAUDE.md`'s trigger-eval section ("Acting on family-only passes") says a sibling stealing a query is usually fixed in the sibling's description.

## Approach

1. Re-run the set three times against the 2026-11-10 baseline to confirm both regressions still hold before changing anything, measuring the source description through the RUNBOOK's scratch-home route: build the scratch home the way `tests/lib/micro_deploy.py` does, then run `HOME="$cfg" MICRO_DEPLOY_PATH="$PATH" python3 tests/trigger_evals/run.py --eval-set tests/trigger_evals/agent_spinner.json --skill agent_spinner --skill-path plugins/ai_dev/skills/agent_spinner --baseline tests/trigger_evals/results/agent_spinner/2026-11-10_123721 --runs-per-query 3 --timeout 45`. Use this route rather than the `tests/CLAUDE.md` "Run pattern" command, which resolves `deployed_root` from the vendor's native skills root and so scores the deployed copy; a post-change measurement on that route would read an unchanged description, and the only other way to refresh it, `make deploy`, is gated on the user by the standing repo rules.
2. For the negative query, sharpen the boundary where the bleed is. Rewrite the closing sentence "Per-harness facts stay with harness_portability." in place so it names per-harness tool and agent-definition questions as harness_portability's, and adjust harness_portability's description only if the agent_spinner change does not hold the query. The `description:` measures 974 characters against `discovery_safety.py`'s 1,000-character listing-budget threshold (`LISTING_BUDGET_RISK_CHARS = 8000 // 8`), so steps 2 and 3 share 26 characters of headroom: fund both by cutting the 42-character span "Every guarantee holds at the inline floor." in place rather than appending, and keep the tokens `tests/agent_spinner/script_tests/run.sh` pins — `orchestrat`, `fan-out`, `verif`, `parallel`, `task_*`, `wiki_fix` — in place. A substitute span is admissible only when it is at least as long and carries none of those tokens. Measure harness_portability's own trigger behaviour with its set when its description changes; if it has none, note that in the record.
3. For the positive query, rewrite the phrase "aggregating helper reports" in place into a clause that says what the skill does with helper reports (merges cited findings by substance rather than by vote) instead of adding keywords, inside the same budget, and measure it the same way.
4. After each material `description:` edit in steps 2 and 3, run `python3 tests/agent_spinner/trigger_overlap.py` and record its output in `tests/agent_spinner/RUNBOOK.md`'s "Recorded measurements" section. For each set it names, run that set on the same scratch home step 1 builds, carrying the edited `agent_spinner` description at `$cfg/.cursor/skills/agent_spinner` and that set's skill family staged from source beside it (`cp -R plugins/ai_dev/skills/<set-root>* "$cfg/.cursor/skills/"`, so the `task` set finds its `task_*` siblings and its family grading stays meaningful) under `HOME="$cfg"` and `MICRO_DEPLOY_PATH="$PATH"`, passing that set's own `--eval-set`, `--skill`, `--skill-path`, and, as `--baseline`, the newest run recorded for that set before this task's runs, so the run scores the edited description rather than the deployed copy, and record that run. When `run.py` logs "baseline vendor mismatch" or "baseline worker mismatch" for that baseline — the branch the recorded `task` runs take, since their `results.json` records no `vendor` key, which `run.py` reads as its `claude` default — record the skipped comparison and read that run's per-query rows in its `results.json` as the set's disposition, rather than reading `run.py`'s exit 1 as a regression. When no set qualifies, record that instead; when a named set's skills cannot be staged from source, record the set as not run together with the staging error in place of its run. The RUNBOOK's "Deploy-time obligation" paragraph stays with the first `make deploy`, which the standing repo rules gate on the user.
5. When a query still fails three runs after a tried rewrite, give its eval-set entry in `tests/trigger_evals/agent_spinner.json` a `note` that records the disposition, as `tests/CLAUDE.md` describes for persistent, understood failures, and keep the shipped description.

## Acceptance

- `tests/agent_spinner/RUNBOOK.md`'s "Recorded measurements" table carries the confirming runs made at implementation time and, where a `description:` edit was made, that edit's post-change runs, each with date, vendor, model, and per-category counts, with the per-query result for the two drifted queries in the prose beneath it.
- Each of the two queries either passes in at least two of three post-change runs against the 2026-11-10 baseline, with no other query regressing, or carries a `note` disposition in `tests/trigger_evals/agent_spinner.json`. A query whose confirming run already passes needs no description change: that confirming run, recorded in the RUNBOOK's "Recorded measurements" section, stands as its proof.
- A description change ships under the standing versioning rules, and `skill_doctor`'s `discovery_safety.py` reports the new description under the listing budget.
- `tests/agent_spinner/RUNBOOK.md` records the output of `python3 tests/agent_spinner/trigger_overlap.py` after each material `description:` edit, and the disposition of every set it names including that set's scratch-home cross-set run, or states that no set qualified; for a named set whose skills could not be staged from source, it records the set as not run with the staging error in place of that run.
