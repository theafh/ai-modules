# Enforce, migrate, and align the raw-sidecar origin-field contract (source_url / source_path)

## Goal

The whole wiki skill family enforces and teaches one raw-sidecar origin-field contract: `source_url:` for an externally-published source (a real remote URL), `source_path:` for a source tracked inside the repo (repo-relative), and neither field for a local file outside the repo (captured by a body excerpt plus a prose locality note). Four gaps that currently leave the contract under-specified and unenforced close:

1. **`source_url:` form is validated.** The linter flags a `source_url:` value that is a `file://` URL or a bare path rather than a real remote URL, with a message that points the author at `source_path:` (in-repo) or the out-of-repo excerpt rule, and flags a sidecar that carries both origin fields at once.
2. **Legacy `source_url: file://…` sidecars have a documented migration.** One canonical rule states how a pre-split sidecar migrates — an in-repo target becomes a repo-relative `source_path:`, an out-of-repo target drops to an excerpt plus locality note — and the `auto_shaper_wiki` agent surfaces such a sidecar as drift to route, never rewriting the origin itself.
3. **A SCHEMA customization that contradicts canonical semantics is surfaced, not silently kept.** When a wiki's own `SCHEMA.md` carries content that *contradicts* the canonical semantics rather than merely *extending* them — the motivating case being a `### raw/ Frontmatter` block that teaches the superseded `source_url: file://…` form — the agent surfaces it for the user instead of classifying it as a customization to preserve.
4. **Stale `source_url`-only prose is aligned.** `raw_taxonomy.md` and the three `source_url` or `source_path` phrasings in the agent stop implying `source_url:` is the sole or interchangeable origin field.

## Context

The two-field contract itself shipped and is deliberate — the settled Option A decision in [wiki_lint-local-path-portability.md](archive/wiki_lint-local-path-portability.md) established that `source_path:` is repo-relative only (an absolute, `~`-prefixed, or repo-escaping value is blocking; a non-repo wiki is local-only and skipped), and that an out-of-repo local file is captured by excerpt with no stored path. Read that task for the portability rationale this one extends to the `source_url:` side. The problem is that the contract is enforced and taught on only one of its two fields, and nothing covers the wikis that predate it.

- **`source_url:` is unvalidated.** In [lint.py](../plugins/knowledge_management/skills/wiki/scripts/lint.py), `check_source_path_portable` validates `source_path:` and `check_source_paths_exist` validates the page-level `sources:` inventory, but no check inspects `source_url:` at all — a `file://` value, a bare path, or a both-fields sidecar passes silently. The `file://` form that motivated this task is exactly the invisible case.
- **The "origin optional" posture is intentional, and this task stays consistent with it.** The [wiki_lint-blind-spots-and-false-positives.md](archive/wiki_lint-blind-spots-and-false-positives.md) added `check_raw_frontmatter` and deliberately kept the origin field *optional* (a sidecar for an out-of-repo local source legitimately carries neither field). The new `source_url:` check validates the *form of a value that is present*; it never makes an origin field required, so the two checks sit beside each other in `lint.py` without conflict.
- **No migration story for pre-split wikis.** `init_wiki.sh` copies `template_schema.md` verbatim into a new wiki's `SCHEMA.md`, so a wiki initialized before the split froze an era-1, `source_url`-only snapshot and improvised local conventions (the downstream `source_url: file://sources/…` form). Nothing documents how those sidecars migrate onto the current contract.
- **The agent preserves contradicting SCHEMA content.** The hunk-classification rule in [auto_shaper_wiki.md](../plugins/knowledge_management/agents/auto_shaper_wiki.md) sends any hunk where the wiki has content the canonical lacks to "customization, preserve as-is", with no carve-out for a customization that actively contradicts canonical semantics — so a local `### raw/ Frontmatter` teaching `file://` is silently kept.
- **`source_url`-only prose lingers.** [raw_taxonomy.md](../plugins/knowledge_management/skills/wiki/references/raw_taxonomy.md) predates `source_path:` and frames its bucket table's "Typical `source_url`" column and its `source_url`-keyed classification heuristics as if `source_url:` were the only origin field; the agent's three `source_url` or `source_path` phrasings let a `source_url`-only schema read as satisfying "the canonical shape".

Full edit surface: `lint.py` and `references/lint_checks.md` (gap 1); `references/template_schema.md`, `skills/wiki/SKILL.md`, `skills/wiki_import/SKILL.md`, and `auto_shaper_wiki.md` (gap 2); `auto_shaper_wiki.md` (gaps 3 and 4); `references/raw_taxonomy.md` (gap 4).

Co-edit coordination: [wiki_auto-shaper-internal-contradictions.md](wiki_auto-shaper-internal-contradictions.md) rewrites other blocks of the same `auto_shaper_wiki.md` (its exit criterion and the stale body-Sources anatomy); coordinate so the raw-frontmatter-drift and hunk-classification edits here land coherently alongside it. [wiki_raw-kind-rubric-and-out-of-repo-paths.md](archive/wiki_raw-kind-rubric-and-out-of-repo-paths.md) introduced `source_path:` and the `raw_taxonomy.md` rubric that gap 4 realigns.

## Approach

1. **Validate the `source_url:` form (gap 1).** Add a `source_url:` check to `lint.py` over the `raw/` tree, beside `check_source_path_portable`: a `source_url:` value that uses the `file://` scheme, or is path-like (carries no `scheme://` at all — a bare relative or absolute path), is flagged as a **warn** with a message that redirects the author to a repo-relative `source_path:` for an in-repo source or to the out-of-repo excerpt rule; a value with a genuine remote scheme passes. A sidecar carrying both `source_url:` and `source_path:` also yields a **warn** (the two name mutually-exclusive origin kinds — keep one). Warn rather than blocking because these are overwhelmingly legacy sidecars to migrate (gap 2) rather than newly-authored non-portable paths: matching the sibling `raw-frontmatter` check's treatment of a mechanically-fixable legacy gap, a warn surfaces every one without hard-breaking a pre-split wiki's lint on upgrade. Unlike `check_source_path_portable`, this form check does not depend on the wiki living in a repo, so it runs everywhere. Rewrite the affected rows of `references/lint_checks.md` in place — a new `source_url` form row and any severity-bucket line it belongs in — so the matrix keeps matching the script.
2. **Document the legacy migration once (gap 2).** In the `### raw/ Frontmatter` subsection of `template_schema.md` — the canonical home for the field semantics — state the migration for a legacy `source_url:` holding a `file://` or path value: an in-repo target becomes a repo-relative `source_path:` and the `source_url:` is dropped; an out-of-repo target drops to a body excerpt plus a prose locality note with neither field. State it once there; the `skills/wiki/SKILL.md` capture bullet and the `wiki_import` capture step cite that rule rather than restating it. In `auto_shaper_wiki.md`, extend the raw-source-frontmatter drift detection — which today covers missing `ingested`/`sha256` and a non-portable `source_path:` — to also treat a `file://`-or-path-valued `source_url:` as drift the agent surfaces for the user to route, consistent with the existing posture that the agent never fabricates or auto-rewrites an origin field.
3. **Surface a contradicting SCHEMA customization (gap 3).** Add a carve-out to the agent's hunk classification: a hunk where the wiki has content the canonical lacks is preserved as a customization only when it *extends* the canon; when it *contradicts* canonical semantics it is surfaced for the user instead — the same human-routes-the-conflict posture the contested-page protocol already uses. Write the carve-out at that general altitude (in agent prose it costs no more than an origin-only exception and avoids leaving the same "customization, preserve as-is" rule to be re-edited by a later task), and let the `### raw/ Frontmatter` block teaching `source_url: file://…` be its motivating illustration.
4. **Align the `source_url`-only prose (gap 4).** Rewrite `raw_taxonomy.md`'s "Typical `source_url`" bucket column and its `source_url`-keyed classification heuristics to speak of the origin field in two-field terms (a remote URL in `source_url:`, a repo-relative `source_path:`, or neither for an out-of-repo source). Rewrite the agent's three `source_url` or `source_path` phrasings — the two space-delimited forms plus the hyphenated `source_url`-or-`source_path` shape in the fix-phase `<fix_raw_frontmatter_subsection_missing>` block, the fix mirror of the **Frontmatter field drift.** assess phrasing — so an `or` no longer reads as "either alone satisfies the canonical shape": the canonical template declares both fields with distinct meanings, and at most one carries a value on a given sidecar.

**Out of scope:**

- Making an origin field required, or changing the `check_raw_frontmatter` "origin optional" posture — this task validates a present `source_url:`, it does not mandate one.

## Acceptance

Each item is proven on staged fixtures under the wiki test harness (`tests/wiki/`):

1. A raw sidecar whose `source_url:` is a `file://` URL, and one whose `source_url:` is a bare path, each yield the new `source_url`-form finding as a **warn** with a message naming `source_path:` / the excerpt rule; a sidecar with a genuine `https://` (or other remote-scheme) `source_url:` yields none; a sidecar carrying both `source_url:` and `source_path:` yields the both-fields warn. The finding fires the same in a wiki that is not inside a git repo.
2. `references/lint_checks.md` carries a row for the new `source_url`-form check and lists it in the correct severity bucket, with no stale row implying `source_url:` is unchecked.
3. The `### raw/ Frontmatter` subsection of `template_schema.md` states the legacy-`source_url`-value migration (in-repo → repo-relative `source_path:`; out-of-repo → excerpt plus locality note), and `rg` confirms the `skills/wiki/SKILL.md` capture bullet and the `wiki_import` capture step cite that rule rather than carrying their own copy of the migration steps.
4. An `auto_shaper_wiki.md` fixture: a raw sidecar carrying a `file://`-valued `source_url:` is surfaced as drift to route (origin left unchanged, not auto-rewritten), and a wiki whose `### raw/ Frontmatter` teaches the `source_url: file://…` form is surfaced for the user rather than preserved as a customization. The rewritten `preserve as-is` classification states the carve-out generally — a customization that contradicts canonical semantics is surfaced, an extending one is preserved — with the origin-field case as its illustration, so the rule is not written narrow to `### raw/ Frontmatter`. `rg "source_url.[- ]or[- ].source_path"` (the either-satisfies phrasing in both its space-delimited and hyphenated forms, the latter in the `<fix_raw_frontmatter_subsection_missing>` fix block) returns no match that reads as "either field alone satisfies the canonical shape".
5. `references/raw_taxonomy.md` no longer frames the origin field as `source_url`-only: the bucket table's origin column and the classification heuristics reference the two-field contract, and `rg` confirms the old `source_url`-only column phrasing is superseded.
6. Script unit tests under `tests/wiki/` cover the gap-1 fixtures and `tests/wiki/run_all.sh` passes.
