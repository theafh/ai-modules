# Intent guardrail for autonomous task operation

## Goal

Give the task family an optional intent guardrail that keeps autonomous AI writes from drifting a project away from its stated intention, and couple that guardrail to the autonomy features so its complexity is only paid for when it buys something. A project that turns on autonomous agents gains a falsifiable identity contract those agents are checked against; a project using the manual task chain takes on nothing new. The deliverable is a root `INTENT.md` contract, a branch-gated hook that hard-blocks edits to it, an intent-validation step wired into the autonomous writers, and a helper that derives and checks the contract.

## Context

The guardrail exists specifically to bound autonomous operation, so it is the safety floor the autonomous loops — including the [autonomous tree-shaper](task-family_autonomous-tree-shaper.md) — stand on. When no `INTENT.md` is present, the guardrail is inert and the task family behaves exactly as it does today — autonomy and its guardrail switch on together.

Two design questions are settled here. First, where the contract lives: by the filing rule that task-system material lives in `tasks/` while project-wide material lives in a root `UPPERCASE.md` doc, the intent contract is project identity (beyond the task system), so it lives at repo root as `INTENT.md`, a peer of the standing repo rules — not under `tasks/`, which the agents must be free to write. The base `task` skill already treats standing project instructions as a substrate tasks cite rather than copy, and `INTENT.md` is exactly such a standing doc. Second, the mechanism shape follows the wiki skill's schema approach — a base layer shipped with the skills plus a project-extensible layer that the skills read and enforce — but the artifact is a root contract, not a `tasks/` schema, because its content is project identity, not task-authoring convention. A separate task-authoring schema is deliberately not introduced: the base task rules already live in the skills, and a required schema doc would be the kind of tedious ceremony this family avoids.

## Approach

Create both artifacts and keep their roles separate. Create this repo's real, activating project contract at root path `INTENT.md`, populated for `ai-modules` rather than left as a placeholder. Also ship an inert reusable template at `plugins/ai_dev/skills/task_intent/assets/INTENT.template.md` with the same falsifiable structure — Core Purpose, DOES / DOES NOT domain boundaries, Key Invariants, Intentional Constraints — for other projects to copy or derive from. Validation activates only from a target repo's root `INTENT.md`; the helper template never activates validation by itself.

Wire the required pre-write step into the currently shipped autonomous writer, `plugins/ai_dev/skills/task_auto_check/SKILL.md`: before applying any autonomous task-file edit, validate the proposed change against `INTENT.md` when it exists, proceed only on a pass, and surface a conflict (leaving the work untouched) otherwise. Coordinate future autonomous writers by updating `tasks/task-family_autonomous-tree-shaper.md` and `tasks/task-family_autonomous-implement-loop.md` so each future skill must reuse the same helper-backed validation before autonomous writes when implemented; this task does not create nonexistent `task_auto_shaper` or `task_auto_implement` skill files. This validation is read-only and non-mutating, but it gates autonomous writes: it reports drift and stops the autonomous writer before any file edit; the hook is the separate hard block for edits to `INTENT.md` itself.

Add the native Claude hook package files at `plugins/ai_dev/hooks/hooks.json` and `plugins/ai_dev/hooks/intent_guardrail.sh`. `hooks.json` defines the Claude Code `PreToolUse` hook for `Edit|Write` and invokes the bundled script through the plugin root path, using `${CLAUDE_PLUGIN_ROOT}/hooks/intent_guardrail.sh` rather than a cwd-relative `./hooks` path. The script reads the hook JSON from stdin, extracts `.tool_input.file_path`, resolves the target repo root from the hook cwd, and exits 2 to block any edit to root `INTENT.md` unless the current branch matches `guardrail/intent-*`. Do not add or change legacy symlink-deployment hook config such as `hooks/claude-code-hooks*.json`, and leave `deployment/deployment.conf`'s Claude `disallow:**` rule unchanged. Document that this hard block deploys for Claude Code only, since some harnesses (Codex) expose no pre-edit hook — there, autonomous agents rely on the soft validation alone.

Add a user-facing `task_intent` skill at `plugins/ai_dev/skills/task_intent/SKILL.md` as the maintenance helper. It derives a draft `INTENT.md` from the codebase for human ratification on the guardrail branch, and validates supplied context (a task body, an edit batch, or the whole backlog) against the contract into a pass line or a damage-ordered conflict list. Register the skill in `plugins/ai_dev/README.md`, the root `README.md`, `plugins/ai_dev/.codex-plugin/plugin.json`, `plugins/ai_dev/.claude-plugin/plugin.json`, `.agents/plugins/marketplace.json`, and `.claude-plugin/marketplace.json`. Keep three layers distinct: the hard hook mechanically blocks contract mutation, the soft validation checks content against the contract, and the `guardrail/intent-*` branch is the human-only path where the contract itself changes under review.

## Acceptance

- This repo has a real root `INTENT.md` populated as the `ai-modules` project contract, and the helper ships an inert reusable template at `plugins/ai_dev/skills/task_intent/assets/INTENT.template.md`; both carry falsifiable Core Purpose, DOES / DOES NOT, Invariants, and Intentional Constraints sections, and validation reads only the target repo's root `INTENT.md`.
- The native Claude hook files named in Approach exist at `plugins/ai_dev/hooks/hooks.json` and `plugins/ai_dev/hooks/intent_guardrail.sh`, with no `hooks/claude-code-hooks*.json` legacy deployment config added or changed and `deployment/deployment.conf`'s Claude `disallow:**` symlink rule unchanged; an implementer-runnable fixture invokes that packaged hook/config path and shows a staged edit to `INTENT.md` exits blocked on a normal branch and allowed on a `guardrail/intent-*` branch.
- An intent-validation step is wired into `plugins/ai_dev/skills/task_auto_check/SKILL.md` and, on a staged task carrying a planted boundary violation, returns a conflict and leaves the task untouched; on a clean task it returns a pass. The follow-up task files `tasks/task-family_autonomous-tree-shaper.md` and `tasks/task-family_autonomous-implement-loop.md` name the same `INTENT.md` helper-backed pre-write validation as part of their future autonomous writer requirements, without this task creating those future skill files.
- With no `INTENT.md` present, a staged `task_auto_check` run that applies an otherwise-valid autonomous task-body repair completes exactly as before with no intent requirement, ceremony, or error, and a separate check confirms the manual create/check/implement chain gains no new requirement and emits no error.
- The hook's Claude-Code-only scope is documented alongside the soft-validation fallback for hookless harnesses; `make lint` passes and the hook, helper, and template are registered in the plugin README, metadata, and both marketplaces.
