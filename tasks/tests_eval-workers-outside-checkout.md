# Stage eval sandboxes outside the checkout and fail a pass whose worker reads the checkout

## Goal

Every eval runner that drives a worker through `micro_deploy.run_worker` stages that worker's sandbox under a fresh root from `worker_isolation.create_sandbox_root`, outside the repository checkout, the home directory, and any git repository, so no worker's working directory, Cursor workspace, or prompt path points into the checkout. Each pass also records a `checkout_unread` check beside `artefacts_read_from_micro_deployment`. That check fails the pass and names the path whenever the worker, or a helper it spawned, read, globbed, or named a path inside the checkout, which is where the harness's own `evals.json`, `grade.sh`, `README.md`, `RUNBOOK.md`, and fixtures live. The user-visible outcome: a verdict measures the skill working from its prompt, its sandbox, and its micro-deployment alone, and a worker that reaches the expectations or the grader it is scored against fails with the path named instead of passing.

## Context

- **Where sandboxes live today.** Most behavioural runners stage each pass inside the checkout. The Pattern A runners set `target = eval_dir / "sandbox"` under the harness's gitignored `workspace/` run directory, and wiki layer 2 stages each scenario through `tests/wiki/layer2/setup_scenarios.sh` into `tests/wiki/layer2/<scenario>/`, a fake `HOME` with the project inside it. Every prompt names the absolute sandbox path: `{workdir}` in each Pattern A `WORKER_PROMPT`, and `{sandbox_root}`, the fake home, and a `--report-path` inside the pass directory in `tests/wiki/layer2/build_prompt.py`. A worker therefore learns where its harness sits and can climb into it. `tests/language_humanizer/evals/run.py` and `tests/natural_language/evals/run.py` already stage every pass under `worker_isolation.create_sandbox_root`, which creates the root under the system temporary directory and raises its create-root refusal when the root resolves under the home directory or inside a git repository.
- **What workers read (recorded Cursor runs, 9 October 2026).** Each pass's `timing.json` carries `artefacts_read_from_micro_deployment.paths`, every path the worker read, globbed, or named in a shell command. All three records below show `"passed": true`, because `classify_out_of_set` in `tests/lib/micro_deploy.py` classifies only skill, agent, and style files by design. The run directories are gitignored local output that exists only on the machine that recorded them:
  - `tests/task_create/evals/workspace/run-20261009-210747/reconcile-recorded/timing.json`: the worker read `tests/task_create/evals/evals.json`, `tests/task_create/evals/grade.sh`, and `tests/task_create/README.md`, named `tests/task_create/evals/fixtures/`, and globbed `tests/task_create/evals/**/*`.
  - `tests/guardrail_audit/evals/workspace/run-20261009-211146/presence_gate/timing.json`: the worker globbed `tests/guardrail_audit/*.{json,md,sh}` and `tests/guardrail_audit/**/presence_gate/**`.
  - `tests/wiki/layer2/workspace/run-20261009-210409/AS-1/pass-1/timing.json`: the worker globbed `tests/wiki/layer2/**/AS-1/**/*`.
- **The read provenance this task extends.** [The micro-deploy task](archive/tests_micro-deployed-eval-workers.md) built `tests/lib/micro_deploy.py`. Its `run_worker` derives the read list from the worker's tool records, a spawned helper's included, and `classify_out_of_set` with `integrity_record` turns that list into the `artefacts_read_from_micro_deployment` record every runner fails a pass on.
- **Instruction files no read check can see.** `wiki/concepts/verification-surfaces.md`, under `### A worker inherits the host's instructions unless it is isolated`, records that a `claude -p` worker whose sandbox sits inside this repository runs under the repository's standing instructions through its ancestor walk. Those files arrive at startup rather than through a tool call, so only relocation keeps them from the worker.
- **Consumers that find paths through the sandbox's location.** Each Pattern A grader takes the sandbox path as an argument, and the host escape guards locate the checkout from their own script directory, so both work unchanged on a relocated sandbox. Two consumers would break:
  - `tests/task_auto_check/evals/grade.sh` reads `RESPONSE="$target/../response.txt"`, which after relocation points beside the root instead of into the run directory. Its transcript checks run only when that file exists, so they would stop running without failing. The `task_create` and `task_fix` graders fall back to the same path, but their runners export `RESPONSE_FILE`.
  - `tests/wiki/layer2/grade.py` sets `sandbox_root = LAYER2_ROOT / scenario["sandbox_path"]` and compares the worker's reported paths against it in `no_files_outside_sandbox` and `response_text_contains_path`.
- **Shared surfaces.** The open tasks whose Approach rewrites one of these `run.py` files edit the same files, among them the per-runner `tests_*-parallel-evals.md` tasks, the wiki layer 2 runner-dedup task, and the agent_spinner runner-modes task. `tests/lib/eval_runner.py` leaves staging to its caller ("Job callables own sandbox staging"), so the sandbox-root change lands in whichever staging code exists when this task is implemented, and either order absorbs it.

## Approach

1. **Relocate the sandbox.** Every runner that calls `micro_deploy.run_worker` and does not yet create its sandbox through `create_sandbox_root` adopts it. Derive that set as the files `rg -l 'micro_deploy\.run_worker' tests -g run.py` lists minus those `rg -l 'create_sandbox_root' tests -g run.py` lists. Each pass creates its own root with `worker_isolation.create_sandbox_root`, under a prefix naming the harness, and stages into it what the runner stages into `eval_dir / "sandbox"` today. The sandbox project inside the root (`proj`, `sandbox_proj`, or `sandbox_repo`) becomes the worker's `cwd`, micro-deploy's sandbox project, and the `{workdir}` the prompt names, and the root holds that project and whatever else the stager writes beside it. Use the root's resolved path throughout, because on macOS the temporary directory resolves through `/private`, and the paths in prompts, records, and grader comparisons must match what the worker's `pwd` prints. Grade the relocated sandbox in place, then copy the post-run tree with its symlinks into the run directory where it sits today (`<eval_dir>/sandbox/`), and remove the root on every exit path, a cache hit and a failed worker or grader included.
2. **Relocate wiki layer 2.** Teach `tests/wiki/layer2/setup_scenarios.sh` to stage one scenario into a directory its caller names, and have `run.py` stage each pass into its own fresh root in place of restaging `tests/wiki/layer2/<scenario>/`. Pass that root to `build_prompt.py --sandbox-root`, point `--report-path` at a file inside the root and copy that file into the pass directory after the worker returns, and take `sandbox-snapshot/` from the root before removing it. Record the root as `sandbox_root` in the pass's `timing.json`, and have `grade.py` use the recorded root for `no_files_outside_sandbox` and `response_text_contains_path`, naming that root in the `no_files_outside_sandbox` evidence line.
3. **Pass the response path explicitly.** Have the `task_auto_check` runner export `RESPONSE_FILE`, as the `task_create` and `task_fix` runners do, and rewrite `RESPONSE="$target/../response.txt"` in `tests/task_auto_check/evals/grade.sh` to `RESPONSE="${RESPONSE_FILE:-$target/../response.txt}"`, the form the other two graders use.
4. **Fail a pass that reads the checkout.** Add to `tests/lib/micro_deploy.py`, beside `classify_out_of_set`, a classifier that returns every read path resolving inside the repository checkout (`REPO_ROOT`), with relative paths resolved against the worker's `cwd` the way `classify_out_of_set` resolves them. A path that keeps an unexpanded variable or a leading `~` cannot be placed, so it stays unflagged. `run_worker` returns the flagged paths on `WorkerRunResult`, so a spawned helper's checkout reads count the way its artefact reads do. Every runner that records `artefacts_read_from_micro_deployment` also records `checkout_unread` beside it in the pass's `timing.json`, holding `passed` and the flagged paths as `inside_checkout`, and fails the pass when that list is non-empty. Wiki layer 2's `grade.py`, which fails a pass on `artefacts_read_from_micro_deployment` from `timing.json`, fails it on `checkout_unread` the same way. Relocation leaves no legitimate checkout path in a pass, so the check carries no in-set exemption, and a runner whose sandbox still sits inside the checkout fails its first pass. Relocation and the check therefore land together for every runner.
5. **Tests.** Extend `tests/lib/test_micro_deploy.py`, with no model call, so it proves the following:
   - The checkout classifier flags a read of a harness's `evals/evals.json`, `evals/grade.sh`, `README.md`, and `RUNBOOK.md` and of a file under its `evals/fixtures/`, a glob rooted in a harness directory, and a shell command that names a checkout path, a `cd` into the checkout included.
   - It flags the three 9 October 2026 shapes from Context, rebuilt against the checkout root: the `task_create` reads, the `guardrail_audit` globs, and the wiki layer 2 `AS-1` glob.
   - It leaves unflagged a read inside a sandbox project under a `create_sandbox_root` root, a relative path resolved against that project, a scratch-home path, `/dev/null`, and a path that keeps an unexpanded variable.
   - `run_worker` returns the flagged paths for a recorded Cursor chat transcript and for a recorded Claude stream in which a spawned helper reads a checkout path.
   - The `checkout_unread` record carries `passed: false` and the flagged paths for a non-empty list, and `passed: true` with an empty `inside_checkout` list otherwise.
6. **Docs.** Rewrite each affected passage in place so one statement of each rule remains:
   - `TESTING.md` `## Test Design Principles`, item **Stage a sandbox per scenario.**: rewrite its opening sentence, "Every harness operates on a fresh temporary tree, never on the working checkout.", so it also states that a behavioural worker's sandbox sits under a root outside the checkout, the home directory, and any git repository, and that a pass fails when its worker reads, globs, or names a path inside the checkout.
   - The lockstep paragraph naming `artefacts_read_from_micro_deployment` in `tests/CLAUDE.md` (`### Model policy`) and `tests/AGENTS.md` (`### Skill and agent loading`): rewrite it so it states both read checks, `checkout_unread` and what fails it included.
   - The `tests/CLAUDE.md` `### Worker isolation` sentence beginning "Runners that import the helper take their sandbox roots" and the `tests/AGENTS.md` `### Verdict cache, timeouts, isolation` passage ending "Those sandboxes come from `tests/lib/worker_isolation.py`.": state that every behavioural runner takes its sandbox root from `create_sandbox_root`, while `isolation_args` stays with the runners that pass it today.
   - The `## Vendor switch` paragraph of `tests/README.md`: name `checkout_unread` beside `artefacts_read_from_micro_deployment`.
   - The `tests/CLAUDE.md` `### Parallel workers` entry for `tests/wiki/layer2/run.py` ("one sandbox directory per scenario") and the `tests/wiki/README.md` passages that place a run's sandboxes under `tests/wiki/layer2/<scenario>/` (the layout tree's `L2-1/ ... L2-5/` entry among them): describe the per-pass root.

**Out of scope:**

- `tests/trigger_evals/`, which measures the deployed skill tree by design and records no read provenance.
- Moving the scaffolding a stager writes beside the sandbox project (start markers, sha256 baselines, isolated host-tree copies) out of the root, since it moves with the root and the checkout check covers the checkout only.
- Adding `isolation_args` to runners that do not pass it today, since relocation changes where a sandbox lives and leaves each worker's arguments as they are.

## Acceptance

- `python3 tests/lib/test_micro_deploy.py` passes with the cases Approach **Tests.** lists.
- Every file `rg -l 'micro_deploy\.run_worker' tests -g run.py` lists also appears in the output of `rg -l 'create_sandbox_root' tests -g run.py`, and `rg -n 'create_sandbox_root\(' tests -g run.py` shows each of those runners passing a prefix that names its harness.
- `rg -l 'artefacts_read_from_micro_deployment' tests -g run.py -g grade.py` and `rg -l 'checkout_unread' tests -g run.py -g grade.py` list the same files.
- `rg -n 'RESPONSE="\$target/\.\./response\.txt"' tests -g grade.sh` prints nothing, and every harness whose `grade.sh` reads `RESPONSE_FILE` exports it from its `run.py`.
- On the default vendor (Cursor, run without `--vendor`), `python3 tests/task_create/evals/run.py reconcile-recorded --force`, `python3 tests/guardrail_audit/evals/run.py presence_gate --force`, and `python3 tests/wiki/layer2/run.py --scenario AS-1 --passes 1` each run one pass after the change, followed by a second, cached run of `python3 tests/task_create/evals/run.py reconcile-recorded`. These are the three evals whose 9 October 2026 records read their harness, and each pass's `timing.json` in its run directory holds the recorded measurement:
  - The read paths show the sandbox under a root in the system temporary directory, and `checkout_unread` is present and passes with an empty `inside_checkout` list.
  - None of the roots these runs created remains afterwards, the cached run's included, and each executed pass's run directory holds its post-run sandbox copy (`<eval_dir>/sandbox/` or `sandbox-snapshot/`).
  - When a worker still reaches the checkout, its pass fails with `checkout_unread` naming the path, and the report names that path and the vendor instead of re-running for a clean draw.
- The `AS-1` pass's `timing.json` records a `sandbox_root` under the system temporary directory, its `prompt.md` names no path inside the checkout, and its `grading.json` passes `no_files_outside_sandbox` with evidence that names that recorded root.
- `TESTING.md`'s **Stage a sandbox per scenario.** item states the root outside the checkout for a behavioural worker's sandbox and the failing read back into the checkout, and no other `TESTING.md` passage restates that rule. `rg -n 'checkout_unread' tests/CLAUDE.md tests/AGENTS.md tests/README.md` prints a match in each file, and the `tests/CLAUDE.md` and `tests/AGENTS.md` paragraphs state the same rule.
- `rg -n 'take their sandbox roots and their worker' tests/CLAUDE.md` and `rg -n 'one sandbox directory per scenario' tests/CLAUDE.md` print nothing, and `tests/CLAUDE.md` `### Worker isolation`, `tests/AGENTS.md` `### Verdict cache, timeouts, isolation`, and the `tests/wiki/README.md` layout tree describe the sandbox root the way Approach **Docs.** names.
