# Add Antigravity coverage to harness_portability and drop Gemini CLI as a target

## Goal

Update the `harness_portability` skill so it covers **Google Antigravity** as a first-class target harness with verified current facts, rewrites the now-stale Gemini-CLI-derived claims so they describe Antigravity where the live Google surface is meant, and records one short note that Gemini CLI is dropped as a supported target because its consumer surface is retired.

The user-visible outcome is that an agent consulting the skill treats Antigravity — the live Google surface delivered as an IDE, a CLI, and the 2.0 desktop app — as *the* Google target, with correct config paths and correct skill / agent / hook / plugin models, and no longer encodes the retired consumer Gemini CLI as a live deploy target or carries Gemini CLI's strict-frontmatter behaviour as if it were Antigravity's.

## Context

**Why this change.** Google's consumer Gemini CLI surface was retired on 18 June 2026 for Google AI Pro, Google AI Ultra, and free individual usage, while Standard/Enterprise and paid API-key access stay outside this task's consumer-target scope ([transition blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/), [gemini-cli discussion #27274](https://github.com/google-gemini/gemini-cli/discussions/27274)). The `google-gemini/gemini-cli` repo stays active as a spec, but the live Google surface for this task is now **Antigravity** — a Go rewrite that shares the `~/.gemini` lineage and inherited Skills, Hooks, Subagents, and Extensions (renamed "plugins"). So the skill's Gemini coverage is both stale (it points agents at a retired consumer serving target) and mis-scoped (Antigravity, not Gemini CLI, is the live surface). The skill's current treatment of Gemini CLI as an agent-definition-only, strict-schema surface is doubly out of date.

**Current skill passages to rewrite in place** (all in `plugins/ai_dev/skills/harness_portability/SKILL.md`): the `description:` frontmatter; the `<target_harnesses>` scope clause; the `<policy>` union-of-native-fields rule's `reach a strict-schema target through a generated variant instead of the shared file` clause; the Gemini-naming `<agent_definition_surfaces>`, `<frontmatter_schema_tolerance>`, `<tool_name_namespaces>`, `<readonly_agent_enforcement>`, `<reasoning_effort_portability>`, and `<native_fields_and_deploy_bridges>` sections; and the non-Gemini harness enumerations in `<codex_model_inheritance>`, `<cross_harness_artefact_discovery>` `<opencode_isolation_switches>`, `<hook_portability>` `<dual_harness_layout>` and `<shared_hook_scripts>`, `<review_checklist>` `<artefact_discovery>`, and `<review_checklist>` `<dual_harness_hooks>`. Antigravity is absent from the skill entirely. The skill already models a diverging full target (OpenCode) through a `<cross_harness_artefact_discovery>` block, an `<opencode_plugin_hooks>` hook block, and per-surface agent coverage — that treatment is the template for Antigravity.

Giving `.agents/` an owner changes what one neighbouring passage means. `<opencode_isolation_switches>` currently presents `OPENCODE_DISABLE_CLAUDE_CODE=1` as a Claude-compatibility toggle that "also stops `.agents/skills` discovery", closing on "everything a sibling tool deployed into `~/.claude`". Once `.agents/` is documented as Antigravity's native workspace tree, that same Claude-named switch scopes away the Google harness's own artefacts — a materially different fact for an operator than the passage now conveys.

**Antigravity facts to encode.** Each carries a confidence flag; the skill's own `<policy>` rule — *"State the provider documentation source or the verification gap when a change depends on harness-specific execution, initialization, configuration, filesystem, environment, permission, or tool-discovery behavior"* — governs how an unconfirmed fact is written, so anything below marked *verify* is encoded with its source or as an explicit gap, never as settled fact.

- **Global and workspace config paths** *(the split resolved at implementation time: it runs per artefact class, not per product)*: the workspace tree is uniform — `.agents/{skills,agents,rules,plugins}/` plus `.agents/hooks.json` and `.agents/mcp_config.json`, with `.agent/` back-compat on the skills and rules pages and `_agents/` on the plugins pages. Globally, exactly two classes diverge by product: skills three ways (`~/.gemini/config/skills/<skill-folder>/` on `/docs/skills`, `~/.gemini/antigravity/skills/<skill-folder>/` on `/docs/ide/skills`, `~/.gemini/antigravity-cli/skills/` on `/docs/cli/plugins`) and plugins two (`~/.gemini/config/plugins/` for 2.0 and the IDE against `~/.gemini/antigravity-cli/plugins/<plugin_name>/` for the CLI). Everything else is single-rooted under `~/.gemini/config/` — `agents/`, `hooks.json`, `mcp_config.json`, `sidecars/` — with global rules as the single `~/.gemini/GEMINI.md` one level above `config/` and CLI preferences at `~/.gemini/antigravity-cli/settings.json`. So "one global deploy reaches IDE, CLI, and 2.0" holds for agents, hooks, MCP, and sidecars and fails for skills and plugins; the skill states that resolution with its per-page sources rather than carrying it as an open gap. The `~/.gemini/antigravity` and `~/.gemini/antigravity-cli` trees still double as transcript/artifact or CLI profile paths depending on the page, so the skill must distinguish config/customization roots from transcript/artifact output paths instead of treating the whole per-product tree as non-config.
- **Skills** *(confirmed, [antigravity.google/docs/skills](https://antigravity.google/docs/skills), [antigravity.google/docs/ide/skills](https://antigravity.google/docs/ide/skills), and [antigravity.google/docs/cli/plugins](https://antigravity.google/docs/cli/plugins))*: `SKILL.md` + `name`/`description` frontmatter under the Agent Skills open standard, model-invoked with progressive disclosure; workspace `.agents/skills/<skill>/`; global `~/.gemini/config/skills/<skill>/` in Antigravity 2.0 docs, `~/.gemini/antigravity/skills/<skill>/` in IDE docs, and `~/.gemini/antigravity-cli/skills/` in CLI docs. The workspace `.agents/skills/` path is Antigravity's native skill root, and the portability point is the convergence with Codex project-level skill deployment and OpenCode discovery on that same path rather than Antigravity adopting a foreign directory.
- **Subagents** *(confirmed schema, [antigravity.google/docs/subagents](https://antigravity.google/docs/subagents); re-verify the full field list)*: `.agents/agents/<name>.md` or `.agents/agents/<name>/agent.md`; global `~/.gemini/config/agents/…`; bundled `plugins/<plugin>/agents/`. Frontmatter: `name`, `description`, `tools[]` (native tool names; an unmapped/misspelled name causes a runtime **hang**, not a load rejection), `model` (`inherit`|`flash`|`pro`, default `inherit`), `commandExecutionPolicy` (`off`|`auto`|`eager`|`sandbox`, default `sandbox`), `mainAgent`/`subagent` booleans (both default `true`), `mcpServers` (camelCase), `skills`/`plugins` dependency arrays. A `flash_lite` tier plus `hidden`/`inheritMcp` circulate in community docs but appear in neither the subagents frontmatter table nor the model list, so they are unsupported rather than native. The CLI reads the same definitions from the same roots and refers back to this one specification, so the subagent schema is unified across products.
- **Tool namespace** *(one vocabulary, two partial published views — corrected against the docs at implementation time)*: the subagents page's own `tools` example names `view_file`, `grep_search`, and `run_command`, and the Hooks page's matcher list adds `write_to_file`, `replace_file_content`, `multi_replace_file_content`, `list_dir`, `find_by_name`, `search_web`, `read_url_content`, `manage_task`, `schedule`, `list_permissions`, `ask_permission`, `invoke_subagent`, `define_subagent`, `send_message`, `manage_subagents`, `ask_question`, and `generate_image`. Neither page states that the allowlist and matcher vocabularies differ, and no canonical tool list is published anywhere in the docs — the permissions and CLI reference pages carry none either — so treat the two lists as partial views of one vocabulary rather than two namespaces. The `read_file` and `edit_file` names that circulate for Antigravity allowlists appear on neither page. The absent registry is what makes the documented bad-tool-name **runtime hang** matter: no name can be validated before shipping, so copy one verbatim from a published list. Read-only enforcement = a `tools` allowlist over the read-only names that vocabulary sources (`view_file`, `grep_search`) plus `commandExecutionPolicy` (`off`/`sandbox`), the Antigravity equivalent of the levers `<readonly_agent_enforcement>` already lists per harness.
- **Hooks** *(confirmed, [antigravity.google/docs/hooks](https://antigravity.google/docs/hooks))*: declarative `hooks.json` in `.agents/` (workspace) or `~/.gemini/config/` (global); events `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`; stdin/stdout JSON with **camelCase** fields (`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`); `PreToolUse` returns a `decision` of `allow`|`deny`|`ask`|`force_ask`; the same `hooks.json` locations, five events, camelCase envelope, and decision values are given identically by the 2.0 and IDE hook pages, so hooks do not follow the per-product root split. **Divergence trap to encode:** the event names are Claude's while nothing behind them is, and that is the trap that matters for a repo-to-target deploy — a `PreToolUse` hook that works under Claude reads a snake_case envelope and blocks by exit code, so deployed unchanged to Antigravity it parses the wrong field names and exits into a handler expecting a `decision` on stdout, failing open silently. Matching event names are the reason to check the envelope, not a reason to skip the check. Unlike OpenCode's code-only bridge, Antigravity hooks are declarative, so they sit closer to the Claude/Codex JSON-config model.
- **Plugins (bundling unit)** *(confirmed bundle, [antigravity.google/docs/plugins](https://antigravity.google/docs/plugins); mapping undocumented)*: `plugin.json` under `.agents/plugins/` or `~/.gemini/config/plugins/`, bundling skills + rules + MCP + hooks (and agents via `plugins/<plugin>/agents/` per the subagents doc, though the plugins overview omits agents — a documented inconsistency). The bundle also carries sidecars, per the sidecars fact above. Migrating an existing Gemini CLI setup into Antigravity is out of this skill's scope — the skill deploys this repo to a target rather than converting one target to another — so no extension-to-plugin conversion guidance belongs in it. `.agents/plugins/` is a shared directory rather than an Antigravity-only one: this repo's own Codex marketplace registration sits at `.agents/plugins/marketplace.json`, so one workspace directory carries two harnesses' differently-schemad manifests — the same discovery-collision class `<cross_harness_artefact_discovery>` exists to record.
- **Rules / workflows** *(confirmed at implementation time against `/docs/rules-workflows`)*: workspace rules are markdown under `.agents/rules/` (back-compat `.agent/rules/`) capped at 12,000 characters each, with four activation modes named Manual, Always On, Model Decision, and Glob; global rules are the single `~/.gemini/GEMINI.md`; workflows are markdown files in either scope under the same 12,000-character cap, invoked as `/workflow-name` slash commands. Both a project's `GEMINI.md` and its `AGENTS.md` are parsed for rule constraints, and no page states which wins when the two disagree — so precedence stays unresolved rather than being asserted either way.
- **Sidecars** *(confirmed at implementation time against `/docs/sidecars`)*: supervised long-running background processes, each its own directory holding a `sidecar.json` naming the command, restart behavior, and environment, discovered at `~/.gemini/config/sidecars/` standalone and `~/.gemini/config/plugins/<pluginName>/sidecars/` inside a bundle, addressed as `<pluginName>/<sidecarName>`. This is the one Antigravity component that keeps running between turns, so it is a process-lifecycle surface rather than a config file.
- **SDK lifecycle hooks** *(confirmed at implementation time against `/docs/sdk/overview`)*: the Antigravity SDK (`pip install google-antigravity`, Python only) carries its own programmatic lifecycle hooks — three categories (inspect, decide, transform) across nine lifecycle points — which are in-process Python callbacks for an SDK-built agent rather than a config file the IDE or CLI reads, so they are a second hook surface beside the declarative `hooks.json` rather than a replacement for it.

**Verification gaps to carry as gaps, not facts** — the highest-value one being frontmatter strictness: Gemini CLI's Node loader rejected a single unknown frontmatter key; whether Antigravity's Go loader does the same is **unconfirmed and the evidence leans tolerant** — official subagents/skills docs are silent, the only documented Antigravity validation gotcha is the bad-tool-name runtime hang, and the fixed-allowlist "unexpected fields" behaviour that circulates is VS Code's own SKILL.md editor linter ([microsoft/vscode #294520](https://github.com/microsoft/vscode/issues/294520)), which may surface cosmetic warnings inside Antigravity's editor but is not a runtime load rejection and never names Antigravity. Three further gaps survived implementation-time verification and stay recorded as gaps because the docs are genuinely silent, not because they went unchecked: whether plugin-bundled agents register at all, since the subagents page names `plugins/<plugin_name>/agents/` while both the 2.0 and IDE plugins pages omit agents from the component list; which of a project's `GEMINI.md` and `AGENTS.md` wins when they disagree; and whether Antigravity discovers artefacts from another harness's directories (`.claude/skills/`, `.claude/agents/`) — no page reviewed mentions such discovery and none documents an environment variable or config key that scopes it, so the skill states the own-roots-only expectation with that absence as its evidence and directs a confirmation on the installed build. That last one is the cell `<foreign_directory_adoption>` and `<agent_definition_surfaces>` already fill for every other harness, and which the `<policy>` artefact-discovery rule and the `<review_checklist>` `<artefact_discovery>` "any available isolation switch is documented" clause both require of a full target.

**Shared surfaces.** [deployment_opencode-hook-bridge.md](../deployment_opencode-hook-bridge.md) co-edits the same skill's hook-portability guidance; its `**OpenCode-specific caveats to encode and document**` block owns the OpenCode hook model and caveats that this task must preserve while adding Antigravity hooks. When adding the `<antigravity_hooks>` block beside `<opencode_plugin_hooks>`, preserve or reconcile the OpenCode `tool.execute.before` bridge-plugin model, subagent-bypass limitation, and inert `permission.ask` caveat as the canonical OpenCode passage, while keeping Antigravity's declarative `hooks.json` model distinct. [deployment_antigravity-target-gemini-retire.md](../deployment_antigravity-target-gemini-retire.md) owns the live deployment-script work that retires the `gemini` target and removes the current Gemini generator helpers, so this task treats Gemini CLI generator facts only as retired-consumer-surface history and cites the sibling as the owner of deploy-target retirement rather than as current deployment code for the skill to describe. This task's per-page Antigravity root split supersedes that sibling's older "transcript/artifact output paths, not config" and "one deploy reaches IDE, CLI, and 2.0" framing for skill documentation; the deployment task reconciles those deployment paths when it builds or re-verifies.
