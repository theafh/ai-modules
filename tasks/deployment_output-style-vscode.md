# Deploy the output style to VS Code Copilot

## Goal

GitHub Copilot in VS Code receives the repository's output style as a generated instructions file, deployed at whichever scope the run selects and needing no activation key at either. Under `--global` it lands in Copilot's own user-profile instructions root and applies across every workspace. Under `--project-dir` it lands in that project's own instructions directory and applies to work in that repository. This is the cheapest of the non-Claude targets, since deployment and activation are the same act in both scopes.

## Context

This builds on [the Claude groundwork task](archive/deployment_output-style-claude-groundwork.md), which shipped the repo-root source directory, the `style` artefact type, and the deploy-log restore behaviour. This task adds one target.

The wiki records the mechanism in [system prompt substitution across harnesses](../wiki/comparisons/system-prompt-substitution-across-harnesses.md). The essentials: instructions files combine rather than compete, the user-profile instructions root applies across every workspace and adds to repository and organization guidance, since Copilot combines applicable user and repository instructions without a general precedence order between instruction files (VS Code's custom instructions reference), and nothing has to be switched on for a file placed there to take effect. VS Code is append-only, so the deployed prose competes with default guidance rather than displacing it, which the docs should say plainly.

One trap belongs in the implementation. Copilot also reads a rules folder and a `CLAUDE.md` from the Claude configuration tree, and the documentation presents that path alongside its own. Those are adoption roots, and the standing rule in the harness portability skill's policy is to deliver a per-harness variant into the target's own native root and treat adoption as contamination. Writing the variant into the Claude tree would put one file in front of two harnesses and hand VS Code a Claude-shaped artefact, so the deploy writes only into Copilot's own instructions root.

## Approach

Generate a VS Code variant of the style and write it as a single Markdown file, resolving the destination from the script's existing Copilot directory variable rather than a hardcoded path so the same code serves both scopes. Under `--global` that is Copilot's user-profile instructions root, `~/.copilot/instructions`. Under `--project-dir` it is that project's own instructions directory, `${VSCODE_COPILOT_DIR}/instructions`, which resolves to `<project>/.github/instructions` because `deployment/deployment.sh` sets `VSCODE_COPILOT_DIR="${PROJECT_DIR}/.github"` in project mode.

Refresh the wiki pages this task edits through the wiki skill family rather than editing them directly, landing each required wording in place at the site named. The wiki's [GitHub Copilot in VS Code](../wiki/entities/github-copilot-vs-code.md) page records the mechanism today. Both scopes take the `*.instructions.md` form: VS Code's custom instructions reference documents `~/.copilot/instructions/**/*.instructions.md` for user modular instructions and `.github/instructions/**/*.instructions.md` for project targeted instructions. The entity page already records that form for the project scope only, naming `~/.copilot/instructions` for the user profile without a filename form, so the user-scope form comes from the reference and is not yet on the page. Write `${VSCODE_COPILOT_DIR}/instructions/${name}.instructions.md` at either scope, and record that filename at both scopes on the entity page, dated to the verification, so the next reader does not repeat the check. In that same edit, rewrite that page's `### Instruction roots` sentence that places the user-profile root "at the top of the documented precedence, above repository and organization instructions" in place, keeping its cross-workspace reach, so it states that the user-profile root applies across every workspace and that Copilot combines applicable user and repository instructions with no general precedence order between instruction files. Two further statements on that page take the same wiki-family pass. In `### Instruction roots`, the sentence "The `chat.instructionsFilesLocations` setting adds further workspace locations." becomes a statement that the setting adds further search locations beside the roots listed above and that its documented default map already covers the workspace and user roots, `~/.copilot/instructions` and `~/.claude/rules` among them. In `### Adoption of the Claude tree`, the sentence "Unlike every other adopter here, VS Code offers per-path switches for its **Local** harness." becomes a statement that VS Code offers per-path switches over its instruction and hook locations, and the sentence "Those switches configure the Local harness only." becomes a statement that `chat.instructionsFilesLocations` configures instruction locations the editor discovers and forwards to Agent Host harnesses, Copilot included per VS Code's `migrate-customizations` page (read 25 November 2026), while `chat.hookFilesLocations` does not configure Copilot hook discovery. In that same section, the sentence that ends "but only the named key is documented." becomes a statement that VS Code forwards instruction files discovered in additional configured locations to Agent Host harnesses, including Copilot, so `chat.instructionsFilesLocations` does reach Copilot discovery and setting `~/.claude/rules` to `false` closes that rules-folder route for Copilot. Where the project-scoped file supports an `applyTo` glob, write the value that scopes it to every file rather than leaving the field out, so the rule is unambiguously always-on.

Generate rather than copy. Strip the Claude frontmatter, which this target does not implement, and rewrite the `<engineering_behavior>` element that names Claude's `keep-coding-instructions` mechanism, following `generate_cursor_style_rule` in `deployment/deployment.sh`, which replaces that element wholesale. The style source carries no `$VAR$` token, so no `replace:` rule applies to it.

Narrow the editor-side adoption of the Claude tree on `--global` alone, as hygiene rather than a closed route. VS Code reads user-level instructions from `~/.claude/rules` as well as its own root, and `chat.instructionsFilesLocations` maps a path to a boolean where a `false` disables it even when it is a documented default: `promptSourceFolders` in `src/vs/workbench/contrib/chat/common/promptSyntax/config/config.ts` (read at tag `1.142.0`) keeps each default folder only when `value[defaultFolder.path] !== false`, so a `false` entry removes a documented default rather than merely adding a location. The map's documented default already includes `~/.claude/rules`, per VS Code's `ai-settings` reference, and VS Code's `migrate-customizations` page states that "VS Code forwards files discovered in additional configured locations to Agent Host harnesses, including Copilot" and that "Additional locations supplement the harness's built-in locations without removing them" (both quoted from that page, read 25 November 2026), so setting that path to `false` removes it from what the editor forwards and closes the `~/.claude/rules` route for Copilot. This merge still closes no route for this style: Copilot's adoption list excludes `~/.claude/output-styles`, so a Claude style never arrived this way. The cost it carries is that the user's own Claude rules stop loading in the Local harness and stop reaching Copilot through the editor's forwarding, accepted in exchange for keeping Claude-tree instructions out of both views. Merge `{"~/.claude/rules": false}` into the user's VS Code settings file through `merge_settings_map_entries`, the entry-grain settings-map helper already defined in `deployment/deployment.sh` and already exercised with this exact key in `tests/deployment/script_tests/vscode_hook_run.sh`; `merge_json_key` supplies only the prior capture and restore log shape, since it writes the whole key. That file is `$(dirname "$VSCODE_PROMPTS_DIR")/settings.json`, which resolves to `~/Library/Application Support/Code/User/settings.json` on macOS and `~/.config/Code/User/settings.json` on Linux. The `vscode` `backup_roots` list does not grow for it: a merge writes one key into one existing file rather than copying a tree, so the deploy log's prior capture and restore carries the undo, and `logged_path_scope` already derives `global` for that directory through its `"vscode|${vscode_prompts_root%/*}"` root, so a scoped uninstall still matches the entry. That helper captures the prior value on first write and restores it on uninstall, and narrows the merge to that one path so every other entry the user set survives. A `--project-dir` run writes no settings key and leaves that route as it found it, since the file it would touch is the user's own VS Code settings outside the project. The hook half of the same adoption landed without a settings write in [deployment_vscode-hook-routing.md](archive/deployment_vscode-hook-routing.md), because no editor setting is documented to close that route, so this style merge is the first deploy-path caller of that helper.

Rewrite [Output style delivery design](../wiki/concepts/output-style-delivery-design.md)'s `### What the deploy writes per target` in place so its `Copilot in VS Code` row states both destinations and the settled filename (`~/.copilot/instructions/natural-language.instructions.md` at `--global`, `.github/instructions/natural-language.instructions.md` at `--project-dir`, body only), records the `chat.instructionsFilesLocations` key as a `--global` settings write beside the style's own no-activation-key delivery, and carries the shape `file plus key at --global; file only at project scope`; and so the built-rows paragraph beneath that table (opening `Claude, Cursor, and Antigravity are the built rows` and closing `Every other row stays per-target delivery work`) names Copilot in VS Code among the shipped rows. [The Antigravity style task](archive/deployment_output-style-antigravity.md) has already landed its edit to that paragraph, so read it as it stands and keep every row it names, Antigravity's included. Replace the existing text at each site rather than adding a second account beside it.

**Out of scope:**

- Delivering the style through a Copilot agent plugin, which has no instructions component, so its only routes are a selectable agent or an on-demand skill and neither is standing.
- Writing anything into the Claude configuration tree to reach this target, which the **Context** rejects as adoption rather than delivery.
- Realigning the two passing mentions of this mechanism outside the entity page: `wiki/procedures/isolating-vs-code-from-foreign-config.md`, whose sentence records that `chat.instructionsFilesLocations` reaching the Copilot harness "the same way is unverified", and `wiki/concepts/foreign-directory-adoption.md`, which carries the same claim in its **not verified** form. The entity page is the canonical home for this harness's behaviour and is the page this task edits, so the `## Approach` wiki pass and the page-anchored `## Acceptance` item stay scoped to it; bringing the other two pages into line with it belongs to `wiki_fix`, which owns the wiki's own consistency pass.

- A dry run under `--project-dir` reports exactly one file write, into that project's `.github/instructions/` directory, and it touches nothing under the home directory and reports no `chat.instructionsFilesLocations` merge.
