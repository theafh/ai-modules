# Keep the task body a resolved, general, forward spec at an implementable density

## Goal

Four authoring rules for the task body get a sharpening pass, so a body carries the resolved, general, forward-looking spec and stays dense enough to implement from. Three tighten rules that already shipped; the fourth is new and bounds them.

- **Resolve what you can derive.** Before labeling a decision open, the agent exhausts the resolution paths available at authoring time — the cited skills, the codebase, the project's standing knowledge. A fork answerable from that material is not genuinely open and gets decided; labeling open stays the last resort for a choice that genuinely needs input the agent cannot derive, and the one-open-decision ceiling stands.
- **Generalize from the motivating instance.** When a task is mined from a concrete episode to improve a reusable artifact — a skill, a framework, a shared rule — the unit of meaning to keep is the general lesson, not the episode's specifics. The agent writes the general rule and demotes the originating instance to a brief motivating illustration, leaving out instance and session detail that does not generalize.
- **Keep rejected-option debate out.** The body states the current state (what exists, and what is not there yet) and the target (what to add, and how). The rationale for options the agent weighed and rejected lives where design rationale belongs — the change's own commit or pull-request description, or a wiki page when it is durable design knowledge — not in the task an implementer follows.
- **Compact only to the implementable floor.** A body is written compact, and compression stops at the floor where a one-shot implementer can still act without re-deriving what was dropped. Past that floor, compression is a defect rather than economy: clauses stacked until the logic between them is lost, an edit site named without the shape of the change, a rule given without the one example that fixes its meaning. Each such gap is filled by a guess, and a guess is where a wrong or incomplete implementation enters. This rule is the counter-weight to the three above — they move residue out of the body, and it keeps that removal from cutting into the detail the work needs.

## Context

The first three rules each extend a rule that already shipped into the base `task` skill, so each is a follow-up that sharpens an existing rule. The fourth is new. All edit sites are in `plugins/ai_dev/skills/task/SKILL.md`; siblings inherit through `<authority>`.

That rule set the ceiling and "resolve every either/or before the file is written" but no test for what makes a decision *genuinely* open; this adds the exhaust-derivable-resolution test. Edit site: `<body>` **Decide or label**.
- **Generalize from the motivating instance** reconciles two shipped rules for a case neither covers: [task-skill_lossless-conversion-check.md](archive/task-skill_lossless-conversion-check.md) preserves "Every relevant unit of meaning in the source", and [task-skill_gather-altitude-probe.md](archive/task-skill_gather-altitude-probe.md) makes an incident-shaped request "default to the point-fix". When the source is an episode mined to improve a reusable artifact, the relevant unit is the general lesson and the point-fix under-reaches. Edit sites: the `<gather>` altitude paragraph (the home of the new statement, since it already decides point-fix vs general), the `<lossless_conversion>` contract (which references that statement), and the `<body>` **Illustrate** rule the demotion leans on.
- **Keep rejected-option debate out** narrows [task-skill_positive-task-body-rule.md](archive/task-skill_positive-task-body-rule.md). That rule's "Write the body positive and action-oriented" welcomes, among negatives, "a deferred or explored alternative"; this narrows the explored-alternative allowance so a brief non-goal or guardrail stays while the rejected-options rationale moves out of the task. - **Compact only to the implementable floor** has no prior task. It operationalizes the base skill's self-sufficiency bar (the `<single_shot_ready>` pitfall) and sharpens the `<readiness_checklist>`'s **Ambiguity / under-specification** item, which today catches missing requirements but not prose compressed past the point of reliable execution. Edit sites: a new rule in the `<body>` authoring block, and a pointer from that readiness item. It belongs in this task because it is the direct counter-weight to the three removal rules — co-locating them lets an implementer, and the readiness check, balance "cut the residue" against "keep what the work needs" in one place.

The four cohere as one change to the same `<body>` and `<readiness_checklist>` surface: three move a kind of residue out of the body — an unresolved fork, an originating specific, a rejection debate — and the fourth keeps that removal from cutting past the implementable floor. They ship as one task because splitting them would make each re-derive that shared spine, and would separate the removal rules from the counter-weight that bounds them.

Motivating episodes, kept as illustrations: an agent mined a multi-session work episode into tasks for a skill family and, in the body it wrote, left a decision labeled open that it resolved from first principles the moment it was asked to, argued the body around rejected design options, and — until told up front — risked carrying the episode's domain specifics into a general rule (the first three rules). Reviewing a later draft, the reader found rules named but their edit shape compressed away, leaving an implementer to guess (the fourth). The same episode's create-decision lessons — re-deriving the delta against shipped work and sizing by cohesion — ride the sibling task [task-skill_prior-art-delta-and-cohesion-sizing.md](task-skill_prior-art-delta-and-cohesion-sizing.md); this file leaves them there and carries only the body-writing rules.

## Approach

- **Decide or label.** In the `<body>` **Decide or label** rule, add the derivable-resolution test: the agent first resolves the fork from the material available at authoring time — cited skills, codebase, standing knowledge — and labels open only a choice that genuinely needs input it cannot derive. Keep the ceiling and the existing "resolve before writing" thrust; point the rule at this test rather than restating the ceiling.
- **Generalize.** Author the artifact-improvement case once, in the `<gather>` altitude step. State that when the source is a concrete episode mined to improve a reusable artifact — for example, a working session with a skill that exposed a rough edge, yielding a task to improve that skill — the altitude is the general rule the episode argues for, not the point-fix, and the originating episode rides along only as the brief illustration the `<body>` **Illustrate** rule already provides. Then reference that one statement from `<lossless_conversion>`, so "every relevant unit of meaning" reads, for this case, as: the unit to preserve is the general lesson; the episode's specifics are illustration, not content to retain verbatim.
- **Positive framing.** In the `<body>` positive-framing rule, narrow the explored-alternative allowance: a brief non-goal or guardrail stays welcome in the body, and the rationale for options weighed and rejected moves out of the task — to the change's commit or pull-request description, or to a wiki page when it is durable design knowledge (the `<not_a_wiki>` pitfall's path for a lasting lesson). Frame the body shape as current-state (what exists, what is not there yet) to target (what to add, how). Update the `<readiness_checklist>`'s **Negation-framed behaviour** item to point at the narrowed rule.
- **Density floor.** Add the fourth rule to the `<body>` authoring block: write compact, and stop at the floor where a one-shot implementer can act without re-deriving dropped detail. Name the failure shapes it guards against — clauses stacked until the logic between them is lost, an edit site named without the shape of the change, a rule given without the one example that fixes its meaning — and the test that applies it: would this file, plus the project, let an implementer produce the intended change without filling a gap from outside? Compress while that holds; stop when it breaks. Point the `<readiness_checklist>`'s **Ambiguity / under-specification** item at this rule so the check covers over-compression, not only missing requirements.
- Author each rule once in the base skill, leading with positive carriers, and let the siblings inherit by reference per the family's single-source convention.
