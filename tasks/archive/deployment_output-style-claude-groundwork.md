# Track output styles in the repo, deploy them to Claude, and capture priors for uninstall restore

## Goal

The repository holds its output styles as tracked source, and `make deploy` installs them into a Claude configuration at whichever scope the run selects. Under `--global` that is the user configuration tree, giving the machine-wide default that governs every Claude session unless a project- or local-level `outputStyle` overrides it. Under `--project-dir` it is that project's own `.claude` tree, giving one repository its own style without touching the machine default. Both scopes are the same two placements and the same code path; only the resolved configuration root differs. Today the working style exists only as an untracked file in the user's own Claude configuration directory, so it lives on one machine, has no history, and cannot be reviewed. After this task it is versioned in the repo and reproducible on any machine by running the deploy.

This task also lays the groundwork every later harness reuses: the source directory, the artefact type, the discovery root, and the uninstall behaviour for a deployed configuration key. The sibling harness tasks listed under **Context** each add one target on top of it and add no new machinery.

## Context

An output style is a Claude-only component. The wiki documents the mechanism on its [Claude output styles](../../wiki/concepts/claude-output-styles.md) page, and the two facts this task depends on are its delivery-modes and locations-and-activation material: a machine-wide style is two placements rather than one, a Markdown file in the user configuration tree plus an `outputStyle` key in the user settings file, and nothing in the plugin system writes either of them. A deploy step is therefore the only route to that mode, which is why this work belongs to the deployment script rather than to a plugin.

Seed the tracked style once from the reporting user's existing Claude `output-styles/` file when that file is present; when it is absent, author the tracked Markdown so it includes `keep-coding-instructions: true` and the frontmatter Claude's loader accepts. After that seed (or authoring) step, the tracked file under repo-root `styles/` is the sole content source for deploy and for Acceptance — later work does not re-read a machine-local Claude tree for content.

Deployment mechanics that this task extends, all in `deployment/`:

- Artifact discovery is plugin- and folder-based today, described in `deployment/README.md` under the heading `## Artifact Discovery`, and resolves `plugins/<plugin>/<asset-folder>/` with the folder name selecting the type. This task adds the first asset source outside that tree, so discovery grows a second root.
- `deployment/deployment.sh` already merges a JSON key into a target settings file through its `merge_json_key` function, used today by Claude hooks (`settings.json` `hooks`), Codex hooks (`hooks.json` `hooks`), and Antigravity (`hooks.json` `charter_guardrail`) by reading the value from a source JSON file. Prior-value capture for uninstall restore belongs on that shared function; the Claude style key extends the same merge-and-log path so it can take a conf-sourced scalar (`style:<name>` → `"outputStyle": "<name>"`) and participate in that capture.
- `deployment/deployed_artefacts.log` is tab-separated with four fields per line, destination then target then type then source, and a merged key is already logged with the destination written as `<target-file>[<key>]`. There is no field for a previous value, which is what the restore requirement below adds.
- `deployment/deployment.conf` is parsed for per-tool `disallow:` and `replace:` lines, so it is the natural home for a per-tool `style:<name>` line naming which style is the active one (for example under `#claude`, `style:natural-language`).
- `deployment/deployment.sh` sets `CLAUDE_DIR` to `${HOME}/.claude` under `--global` and to `${PROJECT_DIR}/.claude` under `--project-dir`. Claude reads both trees: an `output-styles/` directory and an `outputStyle` settings key exist at user level and at project level, and the project values outrank the user ones. A style arm written against `CLAUDE_DIR` rather than against a hardcoded home path therefore serves both scopes through one code path, and adding a project-mode skip would be extra code suppressing behaviour that path already provides.
- Project styles load from every `.claude/output-styles/` between the working directory and the repository root, and since v2.1.178 the directory nearest the working directory wins when two of them define the same style name. A project deploy therefore needs no collision handling of its own beyond writing one file into the target project's own tree.

Sibling tasks, each adding one target on top of this groundwork and each waiting for it to ship: [Cursor](../deployment_output-style-cursor.md), [Codex](../deployment_output-style-codex.md), [OpenCode](../deployment_output-style-opencode.md), [Antigravity](../deployment_output-style-antigravity.md), and [VS Code Copilot](../deployment_output-style-vscode.md).

## Approach

Add a repo-root `styles/` directory holding one Markdown file per style, in Claude's own output-style format. Keep it out of `plugins/` and do not register it as a Claude plugin component. A plugin-root `output-styles/` folder would be auto-discovered by Claude and produce a second, namespaced copy of the same style that is availability-only and competes with the deployed one; the repo's standing rules also make the plugin the unit of distribution, and a style belongs to no single plugin's capability. The standing repo rule **Bundle a skill's helper scripts inside the skill.** (in `CLAUDE.md`; AGENTS.md has no parallel) carves out only repo-root `scripts/`. This task is the parallel explicit request for repo-root `styles/` on that footing, recorded through the already-required `## Layout` tree updates in `README.md`, `AGENTS.md`, and `CLAUDE.md`, without widening that rule beyond its `scripts/` carve-out. Populate `styles/natural-language.md` by that one-time seed-or-author step; thereafter deploy copies the tracked file verbatim, frontmatter included.

Add a `style` artefact type to `deployment/deployment.sh`, selectable through the existing `--type` filter, discovering each top-level `*.md` file in the repo-root `styles/` directory. Settle the type name and the discovery root as part of this task rather than later, because both are recorded in the deploy log and renaming either one afterwards means migrating log entries that already exist.

For the Claude target, deploy in two parts, and resolve both against `CLAUDE_DIR` so the same code serves `--global` and `--project-dir` without a scope branch. Copy the style file verbatim, frontmatter included, into `<claude-dir>/output-styles/<name>.md`. Then merge `"outputStyle": "<name>"` into the settings file in that same tree by extending `merge_json_key` itself so the merge-and-log path accepts a conf-sourced scalar rather than only a value sliced from a source JSON file, and so the first-write prior-value recording below lives on that shared function rather than on a style-only wrapper around it; the deployed style is then active rather than merely available. Take the name from a per-tool `style:<name>` line in `deployment/deployment.conf` (under `#claude`, `style:natural-language`), which is where it has to live: the output-style frontmatter schema is strict at four keys and rejects a fifth, so a marker inside the style file would break Claude's own loader. Extend `parse_deployment_conf` in place so it recognizes `style:<name>` the same way it already recognizes `disallow:` and `replace:` (today any other directive line is ignored), storing the per-tool name in a map parallel to `DISALLOW_MAP` (for example `STYLE_MAP[tool]=name`); the Claude arm reads that map for the merge value.

Put first-write prior-value capture on that shared `merge_json_key` path and extend the deploy log so a merged key can be reversed to what it replaced. On the first write of a key through that function, record the previous value, or an explicit marker when the key was absent. A later redeploy of the same key leaves that first-recorded prior unchanged and does not re-sample the live settings value. On uninstall, newly logged `path[key]` merges restore that recorded prior, and delete the key only when the absent marker was recorded. Amend the `path_exists` post-check inside `uninstall_logged_artifacts` so a `path[key]` uninstall counts as success when restore wrote the recorded prior back (the key may still be present with that prior value), and counts key absence as success only when the absent marker was recorded or a legacy four-field strip removed the key. Restoring to a hardcoded harness default is wrong here, because the default is whatever the user had rather than a vendor constant, and a user who had selected a built-in style would lose it. The storage shape is the implementer's choice between a further log field and a sidecar file, provided (a) any jq value — scalars, objects, and arrays — round-trips through record and restore unchanged, (b) existing four-field log lines keep parsing under the current tab-separated reader, and (c) `sort -u` dedup on exit still collapses identical lines without inventing a second prior for the same key. Pre-change four-field `path[key]` log lines continue to uninstall by stripping that key from the target file (the existing `strip_json_key` path), which matches "delete the key only when nothing was recorded" when no prior value exists on the line.

Rewrite the Current-directives lists in the `deployment/deployment.conf` and `deployment/deployment.sh` file headers (today `disallow:` and `replace:` only) so each list includes `style:<name>`. Rewrite the Discovery blurb in the `deployment/deployment.sh` file header (today the claim that discovery is plugin- and folder-based under `plugins/<plugin>/<asset-folder>/` only) so it states both discovery roots — `plugins/<plugin>/<asset-folder>/` and repo-root `styles/` — and names `style` among the artefact types; keep `VALID_TYPES` and `--help` aligned with that same type set. Rewrite the `## Layout` trees in `README.md`, `AGENTS.md`, and `CLAUDE.md` so each includes the repo-root `styles/` directory. Update `README.md` at the repo root and `deployment/README.md` so both describe the new artefact type, the new discovery root, the per-tool `style:<name>` line, and the restore behaviour on uninstall.

**Out of scope:**

- Every harness other than Claude, each owned by the sibling task named for it under **Context**.
- Transforming the style body for a harness that cannot read Claude's format, which is per-target work owned by those same sibling tasks.
- Shipping the style as a Claude plugin component, which the **Approach** rejects outright rather than defers, since the plugin route cannot reach the machine-wide mode this task delivers.

## Acceptance

**Isolation protocol.** Every deploy and uninstall Acceptance item below runs with `deployment/deployed_artefacts.log` copied aside when present, the live log cleared for the check, and the aside restored on exit (same pattern as `tests/deployment/script_tests/run.sh`). Every `--global` Acceptance item below also sets `HOME` to a scratch home tree for that check. Items that are both deploy/uninstall and `--global` apply both.

- A repo-root `styles/` directory exists and holds the natural-language style as a tracked Markdown file whose frontmatter includes `keep-coding-instructions: true` and stays within Claude's accepted output-style frontmatter keys.
- `grep -c "output-styles" plugins/*/.claude-plugin/plugin.json` returns no match, and no plugin directory contains an `output-styles/` folder, confirming the style is not also shipping as a plugin component.
- `deployment/deployment.sh --help` lists `style` among the values accepted by `--type`.
- A dry run under `--global` restricted to the new type and the Claude target reports two actions for one style: a file copy into the Claude user `output-styles/` directory, and a key merge into the Claude user settings file.
- A dry run under `--project-dir` restricted to the new type and the Claude target reports the same two actions resolved against that project's `.claude` tree, and touches nothing under the home directory.
- A real deploy under `--project-dir` into a scratch project produces `<project>/.claude/output-styles/<name>.md` byte-identical to the repo source and sets `outputStyle` in that project's settings file to the name given by the per-tool `style:<name>` line, while the home-directory settings file keeps whatever value it held before the run.
- Uninstalling a `--project-dir` deploy restores that project's prior `outputStyle` value, or leaves the key absent when the absent marker was recorded, on the same rules as the global scope.
- A real deploy under `--global` into a scratch home Claude tree produces `<claude-dir>/output-styles/<name>.md` byte-identical to the repo source and sets `outputStyle` in that tree's settings file to the name given by the per-tool `style:<name>` line.
- Deploying twice in a row leaves the same single log entry per artefact and the same settings value, with no duplicate lines.
- Deploying into a scratch settings file that already sets `outputStyle` to a non-deployed value, deploying a second time, then uninstalling, leaves that original pre-first-deploy value in place rather than the value present just before the second deploy, the deployed style name, or an absent key.
- Running the deploy against a scratch settings file that already sets `outputStyle` to a different value, then uninstalling, leaves that original value in place rather than the deployed one or an absent key, with uninstall succeeding under the amended `path_exists` post-check while the key remains present with that prior, and the deploy log no longer contains that settings `path[key]` line.
- Running the deploy against a scratch settings file with no `outputStyle` key, then uninstalling, leaves the key absent rather than set to any default, and the deploy log no longer contains that settings `path[key]` line.
- In `deployment/deployment.sh`, first-write prior recording (previous value or absent marker) lives inside `merge_json_key` itself rather than only in a style-specific caller, and `uninstall_logged_artifacts` restores any newly logged `path[key]` prior (or deletes the key when the absent marker was recorded) through that shared path.
- A first-write prior that is a nested JSON object or array, staged in a scratch settings file under a non-`outputStyle` key, recorded through a direct `merge_json_key` call (not the Claude style path) that writes a different value for that key, then restored on uninstall, round-trips unchanged to the original value under jq comparison; the scalar `outputStyle` restore Acceptance items remain the proof for string priors.
- In `deployment/deployment.sh`, `parse_deployment_conf` recognizes a per-tool `style:<name>` line and stores the name in a per-tool map parallel to `DISALLOW_MAP` (for example `STYLE_MAP[tool]=name`); the Claude arm passes that map's scalar into `merge_json_key`'s conf-sourced-scalar path for the `outputStyle` merge, with no temporary or source JSON file written or read to supply the value.
- Running uninstall against a log that still contains a pre-change four-field `path[key]` line for a scratch settings file that holds that key removes the key from the file (and a dry run against the same log reports the strip without requiring a fifth field).
- `README.md` and `deployment/README.md` both describe the `style` type, its discovery root, the per-tool `style:<name>` line, and the uninstall restore behaviour; the Current-directives lists in `deployment/deployment.conf` and `deployment/deployment.sh` headers include `style:<name>` in place of the prior two-directive-only list; the Discovery blurb in the `deployment/deployment.sh` file header states both discovery roots and the `style` type in place of the prior plugin-only claim; and the `## Layout` trees in `README.md`, `AGENTS.md`, and `CLAUDE.md` include `styles/`.
