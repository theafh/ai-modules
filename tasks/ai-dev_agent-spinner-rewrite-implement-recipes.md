# Ship agent_spinner's rewrite and implementation recipes

## Goal

agent_spinner is the skill an orchestrating agent, the orchestrator, reads before it runs helper agents. A recipe is a reference file under `plugins/ai_dev/skills/agent_spinner/references/recipes/` that gives the step-by-step procedure for one common kind of job: its helper phases, the steps the orchestrator runs itself, and its checks.

After this task, an orchestrator whose ask applies one wording rule across many files, or implements one task whose change spans many files, finds a matching recipe there. It follows that recipe's phases, orchestrator steps, and checks.

This task ships two recipe files, `prose-sweep.md` and `multi-file-task.md`, with their rows in the `<selector>` recipe table, which maps each kind of ask to its recipe file. It also ships four evals, each a behavioural test on a staged fixture. Two stage the sweep's sampling rule, which decides when only a sample of the changed files gets a checker. One covers the sweep's triage pass, a cheaper pass over the files where the first scan found no target. One covers the multi-file recipe's move-integrity gate, which flags a move that git records as a delete plus an add, or with a similarity below the plan's threshold.

For example, C1 checks every landed write, meaning every change that reached a file, and C5 allows one repair round with one re-check. It adds run.sh's per-recipe checks, a loop over every recipe file whose data sits in the arrays `RECIPE_FIELDS`, `RECIPE_SHARED_LINES`, and `RECIPE_REPAIR_LINES`. `RECIPE_FIELDS` lists the field tags every recipe holds, in order. `RECIPE_SHARED_LINES` holds a phrase from each line every recipe carries word for word, and `RECIPE_REPAIR_LINES` does the same for the three lines a recipe with a repair round adds. This task follows it, so those checks cover the two files added here.
- **Terms the recipes use.** The run protocol and the checks define these terms:
  - The run ledger is the program `scripts/run_ledger.py`, bundled with the skill, which keeps a run's records under `.agent_spinner/`. Its commands are verbs. `init` opens a run over an enumerated list and records the baseline, and `close` ends the run. A clean `close` exits 0, which it does only when nothing is left open.
  - The baseline is the state of the files, and the output of each named gate, when the run opens. The net diff is every change between the baseline and the final tree, which `diff` measures and writes per file under `diffs/`. A hunk is one changed block of a diff.
  - A gate is either a deterministic command, such as a linter or a build, or a user gate, a question the user must answer before the run goes on. `gate` runs a command gate and compares its result with the baseline run. A positive control is a known positive that a count or search must find before its empty result counts (C4).
  - The roster lists the run's rows. A row is mostly one helper's work on one unit, such as one file, and it carries a bound, the time after which the orchestrator stops waiting for it. `rows` creates the rows of a later phase from accepted records, one row per record.
  - A return is what a helper hands back. `accept` checks a return against the return contract and imports its records before the return counts. A beyond-brief defect is one a helper noticed outside its brief, and an incident is something that went wrong during its work.
  - `snapshot` copies the files a reading helper needs into the run directory, and `snapshot --base` copies them as they stand at the base commit.
  - A wave is a group of helpers sent out together. A barrier is the point where the orchestrator waits for every return of a phase before it goes on.
  - The tiers are the ways a run can execute. At the inline floor the host offers no way to spawn helpers, so the orchestrator runs every pass itself, one after another. Under batch delivery, a batch of spawned helpers returns together inside the turn. Under notice delivery, a spawn returns at once and a notice reports its completion later.
  - A check is recall-limited when the checker already saw the work being made, as at the inline floor, where one context holds every pass. A pass is blind by prompt when only its brief keeps a claim from it, with no host record to confirm that it never read the claim (C2).
  - A fork is a real decision that belongs to the user. A lens is one angle a helper works from. Depth is the model and effort a helper runs at.
  - A stamp is a status field that a separate gate owns, such as a task's implemented status. A marker records what an earlier pass examined, such as a capture hash on a source record. The family skill that owns a stamp or marker updates it through its own gate (C9).
  - A narrowing is any cut to what the run checks, which the run names aloud and puts to the user when it drops a check. The tree guard compares HEAD, the stash list, and the git status with their baseline records. Yield is the helpers dispatched set against the decisions or edits they produced.
- **Approved decisions these recipes apply.** The owner approved each on 2026-10-03.
  - One repair round, then one re-check of each repaired item at no lower depth than its first check, and no second round.
  - Every run states an estimate. The run asks before any widening past the enumerated list, and before it goes above a size guideline the host or user states. An answer stated in the request counts as the user's answer.
  - `init` refuses to register an auto-fix gate, a linter run in a mode that edits files, while run state exists. The sweep therefore names each linter in its check mode, which only reports.
  - Read snapshots are file copies under the run directory, and the run writes no ref, tree, commit, or object into the user's repository.
  - A defect inside a governed family loop belongs to that family, where such a loop is one a family skill runs under its own rules. The multi-file recipe therefore leaves the implemented stamp to the implementation skill's own step, and hands each capture hash to the owning family's gate.
- **Coverage rule.** The sweep's sampled checker set narrows what the run checks, and its triage pass widens what it writes. Each goes to the user, as the `CHARTER.md` rule beginning "An autonomous component keeps its audit, detection, and coverage scope intact" requires.

These checks of it therefore reach the recipe files: `every target product name cites harness_portability`, `no per-harness frontmatter keys or tool identifiers`, `no harness agent directory paths`, `no instruction to write a global rules or agent-config file`, and `no template claims precedence over the surrounding conversation`.

## Approach

### Recipe file layout

Write both files in the layout the recipes the review-repair recipes task ships use, which that task's per-recipe checks enforce. Each file has one outer tag named after the file stem, the field tags `RECIPE_FIELDS` lists, in that order, two to four numbered phases in `<phases>`, and at most 12,288 bytes. Write in pseudo-XML with positive, action-oriented wording, as the standing repo rules require. Write rules only, with no session figure, cost observation, case evidence, harness product name, tool identifier, harness path, instruction-file name, or precedence phrase. Cite run-protocol steps and checks by their P and C labels, and name ledger verbs and flags only from the command reference in run-protocol.md.

Copy every shared line from the same field of `fidelity-review.md`, which the review-repair recipes task ships, where each stands as a paragraph of its own and holds its `RECIPE_SHARED_LINES` phrase. Put this recipe's shape in the trigger line. Both recipes run a repair round, so both also copy the three paragraphs that hold the `RECIPE_REPAIR_LINES` phrases. The repair-round paragraph in each `<orchestrator_gates>` cites C5. As in those recipes, the first orchestrator step runs the gate-scope check before dispatch, and the **Report** step builds the report from the ledger after a clean `close` (P6). `<tier_notes>` holds one note each for the inline floor, batch delivery, and notice delivery. The field contents below leave out what the shared lines already say, so each field holds its shared lines plus the content listed here.

In each recipe section below, the bold label of a field bullet names its field, such as **Trigger.** for `<trigger>` and **Cost profile cuts.** for `<cost_profile>`. **Ledger steps.** names the ledger commands the run makes, **Width.** says how many helpers each phase gets, and **Adversarial checks.** says how checkers try to refute the work. **Orchestrator gates, in run order.** lists the steps the orchestrator runs itself, and **Tier notes.** says what changes at each tier.

### `prose-sweep.md`: J2, meaning-preserving prose sweep

Its H1 reads `# J2. Meaning-preserving prose sweep`, and its outer tag is `<prose_sweep>`.

- **Trigger.** The shape is per-artifact fan-out. The ask applies one style or wording rule in place across a document tree, keeping meaning, requirement strength, and length. Requirement strength is the force of words such as must and should. Typical rules remove dashes, lighten jargon, rewrite contrastive negation, or split long sentences. These signals mark the ask: a style file, many prose files, lines a linter or parser reads, graders that match corpus literals, and hard-wrapped prose. Corpus literals are exact strings from the files that a test grader looks for.
- **Ledger steps.** `init` takes the in-scope list, the exclusions, the named gates, each linter in its check mode, one `triage:missed-scan` unit, registered only when the plan names the triage pass, whose row runs that pass, and one `residual:sweep` unit, always registered, whose row runs the residual sweep. The two units carry distinct item names, `missed-scan` and `sweep`, because `init` refuses two units whose items share one case-folded slug, and every later mention of the triage unit uses its label `triage:missed-scan`. A sweep whose plan omits the triage pass therefore opens no triage row and still reaches a clean `close`. The residual row's accepted return carries one `findings` record per file that still holds a residual, its `path` naming that file and its claim listing every residual in it. `gate --on-baseline` runs the linter and the build, each with the expectation its baseline run meets (C4). An expectation names the result a gate run should show. That expectation is `exit0` where the baseline run exits 0, and `nonempty` where it already reports findings, so the gate line reports the difference. Each counter, a script that counts the rule's targets, runs with `--expect count`. Each wave runs `diff --count`, then `diff --add-checks`, then the checker wave. Each changed path the sample leaves out keeps the `check:<slug>` row that `--add-checks` made, and the run closes that row with `accept check:<slug> --stdin --classify 'sampled out; per-file gates cover it'`, piping the sample's reason as the free text. That row records `accepted` with its classification, so `close` finds no pending row and no changed path without an accepted check. Once the checker returns are accepted, `rows --phase repair --role writer --from-records 'check:*:findings:*'` creates one repair row per accepted finding record. The residual findings take their repair rows one record at a time, because `rows` labels each row by record id and reads no row's path, so one glob cannot express the filter. The orchestrator compares each accepted residual finding record's `path`, one record per file, with the paths of the repair rows already on the roster, and calls `rows --phase repair --role writer --from-records 'residual:sweep:findings:<n>'` once for each record whose path holds no repair row, naming that one record id in full, such as `residual:sweep:findings:2`, with no wildcard. A path with both a non-kept hunk and a missed residual therefore ends with exactly one repair row. Each repair brief passes `--kind repair`, so a path repaired once refuses a second repair. The residual gate, the final count of targets left anywhere in scope, runs before `close`.
- **Phases.** **Rewrite**: a writer rewrites each roster file, wave by wave. It reads no earlier helper return. Once the first wave has set them, it also reads the ruling table and the calibration pairs, which the **Calibration** step sets. **Check**: a checker reads each changed file's diff against the baseline, with its Rewrite return verbatim.
- **Width.** Writers take one file each, W per wave, where W is the wave size the plan sets. Give every changed file one checker by default. A rule that rewrites a sentence to remove a mark bears on meaning, like any rewording. A sampled checker set is possible only while every hunk the rule makes is a glyph-for-glyph substitution, as each wave's diff shows, and the run re-checks that condition on every wave's diff rather than once at calibration. Such a substitution swaps one character for another and leaves the rest of the text as it was. A wave whose diff breaks the condition gives every changed file in that wave a checker, and the run puts that widening to the user, since it restores the checks the sample dropped. The sample then covers a fixed share of the files, every file whose fidelity gates moved, and every file with a flagged call, and the gates still cover every file (C1). Every changed file the sample leaves out closes its `check:<slug>` row with the classification **Ledger steps.** gives, so the sample stands as a recorded narrowing rather than an open row. The fidelity gates are the per-file counts under **Gates beside the steps**, and a flagged call is a borderline call the writer flagged. Where a gate this recipe relies on is unavailable, give every changed file its checker, or ask the user (C4). Spend checkers where meaning can move, no shallower than their writers (P1). Choose a checker role whose contract is review, and require a cited span per checklist line. When the user tightens the rule within the session, keep the pre-session baseline fixed. In that case, also prefer one composite pass per file that carries every rule still in force, and send files touched twice to the checker first.
- **Triage pass**, also in `<width>`: "A cheaper triage pass may take the rows the scan did not hit, where the plan names it. Its widening still goes to the user." The scan is the scout's count of targets per file, and the rows it did not hit are the files where it found no target. The triage helper runs at a lighter model or effort. Its brief names each in-scope file the scan did not hit, one section per file, and the helper returns one finding per file where it found a missed target, carrying that file's path and a claim that lists every target the scan missed there with its quote and anchor. Once the user approves the widening, `rows --phase rewrite --role writer --from-records 'triage:missed-scan:findings:*'` creates one Rewrite-phase row per such file with role writer, so each file with a missed target gets a writer.
- **Roles and returns.** Writers write their return files.
  - The writer brief carries the rules file, the preserve list, the ruling table, and the calibration pairs verbatim. The preserve list names text the writer leaves exactly as it stands. The brief also carries its kind note, one path, a negative list, and its own scratch directory under the run directory. The kind note says how this class of text may change, and the negative list names the files the writer leaves untouched: the other roster paths and the log, schema, and generated files.
  - The writer returns its label and path and the diffstat measured by the named command. It adds counts in the template's unit with the method used, two to four before-and-after pairs, borderline calls tagged by ruling class, beyond-brief defects with path, line, and quote, incidents it broke and repaired, and doubts.
  - Each edit spans the whole sentence across line breaks, and then the writer reflows the paragraph and re-reads it. Replacement tables keyed on single lines serve pointer-class text only, meaning paths, identifiers, link targets, and slugs (`references/edit-mechanics.md`).
  - The checker returns a verdict per hunk (kept, narrowed, lost, inverted, or garbled) with the old and new text, and it records each file with a non-kept hunk as one finding whose claim lists those hunks. It also returns a `checklist` entry per checklist line, each with verdict `pass` or `fail` and its citing span, and the number of hunks it examined. Each return carries every key `accept` validates, and each finding carries `claim`, `severity`, `quote`, `anchor`, and `path`, with `path` naming the file the finding concerns and its severity drawn from the run's severity ladder, which `init --severity` sets when the recipe's classes differ from the default `blocker`/`major`/`minor`.
- **Adversarial checks.** The checker opens from the position that the rewrite lost or changed meaning, and it names the cost: a missed loss leaves a wrong page that others will cite. It reads the rules file byte for byte, the writer's return verbatim, and the diff against the baseline. Its closed checklist has lines for forbidden marks under the writers' exclusions; modal and requirement strength; numbers, literals, and attributions; and each removed clause's claim still made somewhere. Further lines cover orphaned continuation lines and lost antecedents, such as a pronoun whose noun was cut; headings that still name their sections; lengthening and markup; and one line per call the writer flagged. A pass cites a hunk per line, and a pass with no hunk count goes back for re-checking. Afterwards, prove that the check phase changed nothing (P5).
- **Orchestrator gates, in run order.**
  - **Scout**, before the first wave: list the candidate universe, every file the rule could reach, with the in-scope list and each exclusion's reason. Confirm that in-scope plus excluded equals the universe. Count targets per file with a bundled counter whose positive control passed (C4). Read every machine-parsed file with the tool that parses it, and write a kind note for each load-bearing line, one that a parser, linter, or grader reads. The preserve list takes those notes, inline code, and text an agent must emit verbatim. List the link sites that point at headings the sweep may change, run the gate-scope check, and record the baseline (P1).
  - **Calibration**, on the first wave: the first wave pilots three to five structurally different files. Cluster every hard construct into named classes, with one ruling per class in a ruling table. For a rule that needs judgement on each instance, show the user eight to ten before-and-after pairs, the cut-and-keep ratio, and the bar. For such a rule, send later waves only after the user confirms. Put these to the user, each with its share of the estimate and a cheaper alternative: strictness, scope categories, depth, borderline classes, and every widening past the files the scan hit. Put a sampled checker set, where Width allows one, to the user here, with the checks it drops and its share of the estimate. Use it only on the user's word.
  - **Per-wave gates**: run the per-file gates on every file the wave changed (C4).
  - **Residual sweep**, after the last wave: count the target class over every in-scope file, edited or not, with the writers' exclusions, then dispatch the `residual:sweep` row. A residual is a target still present after the rewrite. That row's accepted return classes each residual as kept, citing its rule or class, or as missed, and greps each ruling class for uniformity (C8).
  - **Repair round**: missed residuals and every hunk the checker judged other than kept go to one writer per file.
  - **Closing differentials**: run the whole-tree lint and build differentials, the net-diff audit, and the tree guard (C4, P5). A differential compares a gate's final run with its baseline run.
  - **Report**: the report step that `### Recipe file layout` describes.
- **Gates beside the steps**, closing `<orchestrator_gates>`. Per file, the gates count modal and requirement words, hedges, numbers, link targets, quoted strings, contrast markers, and character growth, baseline against working copy. Each count is judged against the direction the rule explains. The wrap-seam detector finds sentences an edit split or joined at a line wrap. The linter runs per file and over the whole tree, and the build runs too, each with its expectation (C4). Every link is checked against each heading anchor the sweep changed. Totals come from the diff, with the self-reported sum shown beside them.
- **Failure handling.** A writer that was killed, aborted, or ran past its bound after it may have written leaves its path unknown. Settle that path from the diff and send it to the checker. After a resume, the check set is every path the diff shows changed. An incident that appears in a helper's narration but is missing from its return is a contract violation.
- **Stop and ask.** Settle forks, the calibration bar, and every widening on the first wave, before any later wave goes out. Before dispatch, route every write to a stamped artifact to its owning family's gate or to the user, whatever the write changes (C9). A conflict between the user's exclusions and the repository's bookkeeping rules goes to the user.
- **Report.** The report gives measured totals from the diff, with the residual count before and after the repair round. It lists each ruling class with its count, the borderline calls for review, and every beyond-brief defect. It tallies checker verdicts by hunk class and gives every gate delta with its expectation. It names every unavailable gate as a narrowing and states yield as cost per changed file.
- **Cost profile cuts.** The cuts are a sampled checker set, where Width allows one, and the triage pass. Cutting the triage pass leaves the targets the scan missed unfound. The checking share buys meaning checks only through a review-capable checker that cites a span per checklist line.
- **Tier notes.** Inline floor: each file's write, gates, and check run before the next brief. Batch delivery: one batch holds a wave's writers and the next holds its checkers, the gates close the wave, and a row that returns late is marked as over its bound (P4). Notice delivery: a file's checker goes out once its writer's return is accepted and its diff is non-empty. Where the notice carries no result, batch the checkers (P3), and poll the last Check wave inside the turn (P4).
- **Post-run checks.** The roster equals the in-scope list, and in-scope plus excluded equals the universe. The changed set is a subset of the roster, every changed file has a gate row, and every file the width rule names has a checker row. Every in-scope file has a residual entry, and every class grep is uniform. HEAD and the stash list match the baseline, and every total in the report comes from the diff.

### `multi-file-task.md`: J3, multi-file task implementation

Its H1 reads `# J3. Multi-file task implementation`, and its outer tag is `<multi_file_task>`.

- **Trigger.** The shape is per-artifact fan-out. The ask implements one task whose change spans many files, verified against the task's written acceptance list. The change is often a mechanical rename plus a semantic rewrite per surface, where a surface is one file or block the change reaches. The implementation skill keeps the task's lifecycle (stamp, audit, close-out), and this recipe governs the helpers inside that run.
- **Ledger steps.** Copy the acceptance list verbatim into a file in the run directory, and name that file by path in every checker brief. Pass the semantic roster, built from the task's own selectors, to `init`. The semantic roster lists the files that need a semantic rewrite, and a selector is the glob or label the task uses to pick its files. Run `snapshot` after the mechanical pass and again before the check phase, then run `diff`. Name each checker's snapshot copy and its per-file diff under `diffs/` in its brief. Run the full named gate suite through `gate --on-baseline`. Hand the implemented stamp to the implementation skill's own step after `close` shows every checker row terminal, meaning in a final state such as accepted or failed. `rows --phase repair --role writer --from-records '<checker row>:findings:*'` creates the repair rows from the accepted checker finding records, one row per finding record.
- **Phases.** **Weigh**: two or three lens designers compare the change with its alternatives over `snapshot --base`. This phase runs only when the task adds a public surface or rules out a competing mechanism. The designers read no earlier return. Each returns a verdict on the planned change and, per alternative, why it wins or loses, its cost, and its coverage regression, meaning the coverage it would lose. **Write**: a writer rewrites each semantic roster row and reads no earlier helper return. Claim-class occurrences go to these writers: quotations, commands pinned to an older commit, historical narration, and every hard-wrapped sentence the change touches. Pointers are paths, identifiers, link targets, and slugs, and every other occurrence is claim-class and changes only through a writer. **Check**: a checker reads each written file against the acceptance list, with the writer's return, the file's snapshot copy, and its per-file diff, while the orchestrator holds its own writes (C1, C2, P5).
- **Width.** Write gets one writer per semantic row. Checkers cover every written semantic file plus a fixed sample of the mechanical set, the files the mechanical pass changed, and the gates cover the mechanical set in full. Every mechanical-set file outside that sample closes its `check:<slug>` row with `accept check:<slug> --stdin --classify 'sampled out; per-file gates cover it'`, so the sample stays a recorded narrowing and `close` finds no open row. The declared shape binds, so the run keeps the shape it announced. A switch of shape is a ledger event naming the checks it drops, and a switch that drops a check waits for the user.
- **Roles and returns.** The writer returns its label and path, the disposition applied, before-and-after pairs, each claim-class occurrence it kept verbatim with its reason, brief corrections, incidents, and doubts. A brief correction is a place where the writer found its brief wrong. The checker runs at or above the writers' depth. It returns a `checklist` entry per acceptance line, each with verdict `pass` or `fail` and its citing span, where `met` maps to `pass` and `partly` and `unmet` each map to `fail` with a finding. It also returns unrequested changes, missing changes, narrowed wording, and anything beyond the checklist. Each return carries every key `accept` validates, with its doubts as `notes`, and each finding carries `claim`, `severity`, `quote`, and `anchor`, with its severity drawn from the run's severity ladder, which `init --severity` sets when the recipe's classes differ from the default `blocker`/`major`/`minor`.
- **Adversarial checks.** The checklist copies the acceptance contract, one line per item. Every rewrite item pairs "the old form is absent" with "the required new form is present on every surface the item governs" (C2). The checker reads the acceptance file by path, because a spawned helper receives only its prompt. Two standing lines come from the diff: unrequested changes and missing requested ones. The orchestrator's own writes, such as log appends and link repoints, get their own check rows (C1), and the verdict waits for a pass other than the orchestrator's. The Weigh designers work blind, without sight of the planned change, and the report labels them blind by prompt (C2).
- **Orchestrator gates, in run order.**
  - **Orient and baseline**, before Weigh: read the implementation skill and every skill that owns an artifact class the change touches, such as a knowledge base whose source records carry hashes. Run the dependency gate, which checks that the task's prerequisites have shipped. Honour the branch and charter rules, record the baseline, and run every named gate at the baseline with full output (P1, C4). Run the gate-scope check before dispatch.
  - **Mechanical pass by script**, before Write: apply moves and exact replacements to pointer-class occurrences only (paths, identifiers, link targets, slugs), verify by search, and record the result with `snapshot`.
  - **Named gate suite**, after Check: run the full suite against the baseline with warnings included, then these gates (C4). Move integrity lists every moved path with its rename status and similarity, as git reports them, and an add-plus-delete pair or a similarity below the plan's threshold is a finding. Git reports a similarity only for a rename it detects, so for a delete-plus-add pair the gate keeps the default pass's delete-and-add status and reports beside it the similarity index a second `git diff -M1% --summary` pass measures. Every quoted anchor and pinned command still resolves. After every append-only write, the line count grew by exactly the entry and the diff only adds lines. Wrap width holds on prose. Each capture hash on a source record goes to its owning family's gate by name, or to the user as a fork where no family owns the record.
