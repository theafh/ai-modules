# Run git_auto_review's review-and-fix loop on a checked-out feature branch

## Goal

`git_auto_review` runs its review-and-fix loop on a checked-out feature branch. Its gate reviews everything the branch would bring into the default branch, meaning the branch's commits since the merge base plus the working tree, and `auto_fixer_git` fixes each qualifying finding in the working tree, uncommitted, under the same convergence rules the loop applies on the default branch today. Every automated review-and-fix request routes to `git_auto_review`, a branch or pull-request request included, so a user who asks to auto-review and fix their branch gets the loop rather than a decline or a one-shot review that edits nothing. On the default branch the target and the loop stay as they are.

## Context

The skill restricts itself to the default branch on purpose, and the restriction reaches the user in two ways. A `/git_auto_review` run on a feature branch stops at `<orient>` before any gate call and points the user at `git_review`. A request phrased as "auto-review and fix the branch" routes to `git_review` directly, which has no loop and whose `<reviewer_side_edits>` `<gate>` fixes a defect only on a current-turn ask after a write-permission and fork check, so by default it reviews and edits nothing. In Cursor sessions on 2026-10-29, every branch run in two repositories declined this way, re-declining on each re-sent prompt, while default-branch runs the same day looped normally. Where the user pushed for fixes anyway, the agent improvised a loop over the working tree alone and never reviewed the branch's commits.

These passages carry the restriction:

- `plugins/ai_dev/skills/git_auto_review/SKILL.md`: the frontmatter `description:` ("over the default branch's uncommitted changes and its local commits ahead of upstream"); `<when_to_activate>`, whose routing sentence sends "review of a branch or a pull request, whether manual or the automated review-and-fix shape" to `git_review`; the `<inputs>` **Target.** bullet, which ends "A checked-out branch target and a pull-request target are out of this skill's reach"; and `<orient>`'s "When the current branch is not the resolved default branch, decline the run."
- The `<inputs>` target bullet of `auto_gate_git`, `auto_fixer_git`, and `auto_verifier_git` under `plugins/ai_dev/agents/`, each of which reads "the default branch's uncommitted change".
- `plugins/ai_dev/skills/git_review/SKILL.md`'s frontmatter `description:`, which lists "automatically review and fix this pull request, or auto-review and fix the branch named" among `git_review`'s own triggers and hands only the default-branch case to `git_auto_review`.
- The `ai_dev` description in `plugins/ai_dev/.claude-plugin/plugin.json`, `plugins/ai_dev/.codex-plugin/plugin.json`, `.claude-plugin/marketplace.json`, and `.agents/plugins/marketplace.json` ("an automated review-and-fix loop over that same default-branch uncommitted target"), the `git_auto_review` bullets in `plugins/ai_dev/README.md` and in the root `README.md` `## Plugins` list, and the sentence "`git_auto_review` drives a finished uncommitted change" in `wiki/concepts/agent-delegated-automation.md`.
- Two tests pin the restriction: `tests/trigger_evals/git_review.json` expects `git_review` on "auto-review and fix the branch feature/rate-limit" and on "automatically review and fix pull request #42", and the eval `declines_on_non_default_branch` in `tests/git_auto_review/evals/evals.json` grades the decline.

[The original git_auto_review task](ai-dev_git-auto-review.md) put "Auto-reviewing or auto-fixing a checked-out branch target" in its `**Out of scope:**` block, and this task reverses that one exclusion. The loop machinery that task built (the convergence rules, the relay, snapshots and Restore, the regression ledger, the audit delta, and the concurrent-modification guard) reads `HEAD` and the working tree, so it carries over to a branch unchanged.

Flipping the scope alone leaves the gate blind to half of a branch, because `git_review`'s `scripts/collect_review_evidence.sh` has two modes and neither covers a branch with uncommitted fixes. Branch mode (`--base <ref> --head <ref>`) reads the committed three-dot range and nothing in the working tree. `--uncommitted` reads the working tree and lists the commits ahead of the upstream in `local_commits.txt` as a log without diffs, and on a feature branch that tracks its own remote branch, that upstream covers only the unpushed commits. From round 2 on the fixes sit uncommitted, so a gate that read branch mode alone would re-report findings the fixer already closed.

`<lane_classification>` already makes a committed finding fixable when the working tree still carries its lines, since the **Clean tracked-file membership.** case assigns `working-tree lane` to cited lines that exist in an unmodified tracked file. A citation from the committed range carries `HEAD`-side line numbers, though, and those drift once the working tree edits the same file, which round 1's own fix does. No case re-anchors such a citation today. The **`### staged` re-cite to working tree.** case does the same job for staged citations and is the shape to mirror.

## Approach

Make each edit below as an in-place rewrite of the passage Context names, so one statement of the target remains.

1. **Define the branch target once.** Rewrite the `<inputs>` **Target.** bullet to state two target shapes. On the default branch the target stays as written today. On any other checked-out branch the target is the branch's change: the commits from the merge base of the remote-tracking default ref and `HEAD` up to `HEAD`, plus the working tree (staged, unstaged, and untracked). The base is the `<remote>/<default>` ref that `<orient>` resolves, read without a fetch, so the gate's `--no-fetch` requirement holds. Fixes land in the working tree, uncommitted, and the branch's commits and ref stay as they are. Define the named-target input in the same `<inputs>` section as a third optional prompt input, written anywhere in the prompt as the literal phrase `branch <ref>` or `pull request <ref>`, matched case-insensitively, where `<ref>` is a branch name in the shapes `git_review`'s `<accepted_forms>` accepts (a bare name or the `<remote>/<branch>` form) or a pull-request URL or number, and counts as a named target only when it resolves to an existing branch or pull request; a pull-request ref resolves to its head branch through the same `<pull_request>` route `git_review` uses. Change `<inputs>`'s opening count from "one target and two optional prompt inputs" to "one target and three optional prompt inputs".
2. **Rewrite `<orient>`.** Keep the default-branch resolution and the abort when neither route yields a default branch. Replace the non-default decline with acceptance: the default branch takes the default-branch target, and any other checked-out branch takes the branch target. Keep a decline, with today's terminal move (report, stop before any gate call, no working-tree write, and no relay or evidence-scratch artefact), for two cases: a detached `HEAD`, and a prompt whose `<inputs>` named-target input names a branch or pull request other than the one checked out, recognized only through that input's literal phrase and never from a bare mention of the words "branch" or "pull request", where the report names `git_checkout` as the skill that puts the repository on it.
3. **Collect both evidence sets on a branch.** Add a policy rule to `auto_gate_git` for the branch target. Each round invokes `collect_review_evidence.sh` twice, both times with `--no-fetch`: once in branch mode with `--base <remote>/<default> --head <checked-out branch>`, and once with `--uncommitted`. The `--head` value is the checked-out branch's short name (`git symbolic-ref --short HEAD`), which resolves to the same commit as `HEAD` for every diff, log, and merge-base call the collector makes, while `collect_head_sync`'s `refs/heads/<branch>` and `<branch>@{upstream}` lookups find the local branch and its upstream. The literal `HEAD` resolves neither, so `head_sync.txt` would record `local_head: none`, `upstream: none`, and `head_vs_upstream: no local branch; the remote ref is the only head` on every branch run, and the report lead and `<compare_heads>` would carry that false head state. The review reads both directories and treats their union as its subject, so a defect in the working tree is a finding exactly like a defect in a branch commit. `git_review`'s `<closing_answer>` clause "On a branch or pull-request run, the user's working tree belongs to the lead's tree state" contradicts that subject, so rewrite `auto_gate_git`'s `<policy>` override rule in place: name that tree-state clause as a fourth suppression override beside `<non_findings>`, `<lint_baseline>`, and `<only_what_is_open>`, and reword the rule's "three" to "four". Reword the matching `<output_contract>` template line "with the three suppression overrides applied" to "with the four suppression overrides applied", so the override count carries one statement in each file. `git_review`'s skill text stays as written; the override lives in `auto_gate_git`, which already composes that report. The report uses `git_review`'s `<headings>` set in its stated order with `<first_review_presence>` applied, and its structural-merge answer reads the branch-mode evidence (the test merge and the ahead and behind counts). The report lead names the base ref with its SHA, so a stale remote-tracking base is visible. A delta re-review runs the same two collections, which puts the fixer's uncommitted writes in view. `collect_review_evidence.sh` stays as it is, because both modes already exist and `auto_gate_git` reaches all of its passes without editing `git_review`.
4. **Re-anchor committed-range citations.** Add a location-rewrite case to `<lane_classification>` under the bold label **Branch-range re-cite to working tree.**, as the case numbered 5, immediately after **`### staged` re-cite to working tree.** and modelled on it, so the existing cases 5 through 9 become cases 6 through 10 and the new case sits before every terminal membership case it feeds. A citation from the branch-mode `full_diff.txt` whose added lines appear in the working-tree file is renumbered from that match, anchoring the occurrence at the cited `HEAD`-side numbers when the lines appear more than once, and the walk continues to the membership cases, which assign the lane. A citation whose added lines no longer appear in the working tree falls through to **Catch-all.** and is listed with no fix. Rewrite the block's opening paragraph so its account of which cases are terminal and which only rewrite the location matches the new case list. Carry the renumbering into the comments that cite those cases: in `tests/git_auto_review/evals/fixtures/classifies_lanes_from_evidence/setup.sh`, `tests/git_auto_review/evals/fixtures/anchors_duplicated_staged_lines/setup.sh`, and `tests/git_auto_review/evals/fixtures/lists_local_commits_lane_finding/setup.sh`, every `case 7` reference becomes `case 8`. Case 4 keeps its number, so `tests/git_auto_review/RUNBOOK.md`'s "no verdict stopped at case 4" sentence stays true as written. `auto_gate_git` keeps loading the block from the skill rather than carrying a copy.
5. **Point the agents at the skill's target.** Rewrite the target bullet in the `<inputs>` of `auto_gate_git`, `auto_fixer_git`, and `auto_verifier_git` so it names the run's target as the `git_auto_review` skill's `<inputs>` **Target.** bullet defines it, on either shape.
6. **Route every automated review-and-fix ask to the loop.** Rewrite `git_auto_review`'s `description:` to name both targets and branch-shaped trigger phrases, such as "auto-review and fix this branch" and "loop review and fix over my branch against main". **Out of scope:**

- Rewriting, amending, or committing onto the branch's existing commits; the loop's fixes land as uncommitted working-tree changes.
- Checking out a branch or pull request on the user's behalf, which `git_checkout` owns.
- Editing `git_review`'s `scripts/collect_review_evidence.sh`; the gate combines its two existing modes.
- Changing which findings qualify for a fix under the **Severity floor.**; this task changes which targets the loop accepts.
