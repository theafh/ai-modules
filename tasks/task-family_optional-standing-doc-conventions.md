# Standing docs for the task family: conventions and consumption

## Goal

Define the task family's framework for optionally recognizing *and* consuming standing project documents at the repo root, without adding any required ceremony. It has two halves. The conventions: the filing rule that separates task-system material under `tasks/` from project-wide material at the root as `UPPERCASE.md` docs, and the tiered adoption model laid out as a graduated drift-prevention spectrum — from the hard charter guardrail that fences autonomous agents, through the verified test-discipline rule, to the purely descriptive `ARCHITECTURE.md` and the behaviour ledger. The consumption: the task skills and the agents they spawn consult the standing docs relevant to their work, each read gated on a presence check so it stays strictly optional — `CHARTER.md` is the top guard that any skill or agent about to write task content validates its proposed work against and must not violate, while the softer docs inform without blocking. Every tier and every touchpoint is opt-in, so a bare task repo with no root docs keeps working exactly as it does today, and a project adopts richness only as it reaches for it.

## Context

The filing rule the family adopts: material that is directly about the task system lives under `tasks/`, and material that is about the project as a whole lives at the repo root as an `UPPERCASE.md` document. This task owns the cross-cutting framework — the rule, the tiered model, and the consumption model below — while each individual root doc it governs is defined in its own sibling task, cited where that doc enters the spectrum.

The tiered adoption model reads as a graduated drift-prevention spectrum, each tier adopted only as a project reaches for it. The plain task chain is the default and fences nothing. The optional autonomous readiness loop comes next. Then the autonomous layer raises the one hard fence: the coupled charter guardrail keeps autonomous agents from drifting the project off its declared purpose (see [charter guardrail](task-family_charter-guardrail-for-autonomy.md)). The standing docs sit at softer strengths: the verified test-discipline rule that implement and audit consult but never block on (see [test-discipline skill](ai-dev_test-discipline-skill.md)), and the purely descriptive docs that enforce nothing — the architecture description settled below, and the behaviour ledger (see [feature-ledger behavior record](feature-ledger_behavior-record-skill.md)). Naming where each doc sits by enforcement strength is what makes the optional tiers and their prerequisites discoverable.

At the descriptive end of that spectrum sits `ARCHITECTURE.md`, the one standing doc this task defines directly: an optional, actively-maintained description — goals, stack, and design decisions — read to understand the system. It is deliberately distinct from the charter at the hard end, because the two sit at different altitudes: the charter is a falsifiable guardrail checked against the work, while the architecture doc is explanatory narrative that enforces nothing. It is therefore not folded into the charter, and it must not regress into a status-board or stage index — that ordering role is served by `task_select` and the optional regenerated build-order view — so it stays a description and can be omitted entirely.

Consumption is the operational half: the standing docs earn their place only when the skills *and the agents they spawn* actually read them. The mechanism is deliberately light — each consuming skill or agent carries an inline presence gate in its own rule prose, a portable `test -f "<root>/<DOC>.md"` check with the root resolved from the base skill's existing `<discover>` step (so `discover_tasks.sh` is untouched), and consults the doc only on a hit, proceeding unchanged when it is absent. The reminder lands at the moment the doc is needed, and consumption stays strictly optional. `CHARTER.md` is the top of the spectrum: any skill or agent about to write or change task content checks its proposed work against the charter and stops on a violation — the agents that do the autonomous writing carry this check most pointedly (today the `auto_*_task` agents `task_auto_check` spawns; tomorrow the autonomous implementer and shaper), since an unattended project drifts through them. The softer docs are read for context: task_create reads `FEATURES.md` and `ARCHITECTURE.md` ahead of its codebase scan, task_implement and task_audit read `TESTING.md` for the project's fluid testing specifics when writing or auditing tests, and task_finish updates `ARCHITECTURE.md` when the finished work extended the design.

This task owns the consumption model itself — the presence-gate convention and every doc's read by skills and agents, including the charter-validation read and the `TESTING.md` read — but not the docs' own artifacts and mechanisms. The `CHARTER.md` contract, its reusable template, and the protect hook that hard-blocks edits to the charter itself are created by the [charter guardrail](task-family_charter-guardrail-for-autonomy.md) task; that hook is the one piece reading-and-respecting cannot provide, so it stays the charter's distinct flavour while everything about *how* the docs are consulted lives here as one mechanism rather than a bespoke validator per doc. The standalone `test_discipline` skill that carries the durable testing rules, and the `TESTING.md` extension layer it defines, are owned by [test-discipline skill](ai-dev_test-discipline-skill.md) — this task only wires task_implement and task_audit to read `TESTING.md` when present. The `FEATURES.md` ledger and its refresh-after-ship courtesy stay in [feature-ledger behavior record](feature-ledger_behavior-record-skill.md), with this task adding only the create-time read.

## Approach

Document the filing convention (task-system material under `tasks/`, project-wide material as root `UPPERCASE.md`) in the base `task` skill prose — the family's standing documentation — as the single statement of the rule, keeping it skill-based and deployment-agnostic rather than tied to any one repo's README. The affected existing passage is that skill's `<architecture>` block (greppable tag `<architecture>`), whose `<project-root>/` tree and two-layer prose already describe the file layout the rule extends; rewrite that passage in place so the root `UPPERCASE.md` docs and the existing `tasks/` subtree read as one canonical layout statement rather than adding a second, competing layout description elsewhere in the skill.

Document the tiered adoption model in the base `task` skill prose as the graduated drift-prevention spectrum, building on the skill's `<family>` section (greppable tag `<family>`), which today lists the sibling skills but not the tiers: name each tier from the plain chain, through the autonomous readiness loop and the autonomous layer's hard charter guardrail, to the softer standing docs — the verified test-discipline rule, the descriptive `ARCHITECTURE.md`, and the `FEATURES.md` ledger. Document `ARCHITECTURE.md` as the descriptive-tier instance — an optional descriptive convention explicitly contrasted with both the charter (falsifiable guardrail) and any index or status-board role it must not take on.

State the consumption convention once in the base `task` skill: the task skills and the agents they spawn consult present root `UPPERCASE.md` docs as optional context or guardrails, each consumption gated on a portable presence check against the project root (resolved from the existing `<discover>` step), with the consumer proceeding unchanged and raising no error when the doc is absent. Then add each presence-gated touchpoint, phrased as "when `<root>/<DOC>.md` exists, consult it for «purpose»; when absent, continue unchanged":

- In task_create's `<prior_art>` / `<gather>`: when `FEATURES.md` and/or `ARCHITECTURE.md` exist, read them first as higher-signal prior-art and design context, before the codebase scan.
- In the `<readiness_checklist>` (so task_check and the auto_gate_task gate both apply it) and in the autonomous writing agents (`auto_reviewer_task`, `auto_verifier_task`, and future autonomous writers): when `CHARTER.md` exists, validate the proposed task content against its boundaries and invariants and stop on a violation, surfacing the conflict and leaving the work untouched.
- In task_implement and task_audit: when `TESTING.md` exists, read it for the project's testing specifics (stack, runner, layout, thresholds); the durable, stack-agnostic testing rules live in the standalone `test_discipline` skill, not here.
- In task_finish's `<archive>`: when `ARCHITECTURE.md` exists and the finished task extended the system's design, update it in the same archive pass.

Keep each gate's check POSIX-portable (`test -f`) per the repo's cross-harness portability rule. Add a one-line citation in an affected front-end skill or agent only where its own prose would otherwise read as silent on the doc; otherwise let the `<authority>` inheritance carry the rule.

Non-goals: making architecture or any root doc mandatory, flattening the tiers into one uniform guardrail set, and re-introducing a maintained global index or status board; changing `discover_tasks.sh` or adding any shared discovery script, registry, or session banner; and re-wiring the artifacts owned elsewhere — the `CHARTER.md` contract, template, and protect hook (charter task), the standalone `test_discipline` skill and the `TESTING.md` definition (testing task), and the `FEATURES.md` ledger and its refresh (feature task). Charter validation here is the agents and skills reading and respecting the contract, not a separate validator.

## Acceptance

- The filing convention (task-system material under `tasks/`, project-wide material as root `UPPERCASE.md`) is documented once in the base `task` skill, landed by rewriting the existing `<architecture>` block (greppable tag `<architecture>`) in place so one canonical file-layout statement covers both the `tasks/` subtree and the root `UPPERCASE.md` docs, with no separate competing file-layout statement left elsewhere in the skill.
- The tiered adoption model is documented in the base `task` skill as a graduated drift-prevention spectrum — plain chain → optional readiness loop → autonomous layer with its hard charter guardrail → softer standing docs (the verified test-discipline rule, the descriptive `ARCHITECTURE.md`, the `FEATURES.md` ledger) — naming where each doc sits by enforcement strength, and `ARCHITECTURE.md` is documented as the descriptive-tier instance, explicitly distinct from the charter and explicitly not a status-board or stage index.
- The consumption convention is stated once in the base `task` skill — skills and the agents they spawn consult present root `UPPERCASE.md` docs as optional, presence-gated context or guardrails, proceeding unchanged when a doc is absent — and a `grep` finds no competing second statement of the rule.
- On a staged repo fixture, task_create reads `FEATURES.md` and `ARCHITECTURE.md` for prior-art and design context when they exist and runs unchanged when both are absent; task_implement and task_audit read `TESTING.md` for the project's testing specifics when it exists and run unchanged when it is absent; and task_finish updates `ARCHITECTURE.md` when it exists and the finished task extended the design, leaving the archive flow unchanged when it is absent.
- On a staged task carrying a planted `CHARTER.md` boundary violation, task_check (and the auto_gate_task gate) and the autonomous writing agents `auto_reviewer_task` / `auto_verifier_task` surface the violation and leave the work untouched; with no `CHARTER.md` present, all of them behave exactly as before, and the check is the agent reading and respecting the contract rather than a separate validator.
- Each touchpoint's presence check is POSIX-portable and resolves the project root from the existing discovery step; a check confirms `discover_tasks.sh` is unchanged and no shared discovery registry or banner was added.
