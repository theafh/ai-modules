# Harden auto-loop stop conditions so the orchestrator cannot walk past them

## Goal

`git_auto_review` and the task-family loops stop where their rules say they stop. Only the invoking user's request raises a loop's round cap: the `round-cap-authority: user` attestation is a caller contract, and an orchestrator that writes it violates that contract, with the harness as the hard backstop. From round 2 the gate re-reviews the delta since the prior round, not the whole change, so unchanged code cannot keep generating new findings. A finding on a line the change did not add or modify is a follow-up task proposal, not a fix. Each round records why it continues, and every stop the loop controls writes `report.txt` with the cap source, the per-round continue reasons, and the unapplied findings. The prior severity-floor decision stays in force: `inferred` and should-fix findings remain eligible for a fix while the loop is under its cap.

## Context

- **Observed run.** A recent `git_auto_review` run over a large change in a downstream repository completed 10 rounds plus an aborted 11th, raised 28 qualifying findings, every one `non_blocking`, and landed 25 regression reproductions. The user asked why 11 rounds ran when the default cap is 5.
- **The cap was overridden by the orchestrator.** `<inputs>` accepts the literal phrase `round cap <N>` "written anywhere in the prompt". The orchestrator composes the prompt it invokes `git_auto_review` with, so it wrote `round cap 8`, then `10`, then was on `11` without any user instruction; the gate and fixer prompts are never cap sources. The cap is the loop's designed brake; the override handed the brake to the party the brake exists to restrain.
- **The re-review was not a delta review.** The `<role>` says the loop "re-reviews the delta", but `<round_driver>` says round 2+ uses "the same target shape as round 1". The gate therefore re-read the whole commit plus working tree every round and kept surfacing new `inferred`/should-fix items from unchanged code. That contradiction is the source of the long tail.
- **The scope anchor is elastic.** `<scope_anchor>` admits a finding that concerns "lines the change added or modified, or behaviour the change's intent covers". The second clause admitted an unmodified documentation bullet, an unmodified watcher branch, and an unmodified warm-up function. Those were the findings that pulled the loop into adjacent cleanup.
- **The self-written stop did not fire.** It counts only two consecutive rounds whose findings all sit in code the loop wrote. Findings on the original commit's code never count, so a large first change can run indefinitely without meeting it.
- **No round recorded why it continued.** The per-round record has `decision <continue|stop>` but no reason. A round could continue on a non-blocking nit without saying so.
- **`report.txt` was never written.** The run was stopped by the user, and the orchestrator ended without the terminal report the `<relay>` contract requires. The relay held gate, fixer, verifier, and round-diff files but no `report.txt`.
- **The severity-floor decision stays.** A prior repo decision deliberately removed a severity floor so `inferred` and "should be fixed" findings get fixed. This task does not re-introduce a floor, and it does not change `git_review`'s headings or labels.
- **Existing tests to extend.** `tests/git_auto_review/evals/` carries `honours_round_cap`, `stops_on_self_written_code`, `lists_preexisting_issue`, `lists_scope_extension`, and `fixes_inferred_and_should_fix_findings`; `tests/git_auto_review/script_tests/run.sh` carries `s4_convergence_labels_single_source` and `s5_carryover_blocks`; `plugins/ai_dev/skills/task_auto_check/SKILL.md` `<loop_bounds>` carries the same "unless the user prompt supplies a positive integer override" pattern. The shipped `honours_task_scope_anchor` eval expects an untouched-file finding to be fixed through the task file; it changes to expect a follow-up, because the task-file anchor no longer widens the line-level anchor, while its `honours_task_scope_anchor_no_task` twin already expects that follow-up. The `honours_round_cap` fixtures cite committed lines the change never modifies, so their cited lines move onto changed lines to keep the cap reachable.

## Approach

1. **Make cap authority user-only.** In `plugins/ai_dev/skills/git_auto_review/SKILL.md` `<inputs>`, replace the "written anywhere in the prompt" wording with: the phrase is read only from the invoking user's request, meaning the skill's own invocation prompt carrying the literal attestation line `round-cap-authority: user` that the invoking user's request supplies; an orchestrator-composed gate or fixer prompt is never a cap source; and an orchestrator-composed gate or fixer prompt carrying `round cap <N>` is a contract violation the run reports while still using the default cap. Absent the attestation the run uses the default cap and records `cap-source default`; with it the run records `cap-source user`. The attestation is a caller contract, not a security boundary: the loop trusts its invoking caller, and an orchestrator that writes the line violates the contract; the harness remains the hard backstop. Record `cap-source <user|default>` in the final-state block. Apply the same authority rule to `plugins/ai_dev/skills/task_auto_check/SKILL.md` in that skill's own vocabulary, editing both its `<inputs>` max-round bullet and its `<loop_bounds>`: the override is read only from the invoking user's request and counts only when that request carries the same `round-cap-authority: user` attestation, so a max-round value carried in an orchestrator-composed helper prompt is not an override and the run keeps the default cap. Add no `cap-source` field to `task_auto_check`; that field belongs to `git_auto_review` alone.
2. **State the cap as a hard ceiling.** In `<stop_rule>`, add: after the cap is reached the run stops and writes `report.txt`; no finding reopens a round. Keep the existing default of 5 and the user-supplied override as the only exception.
3. **Make round 2+ a delta review.** In `<round_driver>`, replace "with the same target shape as round 1" with: from round 2 the gate's review subject is the delta between the prior round's pre-fix snapshot and the current tree, so the subject carries the original change's lines plus the fixer's writes since that snapshot, with the current working tree supplying current line numbers only; `git_review` keeps its existing target resolution — a pull request, a branch, or nothing — so the delta is a subject filter the gate applies, not a new `git_review` target shape. The prior gate return supplies the prior findings set. A prior finding outside the delta is re-listed with its prior tag and no fix. A brand-new finding outside the delta is listed under the existing `What should be fixed though it is not a clear bug` heading as a follow-up task proposal, tagged `open`, with no fix; the scope anchor excludes it because its location is outside the delta. This adds no heading and no new tag value. A pre-seeded gate return is the gate's already-classified output and is not re-filtered. Keep the full-change review on round 1 only. In `plugins/ai_dev/agents/auto_gate_git.md`, add the prior-round snapshot path `round-r<N-1>.diff.txt` to `<inputs>` for round 2 on, rewrite the branch-target union-subject clause "collect two evidence sets each round and read their union as the review subject" so the two collections still run but the review subject is the delta above, and replace its `<policy>` delta sentence "take the same target shape as round 1 as the review subject" with: "from round 2 the review subject is the delta between the prior round's pre-fix snapshot and the current tree, composed here without changing `git_review`'s target resolution; a prior finding outside the delta is re-listed with its prior tag and no fix, and a brand-new finding outside the delta is listed under `What should be fixed though it is not a clear bug` with tag `open` and no fix." Update the agent's frontmatter `description` to name the delta subject and the outside-delta disposition.
4. **Tighten the scope anchor to changed lines.** In `<scope_anchor>`, require the finding's `location` to intersect a line the change added or modified, or a line in a path the change created. A behaviour-level finding on unmodified code becomes a follow-up task proposal. A finding whose location does not intersect a changed line or a created path is a follow-up even when the task file's Goal and Acceptance describe the behaviour, because the task file no longer widens the line-level anchor. In `<lane_classification>` case 9, replace "Assign `lane` `working-tree lane`, so a finding the **Scope anchor.** admits outside the diff, including a task-file-anchored finding on an unmodified tracked file and a finding in a local commit or a branch commit whose file the working tree still carries, stays fixable." with: "Assign `lane` `working-tree lane`. A finding whose `location` lies outside a changed line, such as a task-file-anchored finding on an unmodified tracked file, does not meet the **Scope anchor.** and is listed as a follow-up task proposal with no fix; the `lane` assignment records only where its lines live. A finding in a local commit or a branch commit whose file the working tree still carries stays fixable, because that commit's added lines are changed lines under the **Scope anchor.**"
5. **Require a continue justification.** Add a `continue-reason` field after `decision` in the per-round record in `<relay>`: a `continue` decision names the qualifying finding and why it cannot be deferred; an empty reason forces `stop` on the new condition `an empty continue-reason`, added to the **Stop rule.** condition list and the `final-state block` `stop` enumeration. Refresh the worked per-round example line with the new field. Do not force a stop merely because the findings are `non_blocking`; the cap and the delta review are the brakes, and the severity-floor decision stays in force.
6. **Write the report at every stop.** In `<report>`, require `report.txt` on every stop path after the relay exists, including a helper failure after relay creation and the cap; the relay-init failure keeps `<initialise>`'s reprint-only contract because no relay directory exists. Add a final check: before returning, verify `report.txt` exists and carries the final-state block on every path that created a relay, and skip the check on the no-relay init-failure path. Place `cap-source <user|default>` after `stop` in the `final-state block` field list and update the field list.
7. **Pin the text and behaviour in the harness.**
   - Extend `s4_convergence_labels_single_source` in `tests/git_auto_review/script_tests/run.sh` to assert the user-only override sentence, the hard-ceiling sentence, the delta-review sentence, the line-level scope-anchor sentence, the empty-reason-forces-stop sentence, and the `cap-source` and `continue-reason` tokens in `git_auto_review/SKILL.md`, asserting in `task_auto_check/SKILL.md` both its `<inputs>` and `<loop_bounds>` clauses and that no `cap-source` field appears there. Also assert that `rg -F "written anywhere in the prompt"` and `rg -F "or behaviour the change's intent covers"` find nothing in the files they were replaced in.
   - Keep `honours_round_cap` as the user-override run: add the literal attestation line `round-cap-authority: user` to its `evals.json` `prompt` beside `round cap 2`, update its `expected_output` so the default-5 case belongs to the new eval, and assert it stops at 2 and records `cap-source user`. Add a second eval `ignores_orchestrator_round_cap` with its own fixture directory whose staged `prompt` carries `round cap 8` and no `round-cap-authority: user` attestation line; assert the run uses the default 5 and records `cap-source default`. Re-stage both fixtures' `gate-r1.txt` through `gate-r5.txt` so every cited line sits on a line the change adds or modifies, keeping the five-round sequence. Name both ids in their `evals.json` entries, their `setup.sh` and `grade.sh` arms, and `SERIAL_NESTED_LOOP_IDS` in `run.py`.
   - Add an eval `delta_re_review_excludes_unchanged_code`: round 1 fixes an in-scope defect; the round-2 pre-seeded gate return carries a second finding on an unmodified file outside the delta, under `What should be fixed though it is not a clear bug` with tag `open`; assert the loop lists it as a follow-up with no fix, its file stays byte-identical, and the eval is named in `SERIAL_NESTED_LOOP_IDS`.
   - Update `honours_task_scope_anchor`'s `evals.json` `expected_output`, its `gate-r2.txt` prose, and its grade arm to expect the unmodified `helper.py` finding as a follow-up with no fix and the file byte-identical, matching its `honours_task_scope_anchor_no_task` twin; the pair now proves a task-file anchor does not widen the line-level scope anchor. Update the shared fixtures' header comments and `gate-r1.txt` prose, which currently say the task file admits the finding.
   - Extend the `fixes_in_scope_bug` grade arm to assert its round-1 per-round line carries a non-empty `continue-reason` that names the qualifying finding id, so a continuing round records why it continued; add an eval `empty_continue_reason_forces_stop` whose fixture supplies an empty round-1 reason and assert the run records `decision stop` with the `an empty continue-reason` stop label and writes `report.txt`. Name its `evals.json` entry, its `setup.sh` and `grade.sh` arms, and its `SERIAL_NESTED_LOOP_IDS` entry.
   - In the cap and post-init helper-failure grade arms, assert that `loop_report()` succeeds, so the `report.txt` existence promise fails on a reprinted-only run rather than passing through `report_text()`'s response fallback.
   - Record each new or changed eval in `tests/git_auto_review/evals/README.md` and `tests/git_auto_review/RUNBOOK.md`, and run the named evals on the default Cursor `auto` vendor.
8. **Bump versions.** Raise `version` in `plugins/ai_dev/skills/git_auto_review/SKILL.md`, `plugins/ai_dev/skills/task_auto_check/SKILL.md`, and `plugins/ai_dev/agents/auto_gate_git.md` (a patch bump from 1.0.3), and raise `plugins/ai_dev/.codex-plugin/plugin.json`, `plugins/ai_dev/.claude-plugin/plugin.json`, `.agents/plugins/marketplace.json`, and `.claude-plugin/marketplace.json` to the same new plugin version in the implementing commit, per the standing repo rule.

**Out of scope:**

- Re-introducing a severity floor, or changing `git_review`'s headings, its `verified`/`inferred` labels, or how it sorts findings. The prior severity-floor decision stays as made.
- Changing `git_review`'s review criteria or its own target shapes.
- Changing `task_auto_check` beyond the cap-authority sentence and its harness pins.
- Observing or reporting a hard user abort, meaning the harness or user killing the run outside the loop's own stop conditions; a kill the loop cannot observe carries no report requirement.
- The downstream change that exposed the run; this task hardens the loop, not that change.
