# Ship agent_spinner's decision and research recipes, and rewrite variants.md

## Goal

agent_spinner is the skill an orchestrating agent, the orchestrator, reads before it runs helper agents. A recipe is a reference file under `plugins/ai_dev/skills/agent_spinner/references/recipes/` that gives the step-by-step procedure for one common kind of job: its helper phases, the steps the orchestrator runs itself, and its checks. The reference file `references/variants.md` holds less common ways to run helpers, called variants, such as keeping concurrent helpers isolated from each other.

After this task, an orchestrator finds a matching recipe when its ask does one of three things. The ask weighs design options or challenges a built design, researches a corpus into one deliverable, or settles a disputed figure or claim by an edit. The orchestrator then follows that recipe's phases, orchestrator steps, and checks.

This task ships three recipe files, `option-panel.md`, `research-synthesis.md`, and `disputed-claim.md`, with their rows in the `<selector>` recipe table and one eval per recipe. The table maps each kind of ask to its recipe file, and each eval is a behavioural test on a staged fixture. The task rewrites `references/variants.md` around the blind and calibration variants these recipes apply. It also ships the eval for the positive control on a snapshot search, a rule that two of the recipes carry. That rule makes a helper's first search of its file copies find a token the brief names as present, before an empty result counts.

- **Terms the recipes use.** The run protocol and the checks define these terms:
  - The run ledger is the program `scripts/run_ledger.py`, bundled with the skill, which keeps a run's records under `.agent_spinner/`. Its commands are verbs. `init` opens a run over an enumerated list and records the baseline, and `close` ends the run. A clean `close` exits 0, which it does only when nothing is left open.
  - `brief` renders a helper's brief from the run's files. `snapshot` copies the files a reading helper needs into the run directory, and `snapshot --base` copies them as they stand at the base commit, before any working-tree change. `search` searches the run directory, `show` prints one row's records in full, and `dispose` records each record's final disposition.
  - The baseline is the state of the files, and the output of each named gate, when the run opens. The net diff is every change between the baseline and the final tree. A gate is either a deterministic command, such as a linter, or a user gate, a question the user must answer before the run goes on. A positive control is a known positive that a count or search must find before its empty result counts (C4).
  - The roster lists the run's rows, mostly one row per helper and its unit of work. A return is what a helper hands back, and `accept` checks it and imports its records, such as findings and claims, before it counts. `rows` creates the rows of a later phase from accepted records, one row per record.
  - A wave is a group of helpers sent out together. The tiers are the ways a run can execute. At the inline floor the host offers no way to spawn helpers, so the orchestrator runs every pass itself, one after another. Under batch delivery, a batch of spawned helpers returns together inside the turn. Under notice delivery, a spawn returns at once and a notice reports its completion later.
  - A fork is a real decision that belongs to the user. A decision packet puts one fork to the user, with its options, their costs, and a recommendation.
  - A lens is one angle a helper reads from. A refute-by-default checker starts from the position that the work is wrong and clears it only with a cited span. A judge scores every candidate on one criterion. A completeness critic names what a finished body leaves out, and its paired surplus read names what to remove (C6).
  - A finding is recall-confirmed when a checking pass was shown it and did not refute it, and independently surfaced when a pass found it unprompted. A pass is blind by prompt when only its brief keeps a claim from it, with no host record to confirm that it never read the claim (C2).
  - Each fact carries an evidence tier: measured, read, documented, placeholder, or inferred (C10). The **Approved decisions these recipes apply.** bullet says which tiers settle a fact. An unsettled fact stays conditional, meaning a deliverable states it with the probe that would settle it.
  - Tool evidence of a full read is a record, such as the helper's tool log, showing that it read the whole file (C8). Yield is the helpers dispatched set against the decisions or edits they produced.
- **Approved decisions these recipes apply.** The owner approved each on 2026-10-03.
  - Only a fact measured against the primary system, or read in finished content of the artifact the claim is about, counts as settled. Documentation-derived, placeholder, and inferred claims stay conditional. This replaces the archived spinner task's "facts already settled that nobody re-derives". The checking-doctrine task writes it into `<prompt_assembly>` and C10, and the isolation section of `variants.md` follows it here.
  - Read snapshots are file copies under the run directory, and the run writes no ref, tree, commit, or object into the user's repository. A pass that must not see a working-tree change reads `snapshot --base`.
  - Every run states an estimate. The run asks before any widening past the enumerated list, and before it goes above a size guideline the host or user states. An answer stated in the request counts as the user's answer.
- **Why a snapshot search carries a positive control.** `snapshot` copies files under the run directory, whose own `.gitignore` holds `*`. Search tools that honour ignore files, ripgrep among them, find nothing inside such a directory until given an explicit file path. [The host observations note](../wiki/raw/notes/agent-delegation-host-observations-2026-09.md) records this under `## Shell and workstation behaviour`. A designer's or sweeper's search of its copies therefore proves an absence only after it has found a token the brief names as present (C4).
- **Where the evidence lives.** The anonymized wiki page [orchestration failure families](../wiki/concepts/orchestration-failure-families.md) holds the basis for each recipe step. A failure family is a group of observed failures that share one root cause, and the page gives each family's base rates and its cases under neutral labels. Its step map under `### Recipes and step map` keys on the recipe ids J1 to J8 and on the P and C labels. Each recipe therefore keeps its id in its H1 and cites steps and checks by those labels, so each step traces back to its evidence. Recipe files carry rules only and cite no wiki page, because `CHARTER.md` requires that "Published artefacts remain self-contained". The step map's J5 row still names the paired refute-by-default check for a challenged build; this task's Trigger and the selector precedence sentence supersede that clause, and the recipe keeps id J5 as the row's key.
- **Greps over the skill directory.** `tests/agent_spinner/script_tests/run.sh` scans every file under the skill directory, references included. These checks of it therefore reach the recipe files and `variants.md`: `every target product name cites harness_portability`, `no per-harness frontmatter keys or tool identifiers`, `no harness agent directory paths`, `no instruction to write a global rules or agent-config file`, and `no template claims precedence over the surrounding conversation`. Its checks `variants.md carries the information-isolation variant` and `variants.md carries the replicated-draw variant` pin the two existing headings.

The re-run rules under `## Re-run Economy` say when a recorded result stands in for a fresh run. The Test Integrity classes under `## Test Integrity` say how to class an added or edited check. ## Approach

### Recipe file layout

Write the three files in the layout the recipes the review-repair recipes task ships use, which that task's per-recipe checks enforce. Each file has one outer tag named after the file stem, the field tags `RECIPE_FIELDS` lists, in that order, two to four numbered phases in `<phases>`. Write in pseudo-XML with positive, action-oriented wording, as the standing repo rules require. Write rules only, with no session figure, cost observation, case evidence, harness product name, tool identifier, harness path, instruction-file name, or precedence phrase. Cite run-protocol steps and checks by their P and C labels, and name ledger verbs and flags only from the command reference in run-protocol.md.

Copy every shared line from the same field of `check-only-audit.md`, which the review-repair recipes task ships, where each stands as a paragraph of its own and holds its `RECIPE_SHARED_LINES` phrase. Put this recipe's shape in the trigger line. None of the three runs a repair round of its own, so no `<orchestrator_gates>` among them cites C5, and none carries the `RECIPE_REPAIR_LINES` paragraphs. As in those recipes, the first orchestrator step runs the gate-scope check before dispatch, and the **Report** step builds the report from the ledger after a clean `close` (P6). A run whose flag-ledger pass leaves an entry open exits `close` nonzero, and its **Report** step still runs, its opening sentence stating that `close` exited non-zero, as P6 requires. `<tier_notes>` holds one note each for the inline floor, batch delivery, and notice delivery. The option panel and the research synthesis pair their completeness critic with the surplus read C6 requires. The field contents below leave out what the shared lines already say, so each field holds its shared lines plus the content listed here. Where a recipe applies a variant, it names `variants.md` and the variant's heading, as the contents below show.

In each recipe section below, the bold label of a field bullet names its field, such as **Trigger.** for `<trigger>` and **Cost profile cuts.** for `<cost_profile>`. **Ledger steps.** names the ledger commands the run makes, **Width.** says how many helpers each phase gets, and **Adversarial checks.** says how checkers try to refute the work. **Orchestrator gates, in run order.** lists the steps the orchestrator runs itself, and **Tier notes.** says what changes at each tier.

### `option-panel.md`: J5, design option panel

Its H1 reads `# J5. Design option panel`, and its outer tag is `<option_panel>`.

`SKILL.md` carries the routing change in the same commit, so the selector and the recipe name one route. The checking-doctrine task rewrites the `<selector>` paired-check bullet in place to "A write that lands, whoever wrote it, you included: a paired refute-by-default check.", and its Acceptance pins that exact text while its selector rule keeps the bullet through any later edit. Keep the bullet byte-identical. Add one precedence sentence to `<selector>` after its bullet list and before the recipe table: "A challenged built design routes to its recipe row ahead of the paired-check bullet: the design carries no accepted producer return to paste, and the recipe's Refute phase supplies the adversarial read." A challenged built design then matches the recipe table's option-panel row, the run's opening names the lens panel as the Trigger states, and the paired-check bullet keeps its route for every other landed write. The same change narrows `<selector>`'s inline sentence: replace "A read-only diagnostic or single judgement question is answered inline" with "A read-only diagnostic, or a single judgement question about a mechanism not yet built, is answered inline", leaving the rest of that sentence, including "before any helper is spent", byte-identical.

- **Trigger.** The shape is a lens panel, several helpers reading one subject from different angles. The ask matches when the user asks for options, when a built but uncommitted design is under challenge, or when a work item adds a public surface or rules out a competing mechanism. A challenge to a built design matches this recipe under that same lens-panel shape, because the design is the one subject its lenses read and its Refute phase supplies the adversarial read. A question why one mechanism and not another about a mechanism not yet built is a single judgement question, answered inline, unless the ask requests options.
- **Ledger steps.** `init` takes one Design row per designer. Every designer brief lists the same options, with each reading of the user's hypothesis among them, where a reading is one distinct interpretation. Create the blind base snapshot with `snapshot --base`, and name its file paths in every designer brief, so the designers see the files as they stood before the candidate change. Sighted judges and refuters, who may see the change, read a `snapshot` of the working tree. Hand your preference notes to `brief` as withheld text, so only their hash enters the designer rows. The refuters' numbered claims become ledger records, and you build the decision packet from those records, read through `show`.
- **Phases.** **Design**: three to five blind designers each write options over the base snapshot and read no earlier return (`variants.md`, `## Information isolation between concurrent helpers` and `## Blind derivation`). Each returns a fixed template: a verdict on the shipped mechanism and, for each option, why it wins or loses, its cost, its coverage regression, and its preferred end state. A coverage regression is coverage the option would lose, and a preferred end state is the outcome the designer would choose. Where claims can be executed, the designer builds the candidate in its own scratch copy of the base snapshot under the run directory. It runs the existing suite unmodified and reports the measured numbers. The Design phase carries this rule verbatim: "A designer's first search of the base snapshot must find a token the brief names as present there (C4). When that control finds nothing, the designer reads each named file in full and reports the search as blind." **Judge**: a judge per criterion scores the full candidate set, reading every designer return by path against the repository. It scores on an anchored scale with a one-line definition per point, ranks at most three fatal flaws with a span each, and states the strongest argument against its own verdict. **Refute**: lens-split refuters, one each for facts, reasoning, and consequences, test the judges' leading claims, reading the judges' returns.
- **Width.** Design gets three to five designers, Judge gets one judge per criterion (two to four), and Refute gets three refuters. One critic runs with one surplus read.
- **Roles and returns.** The designer and the judge return as their phases state. The refuter returns numbered claims, each with a verdict and a citation, plus its corrected recommendation verbatim. The critic returns gaps with file-and-line citations and paste-ready fixes.
- **Adversarial checks.** Read the refuters for their reasons: number every load-bearing claim, and re-derive each with shown output. A refuter's brief defaults its verdict flag to refuted, so the flag carries no information, and no survival vote comes from it. Support counts as convergence only when every preferred end state matches. The decision rests on re-derived claims and surviving forms, meaning each claim in the form that survived refutation, and the scores appear in the report as context.
- **Orchestrator gates, in run order.**
  - **Scout**, before Design: write the settled facts by tier (C10), meaning the baseline numbers the design addresses, each caller and the options it passes, and any precedent. Derive the candidate's footprint, the files it touches, from the modified and untracked set, then run `snapshot --base` over the tracked paths among them, because `snapshot --base` reads each path at the base commit and stops when the base commit lacks it. Confirm through the ledger's `search`, with its positive control fired, that the base snapshot holds zero hits for the candidate's distinctive tokens (P5). This shows that the blind copies lack the candidate. Run the gate-scope check before dispatch.
  - **Framing and the scope question**, before Design: split the user's hypothesis into its distinct readings and brief each as an option of its own (`variants.md`, `## Splitting a hypothesis into its readings`). Describe the shipped mechanism neutrally, give every option the same fields, record who wrote the descriptions, and leave out selling points. Add an invite-your-own option, a slot for a designer's own proposal, and one angle arguing the change is the wrong call. Keep your preference notes out of the workspace until the designers return, and put scope and the estimate to the user.
  - **Critic with its surplus read**, after Refute: a repository-grounded completeness critic plus a surplus read (C6).
  - **Decision packet**, after the critic (P6): the packet lists each option with its supporters by role, each helper's preferred end state verbatim, and the option's strongest recorded objection. It lists every reconciling variant a helper proposed, meaning an option that reconciles the others. It states the fate of each reading: ruled out, collapsed into another option, or survived. After the choice, the chosen option's objections enter the follow-up item, each with a disposition. The run asks once before writing when an unaddressed objection narrows a blocking check.
  - **Report**, from the ledger after a clean `close`, before any build hand-off.
  - **Build hand-off**: when the ask includes building, run `multi-file-task.md` with the paired check over the diff.
- **Gates beside the steps**, closing `<orchestrator_gates>`. Every comparison is non-vacuous, meaning both sides ran and met their expectation (C4). Measured numbers are compared across helpers in the open, and any mismatch is reported. A base-snapshot check runs before dispatch, and a spot-check of one blind helper's commands runs afterwards.
- **Failure handling.** A missing designer earns one re-invocation. A judge whose tool evidence shows less than a full read of the candidate set violates its contract (P3, C8).
- **Stop and ask.** Ask about the readings before dispatch, at the decision, and before building when a cheaper or safer alternative surfaced.
- **Report.** The report gives the menu of options with its objection lines, each reading's fate, claims marked re-derived or taken on a helper's word, and yield. Label the designers blind by prompt, and blind only where an audit of the host's helper logs, at a path the caller supplies, shows no read outside the pass's admitted inputs (C2).
- **Cost profile cuts.** The cuts are designers beyond three, which drop angles, and criteria beyond two, which drop judged dimensions.
- **Tier notes.** Inline floor: designers run as separate passes over the base snapshot, and the report labels the blindness recall-limited, because one context holds every pass. Batch delivery: one batch per phase. Notice delivery: the judges wait on every designer row, polled inside the turn with `accept --wait` (P4).
- **Post-run checks.** The base snapshot shows zero candidate tokens through `search`, and every option has at least one analysis and an objection line. No preference note existed in the run directory before the designers returned, and the roster held only its hash. The follow-up item names each objection against the chosen option, and each reading's fate is stated.

### `research-synthesis.md`: J6, understand-then-synthesize research

Its H1 reads `# J6. Understand-then-synthesize research`, and its outer tag is `<research_synthesis>`.

- **Trigger.** The shape is a lens panel. The ask is research, an assessment, a feasibility study, or mining across a large corpus into one deliverable, such as a specification, a task, an assessment, or a proposal.
- **Ledger steps.** `init` takes the corpus manifest, the list of sources in scope, with its exclusions and one topic row per reader. `rows --phase verify --from-records '*:findings:*'` creates one verifier row per finding record before any verifier brief exists, and it runs once Judge's returns are accepted; each reader records its load-bearing claims as findings, and each drafter records its own draft's load-bearing claims as findings, so every load-bearing claim, the leading option's among them, has a row and every row gets a verifier. Accept the synthesis candidate only by its echoed id, the identifier its return repeats back. The deliverable and every later artifact get check rows.
- **Phases.** **Understand**: a reader per topic row returns tiered facts and reads no earlier return. Each topic row carries a reason. The shared preamble and the phase's access block, which states what the pass may read and write, give these rules: no writes, cite file and line, tag every fact as measured, read, documented, placeholder, or inferred, and name what could not be verified (C10). The return template holds facts and open questions, and each lineage gets at least one lens on outcome and reaction evidence. **Draft**: three to five drafters each write one angle, reading the briefing file merged from the Understand returns. The angles include the user's floated option and one angle arguing that the premise is wrong. Helper-derived material enters each brief as a hypothesis the drafter verifies, with a brief-corrections slot where the drafter records what it found wrong in its brief. **Judge**: a judge per criterion scores the full draft set, reading every draft by path. It scores on an anchored scale with a one-line definition per point, ranks at most three fatal flaws with a span each, and states the strongest argument against its own verdict. **Verify**: a neutral refuter tests each load-bearing claim, reading the judges' returns and the drafts they score. Verification covers the premises and the leading option's claims. Each claim is stated neutrally, the refuter names what would make it survive, and it returns survives, narrowed, or refuted with a span.
- **Width.** Understand gets one reader per topic row. Draft gets three to five drafters, Judge one judge per criterion, and Verify one verifier per load-bearing claim. One critic runs with one surplus read, and each shipped artifact gets one checker.
- **Roles and returns.** The reader returns facts with tier and span, open questions, and what it could not verify. The drafter returns its draft with its label, its load-bearing claims as findings, and brief corrections. The verifier returns, per claim id, a verdict, a span, a confidence, and what would make the claim survive. The judge returns as its phase states, and the critic returns gaps with file-and-line citations and paste-ready fixes.
- **Adversarial checks.** A pivotal number, one the verdict turns on, gets one blind derivation (`variants.md`, `## Blind derivation`). Refutation is neutral. Before the synthesis reads any candidate, recovered results pass the identity check: one distinguishing line of the candidate must match what the judges said about it (P3).
- **Orchestrator gates, in run order.**
  - **Scout and manifest**, before Understand: inventory every candidate source with counts, deduplicate by content hash, and write the included and excluded sources with a reason for each. Class each source as intent, outcome, or reaction evidence. Run the requirement-source scout (who asked, and where it was discussed), reading each source or asking for it. Run the gate-scope check, and announce the manifest, the unique counts, and the estimate.
  - **Briefing merge**, after Understand: write one briefing file with the open questions attached to their sections, passed by path. Settle only measured and read facts. A documented, placeholder, or inferred fact stays conditional in the unverified-premises block, the part of a brief that lists unsettled claims, and a deliverable states it with the probe that would settle it (C10). Start the flag ledger, a file that lists every narrowed claim, unverified note, and condition with its record id, and add to it each claim Verify narrows. Run the primary-source probe, a check against the system the claim is about, for every negative claim the verdict rests on (C10). Re-derive the three to five claims the verdict will rest on while the helpers run.
  - **Deliverable merge and flag-ledger pass**, after Verify: you or one merge writer merge the deliverable. A separately prompted pass then reads the flag ledger against it and reports each entry used unnarrowed or with its condition unmet, and every such entry blocks. The pass's accepted return carries one finding record per blocking entry, and the run leaves that record undisposed until the entry is resolved, so `close` exits nonzero while one stands (P6).
  - **Critic with its surplus read**, after the flag-ledger pass: a repository-grounded completeness critic and its paired surplus read both review the merged deliverable, and their gaps and uncontested removals fold into it before the check (C6).
  - **Check what ships**, after the critic: run the paired check on the merged deliverable (C1), and the same check on every later artifact built on the run. For an outbound message, that check runs before the send approval.
  - **Report**, after `close` on either exit: the report the **Report.** field describes, and when the exit is not clean it names each open entry that blocked the close and states in its opening sentence that `close` exited non-zero, as P6 requires.
- **Gates beside the steps**, closing `<orchestrator_gates>`. The gates count the helpers dispatched, returned, and accepted per phase. They count settled facts by tier, with only measured and read facts counted as settled. The ledger holds zero unresolved conflicts. The verdict distribution is not uniform: when every claim fell the same way, re-read the prompts for steering (C7, and `variants.md`, `## Calibration controls`).
- **Failure handling.** The acceptance gate, which is the check `accept` makes, runs before any brief uses a return. A placeholder earns one re-invocation, and a hollow return blocks the phase that depends on it.
- **Stop and ask.** Requirement sources out of reach, and scope, go to the user. The user approves before any outbound send. A limit that a critic proposes and that trades against the user's stated aim is adopted only as a surfaced decision, after re-reading the case it cites.
- **Report.** The report gives the tiers, with the provenance class of every number, and the unverified list with each claim's probe. It names the candidate the synthesis used, by id and score, lists the items added and removed with reasons, and states yield.
- **Cost profile cuts.** The cuts are drafters beyond three, which drop angles, and verifier rows for claims the verdict does not rest on, which drop secondary checks.
- **Tier notes.** Inline floor: readers run as separate passes, with the briefing on disk. Batch delivery: one batch per phase, with independent phases in one wave. Notice delivery: re-derive the load-bearing claims while waiting inside the turn in `accept --wait` polls (P4).
- **Post-run checks.** The coverage the lenses read matches the manifest, counting a path as read only where tool evidence shows a full read (C8). Every claim and number in the deliverable carries its tier, every fact below the read tier is stated as conditional with its probe, and no flag-ledger entry is used unnarrowed. Every shipped artifact has a check row, and the synthesis names its candidate by id.

### `disputed-claim.md`: J8, disputed-claim settlement

Its H1 reads `# J8. Disputed-claim settlement`, and its outer tag is `<disputed_claim>`.

`SKILL.md` carries this shape in the same change, so no shape rule contradicts the recipe's two refuters. `<shapes>` adds `<two_refuter_settlement_check>`: **Trigger** a proposed edit that settles a disputed figure or claim; **Width** exactly two refuters per proposed edit, each carrying a different brief, with the count and its reason stated first; **Prompt skeleton** the paired refute check's skeleton, run once per refuter; **Return** the paired refute check's return, plus the alternatives with their derivations and the provenance of every number the edit introduces. Name the paired refute check in plain prose inside this block, because `run.sh` requires exactly six shape tags inside `<shapes>` and a further tagged reference turns that check red, while Acceptance requires `bash tests/agent_spinner/script_tests/run.sh` to pass. `<selector>` adds the bullet "A disputed figure or claim settled by an edit gets a two-refuter settlement check."

- **Trigger.** The shape is the two-refuter settlement check. Two passages of a source, or a source and its derived documents, disagree on a figure or claim, and the ask is to settle it, usually with an edit. A disagreement the ask only asks about is a read-only diagnostic. A disagreement the ask wants settled by an edit matches the two-refuter settlement check, and then this recipe.
- **Ledger steps.** Keep your hypothesis, your own proposed resolution, out of the run directory until the deriver returns. Hand it to `brief` as withheld text when the deriver's brief is rendered, so only its hash enters the deriver's row. Write its text after the deriver returns. `init` writes one sweep row per corpus. `snapshot` copies the sources, and every reading brief names those copies' paths. Give every alternatives entry, each alternative reading a refuter returns, a disposition with `dispose`, and surface each alternative to the user as a fork in the decision packet. The net diff audits the write set before `close`.

Each occurrence carries its exact quote, its anchor, and a provenance class: finished prose, placeholder or to-do note, comment, or derived page. The Sweep phase carries this rule verbatim: "A sweeper's first search of the snapshot must find a token the brief names as present there (C4). It reads the sweep returns' provenance classes and never the hypothesis, and it returns its own resolution with its derivation. **Refute**: two refuters test the proposed edit, reading the sweep returns and the proposed edit as before-and-after text, and their briefs exist only after the deriver returns. Each opens from the position that the edit is wrong or incomplete. Refutation covers a better-supported value, a rewording that keeps the value but changes what it refers to, and a value resting on placeholder content. Each refuter returns its alternatives with derivations and the provenance of every number the edit introduces, and a boolean-only return, a bare yes or no, is rejected.

- **Roles and returns.** The sweeper returns occurrences with provenance. The deriver returns its resolution and derivation. The refuter returns a verdict, alternatives with derivations, and the provenance of each number.
- **Adversarial checks.** Replicated draws, several runs of one identical prompt, are reported unreduced (`variants.md`, `## Replicated draws returned unreduced`). A seeded confirmation, one whose brief carried the claim, counts as recall-confirmed.

  - **Decision packet**, after Refute: every alternative and every placeholder-sourced number goes to the user as a fork with a recommendation. A number settles only when it is measured, or read in finished prose of the source the claim is about. A number from a placeholder or to-do note, a comment, or a derived page stays conditional (C10). Writes stay blocked behind any gate you announced.
  - **Write and net-diff audit**, after the user answers: apply the edit, then run the net-diff audit against the committed baseline.   - **Report**, from the ledger after a clean `close`.

- **Report.** The report puts each checker on its own line with its derivation and its ledger tag: recall-confirmed where its brief relayed the claim, and independently surfaced otherwise. Reserve "confirmed" for a resolution surfaced independently or re-derived against the source, and split the confirmations into recall-confirmed and independently surfaced. Label the derivation blind by prompt unless the log audit shows otherwise, and give the provenance class of every number.
- **Cost profile cuts.** The cut is the second edit refuter, taken as a `<coverage_tradeoff>` narrowing rather than a second allowed width: it drops the second independent look at the edit, and the run puts the narrowing to the user before the refuters' briefs exist, naming the alternatives and placeholder-sourced numbers that look would have surfaced, and takes the cut only on the user's word.

Batch delivery: sweep, derivation, and refutation go out as separate batches, and the refuters' batch waits for the deriver's accepted return. Notice delivery: render the refuters' briefs once the deriver's return is accepted, and poll inside the turn with `accept --wait` (P4).
- **Post-run checks.** The deriver's brief carries no hypothesis text, the roster held only its hash until the deriver returned, and the report labels the derivation blind by prompt unless the log audit shows otherwise.
