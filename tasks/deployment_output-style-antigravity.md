# Deploy the output style to Antigravity

## Goal

Antigravity receives the repository's output style as an always-on rule, deployed by the same `style` artefact type the groundwork task adds, at whichever scope the run selects. Both scopes take the same shape, because current Antigravity reads rules from a `rules/` directory at each: under `--project-dir` the deploy writes one ordinary rule file into that project's `.agents/rules/`, and under `--global` it writes one ordinary rule file into the user-owned `~/.gemini/config/rules/`. The deployed rule file carries `trigger: always_on`, one of the valid values Antigravity requires of every file in a `rules/` directory; a file there that omits frontmatter or names an unrecognised trigger is silently discarded. Uninstall removes exactly the file the deploy wrote and leaves every other rule file byte-identical.

## Context

This builds on [the Claude groundwork task](archive/deployment_output-style-claude-groundwork.md), which shipped the repo-root source directory, the `style` artefact type, and the deploy-log restore behaviour. This task adds one target and no new machinery beyond the rule write described below.

The wiki records the mechanism in [system prompt substitution across harnesses](../wiki/comparisons/system-prompt-substitution-across-harnesses.md), with the paths on its [Google Antigravity](../wiki/entities/google-antigravity.md) page. The essentials, verified against `antigravity.google/docs` on 2026-11-25: the config-tree surfaces document no tone or output-format setting and no system-prompt-replacement feature, so the whole mapping runs through rules, while the Python SDK's `system_instructions` is a separate programmatic surface this deploy does not write. Rules are cumulative rather than replacement-based, so the deployed prose competes with default guidance instead of displacing it.

Antigravity ships as the Antigravity App, the Antigravity CLI (`agy`), the Antigravity IDE and its editor extensions, and the Antigravity SDK. The docs at verification time were App v2.35.1, CLI v1.5.16, and IDE v2.8.0, and the documented CLI install runs `curl -fsSL https://antigravity.google/cli/install.sh | bash` into `~/.local/bin/agy`. A machine can run older builds, so the deploy resolves the documented locations and proves itself on a scratch tree rather than depending on the installed version.

Workspace rules are `<dir>/AGENTS.md`, `<dir>/GEMINI.md`, `<dir>/.agents/AGENTS.md`, `<dir>/.agents/GEMINI.md`, and `<dir>/.agents/rules/*.md`, read at the workspace folder and each parent folder up to the repository root, with the legacy `.agent/rules/*.md` still read. Global rules are the four standalone files `~/.gemini/AGENTS.md`, `~/.gemini/GEMINI.md`, `~/.gemini/config/AGENTS.md`, and `~/.gemini/config/GEMINI.md`, which need no frontmatter and stay always active, plus the modular `~/.gemini/config/rules/*.md`, where frontmatter is required. Antigravity scans each customization folder one level deep, so a rule file sits directly inside `rules/`; a nested file loads only when a `rules.json` manifest names it.

Two limits shape this task. Antigravity truncates any single rule file larger than 24,000 bytes, measured after `@[label](path)` includes expand, and all active global and `always_on` rules share a 20,000-token aggregate budget, over which Antigravity demotes the largest files to pointers. The style body is 14,628 bytes today, so it fits the byte cap; the deploy still measures the generated content against the live cap rather than assuming it fits, and fails with a clear message when it does not.

Antigravity is also a non-Claude harness whose plugin bundle can carry rules, so a plugin-integrated route exists here beside the two config-tree scopes. This task takes the config-tree routes at both scopes and leaves the plugin bundle alone, since bundling ties the rule's reach to an installed plugin rather than to the tree the deploy writes.

## Approach

Generate the Antigravity variant once and write it by whichever shape the scope requires, resolving the destination from the script's existing Antigravity directory variables rather than hardcoded paths: `ANTIGRAVITY_DIR` is `<project>/.agents` under `--project-dir` and `~/.gemini/config` under `--global`, so the rule file lands at `"${ANTIGRAVITY_DIR}/rules/<name>.md"` in both modes.

Write one ordinary Markdown rule file per scope, carrying `trigger: always_on` frontmatter. The file belongs to the deploy, so redeploy replaces it and uninstall removes it outright. Leave every other rule file untouched, and write nothing into the four standalone `AGENTS.md` and `GEMINI.md` files: those belong to the user and carry no frontmatter, so a marked block there would need marker parsing that the modular directory makes unnecessary.

Check the generated content against the 24,000-byte per-file cap before writing, and fail with a message naming the actual size and the limit when it does not fit, rather than truncating or writing a file the harness will truncate. Report the generated size in the deploy output, because the file also competes for the shared 20,000-token `always_on` budget.

Generate rather than copy. Strip the Claude frontmatter and emit `trigger: always_on`; rewrite the `<engineering_behavior>` element that names Claude's `keep-coding-instructions` mechanism, following `generate_cursor_style_rule` in `deployment/deployment.sh`, which replaces that element wholesale. The replacement reads `<engineering_behavior>The wording rules govern the named prose surfaces. Coding and tool-use behaviour stay with Antigravity's defaults. This harness only appends.</engineering_behavior>`. The style source carries no `$VAR$` token, so no `replace:` rule applies to it.

Refresh the Antigravity wiki pages through the wiki skill family. The Google Antigravity page (`wiki/entities/google-antigravity.md`) states the global rules route in two passages, and each takes the same rewrite. The first is `### Global roots split by artefact class`, which today names the standalone `~/.gemini/GEMINI.md` as the single-file alternative one level above `config/`; the second is `### Rules and workflows`, which today offers `~/.gemini/config/rules/` or the standalone `~/.gemini/GEMINI.md` applied across all workspaces. Both name the modular directory beside all four standalone global rule files, so no passage on the page offers one standalone file as the global-rules route. That first passage names `three products` twice, and each occurrence changes. Its opening sentence, `Antigravity ships as three products`, becomes the four current surfaces: the Antigravity App, the Antigravity CLI, the Antigravity IDE and its editor extensions, and the Antigravity SDK. Its reach sentence, `So one global deploy reaches all three products for agents, hooks, MCP, and sidecars, and fails to for skills and plugins`, names the configuration-reading surfaces in place of the count: a global deploy reaches the App, the CLI, and the IDE with its editor extensions for agents, hooks, MCP, and sidecars and fails to for skills and plugins, while the SDK reads no configuration tree and stays outside a global deploy's reach. The page's `### Rules and workflows` passage gains the documented discard rule, that a rule file with missing frontmatter or an unrecognised trigger is silently discarded, and its `## Verification gaps` section keeps `frontmatter tolerance` among its open questions: that gap is unknown-key tolerance, which `/docs/rules/` leaves untouched and which `wiki/queries/antigravity-open-verification-gaps.md`'s `### Frontmatter tolerance` section records as unconfirmed, so the query page stays as written. Rewrite [Antigravity global configuration roots](../wiki/concepts/antigravity-global-roots.md)'s `### Everything else converges` passage, which the entity page links for the per-class paths, so it names those same four standalone files beside the modular directory in place of its single `~/.gemini/GEMINI.md` alternative. Rewrite [Output style delivery design](../wiki/concepts/output-style-delivery-design.md) in place so its account of this target matches the arm the deploy ships: its `### What the deploy writes per target` Antigravity row and its `### The content transform needs no new machinery` paragraph each state the carrier this task delivers and the generation route it uses, while the built-rows paragraph directly beneath that table (the paragraph opening `Claude and Cursor are the built rows` and closing `Every other row stays per-target delivery work`) takes the single job of naming Antigravity among the shipped rows and no longer listing it as per-target delivery work. Replace the existing text at each site rather than adding a second account beside it. Retitle the `### The marked block is the one new mechanism` section `### The marked block stays the unshipped alternative` and rewrite it to record a route no shipped target uses: its body states that Antigravity's global file was that block's candidate and now takes a rule file, and its existing Codex `~/.codex/AGENTS.md` sentence stays inside that section as the second target whose additive route lost to the synthesized replacement. That transform paragraph's claim that the remaining append-only targets still plan a `replace:` placeholder, and that the targets built next choose between the two routes, is the one this task settles, because the Antigravity variant is generated in the generation step as `generate_cursor_style_rule` generates Cursor's.

**Out of scope:**

- The plugin bundle's rules component, which reaches only the sessions where that plugin is installed rather than every session in the tree the deploy writes.
