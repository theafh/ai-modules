# Add git_auto_review, an automated review-and-fix loop around git_review

## Goal

Add `git_auto_review`, an opt-in loop beside `git_review` that does for a finished change what `task_auto_check` does for a task. It runs `git_review` as its only gate under the Approach's `auto_gate_git` contract, fixes the findings that qualify through a single writer agent, verifies each round's fixes refute-by-default, re-reviews the delta, and repeats until no qualifying finding remains under the **Stop rule.**, or another of that rule's stop conditions fires. Every fix stays in the working tree, uncommitted. The loop carries five convergence rules from the start, which the Approach states once under **State the convergence rules once**.

## Context

The user ran `git_review` by hand in rounds with fixes in between throughout October 2026. One change, the git_review secret scan, took nine review rounds and eleven fix rounds in one day. Each round surfaced defects earlier rounds had missed, defects the previous fix had introduced, and requests to extend scope to new input shapes and pre-existing configuration behaviour. Across 34 tasks studied from 2026-09-24 to 2026-10-24, fix rounds introduced about 40 of the 280 findings raised after readiness. Reviews also found what audits had passed, because a review builds adversarial inputs, which is the value this loop automates and the reason it needs explicit convergence rules. The review findings that drove those rounds came from a frontier-model review; the new agents inherit the orchestrator's model like the task family's agents.

The gate is `plugins/ai_dev/skills/git_review/SKILL.md`. Its report sorts findings under "What is critical", "Bugs it may introduce", and "What should be fixed though it is not a clear bug", labels each `verified` or `inferred` and marks the non-blocking ones, and keeps "Decisions the implementer must make before fixing" in a section of its own. On a delta re-review its `<tags>` rule tags every prior finding closed, open, open and not acknowledged, settled by a decision, or regressed, and tags a defect first seen in the delta `new`. When this loop runs `git_review` as the gate, the Approach's `auto_gate_git` contract keeps that skill's review criteria, headings, labels, and `<tags>` as written and forbids its mutation paths, so only `auto_fixer_git` edits the working tree.

The shape to mirror is `plugins/ai_dev/skills/task_auto_check/SKILL.md`: `<single_gate>`, `<relay>`, `<verification_standard>`, `<audit_delta>`, `<concurrent_modification_guard>`, `<agent_failure_policy>`, and `<loop_bounds>`, with its agents under `plugins/ai_dev/agents/` and the doctrine in `wiki/concepts/agent-delegated-automation.md`.

The boundary with [the autonomous implement loop](../task-family_autonomous-implement-loop.md): its `task_auto_implement` runs implement, audit, re-implement on findings, and finish, and its audit answers whether the task was built. `git_auto_review` answers whether the change is correct and mergeable. It runs after a clean audit, or on any change the user names with no task at all, and neither loop re-runs the other's gate.

When neither route yields a default branch, the run aborts; when the current branch is not the resolved default branch, the run declines. Coordinate convention (once): working-tree line numbers when the cited lines exist in the working-tree file the fixer edits — so location, fixer anchor, and the Stop rule's authored-hunk parse share those lines; index-world line numbers still as `path:start` / `path:start-end` when the finding has no working-tree counterpart. The sole signal that a finding is not a working-tree line is `lane` `local-commits lane`; `location` carries no mark field. `auto_gate_git`'s Approach-pinned `<output_contract>` template stays unchanged. Walk the cases in order. Cases 1–3 and 5–8 are terminal: the first matching terminal case sets that finding’s location handling, `lane`, and fix disposition. Case 4 is a location rewrite only: when it matches, rewrite `location` as that case states, then continue the same ordered walk from case 5 so a later terminal case assigns `lane` and disposition; when none of cases 5–7 match, **Catch-all.** is the terminal case:

     4. **`### staged` re-cite to working tree.** Same `### staged` citation whose added lines still appear in the working-tree file: match those lines there and number `path:start` / `path:start-end` from the match; when they appear more than once, anchor the occurrence at the cited index-world numbers. → rewrite to the working-tree `path:start` / `path:start-end` this case states (non-terminal; assigns no `lane`); continue the ordered walk from case 5 using that location.
     5. **`### unstaged` membership.** Path and range fall inside a `### unstaged` hunk at the working-tree lines the location names. → `working-tree lane`.

2. **State the convergence rules once** in a `<convergence>` block of the skill:
   A finding qualifies for auto-fix — and is a qualifying finding for the **Stop rule.** and `auto_verifier_git` triage — only when its `tag` permits qualification, it meets the **Scope anchor.**, meets the **Severity floor.**, has `lane` `working-tree lane` under **Lane classification.**, and is not held under **Decisions.** Tag permit: round-1 `none`, and on a delta re-review `open`, `open and not acknowledged`, `regressed`, and `new`, each still subject to the four conditions that follow; `closed` and `settled by a decision` never qualify and receive no fix. This paragraph states how every gate-listed finding that does not qualify is classified and handled, once: the run lists the finding with its `lane` and no fix, naming it a follow-up task proposal where it is a pre-existing issue or a scope extension under **Scope anchor.**, a lane-excluded finding under **Lane classification.**, a severity-floor-excluded finding under **Severity floor.**, or a tag-excluded finding (`closed` or `settled by a decision`) under this paragraph's tag permit. That one classification renders on the two surfaces each already holds: the gate's `git_review` report keeps the finding under its heading, whose presence follows `<first_review_presence>` and `<delta_presence>` as written, and `report.txt` carries the finding as its one line under `<relay>`. This reporting obligation overrides `git_review`'s `<non_findings>`, `<lint_baseline>`, and `<only_what_is_open>` suppression rules inside `auto_gate_git`'s composition of that gate `git_review` report — the first of those two surfaces — so a non-qualifying finding the classification keeps stays present under its heading there; `report.txt` remains only the loop's terminal surface under `<relay>`, distinct from that gate report, and is not itself the subject of those `git_review` suppression rules.
   - **Scope anchor.** A finding meets the Scope anchor when it concerns lines the change added or modified, or behaviour the change's intent covers, read from the anchoring task's Goal and Acceptance when a task file is given. A reproduction `auto_fixer_git` adds is not part of the change under review: a file reproduction lives at a path of its own that its `ledger.txt` line names and that no path under review shares, and the gate and verifier label a location as reproduction lines when its path matches a path named in `ledger.txt`, so a finding whose location sits only in reproduction lines never meets the Scope anchor, is listed in the report, and receives no fix; the reproduction's own correctness is enforced by the **Regression ledger.** restore-and-retry, not by gate qualification. A pre-existing issue and a scope extension go to the report as follow-up task proposals.
   - **Severity floor.** Findings under "What is critical" meet the Severity floor regardless of `verified` or `inferred` label. `verified` findings under "Bugs it may introduce" also meet the Severity floor. `inferred` findings under "Bugs it may introduce" and every finding under "What should be fixed though it is not a clear bug" are listed in the report. The gate verdict's `non_blocking` field is reporting-only: it carries `git_review`'s non-blocking mark through the structured verdict and does not enter the qualification conjunction.
   - **Regression ledger.** The ledger is `ledger.txt` in the run's relay directory, one reproduction per line, each line the reproduction's path, a tab, then the command that runs it, so the path **Scope anchor.** matches a finding's location against is a named field. A bundled script, `scripts/run_ledger.sh`, runs each line's command field in order and reports each line's 1-based number with its pass or fail; it exits 0 on an all-passing ledger and on an empty ledger, and exits non-zero naming the 1-based number of the first failing entry. The orchestrator runs it after every fix round. A failing line restores the round's pre-fix state and repeats the round once with the failing line named to the fixer; a second failure restores the pre-fix state and the **Stop rule.**'s second-ledger-failure condition stops the run.
   - **Decisions.** Every entry under "Decisions the implementer must make before fixing", and every finding whose fix depends on one, goes to the user and receives no fix. When a task file anchors the run, the run only threads that wording out: `report.txt` carries the wording and the pending decisions under `<relay>`, while the base `task` skill's `<update>` workflow — with `<status_discipline>` deciding the status — is the change the user applies after the stop, so no agent in the run writes outside the working tree and the relay.
   - **Stop rule.** A round is one gate cycle — the unit the cap, the consecutive-round stop, and the authored-hunk append all count. Round lifecycle, in this order:

     1. **Open.** One `auto_gate_git` call (the first review, then each delta re-review).
     2. **Decision-pending early close.** When the gate return carries any entry under "Decisions the implementer must make before fixing", or any finding held under **Decisions.**, the round closes on the Stop condition "a decision is pending" without invoking Triage, `auto_fixer_git`, the ledger check, or `<audit_delta>` — including when other findings would otherwise qualify for auto-fix.
     3. **Empty-qualifying early close.** When Open’s verdict carries no qualifying finding, the round closes on the Stop condition "no qualifying finding remains" without invoking Triage, `auto_fixer_git`, the ledger check, or `<audit_delta>`. Triage never runs on an empty qualifying set.
     4. **Triage.** `auto_verifier_git` triage of that verdict (reached only when the qualifying set is non-empty and **Decision-pending early close.** did not close).
     5. **Empty-approved early close.** When triage of a non-empty qualifying set returns an empty approved set, the round closes on that Stop condition without invoking `auto_fixer_git`, the ledger check, or `<audit_delta>`.
     6. **Self-written early close.** When this round's qualifying findings are a non-empty set, every one of them sits in loop-authored code under case **Self-written stop.** below, and the immediately preceding round also met that same condition, the round closes on the Stop condition "two consecutive rounds whose qualifying findings all sit in code the loop wrote in an earlier round" without invoking `auto_fixer_git`, the ledger check, or `<audit_delta>`.
     7. **CHARTER-refusal early close.** When `CHARTER.md` exists and the orchestrator’s CHARTER-before-write validation refuses the approved set under **Keep the run safe and reversible.** (after that set is known, before any `auto_fixer_git` spawn), the round closes on that Stop condition without invoking `auto_fixer_git`, the ledger check, or `<audit_delta>`; `report.txt` follows the charter-set-refused reporting that block already states.
     8. **Snapshot.** When none of **Decision-pending early close.**, **Empty-qualifying early close.**, **Empty-approved early close.**, **Self-written early close.**, or **CHARTER-refusal early close.** closed the round, `run_snapshot.sh` writes the round's pre-fix artefacts (and the round-1 baseline pair when that pair is absent) after Open's gate return is in place and before the first `auto_fixer_git` invocation; early-close rounds invoke neither `run_snapshot.sh` nor a rewrite of those artefacts.
     9. **Fix.** `auto_fixer_git`'s fix (skipped when **Decision-pending early close.**, **Empty-qualifying early close.**, **Empty-approved early close.**, **Self-written early close.**, or **CHARTER-refusal early close.** closed the round).
     10. **Ledger check.** The **Regression ledger.** check, with its own one restore-and-retry.
     11. **Audit delta.** `<audit_delta>`, with its own one restore-and-retry.
     12. **Close.** The point the loop returns to the gate for the next round or stops. When this round reached **Fix.** and the **Ledger check.** and **Audit delta.** both succeeded with the round's writes still landed (no Restore undid them), the orchestrator rewrites `authored.txt` under the stem directory per the cases below; when a Restore undoes the round's writes, or when an early close skipped **Fix.**, leave `authored.txt` unchanged. After Close, before the next Open, the run evaluates the round-cap stop: every completed gate cycle counts toward the cap (**Decision-pending early close.**, **Empty-qualifying early close.**, **Empty-approved early close.**, **Self-written early close.**, and **CHARTER-refusal early close.** included); when the completed-round count has reached the cap (default 5, or the override), the run stops under the round-cap condition without opening another round.

     A restore-and-retry stays inside its round and never starts or counts a new one. "fix round" and the ledger's "repeats the round once" name this same unit. The run stops when any of these conditions holds:
     - no qualifying finding remains;
     - after `auto_verifier_git` triage of a non-empty qualifying set, the approved set is empty;
     - a decision is pending;
     - a cap of 5 rounds unless overridden, evaluated after Close before the next Open as step **Close.** states;
     - two consecutive rounds whose qualifying findings all sit in code the loop wrote in an earlier round;
     - a helper failure under `<agent_failure_policy>`;
     - a second **Regression ledger.** failure after that rule's one restore-and-retry;
     - a second `<audit_delta>` unmapped-hunk result after its one restore-and-retry;
     - `<concurrent_modification_guard>` finds the working tree diverging from that round's pre-fix snapshot for a reason other than this run's fixer;
     - the CHARTER-before-write validation refuses a write a qualifying finding's `Fix:` requires, so the refused path holds no write from this run.
     Cases for the **Close.** rewrite and the self-written stop:

     1. **Entry shape.** One entry per line; each line is the greppable `path:start` or `path:start-end` form **Lane classification.** already settles (1-based inclusive), naming the path and the line range `auto_fixer_git` changed on that path in whole-file coordinates on the working-tree file the gate numbers `location` against.
     2. **Re-anchor.** A hunk an earlier round recorded is re-derived at its current lines when a later round's fix shifts them.
     3. **Derivation.** Diff the run's authored baseline against the current working tree; take each changed path plus the line ranges that diff marks on the current file, so `authored.txt` holds the loop's cumulative authored changes at their current whole-file lines.
     4. **Baseline vs per-round snapshot.** Authored baseline is the round-1 pre-fix copy kept as `baseline.patch` and `baseline.untracked.tar` under the stem; it is distinct from the per-round `pre-fix.patch` and `pre-fix.untracked.tar` that `run_snapshot.sh` writes and rewrites each round that reaches **Snapshot.** and never writes over the baseline pair.
     5. **Materialize and diff.** Temporary directory = copy of `HEAD` with `baseline.patch` applied and `baseline.untracked.tar` extracted; `diff -ruN -U0` against the working tree yields each changed path (fixer-added or fixer-deleted paths included, present on only one side) and each hunk's line range on the current working-tree file.
     6. **Self-written stop.** Parse each gate finding's `location` for a path and a line or line range; the finding sits in loop-authored code when that path matches an entry's path and the parsed line or range intersects that entry's range; the stop rule reads only `authored.txt`.

Each of these relay files holds exactly one round's record, all under the stem directory: `gate-r<round>.txt` holds that round's gate return, consumed verbatim as the gate return in place of a gate invocation only when `gate-r<round>.preseed` is present beside it at the round's start, so a `gate-r1.txt` an earlier run left with no marker is cleared and the round invokes the gate; `fixer-r<round>.txt` holds the round's `auto_fixer_git` records in invocation order, each one prompt-plus-return pair, its prompt followed by its return, so a retry's additional invocation appends its pair after the prior pair in that same file; `verifier-r<round>.txt` holds the round's `auto_verifier_git` records in invocation order — the triage invocation's prompt-plus-return followed by each delta invocation's prompt-plus-return, its prompt followed by its return in each case, so a retry's second delta invocation appends after the first. `round-r<round>.diff.txt` holds the round's fixer-write diff: the orchestrator writes it after the round's `auto_fixer_git` writes and before the verifier's delta invocation, as a zero-context unified diff (`diff -U0`) of the round's pre-fix snapshot against the current working tree, so each hunk is one contiguous changed region.    - `<verification_standard>`: refute-by-default triage and delta verification through `auto_verifier_git`.

   - `<agent_failure_policy>`: a helper failure stops the run, with no retry.
