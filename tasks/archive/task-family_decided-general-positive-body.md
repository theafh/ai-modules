# Keep the task body a resolved, general, forward spec at an implementable density

## Goal

Six authoring rules for the task body get a sharpening pass, so a body carries the resolved, general, forward-looking spec and stays dense enough to implement from. Three tighten rules that already shipped; three are new — one keeps user-specific and sensitive detail out of the body by default, one bounds the set at an implementable density, and one frames a change to an existing artifact as an in-place rewrite of the affected passage rather than an addition alongside it.

- **Resolve what you can derive.** Before labeling a decision open, the agent exhausts the resolution paths available at authoring time — the cited skills, the codebase, the project's standing knowledge. A fork answerable from that material is not genuinely open and gets decided; labeling open stays the last resort for a choice that genuinely needs input the agent cannot derive, and the one-open-decision ceiling stands.
- **Generalize from the motivating instance.** When a task is mined from a concrete episode to improve a reusable artifact — a skill, a framework, a shared rule — the unit of meaning to keep is the general lesson, not the episode's specifics. The agent writes the general rule and demotes the originating instance to a brief motivating illustration, leaving out instance and session detail that does not generalize.
- **Keep rejected-option debate out.** The body states the current state (what exists, and what is not there yet) and the target it should reach. The rationale for options the agent weighed and rejected lives where design rationale belongs — the change's own commit or pull-request description, or a wiki page when it is durable design knowledge — not in the task an implementer follows.
- **Keep user-specific and sensitive detail out by default.** A body generalizes rather than embedding user-specific or sensitive specifics — absolute or home filesystem paths, secrets and credentials, personally identifiable data, and incidental product, project, tool, or person names. Repo-specific detail enters only when the user explicitly asks for it or the work genuinely needs it, surfaced as a deliberate choice rather than added silently or by default; when the agent judges a specific might be necessary and it is unclear whether to include it, it asks the user for the level of detail rather than guessing it in or out. This protects sensitive information and keeps the spec agnostic from the rare originating incident.
- **Compact only to the implementable floor.** A body is written compact, and compression stops at the floor where a one-shot implementer can still act without re-deriving what was dropped. Past that floor, compression is a defect rather than economy: clauses stacked until the logic between them is lost, an edit site named without the shape of the change, a rule given without the one example that fixes its meaning. Each such gap is filled by a guess, and a guess is where a wrong or incomplete implementation enters. This rule is the counter-weight to the three above — they move residue out of the body, and it keeps that removal from cutting into the detail the work needs.
- **Rewrite in place, don't append.** When a task changes an existing artifact, the body frames the work as rewriting the affected passage in place to its target form — naming the passage that exists and what it becomes — rather than as "add X". An "add X" framing leads an implementer to append a parallel passage and leave the stale original standing, so the artifact ends up carrying two coexisting statements that drift apart. The default is to rewrite or supersede the existing passage; the genuine-addition framing is reserved for where the artifact has no counterpart yet, where the surface is append-only by design (a changelog, an activity or decision log, a commit message), where a comment or design note carries load-bearing evolution, or where two similar-looking rules cover genuinely distinct situations and both belong. This applies the project's standing preference for rewriting a rule in place over appending a refinement to the way a task body itself describes an edit.

## Context

The first three rules each extend a rule that already shipped into the base `task` skill, so each is a follow-up that sharpens an existing rule. The other three are new. Most edit sites are in `plugins/ai_dev/skills/task/SKILL.md` and reach the siblings through `<authority>`; the rewrite-in-place rule also lands a matching advisory in `task_fix`'s assess phase, the way the shipped positive-framing rule did.

- **Resolve what you can derive** extends [task-family_single-statement-open-decision.md](task-family_single-statement-open-decision.md), which shipped "one labeled open decision is the ceiling." into the `<body>`'s **Decide or label** rule. That rule set the ceiling and "resolve every either/or before the file is written" but no test for what makes a decision *genuinely* open; this adds the exhaust-derivable-resolution test. Edit site: `<body>` **Decide or label**.
- **Generalize from the motivating instance** reconciles two shipped rules for a case neither covers: [task-family_lossless-conversion-check.md](task-family_lossless-conversion-check.md) preserves "Every relevant unit of meaning in the source", and [task-family_gather-altitude-probe.md](task-family_gather-altitude-probe.md) makes an incident-shaped request "default to the point-fix". When the source is an episode mined to improve a reusable artifact, the relevant unit is the general lesson and the point-fix under-reaches. Edit sites: the `<gather>` altitude paragraph (the home of the new statement, since it already decides point-fix vs general), the `<lossless_conversion>` contract (which references that statement), and the `<body>` **Illustrate** rule the demotion leans on.
- **Keep rejected-option debate out** narrows [task-family_positive-task-body-rule.md](task-family_positive-task-body-rule.md). That rule's "Write the body positive and action-oriented" welcomes, among negatives, "a deferred or explored alternative"; this narrows the explored-alternative allowance so a brief non-goal or guardrail stays while the rejected-options rationale moves out of the task. Edit sites: the `<body>` positive-framing rule and the `<readiness_checklist>`'s **Negation-framed behaviour** item.
- **Keep user-specific and sensitive detail out by default** has no prior task. It adds a privacy-and-redaction dimension the bundle did not carry. Where **Generalize from the motivating instance** governs *altitude* — keep the general lesson, demote the episode to illustration — this governs the *identifying and sensitive tokens in the prose*: paths, secrets, personally identifiable data, and incidental names, regardless of altitude. It adds two things that altitude rule lacks: an explicit-consent gate (repo-specific detail enters only on the user's request or a genuine need, never silently) and an ask-when-unclear interaction. It reads as a fourth removal rule beside the unresolved fork, the originating specific, and the rejection debate. Edit sites: a new rule in the `<body>` authoring block; the `<gather>` step, which gains the ask-for-level-of-detail interaction beside its altitude decision; and the `<readiness_checklist>`, which gains an item flagging a body that embeds such detail without an explicit need so both `task_check` and the pre-write self-check catch silent inclusion. It points at **Generalize from the motivating instance** and the `<body>` **Illustrate** rule rather than restating them.
- **Compact only to the implementable floor** has no prior task. It operationalizes the base skill's self-sufficiency bar (the `<single_shot_ready>` pitfall) and sharpens the `<readiness_checklist>`'s **Ambiguity / under-specification** item, which today catches missing requirements but not prose compressed past the point of reliable execution. Edit sites: a new rule in the `<body>` authoring block, and a pointer from that readiness item. It belongs in this task because it is the direct counter-weight to the removal rules — co-locating them lets an implementer, and the readiness check, balance "cut the residue" against "keep what the work needs" in one place.
- **Rewrite in place, don't append** has no prior task. It is the operative consequence of the current-state-to-target framing **Keep rejected-option debate out** sets up above: that rule shapes the body as current-state to target, and this one fixes what *the target* is when the artifact already carries a passage on the concern — the rewritten passage, edited in place, not a second one added beside it. It generalizes the project's standing rewrite-in-place-over-append preference to the way a task body describes an edit, and carries that preference's full carve-out set — the exceptions the rule enumerates below. Edit sites: a new rule in the `<body>` authoring block; a reconciliation of **Keep rejected-option debate out**'s current-state-to-target wording so *the target* defers to this rule rather than reading as "what to add" (State once — this rule owns the rewrite-vs-add meaning, the framing rule points at it); the `<readiness_checklist>`, which gains an item flagging an edit-task body framed as "add X" without naming the passage to rewrite; the `<body>` **Acceptance** contract, where an edit-task item asserts the prior passage is superseded rather than only that content was preserved, since a bare preservation check passes an accretive edit; and `task_fix`'s assess phase, which gains a surface-and-propose advisory mirroring the shipped restated-standing-rule advisory in [task-family_fix-restated-rule-check.md](task-family_fix-restated-rule-check.md). Positive-vs-negative phrasing of the edit instruction is already governed by [task-family_positive-task-body-rule.md](task-family_positive-task-body-rule.md); this rule governs placement (rewrite vs append), not phrasing.

The six cohere as one change to the task-body authoring surface and the points that enforce it — `<body>`, `<gather>`, `<lossless_conversion>`, `<readiness_checklist>`, the `<body>` **Acceptance** contract, and `task_fix`'s assess phase: four move a kind of residue out of the body — an unresolved fork, an originating specific, a rejection debate, a user-specific or sensitive specific — one keeps that removal from cutting past the implementable floor, and one governs how the body frames an edit to an existing artifact so the change rewrites a passage in place instead of stacking a second one beside it. They ship as one task because splitting them would make each re-derive that shared spine, would separate the removal rules from the counter-weight that bounds them, and would split the rewrite-in-place rule from the current-state-to-target framing it builds on.

Motivating episodes, kept as illustrations: an agent mined a multi-session episode into tasks for a skill family and, in the body it wrote, left a decision labeled open that it resolved from first principles the moment it was asked to, argued the body around rejected design options, and — until told up front — risked carrying the episode's domain specifics into a general rule (the first three rules); the same kind of episode can pull user-specific paths, incidental names, and other sensitive specifics into a rule meant to generalize, which stay out unless the user asks for them (the redaction rule). Reviewing a later draft, the reader found rules named but their edit shape compressed away, leaving an implementer to guess (the density floor). In the same episode, asked to refine an existing rule, an agent wrote a fresh passage restating the updated version and left the original standing, so the document then carried two overlapping statements of one rule that drifted apart (the rewrite-in-place rule). The same episode's create-decision lessons — re-deriving the delta against shipped work and sizing by cohesion — ride the sibling task [task-family_prior-art-delta-and-cohesion-sizing.md](task-family_prior-art-delta-and-cohesion-sizing.md); this file leaves them there and carries only the body-writing rules.

## Approach

- **Decide or label.** In the `<body>` **Decide or label** rule, add the derivable-resolution test: the agent first resolves the fork from the material available at authoring time — cited skills, codebase, standing knowledge — and labels open only a choice that genuinely needs input it cannot derive. Keep the ceiling and the existing "resolve before writing" thrust; point the rule at this test rather than restating the ceiling.
- **Generalize.** Author the artifact-improvement case once, in the `<gather>` altitude step. State that when the source is a concrete episode mined to improve a reusable artifact — for example, a working session with a skill that exposed a rough edge, yielding a task to improve that skill — the altitude is the general rule the episode argues for, not the point-fix, and the originating episode rides along only as the brief illustration the `<body>` **Illustrate** rule already provides. Then reference that one statement from `<lossless_conversion>`, so "every relevant unit of meaning" reads, for this case, as: the unit to preserve is the general lesson; the episode's specifics are illustration, not content to retain verbatim.
- **Positive framing.** In the `<body>` positive-framing rule, narrow the explored-alternative allowance: a brief non-goal or guardrail stays welcome in the body, and the rationale for options weighed and rejected moves out of the task — to the change's commit or pull-request description, or to a wiki page when it is durable design knowledge (the `<not_a_wiki>` pitfall's path for a lasting lesson). Frame the body shape as current-state (what exists, what is not there yet) to target, and let the **Rewrite in place, don't append** rule define what *the target* is for each affected passage rather than fixing it as "what to add" here. Update the `<readiness_checklist>`'s **Negation-framed behaviour** item to point at the narrowed rule.
- **Redaction and consent.** Add the redaction rule to the `<body>` authoring block: a body generalizes rather than embedding user-specific or sensitive specifics — absolute or home filesystem paths, secrets and credentials, personally identifiable data, and incidental product, project, tool, or person names — and repo-specific detail enters only on the user's explicit request or a genuine need of the work, surfaced as a deliberate choice rather than added by default. In the `<gather>` step, add the interaction beside the altitude decision: when the agent judges a specific might be necessary and it is unclear whether to include it, it asks the user for the level of detail rather than silently including or dropping it. Point the `<readiness_checklist>` at the rule with an item that flags a body embedding such detail without an explicit need. Keep this distinct from **Generalize from the motivating instance** — that rule owns altitude, this owns the identifying and sensitive tokens — and reference the **Illustrate** rule rather than restating it.
- **Density floor.** Add the density-floor rule to the `<body>` authoring block: write compact, and stop at the floor where a one-shot implementer can act without re-deriving dropped detail. Name the failure shapes it guards against — clauses stacked until the logic between them is lost, an edit site named without the shape of the change, a rule given without the one example that fixes its meaning — and the test that applies it: would this file, plus the project, let an implementer produce the intended change without filling a gap from outside? Compress while that holds; stop when it breaks. Point the `<readiness_checklist>`'s **Ambiguity / under-specification** item at this rule so the check covers over-compression, not only missing requirements.
- **Rewrite in place.** Add the rewrite-in-place rule to the `<body>` authoring block: when a task changes an existing artifact, the body frames the work as rewriting the affected passage in place to its target form — naming the passage that exists and what it becomes — and defaults to rewrite/supersede over append, because an "add X" framing leads an implementer to append a second passage and leave the stale one standing. Name the carve-outs where an addition is correct: no existing counterpart, an append-only-by-design surface (changelog, activity or decision log, commit message), a comment or design note whose evolution is load-bearing, and two similar-looking rules that cover genuinely distinct situations. State the rule once and have **Keep rejected-option debate out**'s current-state-to-target framing defer to it for the meaning of *the target*. Point the `<readiness_checklist>` at the rule with an item that flags an edit-task body framed as "add X" without naming the passage to rewrite, carrying the same carve-outs so it does not fire on a legitimate addition. In the `<body>` **Acceptance** contract, add that an edit-task item asserts the prior passage is superseded — one canonical statement remains — rather than only that content was preserved, since an accretive edit passes a bare preservation check. Add the matching advisory to `task_fix`'s assess phase: surface (never auto-fix) a body that framed an artifact edit as an append where an in-place rewrite was intended, propose the rewrite, cite the base `<body>` rule rather than restating it, and respect the carve-outs and the instruct-vs-narrate line the restated-standing-rule advisory already draws.
- Author each rule once in the base skill, leading with positive carriers, and let the siblings inherit by reference per the family's single-source convention.
