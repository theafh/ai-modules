# Add git_auto_review, an automated review-and-fix loop around git_review

## Goal

Add `git_auto_review`, an opt-in loop beside `git_review` that does for a finished change what `task_auto_check` does for a task. It runs `git_review` as its only gate under the Approach's `auto_gate_git` contract, fixes the findings that qualify through a single writer agent, verifies each round's fixes refute-by-default, re-reviews the delta, and repeats until no qualifying finding remains under the **Stop rule.**, or another of that rule's stop conditions fires. Every fix stays in the working tree, uncommitted. The loop carries five convergence rules from the start, which the Approach defines: a scope anchor, a severity floor, a regression ledger, routing of owner decisions, and a stop rule.

## Context

The user ran `git_review` by hand in rounds with fixes in between throughout October 2026. One change, the git_review secret scan, took nine review rounds and eleven fix rounds in one day. Each round surfaced defects earlier rounds had missed, defects the previous fix had introduced, and requests to extend scope to new input shapes and pre-existing configuration behaviour. Across 34 tasks studied from 2026-09-24 to 2026-10-24, fix rounds introduced about 40 of the 280 findings raised after readiness. Reviews also found what audits had passed, because a review builds adversarial inputs, which is the value this loop automates and the reason it needs explicit convergence rules. The review findings that drove those rounds came from a frontier-model review; the new agents inherit the orchestrator's model like the task family's agents.

The gate is `plugins/ai_dev/skills/git_review/SKILL.md`. Its report sorts findings under "What is critical", "Bugs it may introduce", and "What should be fixed though it is not a clear bug", labels each `verified` or `inferred` and marks the non-blocking ones, and keeps "Decisions the implementer must make before fixing" in a section of its own. On a delta re-review its `<tags>` rule tags every prior finding closed, open, open and not acknowledged, settled by a decision, or regressed, and tags a defect first seen in the delta `new`. When this loop runs `git_review` as the gate, the Approach's `auto_gate_git` contract keeps that skill's review criteria, headings, labels, and `<tags>` as written and forbids its mutation paths, so only `auto_fixer_git` edits the working tree.

The shape to mirror is `plugins/ai_dev/skills/task_auto_check/SKILL.md`: `<single_gate>`, `<relay>`, `<verification_standard>`, `<audit_delta>`, `<concurrent_modification_guard>`, `<agent_failure_policy>`, and `<loop_bounds>`, with its agents under `plugins/ai_dev/agents/` and the doctrine in `wiki/concepts/agent-delegated-automation.md`.

The boundary with [the autonomous implement loop](task-family_autonomous-implement-loop.md): its `task_auto_implement` runs implement, audit, re-implement on findings, and finish, and its audit answers whether the task was built. `git_auto_review` answers whether the change is correct and mergeable. It runs after a clean audit, or on any change the user names with no task at all, and neither loop re-runs the other's gate.

## Approach

1. **Write the front end** at `plugins/ai_dev/skills/git_auto_review/SKILL.md`, named `<family>_auto_<rest>` beside the manual `git_review` per the standing repo rules. It accepts only the default-branch target `git_review` already uses for uncommitted work: the staged, unstaged, and untracked changes together with local commits ahead of upstream, reported under the lane labels `working-tree lane` and `local-commits lane` taken from `collect_uncommitted` in `plugins/ai_dev/skills/git_review/scripts/collect_review_evidence.sh` (its step strings `working-tree lane:` and `local-commits lane:`), which this loop's gate verdict reuses as its `lane` vocabulary. **Lane classification.** When `auto_gate_git` builds the structured verdict, it assigns each finding's `lane` from the finding's `location` (`path:start` or `path:start-end`, 1-based inclusive on the reviewed subject): `working-tree lane` if and only if that path and line range fall inside a hunk of collect evidence `worktree_diff.txt`; otherwise `local-commits lane`. Its `<path_resolution>` block resolves `git_review` as a sibling skill under `../git_review/` and the three agents `auto_gate_git`, `auto_fixer_git`, and `auto_verifier_git` by their published names through the harness's normal agent mechanism, using `../../agents/` relative to this skill directory when the harness exposes only file paths. It takes two optional inputs: a task file path that anchors scope, and a positive integer that overrides the round cap.
2. **Write three agents** under `plugins/ai_dev/agents/`, named `auto_<role>_git`:
   - `auto_gate_git` runs `git_review` as a first review and then delta re-reviews, keeping that skill's review criteria, headings, labels, and `<tags>` verbatim while forbidding `<fast_forward_when_clean>`, `<publishing>`, and `<reviewer_side_edits>`, so the user's `HEAD` and committed history stay fixed. After round 1, the orchestrator passes `auto_gate_git` the path of the prior gate return already saved under the relay; `auto_gate_git`'s prompt explicitly directs a `<re_review>` / `<tags>` pass that takes that return as the prior findings set and the same target shape as round 1 as the review subject, without editing `git_review`; round 1 is a first review and receives no prior-return path. Its agent file carries an `<output_contract>` that pins this return shape as the sole verdict template: the `git_review` report, then a structured verdict listing every finding with id, heading, `verified` or `inferred` label, non-blocking mark, location as a greppable `path:start` or `path:start-end` form (1-based inclusive line numbers on the reviewed subject), `lane` under **Lane classification.**, `Fix:` sentence, and re-review tag, plus the decisions list. Because `git_review`'s `<finding_shape>` carries no id, the gate assigns each finding's id when it builds that verdict: consecutive positive integers in the order findings appear in the report, unique within that gate return. Cross-round identity stays with the re-review tag `git_review` already emits. It may write only the evidence-scratch files `git_review` already writes (collect scratch and `report.md`). It carries no `readonly: true`. Working-tree product edits stay with `auto_fixer_git` alone under the mutation forbids.
   - `auto_fixer_git` is the single serialized writer. For each approved finding it makes the fix in the working tree and adds or extends a reproduction, a test or a command that fails before the fix and passes after, and appends that reproduction to the run's regression ledger. It writes only the paths the finding's `Fix:` requires (anchored at that finding's location), the reproduction, and the ledger.
   - `auto_verifier_git` is read-only and refute-by-default. Its frontmatter carries `readonly: true` and `tools: Read, Grep, Glob`, matching `auto_verifier_task`. Its agent file carries two `<output_contract>` templates pinned to these field lists: triage mode returns each finding as approved or not-approved, with a reason on every not-approved finding under the convergence rules; delta mode returns every hunk of the round's diff mapped to an approved finding id or its reproduction, marking any other hunk `unmapped`.
3. **State the convergence rules once** in a `<convergence>` block of the skill:
   A finding qualifies for auto-fix — and is a qualifying finding for the **Stop rule.** and `auto_verifier_git` triage — only when it meets the **Scope anchor.**, meets the **Severity floor.**, has `lane` `working-tree lane` under **Lane classification.**, and is not held under **Decisions.** Findings that fail only the working-tree-lane conjunct are listed in the report as follow-up task proposals and receive no fix.
   - **Scope anchor.** A finding meets the Scope anchor when it concerns lines the change added or modified, or behaviour the change's intent covers, read from the anchoring task's Goal and Acceptance when a task file is given. A pre-existing issue and a scope extension go to the report as follow-up task proposals.
   - **Severity floor.** Findings under "What is critical" meet the Severity floor regardless of `verified` or `inferred` label. `verified` findings under "Bugs it may introduce" also meet the Severity floor. `inferred` findings under "Bugs it may introduce" and every finding under "What should be fixed though it is not a clear bug" are listed in the report.
   - **Regression ledger.** The ledger is `ledger.txt` in the run's relay directory, one reproduction command per line. A bundled script, `scripts/run_ledger.sh`, runs every line and reports each line's pass or fail, and the orchestrator runs it after every fix round. A failing line restores the round's pre-fix state and repeats the round once with the failing line named to the fixer; a second failure restores the pre-fix state and stops the run.
   - **Decisions.** Every entry under "Decisions the implementer must make before fixing", and every finding whose fix depends on one, goes to the user and receives no fix. When a task file anchors the run, the report gives the wording to record in that task, applied through the base `task` skill's `<update>` workflow on the user's answer, with the base `<status_discipline>` rule deciding the status.
   - **Stop rule.** The run stops when no qualifying finding remains, when a decision is pending, at a cap of 5 rounds unless overridden, after two consecutive rounds whose qualifying findings all sit in code the loop wrote in an earlier round, and on a helper failure. After each fix round the orchestrator appends that round's authored hunks — each a path plus the line range `auto_fixer_git` changed on that path — to `authored.txt` in the run's relay directory. For the self-written stop, parse each gate finding's `location` for a path and a line or line range; a finding sits in loop-authored code when that path matches an earlier-round hunk's path and the parsed line or range intersects that hunk's range; the stop rule reads only that file.
4. **Keep the run safe and reversible.** State these once in dedicated blocks of the skill: `<single_gate>` (`git_review` is the only review gate); `<relay>` (files under `.git_auto_review/<run-stem>/`; create `.git_auto_review/.gitignore` containing the sole line `*`; derive `<run-stem>` as the optional task file's basename without extension when that path is given; when it is omitted, use `default`; on start, create that stem directory and clear anything an earlier run left for the same stem; prompts name inputs by path and returns are saved byte for byte); `<verification_standard>` (refute-by-default triage and delta verification through `auto_verifier_git`); `<audit_delta>` (after every fix round whose verifier marks any hunk `unmapped`, restore the round's pre-fix state, retry the fixer once over the approved findings, and on a second unmapped result restore the pre-fix state and stop); `<concurrent_modification_guard>` (each round's baseline is that round's pre-fix snapshot — the tracked patch plus untracked-file copy the restore uses; After every `auto_fixer_git` write in the round, the orchestrator runs the **Regression ledger.** check first, then `<audit_delta>`; **Regression ledger.** and `<audit_delta>` each keep their own one restore-and-retry, so a round may invoke `auto_fixer_git` once for the initial fix and once more per failure class that authorizes a retry; every invocation receives the approved findings that class names; check the baseline before every `auto_fixer_git` invocation in the round; stop only when the working tree diverges from that snapshot for a reason other than this run's fixer); `<agent_failure_policy>` (a helper failure stops the run); and `<loop_bounds>` (the Stop rule's round cap of 5 unless overridden, plus its other stop conditions, stated only under `<convergence>`). Save each round's pre-fix state as a patch of tracked changes plus a copy of untracked files, so a restore never touches committed history. Validate edits against `CHARTER.md` before writing when it exists.
5. **Route and register.** Rewrite `git_review`'s frontmatter `description:` Use-when clause in place so it keeps that skill's current manual-review trigger phrases and adds an automated review-and-fix carve-out, scoped to the default-branch uncommitted target Approach **Write the front end** names, that routes to `git_auto_review`; branch and pull-request review—including an automated review-and-fix ask against those targets—stays with `git_review`, matching how the other `git_*` skills carry activation. Register the skill and the three agents as the standing repo rules for adding a skill and agents require, and record the loop as a worked instance in `wiki/concepts/agent-delegated-automation.md` through the wiki skill family. Peer-roster maintenance for `agent_spinner` is owned by [the agent_spinner routing task](ai-dev_agent-spinner-routing.md), which retires `<worked_instances>`; this task does not rewrite that block.
6. **Build the tests** as a new harness `tests/git_auto_review/` in the skill-creator-aligned Pattern A layout the standing repo rules name, with `script_tests/run.sh` for `run_ledger.sh` and for the relay directory, `.gitignore`, and pre-fix restore artefacts **Keep the run safe and reversible.** names, and the behavioral evals Acceptance names. Every behavioral eval Acceptance names that requires a specific gate finding shape — including a clean or no-qualifying shape — injects that structured `auto_gate_git` verdict (or a stub `auto_gate_git` return) through the relay; live `git_review` is not the fixture mechanism for those shapes. In the same change, rewrite `ALLOWED_ISOLATION_PREFIXES` in `tests/lib/test_worker_isolation.py` in place so it includes `git_auto_review_`, under the standing repo rules for behavioral-eval vendor selection.

**Out of scope:**

- Calling `git_auto_review` from `task_auto_implement` as its final stage, which the autonomous implement loop task owns along with the convergence of its own implement and audit rounds.
- Committing, pushing, posting a review comment, or resolving a review thread.
- Filing follow-up tasks, which stays the user's call on the proposals the report lists.
- Reviewing or fixing a pull request that is not checked out locally.
- Auto-reviewing or auto-fixing a checked-out branch target; that stays with manual `git_review`.
