# Run the trigger evals on Cursor as on Claude, with a fresh directory per worker and same-vendor baselines, drop the Claude-only label, and record a live run on Cursor

## Goal

`tests/trigger_evals/run.py` measures whether a skill's `description:` makes the agent load that skill for a realistic message. Today the runner works only on Claude: it refuses `--vendor cursor`. Every worker also starts in the runner's own working directory, usually the checkout.

After this task the runner measures on Cursor exactly as on Claude. Both vendors run the same eval sets, graded the same way, into the same result schema. Each worker starts in its own fresh directory outside the checkout. `tests/lib/vendor.py`, the shared vendor layer, supplies the parts that differ by vendor: the deployed skill roots and the stream-mode worker command.

`trigger_evals` comes off every list of Claude-only harnesses: in the vendor layer, in the tests guides, and in the wiki. Leaving `CLAUDE_ONLY` also makes Cursor the harness's default vendor, so a trigger run without `--vendor` runs on Cursor. The UUID proxy is skill-creator's fallback measurement, which installs a stand-in command named with a random id and carrying the skill's description. It stays Claude-only and says so, because skill-creator's runner behind it drives `claude -p`. A skill missing from the run vendor's deployed tree fails loudly on either vendor.

A recorded live run on Cursor, the default vendor, proves the measurement there, and the hermetic script tests prove the Claude record shapes; a live Claude run happens only when the operator asks for one. On Cursor, the `wiki.json` queries that expect the `wiki` skill reach a non-zero trigger rate, and most of those queries name the wiki plainly. A clean negative is a query that should load no skill. Each clean negative passes its precise check, or the results note records the skill its failing runs loaded, as a measured load. A measured load is a skill load the detector actually saw, as opposed to a failed worker.

## Approach

### Vendor layer

In `tests/lib/vendor.py`:

- Remove the `trigger_evals` entry from `CLAUDE_ONLY`. Keep every other entry, the natural-language task's included wherever it has landed.
- Add a helper that lists a vendor's user-level skill roots, native root first, built from `Path.home()` and `_VENDOR_ROOTS`. The native root is the one `make deploy` writes for that vendor. Claude has `~/.claude/skills`. Cursor has `~/.cursor/skills`, then `~/.agents/skills`, `~/.claude/skills`, and `~/.codex/skills`, as its skills page lists them.
- Add a builder for the stream-mode worker command, the command whose output is a stream of JSON records.
  - Claude keeps today's argv: `claude -p <query> --output-format stream-json --verbose --include-partial-messages`, then `--model <m>` when a model is set.
  - Cursor gets `agent -p --output-format stream-json --trust --workspace <dir>`, then `--model <m>` when set, then the query.
  - Neither carries `--permission-mode`, `--force`, or `--yolo`, so both CLIs keep their default permission mode. The runner stops each worker at its first tool call, and Context shows a read running in Cursor's default mode.
  - `build_print_cmd` stays as it is for the behavioural runners.

### Runner

In `tests/trigger_evals/run.py`:

- **Deployed tree.** Resolve the skill under the run vendor's native root, where `make deploy` writes it, and name that root in the `Mode: deployed` log line. Point the unavailable-skill branch the guard task adds at that root, so a missing skill fails loudly on either vendor. Run the drift check over each copy under the vendor's skill roots. Warn once per copy whose description differs from the source.
- **Working directory.** Give each worker its own fresh directory under the system temporary directory, outside the checkout and any git repository, as TESTING.md's `## Test Design Principles` asks. Pass it to Cursor as `--workspace` as well, and remove it after the worker exits. Each worker now has its own directory, so default `--workers` to `vendor.DEFAULT_PARALLEL_WORKERS`, following the `### Parallel workers` rule in `tests/CLAUDE.md`.
- **Detection.** Use one detector per vendor. Each returns today's three outcomes: the loaded skill's name, `None` for a decision with no skill, or `WORKER_FAILED`.
  - Claude keeps today's `stream_event` reading.
  - Cursor skips every record type except `tool_call` and `result`, and decides on the first `tool_call` record. A `readToolCall` whose `args.path` ends in `/<name>/SKILL.md` names `<name>` as the loaded skill under any root, a shape `READ_PATH_SKILL_RE` already matches. A sandboxed Cursor worker sees the deployed user-level skills under every root its skills page lists. A read of a compatibility copy such as `~/.claude/skills/<name>/SKILL.md` therefore counts as that skill's load too. Any other first tool call, a read of another path included, is a decision with no skill. `tests/lib/micro_deploy.py` already reads this record shape for its read-provenance check, in `_parse_cursor_event`, so build the Cursor detector on that reader rather than a second one.
  - On both vendors, a `result` record with `is_error` true counts as `WORKER_FAILED` whatever the exit status, so a dead worker never passes a negative query. A clean exit with no tool call stays a no-trigger, and every other ending stays `WORKER_FAILED`.
- **Escape guard.** The escape guard catches a worker that writes into the host checkout. Snapshot `git status --porcelain` of the host checkout before the first worker starts and after the last one exits. TESTING.md's `## Test Design Principles` asks this of a harness run against a real filesystem. When the snapshots differ, the run exits non-zero and names the changed paths on stderr and in `run.log`. The guard brackets the whole run, so it holds with parallel workers.
- **UUID proxy.** On Cursor, `--force-uuid` exits non-zero before any worker starts. Its message names the UUID proxy as a Claude-only path, because skill-creator's runner drives `claude -p`.
- **Records and baselines.** Write `vendor` and `worker_model` at the top level of `results.json`. A baseline is an earlier run that `--baseline` names for comparison. When `--baseline` names a run recorded on another vendor, write this run's results without a comparison, and exit non-zero with a message naming both vendors. Read a baseline with no `vendor` field as `claude`, the only vendor the runner served before this change.
- **Docstring.** Rewrite the module docstring's opening paragraphs and usage block in place. They describe both vendors' deployed roots and load evidence, the per-worker directory, and the Claude-only UUID proxy. The usage block shows `--vendor` with both vendors and the new `--workers` default.

### Live runs and their record

Run `tests/trigger_evals/wiki.json` with `--skill wiki` once on Cursor, with no `--vendor` flag. Use the default worker model, `--runs-per-query 3`, `--timeout 45`, and the default workers. Pass a prior Cursor run as `--baseline` where the machine holds one. Leave the checkout untouched while a live run is in flight, because the escape guard fails the whole run on any change it sees. Make every other edit this task names before the runs start or after they exit.

Judge each run by two rules, and repeat the run after any fix they call for:

- A precise trigger is a run whose first tool call loaded exactly the expected skill. A zero sum of precise triggers over the entries that expect `wiki` is a detection fault, fixed in this task's detector or worker command. Context shows a plain wiki query loading the skill on Cursor, and Claude's detector keeps the reading that recorded such loads before this change.
- A null entry is an eval-set entry whose `expected_skill` is null, so it should load no skill. When a null entry fails and each of its failing runs names the skill it loaded, that is a measured load. The skill shows in a read of its `SKILL.md` or in a Claude `Skill` call. The note records the measured load, and it does not block. A failing null entry with a `WORKER_FAILED` run carries no such record, which makes it a detection fault fixed in the runner.

Record the runs in `tests/trigger_evals/results/vendor_parity.md`. For each run, give the eval set, vendor, CLI version, worker model, date, and run directory relative to the repository root. Add the precise and family pass counts, where a family pass means the first tool call loaded some skill from the family list. Add the summed precise triggers over the entries that expect the target skill, and the verdict of each entry whose `expected_skill` is null. For a failing null entry, add the skill each of its runs loaded. Add any drift warning. Where a baseline comparison ran, add its moves, the queries whose verdict flipped against the baseline. State that runs recorded before this change ran in the launching shell's directory, so a comparison across this change also measures the directory change.

Narrow the Makefile's `EXCLUDE` prune of `tests/trigger_evals/results/` to the per-skill run directories, so files directly under `results/` stay in lint scope. Name the note in the "Currently kept" comment of `tests/.gitignore`. Both edits keep the two lists in step, as TESTING.md's `## Test Organization` requires.
