# Lint Check Matrix

Reference for `scripts/lint.py` — what each check catches and which severity bucket it lands in.

| Bucket | Checks |
| --- | --- |
| schema | `SCHEMA.md` present; the `## Frontmatter` section has a `yaml` block declaring `type: a \| b \| c`. The linter loads the page-type enum and derives the corresponding page directories (`<type>s`, with `-y → -ies` pluralization) from this declaration. **Blocking** when the enum cannot be extracted — type-dependent checks are skipped until the schema is fixed. |
| boilerplate | Verbatim equality of "must-stay-verbatim" regions against the canonical templates in `references/`. Each `VerbatimSlot` pairs a wiki file with a template and an extractor — the default extractor returns everything above the first `##` heading. One slot is defended: the log.md preamble (H1 + conventions blockquote), whose exact wording is the format documentation the log is written against. The SCHEMA.md attribution paragraph is deliberately not a slot — every scaffolded wiki ships it, and an owner may delete it without drawing a finding. Add another slot to enforce additional regions. **Warn** on any mismatch — the lint output is the structural source of truth for these slots, independent of agent diligence. |
| structure | flat `<type>s/<slug>.md` layout enforced. Every expected type folder declared in SCHEMA.md's `type:` enum must exist on disk (**warn** when missing) and every page must live directly at `<pluralized-type>/<slug>.md` — no thematic prefix, no sub-folder nesting inside the type folder, no bare files at the wiki root. **Blocking** for misfiled pages; the message includes the suggested move target. Thematic scope belongs in `tags:` and `type:`, not folder names. |
| frontmatter | required fields (`title`, `created`, `updated`, `type`, `tags`); `sources` is canonical but optional, carried by a page that cites a source captured under `raw/` and absent from one that cites none, so a wiki capturing nothing keeps the key off every page instead of writing an empty list; `type` validated against the schema-loaded enum; `confidence` enum; YYYY-MM-DD date format on `created`, `updated`, and the optional `checked` (the date a page's claims were last checked against their subject — validated in form when present, never required and never auto-filled). The parser reads inline lists (`[a, b]`) and block-style scalar lists (a key with an empty value followed by indented `- item` lines) alike, so a block-style `tags:` / `sources:` validates the same as its inline form. A **warn** fires when a list field has an empty value but the raw block shows indented content the parser could not read as a list (for example a nested mapping) — the belt for whatever the scalar-list parser still cannot read. It covers `tags`, which every page carries, and `sources` only on a page that carries it. |
| custom fields | custom (non-canonical) frontmatter keys validated against their `field: a \| b \| c` declaration in `SCHEMA.md`'s `## Frontmatter`; pages using undeclared custom keys are flagged; declared-but-unused custom fields surface as info |
| links | broken markdown links to `.md` files; orphan pages with zero inbound links. Fenced code blocks and inline code are skipped for both the broken-link emission and the inbound-link count, so a documentation example link is never blocked and never counts as a real inbound reference. An absolute or `~`-prefixed body link target is **blocking** even when it resolves locally — the same portability rule as `broken-source`: it resolves only on the author's machine and dangles on every clone. |
| broken-source | every `sources:` frontmatter entry must be a repo-relative path under the wiki's `raw/` tree that resolves on disk. A `~`-prefixed or `raw/`-escaping entry, or one that resolves to no file, is **blocking** (it resolves only on the author's machine — Python's `pathlib` even lets an absolute entry override the wiki-root join), same severity as broken markdown links. An absolute or `~`-prefixed entry that resolves to an existing file inside `raw/` is instead a safe-auto-fix **warn** carrying its computed `raw/…`-relative rewrite — the same file, portably spelled — while an absolute entry resolving outside `raw/` (or to no file) stays the blocking finding. The frontmatter is the canonical source inventory; a non-resolving or non-portable entry breaks the provenance contract the field exists to enforce. |
| raw-source-path | every raw sidecar's `source_path:` must be a relative path resolved from the wiki root to a source kept inside the repository the wiki ships within — it may point outside the wiki dir via `../` but must stay inside the repo — that resolves on disk; a repo-escaping relative value, or an absolute/`~`-prefixed value resolving outside the repo or to no file, is **blocking** because it resolves only on the author's machine or points outside the versioned tree. An absolute or `~`-prefixed value that resolves to an existing in-repo file is instead a safe-auto-fix **warn** carrying its computed wiki-root-relative rewrite — the same file, portably spelled. A `source_path:` carrying a remote URL scheme is deferred to the `raw-origin` form check (which emits the single redirecting warn everywhere), so this check skips it rather than stacking a misleading "does not resolve" error on top. A local source outside the repo takes no `source_path:` — it is captured by the sidecar body excerpt and a prose locality note, so a sidecar without the field is fine. A wiki that is not inside a git repo is local-only and ships nowhere, so the check is skipped entirely there — every path already resolves on its one machine. Walks the `raw/` tree, which the per-page checks skip. |
| raw-origin | every raw sidecar's origin field is filed under the field whose form fits its value: `source_url:` holds a remote URL for an externally-published source, `source_path:` holds a path resolved from the wiki root to an in-repo source (which may sit outside the wiki dir via `../`). **Warn** on a `source_url:` that is a `file://` URL or a bare path (redirect to a `source_path:` — a path resolved from the wiki root, reaching outside the wiki dir via `../` when needed — or the out-of-repo excerpt rule), on a `source_path:` that carries a remote URL scheme (redirect to `source_url:`), and on a sidecar carrying both fields at once (the two name mutually-exclusive origin kinds — keep the one that fits). These are overwhelmingly legacy or mis-filled sidecars to migrate, so the finding warns rather than blocks. Unlike `raw-source-path`, this check does not depend on the wiki living in a git repo — it runs everywhere, which is what surfaces a URL-valued `source_path:` in a non-repo wiki that the skipped portable check would miss. It never requires an origin field: a sidecar for an out-of-repo local source legitimately carries neither, so it only checks the form of a value that is present. Walks the `raw/` tree, which the per-page checks skip. |
| sources-section | deprecated body `## Sources` / `## Source references` H2 heading inside a wiki page. Source attribution lives in the `sources:` frontmatter (canonical inventory) and inline next to each claim; a bottom-of-page collection duplicates the frontmatter and splits the claim-source binding across the page. The check is body-only and skips fenced code blocks. |
| footnote | `[^name]` footnote references and `[^name]:` definitions outside fenced code blocks and inline code. The wiki uses inline standard-markdown links for claim-level attribution (`[text](relative/path.md)`) so attribution sits adjacent to the claim, feeds the broken-link check, and renders consistently across markdown viewers. |
| index | membership runs both directions on resolved markdown link targets, not raw substring containment. Every content page on disk must be linked from `index.md` (a page whose filename is a substring of a listed one — `alignment.md` inside `misalignment.md` — is no longer counted as listed), and every page the index links must resolve on disk (a dangling entry left behind by a renamed, moved, or archived page is flagged). `index.md` sits outside the page walk, so this is the only check that sees its stale entries. Both directions **warn**. |
| tags | tags used but missing from the `SCHEMA.md` taxonomy; tags in the taxonomy but unused on any page (stale tag detection). `load_taxonomy` reads only **unfenced** `- Label: tag, …` bullets in the `## Tag Taxonomy` section — a taxonomy shown inside a fenced example (the template's "Example for AI/ML:" block) is documentation, never the live tag set. An uncustomized wiki therefore parses as having no taxonomy and fires the "no Tag Taxonomy section" schema warn until its owner defines real bullets, instead of silently validating pages against the placeholder example tags. |
| taxonomy style | SCHEMA.md `## Tag Taxonomy` bullets that drift from the canonical `- Label: tag, tag, …` one-line form. Flags emphasis around the category label (`**Label:**`, `*Label:*`, `__Label:__`, `_Label:_`), `*` or `+` used in place of `-`, and soft-wrap continuation lines that split a bullet across physical lines. Fenced code blocks are skipped, matching `load_taxonomy`, so a fenced example bullet is never flagged. The loader tolerates all three forms so off-taxonomy warnings don't false-positive, and this check nudges authors back to the canonical form so the leniency stays a safety net. |
| stale | `updated` more than 90 days older than the newest cited source's `ingested` date |
| quality | `contested: true`; `confidence: low`; single-source pages with no confidence field set |
| drift | sha256 mismatch on files in `raw/`. The fix path is `python3 scripts/compute_sha256.py <file>` (or no-arg to refresh every raw file); the warning message names the script directly, with `<file>` written as the wiki-root-relative path (`raw/<kind>/<slug>.md`) so the quoted command runs as-is from the wiki root. Only files carrying a `sha256` field are checked here — a raw file missing it is caught by the `raw-frontmatter` check instead. |
| raw-frontmatter | every raw sidecar outside `raw/assets/` carries the re-ingest metadata: an `ingested` date and a `sha256` body digest. Without them the `drift` check is silently inert (it skips any file lacking `sha256`), so a source that skipped hashing is never checked for drift. **Warn** — both are mechanically fixable (`compute_sha256.py` writes the digest, the ingest stamps the date). The origin field's *presence* stays optional, since a sidecar for an out-of-repo local source legitimately carries neither; the *form* of a present value is validated separately by the `raw-origin` check. `raw/assets/` holds binary companions with no frontmatter and is exempt. |
| size | pages over 200 lines |
| log | `log.md` over 500 entries (rotate to `log-YYYY.md`) |
| log-heading | two `log.md` entry headings that repeat byte-identically, which markdownlint MD024 (`no-duplicate-heading`) reports as a duplicate heading and which can block a commit. One finding per duplicate group, in first-occurrence order, so a three-way collision reads as one collision. Duplicate detection only: the check compares whole heading lines and never validates heading format, so a unique legacy date-only heading stays clean and no entry is flagged for lacking the `HH:MM` component the current format carries. The category is its own rather than shared with `log`, because this check emits several findings per `log.md` while the two-field acceptance form below rests on one finding per path; the finding is line-less and its message names the colliding heading verbatim, so the three-field form pins one collision. Info severity: a collision is surfaced for review, and repairing an entry already written is an operator-requested move rather than a routine sweep. |
| log-scope | a `log.md` entry bullet whose **subject** — the text before the bullet's first `:`, ` — `, ` – `, or ` \| ` separator, or the whole remainder when it carries none — is a path token that resolves outside the wiki root. Resolution runs on a dual base: an absolute or `~`-expanded path outside the wiki fires, a wiki-root join that escapes via `..` fires, a repo-root join that is an existing file outside the wiki fires, and everything else is read as wiki-relative and stays clean even when the named file is absent — the check draws a path boundary, not a missing-file one. A subject counts as a path token only when the *entire* subject is one whitespace-free path string carrying a `/` or a dotted extension, so prose that merely embeds path substrings (the scaffold's `Structure created with SCHEMA.md, index.md, raw/, …` seed bullet, or `Outcome: lint passed`) never fires. A symmetric markdown wrapper of backticks, asterisks, or underscores around the whole subject is decoration and comes off, so a bullet written as ``` `concepts/foo.md` ``` or `**plugins/x/y.md**` reads as its bare form; requiring the run to close the way it opened leaves a real filename that merely starts with one of those characters (`_config.yml`) intact. The subject position is the whole discriminator: a non-wiki path cited mid-bullet as the source a claim was drawn from is legitimate provenance, while the same path standing as what the bullet is about is the violation. One aggregated finding per run naming the count and a few offenders, so a wiki with historical violations gets a signal instead of a swamped report; fence-safe, so a bullet inside a fenced example is documentation. Info severity: the log is append-only and no fix move clears a historical violation, so the finding is surfaced for the owner's editorial call while new entries stay correct because the `Scope:` group in `template_log.md` binds the authoring surface directly. |
| markdown style | bullet style (`-` only); header level skipping; trailing punctuation in headers; fenced code without language identifier; multiple consecutive blank lines; bare URLs; list-marker spacing; trailing newline (matches the `format_markdown` skill) |
| wikilink | `[[target]]` or `[[target\|alias]]` wikilink-style references outside of fenced code blocks and inline code. The wiki uses standard markdown links `[text](relative/path.md)` so cross-references resolve in plain renderers and feed the broken-link check; the warning includes a hint suggesting the equivalent markdown form. |

## Page-walk scope

The per-page checks (frontmatter, links, structure, orphans, tags, size, and the rest) run on every Markdown file under the type folders. The walk always skips the `raw/` and `_archive/` trees; a vault extends that skip set by listing extra top-level directories on a `- Page-check exclusions: a, b` bullet in `SCHEMA.md`'s `## Lint` section (documented in `template_schema.md`). The names are read only outside fenced code blocks, so a documented example never becomes a live exclusion. Removing a whole tree from the walk is the coarsest of the three suppression scopes — see **Accepted info-level findings** below for how it divides from the per-type and per-finding ones.

## Severity buckets

- **blocking** — broken markdown links (including an absolute or `~`-prefixed link target that resolves only on the author's machine), `sources:` frontmatter entries that resolve to no file, escape the `raw/` tree, or are absolute/`~`-prefixed and resolve outside `raw/`, raw-sidecar `source_path:` values that escape the repo, resolve to no file, or are absolute/`~`-prefixed and resolve outside the repo, missing or malformed frontmatter, missing `index.md`, missing or unparseable `SCHEMA.md`, pages filed outside their `<type>s/<slug>.md` location. The script exits 1 while any blocking finding remains.
- **warn** — orphan pages, contested pages, source drift (sha256 mismatch), raw sidecars missing `ingested`/`sha256`, an absolute/`~`-prefixed raw-sidecar `source_path:` that resolves to an in-repo file (safe-auto-fix carrying its wiki-root-relative rewrite), an absolute/`~`-prefixed `sources:` entry that resolves inside `raw/` (safe-auto-fix carrying its `raw/…`-relative rewrite), a raw-sidecar origin field filed under the wrong field or a sidecar carrying both `source_url:` and `source_path:` (`raw-origin`), a list field whose block content the parser could not read (`tags` on every page, `sources` only where present), off-taxonomy tags, invalid enum or date values, pages missing from the index, index entries that dangle (link a page absent from disk), missing expected type folder on disk, verbatim-boilerplate mismatches against the canonical references, `[[wikilink]]` references that should be standard markdown links, `[^footnote]` references and definitions that should be inline standard-markdown links.
- **info** — markdown style nits, oversized pages (>200 lines), low-confidence single-source pages, unused taxonomy tags, taxonomy-style drift in SCHEMA.md (emphasis labels, non-`-` bullet markers, soft-wrap continuations), deprecated body `## Sources` sections, log over 500 entries, duplicate `log.md` entry headings (`log-heading`), `log.md` entry bullets whose subject is a path outside the wiki (`log-scope`).

## Accepted info-level findings

An info finding the wiki owner has reviewed and accepted is recorded on an `- Accepted finding: …` bullet in `SCHEMA.md`'s `## Lint` section, read fence-safe exactly like the `Page-check exclusions:` bullet. A matching finding leaves the live counts and the report body for a trailing `ACKNOWLEDGED` section that carries no severity bracket and asks for nothing, so the decision is made once instead of being re-justified in prose and re-logged on every audit. Matching reaches `info` findings alone: a bullet whose text also describes a blocking or warn finding leaves that finding live.

Each bullet names exactly one finding, in one of three forms:

| Form | Grammar | Use |
| --- | --- | --- |
| two-field | `- Accepted finding: <category> — <path>` | `size`, `log`, `stale`, and `log-scope` only — each emits at most one line-less finding per path, and each message embeds a counter or date that moves between runs, so the acceptance keys on the path and survives that churn. A two-field bullet in any other category matches nothing. |
| three-field | `- Accepted finding: <category> — <path> — <message>` | a line-less finding of any other category; the discriminator must equal `Issue.message` exactly. |
| four-field | `- Accepted finding: <category> — <path> — <line> — <message>` | a line-bearing finding, where line and message together pin one finding out of several sharing a path. |

`<path>` is wiki-root-relative. Fields are parsed left-anchored on ` — `, so a message carrying its own em dash survives intact as the trailing field; a digits-only field after the path is read as the line number.

Three suppression scopes sit side by side and never double-handle the same finding. `Page-check exclusions:` works at **directory** level — it drops a whole top-level tree from the page walk, so no check ever sees those files. A growth-pattern declaration works at **page-type** level: where a wiki declares one, size findings are deferred for every page of that type, because the type is expected to grow. An `Accepted finding:` bullet works at **individual finding** level, covering one reviewed finding of any category — including a `size` finding on a page whose type is expected to stay fixed.

## Iteration loop

Run, fix highest severity, re-run. Repeat until the script exits 0. A `contested: true` page keeps its warn by design: that dispute signal is for a human to resolve, so it stays in the report.

Append the outcome to `log.md`:

```text
## [YYYY-MM-DD HH:MM] lint | N blocking, N warn, N info
```

If a check is wrong for the situation (e.g., a deliberately oversized synthesis page), record it once as an `Accepted finding:` bullet — never as rationale prose in the page body, and never as a fresh log paragraph each run. The next run drops it from the live report, so the live info bucket holds only findings nobody has reviewed yet. Leave the script alone: it surfaces, it doesn't enforce.
