# Let the wiki owner acknowledge accepted info-level lint findings

## Goal

A wiki owner can mark a specific info-level lint finding as reviewed-and-accepted, after which subsequent lint runs treat it per **Honour acceptances in the runner.** so it stops driving re-justification. This ends the per-run loop where the agent re-reads the same accepted findings, writes a fresh justification paragraph, and records the same rationale in the log on every audit.

## Context

`lint.py` emits info-level findings for conditions that are often intentional and accepted by the wiki owner — `confidence: low` frontmatter, pages over the 200-line soft cap ([skills/wiki/scripts/lint.py](../../plugins/knowledge_management/skills/wiki/scripts/lint.py) `check_page_size`), and taxonomy tags defined but unused (`check_unused_tags`). These re-surface on every run because there is no way to acknowledge an individual finding. The only suppression today is the `--quiet` argparse flag, which hides **all** info indiscriminately — too blunt, so it goes unused, and instead each audit re-litigates the same accepted findings in prose and adds another near-identical log entry. The info count creeps upward across a session purely from this churn.

This is the *general* per-finding accept mechanism. A narrower, type-based mechanism for the specific case of expected page growth is being designed separately in [wiki_page-type-growth-and-anatomy.md](../wiki_page-type-growth-and-anatomy.md) (growth-pattern declarations that make the linter defer size findings for backlog/synthesis pages). The boundary, decided: a declared growth pattern defers size findings for a whole page type, while the per-finding accept here covers an individual reviewed finding of any category, including a size finding on a `fixed`-growth page. A third mechanism sits beside both — the SCHEMA `## Lint` section's `Page-check exclusions:` bullet removes whole directories from the page walk rather than suppressing individual findings. Document all three boundaries together. Both live tasks also add a bullet to that same `## Lint` section and register it in the same agent `<configurable_zones>` list, and both rewrite the agent's `<topic_separation>` objective (this task for the Accepted finding route; [wiki_page-type-growth-and-anatomy.md](../wiki_page-type-growth-and-anatomy.md) for per-pattern size thresholds), so coordinate those shared edits whichever lands first: compose growth thresholds and the Accepted finding route into one `<topic_separation>` statement rather than last-writer-wins. [wiki_schema-template-generalization.md](../wiki_schema-template-generalization.md) rewrites the `template_schema.md` `## Lint` opener from bare `` `scripts/lint.py` walks `` to `$WIKI_SKILL/scripts/…` and leaves machine-read `## Lint` bullets to this task; this task's **Document** compose must keep that path form rather than last-writer-wins.

Storage has an established home: `lint.py` already scans the SCHEMA `## Lint` section fence-safe for labeled bullets (the `Page-check exclusions:` parse, `LINT_EXCLUDE_RE`), and SCHEMA.md carries no YAML frontmatter of its own — so a frontmatter-based acceptance store has nowhere to live, and the acceptance store follows the `## Lint` bullet pattern instead.

Coordination with [wiki_log-heading-uniqueness-and-repair.md](../wiki_log-heading-uniqueness-and-repair.md): the two-field acceptance form in **Store acceptances in the SCHEMA `## Lint` section.** whitelists `log` on the premise that a `log` finding emits at most one Issue per path. That task keeps the premise true by filing its new duplicate-heading finding under a distinct `log-heading` category rather than `log`, so `log` stays single-emit, and `log-heading` (several per path) takes the three- or four-field discriminator forms like any other category.

Files involved:

- [plugins/knowledge_management/skills/wiki/scripts/lint.py](../../plugins/knowledge_management/skills/wiki/scripts/lint.py) — finding emission and the main runner; the `--quiet` flag.
- [plugins/knowledge_management/skills/wiki/references/lint_checks.md](../../plugins/knowledge_management/skills/wiki/references/lint_checks.md) — document the accept mechanism.
- [plugins/knowledge_management/skills/wiki/references/template_schema.md](../../plugins/knowledge_management/skills/wiki/references/template_schema.md) — the `## Lint` section where acceptances are declared and documented.
- [plugins/knowledge_management/skills/wiki/SKILL.md](../../plugins/knowledge_management/skills/wiki/SKILL.md) and [agents/auto_shaper_wiki.md](../../plugins/knowledge_management/agents/auto_shaper_wiki.md) — teach the accept workflow so the agent uses it instead of re-justifying in prose.

## Approach

1. **Store acceptances in the SCHEMA `## Lint` section.** One labeled bullet per accepted finding. Three grammar forms: (a) two-field for `size`, `log`, and `stale` — categories whose messages embed a volatile counter or date and that emit at most one Issue per path — `- Accepted finding: <category> — <wiki-root-relative-path>`, and never key on the volatile message substring; (b) three-field for every other category when `Issue.line` is absent — `- Accepted finding: <category> — <wiki-root-relative-path> — <stable message discriminator>`; (c) four-field when `Issue.line` is present — `- Accepted finding: <category> — <wiki-root-relative-path> — <line> — <stable message discriminator>`. Match predicate so each acceptance matches exactly one finding: a two-field acceptance matches when the bullet's category is `size`, `log`, or `stale`, `Issue.category` equals that category, the wiki-root-relative path equals the bullet's path, and `Issue.line` is absent — a two-field acceptance whose category is outside that whitelist matches no finding; a three-field acceptance matches only when category and path equal, `Issue.line` is absent, and `Issue.message` equals the discriminator exactly — a three-field bullet does not match a line-bearing finding; a four-field acceptance matches only when category, path, line, and message all equal the bullet. Parse each acceptance bullet left-anchored on ` — `: after the `Accepted finding:` label, take category, then path; if the next field is all digits, treat it as `Issue.line` and the remainder (which may contain ` — `) as the discriminator; otherwise the remainder after path is the discriminator (which may contain ` — `). Grammar and fence-safe parsing mirror the `Page-check exclusions:` bullet. Acceptances stay reviewable in one place, and page bodies carry no marker comments. Register the new bullet in the agent's `<configurable_zones>` entry for `template_schema.md`, which today names only the `Page-check exclusions` bullet as wiki-owned inside `## Lint`: without that entry the acceptances survive on nothing but `<hunk_classification>`'s generic extends-the-canon fallback, and an audit reading them as scaffold drift would tidy a wiki owner's reviewed decisions away. When rewriting that entry, compose with [wiki_page-type-growth-and-anatomy.md](../wiki_page-type-growth-and-anatomy.md): keep any already-landed Growth patterns registration and add the Accepted finding bullet beside it (do not replace Growth with acceptance-only); if Growth is not yet present, write the Accepted finding registration so a later growth-task edit can add Growth patterns without removing the acceptance half.
2. **Honour acceptances in the runner.** Matching applies only to `SEV_INFO` findings; a matching acceptance never suppresses a non-info finding. When an info-level finding matches an acceptance, exclude it from the live INFO count and from the default report body so it stops inflating the live info count and stops prompting re-justification; an optional separate "acknowledged" section may list those findings as non-actionable context only.
3. **Teach the workflow.** Update SKILL.md and the auto-shaper so that, when an info finding is intentional, the agent records the acceptance via this mechanism **once** — never by writing rationale prose into the page body (that prohibition is owned by [wiki_meta-prose-in-page-bodies.md](../wiki_meta-prose-in-page-bodies.md)) and never by appending a fresh log paragraph every run. **(i) Meta-prose-overlapping sites** — the sites that task and [wiki_meta-prose-in-page-bodies.md](../wiki_meta-prose-in-page-bodies.md) both touch for the SCHEMA `## Lint` prose route: the agent's `<fix_oversized_page>`, `<relint_until_clean>`, and `<linter_is_truth_for_structure>`, SKILL.md's `<inline_iteration_loop>`, and `references/lint_checks.md` `## Iteration loop`. Landing after it, upgrade that prose route to the acceptance bullet; landing first, point those sites at the bullet directly. When rewriting SKILL.md `<inline_iteration_loop>` and `references/lint_checks.md` `## Iteration loop`, supersede each site's prior "Only acceptable info-level findings remain" / "only acceptable info-level findings remain" stop criterion so intentional accepted infos leave the live report per **Honour acceptances in the runner.**, while the contested-page warn carve-out (`contested: true — reconcile or document the dispute`) remains. **(ii) Independent rewrites** — not meta-prose prose routes. When rewriting `<lint_clean>`, supersede its prior "Only acceptable info-level findings remain" stop criterion so intentional accepted infos leave the live report per **Honour acceptances in the runner.**, while the contested-page warn carve-out remains. When rewriting `<topic_separation>`, compose with [wiki_page-type-growth-and-anatomy.md](../wiki_page-type-growth-and-anatomy.md): keep any already-landed growth-aware threshold statement and add the Accepted finding route beside it (do not replace thresholds with acceptance-only prose); if thresholds are not yet present, write the Accepted finding route so a later growth-task edit can add thresholds without removing the acceptance half.
4. **Document** the mechanism and its boundaries with the growth-pattern deferral and the `Page-check exclusions:` walk exclusion in `lint_checks.md`, and document the acceptance bullet in `template_schema.md` `## Lint` as a fenced example mirroring the `Page-check exclusions:` bullet (documentation inside the fence; live settings stay outside fences). When rewriting that `## Lint` section, compose with [wiki_schema-template-generalization.md](../wiki_schema-template-generalization.md): keep any already-landed `$WIKI_SKILL/scripts/…` form of the section's lint opener and add the acceptance documentation beside it (do not restore the bare wiki-root `scripts/lint.py` form over an already-landed `$WIKI_SKILL` path); if the path rewrite is not yet present, write the acceptance documentation so a later schema-template edit can rewrite the opener to `$WIKI_SKILL/scripts/…` without removing the acceptance half.

## Acceptance

- Accepted findings follow **Honour acceptances in the runner.**: matching applies only to `SEV_INFO`; excluded from the live INFO count and default report body; if an optional acknowledged section is present, it is non-actionable and does not re-prompt justification.
- A Layer 1 fixture info finding marked accepted via the live `## Lint` acceptance bullet is absent from the live finding count on the next run.
- A Layer 1 fixture non-info finding whose text would match an acceptance bullet remains in the live report and count.
- A Layer 1 accepted fixture stores its acceptance only via the live `## Lint` acceptance bullet; the page body carries no acceptance markers.
- A Layer 1 *unaccepted* info finding still appears normally.
- A Layer 1 fixture whose only matching acceptance text sits inside a fenced example does not suppress the finding (fence-safe parse).
- A Layer 1 fixture with two same-path line-less non-two-field info findings proves the match predicate in **Store acceptances in the SCHEMA `## Lint` section.**: accepting one via an exact `Issue.message` discriminator leaves the sibling live; Layer 1 two-field acceptances for `size`, `log`, and `stale` each continue to match after that finding's volatile message substring changes.
- A Layer 1 fixture with a single-emit line-less non-two-field info finding proves **Store acceptances in the SCHEMA `## Lint` section.** requires the three-field form for that category: a two-field acceptance for it leaves the finding live; a three-field acceptance whose discriminator equals `Issue.message` exactly suppresses it, and a three-field acceptance whose discriminator differs leaves it live.
- A Layer 1 three-field acceptance whose discriminator equals an em-dash-bearing `Issue.message` exactly suppresses that finding, proving the left-anchored remainder-as-discriminator parse in **Store acceptances in the SCHEMA `## Lint` section.**
- A Layer 1 fixture with two same-path same-message line-bearing info findings proves **Store acceptances in the SCHEMA `## Lint` section.** requires the four-field form when `Issue.line` is present: a three-field acceptance for that category/path/message leaves both findings live; a four-field acceptance whose line and discriminator equal one finding suppresses only that finding and leaves the sibling live.
- `lint_checks.md` documents the accept mechanism and its boundaries with the type-level growth-pattern deferral and the directory-level `Page-check exclusions:` walk exclusion, matching **Document**; the mechanisms do not double-handle page-size findings.
- After this task's `template_schema.md` `## Lint` documentation rewrite, the acceptance bullet is documented as a fenced example mirroring `Page-check exclusions:`, matching **Document**, and any already-landed `$WIKI_SKILL/scripts/…` opener from [wiki_schema-template-generalization.md](../wiki_schema-template-generalization.md) remains; the rewrite does not last-writer-wins over that path form.
- SKILL.md `<inline_iteration_loop>`, auto-shaper `<fix_oversized_page>`, `<relint_until_clean>`, `<linter_is_truth_for_structure>`, and `lint_checks.md` `## Iteration loop` instruct recording acceptance through this mechanism rather than prose or repeated log entries, and supersede the prior rationale-on-page / SCHEMA prose routes at those sites.
- After this task's `<lint_clean>`, SKILL.md `<inline_iteration_loop>`, and `lint_checks.md` `## Iteration loop` rewrites, each site's prior "Only acceptable info-level findings remain" / "only acceptable info-level findings remain" stop criterion is superseded; intentional accepted infos leave the live report per **Honour acceptances in the runner.**; the contested-page warn carve-out remains.
- After this task's `<topic_separation>` rewrite, the Accepted finding route is present and any already-landed growth-aware threshold statement from [wiki_page-type-growth-and-anatomy.md](../wiki_page-type-growth-and-anatomy.md) remains; the rewrite does not last-writer-wins over thresholds.
