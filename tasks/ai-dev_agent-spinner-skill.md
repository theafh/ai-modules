# Add an agent_spinner skill

## Goal

Add a new `agent_spinner` skill to the `ai_dev` plugin that encodes how an orchestrating agent runs helper agents, so one prompt yields comparable quality on every target harness rather than only where a vendor switch turns orchestration on. The skill owns one question: given a job and whatever delegation the host offers, how do helpers spin off, stay contained, cross-check each other, fail, report, and get aggregated into one answer. Ship it prose-only, with the long material in `references/` and no bundled helper agent definitions.

The user-visible outcome is a run that opens by naming the capability tier it established, states its phase plan, its item count, and the items it deliberately left out before the first helper starts, and closes with a verdict-first report carrying the dispatched-against-returned count. Where the host exposes a spawn surface, the run fans out. Where it does not, and no governing skill forbids it, the same run performs the same passes inline in one context and says so. The quality contract reads the same in both cases, because every guarantee the skill makes is written to hold at the inline floor.

## Context

The orchestration shape already runs in this repository and is already written down, but only in places that travel nowhere. The wiki page [agent-delegated-automation](../wiki/concepts/agent-delegated-automation.md) states the architecture: readers fan out, one writer holds the graph, the verifier refutes by default, and judgement routes to the human. The standing repo rules keep the wiki inside this repository, so a skill used elsewhere cannot cite that page as its authority. The doctrine belongs in the skill body and its `references/`, and that page then records where the rule now lives.

The generic half of the discipline also ships already, entangled with task-specific gates. The `<agent_failure_policy>`, `<loop_bounds>`, `<concurrent_modification_guard>`, and `<verification_standard>` blocks in [task_auto_check](../plugins/ai_dev/skills/task_auto_check/SKILL.md) carry the retry taxonomy, the bounded loop, and the reject-by-default standard. [task_fix](../plugins/ai_dev/skills/task_fix/SKILL.md) and [auto_shaper_task](../plugins/ai_dev/agents/auto_shaper_task.md) own containment as a single-writer rule over a shared link graph. [auto_verifier_task](../plugins/ai_dev/agents/auto_verifier_task.md) fixes the structured, non-overlapping, anchored return contract. `agent_spinner` ships advisory against all of them: it states the general shape and cites each surface by name as a worked instance, and it restates no rule those surfaces already state.

Two of those citations carry live conflicts the skill resolves by deferring rather than by overriding. `task_auto_check`'s `<agent_failure_policy>` ends with a stop-and-ask boundary for a harness that offers no spawn mechanism, refusing to execute helper roles inline; an unqualified inline floor would silently convert that stop into an unattended run that writes task files. The same block distinguishes four helper failures where a single collapse-everything rule would discard three real signals. Both are reasons the skill's own contract yields to a governing skill inside that skill's run.

Every per-harness fact stays with [harness_portability](../plugins/ai_dev/skills/harness_portability/SKILL.md), which already owns agent definition files as a portability surface, registration verification, native read-only levers, and effort inheritance. `agent_spinner` carries no frontmatter key, tool name, registration path, or tolerance claim of its own, and cites that skill for whether a spawn surface exists on a target.

The ground is uneven enough that parallelism is never a precondition. One target registers Markdown agent definitions and takes a tool allowlist; another registers roles only outside any plugin and reaches read-only through a command-approval sandbox rather than a denial; a third reads agent definition files and recognises a read-only flag while exposing no recorded surface that spawns one, which makes definition-present-and-uncallable a real state a registration check reports as available; a fourth may hang a subagent on an unmapped tool name instead of failing at load; a fifth forwards unrecognised frontmatter to the provider as a bogus model option and lets subagent calls bypass its before-hook guard; a sixth prepends a role body to the user turn and sets the floor. No concurrency contract is recorded anywhere, so coverage is counted in independent looks rather than in simultaneity, and the skill claims no wall-clock benefit.

`CHARTER.md` is the hard boundary this skill designs against. Its coverage invariant requires an autonomous component to keep audit, detection, and coverage scope intact when it optimises for cost or speed, and to surface a narrowing tradeoff for human review rather than take it silently. The skill's selector exists to spend fewer helpers, so every narrowing it takes gets named out loud.

`agent_spinner` owns no artifact class and writes no domain state. A request naming tasks routes to the `task_*` family, a request naming the wiki routes to [wiki_fix](../plugins/knowledge_management/skills/wiki_fix/SKILL.md), and both stay worked instances of this shape at different sizes. The standing repo rules own skill authoring, registration, the pseudo-XML and positive-language conventions, the both-audiences `description:` contract, and the layout and assertion rules for the tests tree, so this task supplies only the `agent_spinner`-specific behaviour.

## Approach

Implement the skill as `plugins/ai_dev/skills/agent_spinner/SKILL.md` with a `references/` directory, following the standing repo rules and the pseudo-XML and positive-language conventions. Organise the body as a selector in front of a named shape library, so an orchestrator picks a weight before it picks a mechanism. Push prompt templates, worked report shapes, and degradation examples into `references/`, because one target truncates skill metadata to a context budget and another skips an oversized plugin skill.

Encode these blocks:

- **`<invocation_boundary>`: a governing skill's contract wins.** A run already governed by a named skill keeps that skill's orchestration contract, and where that skill states its own loop bounds, helper-failure policy, verification standard, or aggregation rule, this skill adds nothing to that run. Read `agent_spinner` when the orchestration decision belongs to the orchestrator, meaning a request about running helpers in general or a job no shipped family owns.
- **`<capability_probe>`: establish callability, never infer it.** A role definition on disk is evidence the file deployed, not evidence it can be called. Establish callability through the harness's own spawnable-role surface, and where the harness advertises none, record the delegation surface as absent however many definitions are present. Probe four things: a delegation surface, a native read-only lever, a depth or effort control, and whether two helpers run at once. A capability that resists establishment resolves to absent, and the run says which capabilities it established and which it assumed away.
- **`<degradation>`: one ordered tier ladder with an inline floor.** The floor is a sequence of separately prompted passes performed inline in one context. Above it sit spawned roles in their own context, harness-enforced read-only, a depth pin for the adversarial pass, and concurrent fan-out at the top. Write every guarantee to hold at the floor, so no step depends on a fresh context, an isolated tool set, or a process boundary. The run states the tier it reached in its opening sentence. Inline degradation is the floor for a run the orchestrator owns outright: where a governing skill states its own stop-and-ask boundary for a spawn-less harness, honour that boundary and perform no helper role inline, as `<invocation_boundary>` already establishes.
- **`<selector>`: match orchestration weight to the ask.** A read-only diagnostic or a single judgement question is answered inline from the orchestrator's own reads before any helper is spent. A turn mixing a question with an imperative gets its answer in the reply that launches the run. A handful of already-approved edits gets plain helpers with a do-not-relitigate clause instead of the full machinery. An enumerated imperative over many artifacts gets per-artifact fan-out. A corpus too large for one pass gets a lens panel. An ask matching no listed shape gets the smallest shape that covers it, named as such.
- **`<shapes>`: the library, one sibling tag per shape.** Give each of six shapes a trigger condition, a width rule, a prompt skeleton, and a return contract: per-artifact fan-out, lens panel, paired refute-by-default check, judge panel, completeness critic, and single-writer terminal validator. Write them as sibling tags rather than a nested tree so the body stays within the markdown linter's nesting limit.
- **`<width>`: derive breadth from the enumerated list.** The helper count equals the length of a list the orchestrator wrote out before dispatch, never a round number and never a merge of items to save calls. Per-artifact fan-out takes one helper per file path. A lens panel takes three to five named lenses over the identical corpus, each told that siblings cover the other angles so depth beats breadth. Replication of one identical prompt is reserved for a single indivisible factual or arithmetic claim.
- **`<phase_plan>`: declare the run before the first helper.** Plan two to four named phases, each a single verb plus one clause saying what one helper does and over what unit; a phase needing more than one clause is two phases. State the sequence, the item count, the per-helper wall-clock bound, and the items deliberately excluded with a reason each, then announce each phase boundary as it is crossed. Label every helper `role:item` from a stable per-item slug rather than a property several items share, because a repeated label leaves a dead helper unattributable.
- **`<run_economy>`: gate breadth and report yield.** Ask before dispatching more than ten helpers. When the first third of a fan-out returns nothing to report, stop, say what those returns showed, and ask whether to continue. Close every run with its yield in one clause, the helpers dispatched against the decisions or edits they produced, and say plainly when a run cost more than it returned.
- **`<coverage_tradeoff>`: name every narrowing out loud.** When the run answers inline rather than fanning out, verifies a subset rather than every finding, or drops a phase for cost, state in the same reply which checks go unrun and what would surface them, and proceed on the user's word where the narrowing removes a check the fuller shape would have made. This is the `CHARTER.md` coverage invariant applied to this skill's own economy rules.
- **`<containment>`: one path per helper, one writer per tree.** Each write helper's prompt names its single target path and carries an explicit negative list of the neighbouring artifact classes it may not touch; no helper receives two paths and no two helpers share one. Where concurrent helpers each create a file in one directory, each lists the directory first and picks a non-colliding name. A tree-wide validator runs alone and after every writer has returned and is told so, is fenced to a named set of mechanically fixable findings, and reports every judgement finding rather than resolving it. A step that reads the aggregate waits for the full set and names the aggregate it reads; state that reason in one clause. Where the target repository carries a `CHARTER.md`, validate each edit against its boundaries before writing, and on a conflict write nothing, leave the file byte-for-byte unchanged, and report the conflict.
- **`<delegation_depth>`: one level per run.** State in every helper prompt that the helper performs its own item and delegates no part of it, and that work it cannot complete comes back as an out-of-scope finding. An item that genuinely needs its own fan-out returns as a finding and gets sized in the next run, where the user also gets a decision point.
- **`<prompt_assembly>`: three parts, authority-neutral.** An invariant preamble holds the hard rules, the shared vocabulary, the severity ladder, and the facts already settled that nobody re-derives. A hand-written per-item brief names that item's situation and target state. A kind note from a small table handles items whose class needs different treatment. The preamble goes unchanged into checking passes as well as producing ones. Write every role contract to work as text the pass reads inside its own turn: open with the pass's first concrete action, state each prohibition as something the pass does, and restate load-bearing prohibitions at the point of use, because on at least one target a role body arrives inside the user turn with no authority over the surrounding conversation.
- **`<brief_as_hypothesis>`: the artifact is the authority.** Every brief states that its claims came from an earlier pass and may be wrong, that the helper checks each against the source before relying on it, and that a contradicted claim comes back as refuted with its disproof. The return shape carries a named slot for those corrections. Never tell a helper that a diff or a status listing will show only its own change.
- **`<checking>`: refute by default, cite to clear.** The checker receives the producer's report verbatim, opens from the stated position that the work is incomplete or wrong, and concedes only after running a closed numbered checklist. Name the cost that sets the default in the same sentence so the helper weighs it rather than obeys it. The checker changes nothing and is told which read-only operations to use; where a target's read-only mode gates commands behind approval rather than denying them, the checking pass avoids shell use entirely. Each finding carries a verdict from a small closed set, a confidence, a verbatim quote, a path with a heading or symbol anchor, and a severity from a defined ladder. A clean verdict cites the span that settled it, so a first-pass all-clear with no citation routes back rather than passing. The checker may narrow an overstated claim instead of killing it, and the narrowed wording propagates. A helper acting on findings re-derives each one first and reports a disproved finding as refuted. Every reviewing pass reports what it examined and cleared, and an empty finding list is a valid and expected outcome.
- **`<confirmation_provenance>`: record how a finding survived.** A finding the checking pass was shown and did not refute is recall-confirmed and says so in the report. A finding a pass surfaced without having been shown it is independently surfaced. Recognising a stated issue is easier and steadier than generating it, so a recall-confirmed finding carries less weight, and a decision resting only on recall-confirmed findings says so.
- **`<helper_failure>`: classify a non-result before acting on it.** Distinguish a deliberate self-reported inability, which records its stated reason, spends no retry, and routes to the user; a spawn glitch, meaning a near-instant return with no tool use whose whole output is harness boilerplate, which earns one identical-prompt re-invocation; and a spawn failure, mid-run death, or contract-violating shape, which earns the same single re-invocation. When a re-invocation fails again, mark the item failed against the roster and report it, and take a degraded path such as an inline redo only after the user chooses it. This mirrors the taxonomy `task_auto_check`'s `<agent_failure_policy>` already fixes for its own loop; cite that block rather than restating its wording. A helper that passes its stated wall-clock bound with no return stops being waited on, is marked unreturned against the roster, and is reported as such, because a hung helper and a helper that found nothing are otherwise indistinguishable. A helper whose depth pin the provider rejected can die quietly, so state verifier rigour as a behavioural contract in the prompt rather than buying it with a knob. Downstream steps guard against a dead upstream before reading its output.
- **`<remediation>`: one round, never loop until pass.** Only the items that failed verification enter repair, they enter once, and the report marks the repaired output as unverified rather than implying end-to-end coverage. Repeating a stochastic check until it passes selects its most lenient draw rather than verifying. A follow-up fan-out is guarded on the count of items that need it, and a pass over an empty list dispatches nothing and says so.
- **`<run_state>`: keep the roster outside your own context.** Write the dispatch roster to a scratch file before the first helper, one line per item with its identifier, its assigned path or lens, and its state, and update the state as each result lands. When the run stops early for any reason, report from that roster which artifacts were modified, which were untouched, and which are in an unknown state, and settle the unknown ones by reading the files rather than by trusting a helper's return or a completion notice.
- **`<aggregation>`: merge cited findings, never count agreement.** Two helpers raising the same item is shared priors rather than confirmation, so proposals are unioned and each goes through its own refute-by-default check. The orchestrator does arithmetic, partitioning, and joining in the open, keyed by the stable per-item identifier rather than by arrival order. Discarded findings survive into the report with their one-line reason. Cap any payload pasted into a downstream prompt at a stated size, tell that pass its material may be cut and that anything load-bearing gets re-read from the source, and list the identifiers of every item whose detail was trimmed.
- **`<reporting>`: verdict first, three things kept apart.** The opening sentence gives the answer, the tier reached, and the helpers dispatched against returned. The body distinguishes what the run established, what a helper found beyond its brief, and what a helper decided on its own authority that the user should review. Helper return shapes stay internal. Before writing the report, identify the single claim the verdict rests on and check it against the artifact rather than against a helper's report; name what was re-derived and what was taken on a helper's word, and report a verdict that resisted re-derivation as the helpers' finding rather than as the run's conclusion.
- **`<judgement>`: route the real forks to the user.** Removing most of a body, deleting a load-bearing section, picking one side of a real fork, resolving a contradiction, or touching an artifact already marked complete are surfaced rather than settled, at every tier, and no helper writes a field a named gate owns. A run whose ask was which work to do changes nothing, states the no-edit rule in every helper prompt, and closes by asking for the go-ahead. The judge panel shape scores competing options against a small fixed criteria list, gives each judge its own weighting sentence so the panel is not three copies of one taste, requires a verdict on the incumbent option beside the ranking, and keeps a strongest-argument-against-your-own-verdict field required.

Put the four role prompt templates (producing, lens, checking, synthesis), the worked report shapes, the degradation examples, and the two lower-frequency variants (information isolation between concurrent helpers, and replicated draws returned unreduced with each draw showing its own derivation) under `references/`. Keep `SKILL.md` under 25000 bytes and the `description:` value under 1500 characters, so the body stays close to the smallest shipped `ai_dev` skills and the metadata survives a truncating listing.

Deliver every cross-role rule inside each role's own prompt. Build the test surface on the skill-creator-aligned harness pattern that `tests/git_commit/` demonstrates, following the standing repo rules for the tests tree, which set the harness layout, the preference for filesystem-state and structured-field assertions over checks on agent prose, the sandbox-isolation fail-safe, and the paired edit of the ignore list and the lint exclusion list when a regenerated subtree appears. Apply `harness_portability` to the wording so nothing in the skill depends on a spawn call, a frontmatter key, or a hook that only one target provides.

**Out of scope:**

- Editing `task_auto_check`, `task_fix`, `wiki_fix`, or any file under `plugins/ai_dev/agents/` to cite `agent_spinner` for their generic blocks, since this skill ships advisory and those surfaces keep authority over their own runs; reversing that direction rewrites a shipped autonomous loop and its harness, and belongs in its own task.
- Bundled `auto_<role>_agent` helper definitions, since the skill's guarantees are written to hold without them and a bundled agent reaches one primary target only through the deployment script, so a marketplace install would rest them on roles that do not exist.
- Any per-harness fact, including frontmatter keys, tool vocabularies, registration paths, sandbox values, and tolerance categories, which `harness_portability` owns under a fact-sourcing rule requiring re-verification against docs or the installed build.
- A literal spawn-call syntax for any harness, since no spawn contract is recorded for any target and a hardcoded call is unportable by construction.
- Hooks as the enforcement layer for read-only or single-writer, since delegation is the case that escapes the before-hook guard on one target and the hook contract is unworked on another.
- A global rules or standing-instructions file as the delivery mechanism for this skill's contracts, since only one target propagates such a file to its subagents and on that target the write suppresses the user's existing rules file rather than sitting beside it.
- Worktree or branch isolation as the containment mechanism, since this repository contains writes by partitioning paths and serialising through one writer instead.
- Voting, quorum, and consensus as aggregation, and loop-until-pass as verification, since agreement between instances of one model measures shared priors and repeating a stochastic gate selects its most lenient draw.
- A bundled runtime script, workflow runner, or scheduler, which the standing repo rules keep out of the toolchain.
- Ownership of any artifact class or domain state, since the task family owns task files and their gate and the wiki family owns wiki pages and their linter.
- A wall-clock or speed claim for fan-out, since no concurrency contract is recorded for any target.

- The body carries one block per named contract in **Approach**, greppable by the tag names listed there, and `wc -c` on `SKILL.md` returns under 25000.
- The `<capability_probe>` block names all four probed capabilities and states that a visible role definition is evidence of deployment rather than of callability; on a staged fixture carrying agent definition files with no spawn surface, the run reports the delegation surface as absent and claims no harness-enforced read-only.
- A grep of `plugins/ai_dev/skills/agent_spinner/` for per-harness frontmatter keys, tool identifiers, agent directory paths, and sandbox mode values returns no matches, and every hit for a target product name is a citation of `harness_portability`; a grep of the skill and its `references/` returns no instruction to write a global rules, instructions, or agent-configuration file.
- The change adds no file under `plugins/ai_dev/agents/` and modifies no file under `plugins/ai_dev/skills/task_auto_check/`, `plugins/ai_dev/skills/task_fix/`, `plugins/ai_dev/agents/`, or `plugins/knowledge_management/`.
- On a staged fixture whose harness exposes no delegation surface and whose ask names no governing skill, the run performs its passes inline, states the floor tier in its opening sentence, and produces the same phase plan and the same checking pass as the fixture that does expose one.
- On a staged fixture with no delegation surface whose prompt names a task readiness loop, the run offers that loop's manual routes and executes no helper role inline.
- On a staged fixture exposing a delegation surface, the pre-dispatch announcement states the phase sequence with its one-clause details, the item count, the per-helper wall-clock bound, and, on a fixture with eight candidate artifacts of which three are out of scope, the five included and the three excluded with a reason each.
- On a staged fixture that asks only a read-only diagnostic question, the run spawns zero helpers and its reply names the checks the fuller fan-out would have run.
- On a staged write job over three files, every helper prompt names exactly one target path and carries a negative list, no prompt names two target paths, no two prompts name the same one, and every prompt carries the no-further-delegation clause; on a staged fixture containing an item that would need its own fan-out, the run returns it as a finding and spawns no second level.
- On a staged repository whose `CHARTER.md` the planned edit violates, the writing pass leaves the target file byte-for-byte unchanged and reports the conflict.
- On a staged fixture returning one self-reported inability, one boilerplate-only return, and one absent return, the run spends no retry on the first, exactly one re-invocation on each of the other two, and reports all three separately in the dispatched-against-returned arithmetic; on a staged fixture with one non-returning helper, the run stops waiting at its stated bound and reports that item as unreturned.
- On a staged fixture where the run stops after two of four writers, the roster file exists with per-item state and the closing report enumerates the modified, untouched, and unknown-state artifacts from it, with the unknown ones settled by reading the files.
- On a staged fixture where a checking pass returns a clean verdict with no cited span, the run routes that verdict back for re-checking rather than accepting it.
- On a staged fixture with a planted defect in a produced artifact, the checking pass names that defect; on a staged fixture whose corpus is clean, the run reports zero findings, invents none, and records what it examined and cleared.
- On a staged fixture where two helpers raise the same finding, the run sends that finding through its own refute-by-default check and the report contains no vote, majority, or agreement-as-confirmation wording; on a fixture whose planted defect one pass surfaces and a second pass is shown, the report marks the second as recall-confirmed and the first as independently surfaced.
- On a staged fixture whose verification fails, exactly one remediation round runs, no second verification loop is attempted, and the report states the remediated output is unverified.
- On a staged fixture whose helper reports exceed the stated payload cap, the synthesis prompt carries the truncation notice and the digest lists the trimmed identifiers.
- On a staged fixture containing a judgement-class change, such as removing most of a body or picking one side of a fork, the run surfaces it and leaves it unsettled.
- The closing report opens with the verdict, the tier reached, and the dispatched-against-returned count, carries the yield clause, pastes no helper return shape, and separates what the run established from what a helper found beyond its brief and what a helper decided on its own authority; on a staged fixture whose helper reports are internally consistent but contradicted by the fixture's own files, the report either corrects the verdict or labels it as not re-derived.
