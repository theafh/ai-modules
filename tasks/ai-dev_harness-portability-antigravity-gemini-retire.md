# Add Antigravity coverage to harness_portability and drop Gemini CLI as a target

## Goal

Update the `harness_portability` skill so it covers **Google Antigravity** as a first-class target harness with verified current facts, rewrites the now-stale Gemini-CLI-derived claims so they describe Antigravity where the live Google surface is meant, and records one short note that Gemini CLI is dropped as a supported target because its consumer surface is retired.

The user-visible outcome is that an agent consulting the skill treats Antigravity — the live Google surface delivered as an IDE, a CLI, and the 2.0 desktop app — as *the* Google target, with correct config paths and correct skill / agent / hook / plugin models, and no longer encodes the retired consumer Gemini CLI as a live deploy target or carries Gemini CLI's strict-frontmatter behaviour as if it were Antigravity's.

## Context

**Why this change.** Google's consumer Gemini CLI surface was retired on 18 June 2026 for Google AI Pro, Google AI Ultra, and free individual usage, while Standard/Enterprise and paid API-key access stay outside this task's consumer-target scope ([transition blog](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/), [gemini-cli discussion #27274](https://github.com/google-gemini/gemini-cli/discussions/27274)). The `google-gemini/gemini-cli` repo stays active as a spec, but the live Google surface for this task is now **Antigravity** — a Go rewrite that shares the `~/.gemini` lineage and inherited Skills, Hooks, Subagents, and Extensions (renamed "plugins"). So the skill's Gemini coverage is both stale (it points agents at a retired consumer serving target) and mis-scoped (Antigravity, not Gemini CLI, is the live surface). The skill's current treatment of Gemini CLI as an agent-definition-only, strict-schema surface is doubly out of date.

**Current skill passages to rewrite in place** (all in `plugins/ai_dev/skills/harness_portability/SKILL.md`): the `description:` frontmatter; the `<target_harnesses>` scope clause; the Gemini-naming `<agent_definition_surfaces>`, `<frontmatter_schema_tolerance>`, `<tool_name_namespaces>`, `<readonly_agent_enforcement>`, `<reasoning_effort_portability>`, and `<native_fields_and_deploy_bridges>` sections; and the non-Gemini harness enumerations in `<codex_model_inheritance>`, `<cross_harness_artefact_discovery>` `<opencode_isolation_switches>`, `<hook_portability>` `<dual_harness_layout>` and `<shared_hook_scripts>`, `<review_checklist>` `<artefact_discovery>`, and `<review_checklist>` `<dual_harness_hooks>`. Antigravity is absent from the skill entirely. The skill already models a diverging full target (OpenCode) through a `<cross_harness_artefact_discovery>` block, an `<opencode_plugin_hooks>` hook block, and per-surface agent coverage — that treatment is the template for Antigravity.

Giving `.agents/` an owner changes what one neighbouring passage means. `<opencode_isolation_switches>` currently presents `OPENCODE_DISABLE_CLAUDE_CODE=1` as a Claude-compatibility toggle that "also stops `.agents/skills` discovery", closing on "everything a sibling tool deployed into `~/.claude`". Once `.agents/` is documented as Antigravity's native workspace tree, that same Claude-named switch scopes away the Google harness's own artefacts — a materially different fact for an operator than the passage now conveys.

**Antigravity facts to encode.** Each carries a confidence flag; the skill's own `<policy>` rule — *"State the provider documentation source or the verification gap when a change depends on harness-specific execution, initialization, configuration, filesystem, environment, permission, or tool-discovery behavior"* — governs how an unconfirmed fact is written, so anything below marked *verify* is encoded with its source or as an explicit gap, never as settled fact.

- **Global and workspace config paths** *(current docs split; encode the split or an explicit verification gap rather than flattening it)*: Antigravity 2.0 customization docs name global `~/.gemini/config/{skills,agents,plugins,sidecars}/` plus `~/.gemini/config/{mcp_config.json,hooks.json}`, with `~/.gemini/GEMINI.md` sitting one level up (not under `config/`); workspace customization docs name `.agents/{skills,agents,rules,plugins}/` with `.agent/` and `_agents/` as back-compat. Product-specific docs also name different global roots: IDE Skills uses `~/.gemini/antigravity/skills/<skill-folder>/`, CLI Plugins & Skills uses `~/.gemini/antigravity-cli/{plugins,skills}/`, and CLI Settings uses `~/.gemini/antigravity-cli/settings.json`. The skill must not claim one global `~/.gemini/config` deploy reaches IDE, CLI, and 2.0 unless implementation-time verification reconciles that split; otherwise it records the disagreement as a verification gap and states only the roots each official page confirms. The `~/.gemini/antigravity` and `~/.gemini/antigravity-cli` trees still double as transcript/artifact or CLI profile paths depending on the page, so the skill must distinguish config/customization roots from transcript/artifact output paths instead of treating the whole per-product tree as non-config.
- **Skills** *(confirmed, [antigravity.google/docs/skills](https://antigravity.google/docs/skills), [antigravity.google/docs/ide/skills](https://antigravity.google/docs/ide/skills), and [antigravity.google/docs/cli/plugins](https://antigravity.google/docs/cli/plugins))*: `SKILL.md` + `name`/`description` frontmatter under the Agent Skills open standard, model-invoked with progressive disclosure; workspace `.agents/skills/<skill>/`; global `~/.gemini/config/skills/<skill>/` in Antigravity 2.0 docs, `~/.gemini/antigravity/skills/<skill>/` in IDE docs, and `~/.gemini/antigravity-cli/skills/` in CLI docs. The workspace `.agents/skills/` path is Antigravity's native skill root, and the portability point is the convergence with Codex project-level skill deployment and OpenCode discovery on that same path rather than Antigravity adopting a foreign directory.
- **Subagents** *(confirmed schema, [antigravity.google/docs/subagents](https://antigravity.google/docs/subagents); re-verify the full field list)*: `.agents/agents/<name>.md` or `.agents/agents/<name>/agent.md`; global `~/.gemini/config/agents/…`; bundled `plugins/<plugin>/agents/`. Frontmatter: `name`, `description`, `tools[]` (native tool names; an unmapped/misspelled name causes a runtime **hang**, not a load rejection), `model` (`inherit`|`flash_lite`|`flash`|`pro`), `commandExecutionPolicy` (`off`|`auto`|`eager`|`sandbox`, default `sandbox`), `mainAgent`/`subagent` booleans, `mcpServers` (camelCase), `skills`/`plugins` dependency arrays, plus `hidden`/`inheritMcp` seen in community docs.
- **Tool namespace** *(official-doc set)*: Subagents docs source `read_file`, `edit_file`, `grep_search`, and `run_command` as `tools[]` allowlist examples and separately mention `view_file` / `run_command` as exact names to check; Hooks docs source `view_file`, `write_to_file`, `replace_file_content`, `multi_replace_file_content`, `grep_search`, `run_command`, `invoke_subagent`, and `define_subagent` as hook matcher tool names. Keep `edit_file` as source-backed for subagent allowlists while distinguishing it from the Hooks file-edit tool names. Read-only enforcement = a `tools[]` allowlist using the read-only subset (`read_file`, `grep_search`, `view_file` where supported by the surface) plus `commandExecutionPolicy` (`off`/`sandbox`), the Antigravity equivalent of the levers `<readonly_agent_enforcement>` already lists per harness.
- **Hooks** *(confirmed, [antigravity.google/docs/hooks](https://antigravity.google/docs/hooks))*: declarative `hooks.json` in `.agents/` (workspace) or `~/.gemini/config/` (global); events `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`; stdin/stdout JSON with **camelCase** fields (`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`); `PreToolUse` returns a `decision` of `allow`|`deny`|`ask`|`force_ask`; works in both IDE and CLI; a Python SDK hooks module also exists. **Divergence trap:** Gemini CLI's own hooks used `BeforeTool`/`AfterTool` — Antigravity uses the Claude-style `PreToolUse`/`PostToolUse` names but with camelCase JSON, so equivalence between the two Google surfaces cannot be assumed. Unlike OpenCode's code-only bridge, Antigravity hooks are declarative, so they sit closer to the Claude/Codex JSON-config model.
- **Plugins (bundling unit)** *(confirmed bundle, [antigravity.google/docs/plugins](https://antigravity.google/docs/plugins); mapping undocumented)*: `plugin.json` under `.agents/plugins/` or `~/.gemini/config/plugins/`, bundling skills + rules + MCP + hooks (and agents via `plugins/<plugin>/agents/` per the subagents doc, though the plugins overview omits agents — a documented inconsistency). Gemini CLI Extensions migrate into Antigravity plugins, but how a `gemini-extension.json` maps onto `plugin.json` is undocumented. `.agents/plugins/` is a shared directory rather than an Antigravity-only one: this repo's own Codex marketplace registration sits at `.agents/plugins/marketplace.json`, so one workspace directory carries two harnesses' differently-schemad manifests — the same discovery-collision class `<cross_harness_artefact_discovery>` exists to record.
- **Rules / workflows** *(partial)*: workspace rules `.agents/rules/*.md` (≈12,000-char cap, four activation modes), global rules `~/.gemini/GEMINI.md`, project-root `AGENTS.md` (precedence over `GEMINI.md` is secondary-sourced); workflows are markdown slash commands.

**Verification gaps to carry as gaps, not facts** — the highest-value one being frontmatter strictness: Gemini CLI's Node loader rejected a single unknown frontmatter key; whether Antigravity's Go loader does the same is **unconfirmed and the evidence leans tolerant** — official subagents/skills docs are silent, the only documented Antigravity validation gotcha is the bad-tool-name runtime hang, and the fixed-allowlist "unexpected fields" behaviour that circulates is VS Code's own SKILL.md editor linter ([microsoft/vscode #294520](https://github.com/microsoft/vscode/issues/294520)), which may surface cosmetic warnings inside Antigravity's editor but is not a runtime load rejection and never names Antigravity. Also verify or explicitly gap-label: the split between Antigravity 2.0 `~/.gemini/config/…`, IDE `~/.gemini/antigravity/…`, and CLI `~/.gemini/antigravity-cli/…` global roots; the hook event names and camelCase envelope; the `plugin.json` layout; whether agents are officially part of plugin bundles across 2.0/IDE/CLI; the extension→plugin mapping; and whether Antigravity itself discovers artefacts from another harness's directories (`.claude/skills/`, `.claude/agents/`) together with any isolation switch that scopes discovery to its own roots — the per-target cell `<foreign_directory_adoption>` and `<agent_definition_surfaces>` already fill for every other harness, and which the `<policy>` artefact-discovery rule and the `<review_checklist>` `<artefact_discovery>` "any available isolation switch is documented" clause both require of a full target.

**Shared surfaces.** [ai-dev_rename-harness-portability-to-plugin-portability.md](ai-dev_rename-harness-portability-to-plugin-portability.md) renames this skill's directory and identifiers to `plugin_portability` and co-edits the same `SKILL.md`. Keep this task's edits name-agnostic — change section bodies and the frontmatter `description`, not the skill's identity — so whichever task lands second reconciles without conflict. If the rename lands first, edit the skill at its current path and re-point this file's `scope:` to `plugins/ai_dev/skills/plugin_portability` in the same task-body/status edit so the task linter still resolves the target directory. [deployment_opencode-hook-bridge.md](deployment_opencode-hook-bridge.md) co-edits the same skill's hook-portability guidance; its `**OpenCode-specific caveats to encode and document**` block owns the OpenCode hook model and caveats that this task must preserve while adding Antigravity hooks.
