# Add a git_review skill

## Goal

Add a new `git_review` skill to the `ai_dev` plugin as the fourth member of the `git_*` family beside `git_commit`, `git_checkout`, and `git_refresh`. It serves one request: assess the set of changes the user points at and say whether it could be approved in general and whether it can be structurally merged as it is. The target is one of three things: a pull request named by URL or number, a branch named by name or already checked out, or, when the repository sits on its default branch, the uncommitted working-tree changes together with any local commits not yet on the upstream. Ship it at `version: 1.0.0`.

The user-visible outcome: one review report in a fixed section order that mirrors the questions a reviewer asks (what the changes do and implement, what they retire, what of the existing workflow changes, what is critical, which bugs they may introduce, what should be fixed though it is not a clear bug, and which decisions the implementer must make before fixing), opened by a verdict on approvability and closed by a yes or no on structural mergeability with its evidence. Findings-section presence follows the first-review versus delta heading rule in Approach. A later run against the same target reviews the delta since the last review instead of repeating the whole report, and on explicit request the skill publishes the report, or a slice of it, to the pull request under the user's own account.

## Context

The prompt this skill generalizes grew over some twenty review rounds on pull requests in another repository, re-issued as a pasted template whenever the branch moved. It settled on the question list above, on "report only sections that have findings", and on the word "structurally" for the merge question. Three lessons from those rounds carry the design and belong in the skill body rather than in a prompt the user re-types.

**Two verdicts, kept apart.** Approvable in general judges substance. Structurally mergeable judges the branch's own properties: a conflict-free test merge against the base, the ahead and behind counts, and the status of the continuous integration checks. Required approvals and other branch-protection policy are context, never a blocker, because the requester is producing the very review such a policy waits for. The round that coined "structurally" was one where a report had counted the missing approval as one of two reasons the pull request could not be merged.

**Read the discussion first, then verify claims instead of trusting them.** A re-review that read review states but not the comment bodies re-raised items the author had already fixed. A first review that skipped several thousand changed lines declared the change approvable and had to reverse. Author notes naming fixing commits were only right when checked against the tree. Records outside the repository that the pull request cited, such as a chat thread or a wiki page, settled decisions a report had listed as open. Every claim in a pull request body, a commit message, or an author reply is therefore an input to verify, and a decision counts as open only after the discussion and the linked records have been read.

**A human acts on the output, so its shape is part of the contract.** Requests to post only the sections from one heading to another, to write from the reviewer toward the author, to state what is true rather than what is not, to report only what is genuinely open, and to omit an attribution line recurred across rounds. One post published the whole report because a range instruction and a drop instruction in one sentence were read as a single instruction, and later corrections asked for edits in place rather than second posts. Parallel runs of the same prompt agreed on the mechanical steps and diverged on heading names, on the fringe of findings, and on documentation coverage, so the skill pins the headings, the evidence set, and the check list and leaves the judgement to the model.

[git_checkout](../plugins/ai_dev/skills/git_checkout/SKILL.md) owns putting the repository onto a branch and is the sibling this skill hands a branch to when the user names one that is not checked out; [git_refresh](../plugins/ai_dev/skills/git_refresh/SKILL.md) owns branch cleanup after the merge, and `git_commit` owns any commit the user asks for along the way. All three siblings put the explicit-request guard in the `description:` prose, bundle their git work under `scripts/`, and carry a `references/` manual fallback. `git_checkout` and `git_refresh` take the conservative dirty-worktree stance that surfaces blocked state rather than stashing or resetting it. `git_commit` proceeds on an ordinary dirty worktree and pauses only for hard blockers or detected foreign drift. `git_review` follows the shared packaging conventions and the checkout/refresh dirty-tree stance: no stash, reset, or checkout-discard on the user's tree. Harness-native diff reviewers, such as a slash command that reads the current diff for bugs, stay complementary: they judge a diff, while this skill judges a merge decision and runs in every harness the plugin deploys to. The forge layer relies on the GitHub CLI `gh` as an optional run-time tool the skill detects and does without, so the repository's default maintenance surface stays unchanged. The standing repo rules own skill authoring, registration, versioning, and the both-audiences `description:` contract; this task supplies only the `git_review`-specific behaviour.

## Approach

Implement the skill as `plugins/ai_dev/skills/git_review/SKILL.md` with bundled `scripts/` helpers and `references/` notes, following the standing repo rules and the pseudo-XML and positive-language conventions. The run has these stages.

In addition, ship the required plugin wiring and regression harness: register the new `git_review` skill in `plugins/ai_dev/.claude-plugin/plugin.json` and `plugins/ai_dev/.codex-plugin/plugin.json` (Codex keeps `"skills": "./skills/"`), both `.agents/plugins/marketplace.json` and `.claude-plugin/marketplace.json`, `plugins/ai_dev/README.md`, and the root `README.md` layout tree and skill list, rewriting the `description` field in `plugins/ai_dev/.claude-plugin/plugin.json`, `plugins/ai_dev/.codex-plugin/plugin.json`, and the matching `ai_dev` plugin object in both marketplace files so the git family names review of a pull request, branch, or uncommitted default-branch changes beside commit, checkout, and refresh, and create `tests/git_review/` (with `script_tests/` and `evals/`) following the `tests/git_commit/` layout (skill-creator-aligned Pattern A); staged remotes reuse the `tests/git_checkout/` fixture helpers (`init_remote_repo` / `seed_bare`); rewrite the `## Current harnesses` list in `tests/README.md` and every `git_review/` runner-enumeration site in `tests/CLAUDE.md` in place, so each names `git_review/evals/run.py` beside the existing Pattern-A runners: the `What's here` table, the Worker/sonnet table row, both behavioral-eval-runners parentheticals, the Pattern-A behavioral-runners count sentence, and the `worker_auth` import list.

**Resolve the target.** Accept a pull request URL or number, a branch name, the remote-qualified branch form, or nothing. With nothing given, review the checked-out branch against the repository's default branch; when the checked-out branch is the default branch itself, review the uncommitted changes (staged, unstaged, and untracked) plus any local commits ahead of the upstream, reporting the two lanes separately. A pull request resolves to its head and base branches through the forge layer. When the user names a branch that is not checked out and asks to be put onto it, hand the switch to `git_checkout`. If that sibling surfaces a dirty-worktree block, leave `HEAD` where it is, name the blocking paths, and finish the review from the remote-tracking ref in the detached scratch worktree the Pin-the-reviewed-commit stage already uses. When the user does not ask to switch, read the branch from its remote-tracking ref without moving `HEAD`. Take the base from the pull request, or detect the default branch from the remote `HEAD` the way `git_refresh` does, rather than hardcoding a name.

**Pin the reviewed commit and leave the tree alone.** Fetch the base and head refs before any diff, since a stale local base inflates the diff and a stale local head reviews the wrong code. Compare the checked-out `HEAD` with the remote head and, for a pull request, with the forge's head commit. When `HEAD` is behind on a clean tree, fast-forward it and say so. When the tree is dirty, the local branch has diverged, or a repository hook refuses the checkout, review the remote ref and run every command that needs files in a detached scratch worktree that the run removes afterwards; a hook refusal is a finding to report, never something to bypass. Use no stash, reset, or checkout-discard on the user's tree. Open the report with the reviewed commit and the tree state left behind, so a later delta run has its anchor.

**Gather the git layer.** Compute the merge base and the ahead and behind counts; take the three-dot diff stat and name-status with rename detection; list the commits with full messages both without merges and along the first parent, so in-branch merges from the base stay visible and the branch's own contribution is separated from what the base already holds; build a removed-hunks view for the retirement section; read deleted files and prior versions from the base with `git show`; run a test merge with `git merge-tree` to name conflicting files; scan the diff for secrets and hardcoded home paths; report the size and the share of binary or generated files. Check version and manifest lockstep and the pull request body against the branch for version and test-count claims. Two documentation findings carry their own weight: a standing instruction or document that still references a file the change deleted or renamed, which misdirects every later reader rather than merely reading stale, and a derived artifact whose source the change edited, which the report flags for regeneration by its owner rather than repairing inside the review. Judge a lint hit against the repository-wide baseline before calling it a defect.

**Gather the forge layer when it exists.** When `gh` is installed and authenticated and the remote is a GitHub repository, read the pull request body, the review bodies, the issue comments, and the inline review threads through the paginated review-thread connection, the one forge surface carrying each thread's resolved and outdated state, each with its count so that "no comments" is proven; page past the first page of the threads and of the comments inside each thread, and keep the resolved and the outdated threads rather than filtering them away, since a thread resolved with no matching change in the tree is exactly what a delta tag reads; read the checks, the mergeable state and its reason, the review decision, and the branch rulesets when readable. When any of that is missing, review from git alone and name the forge layer as unavailable in the report lead; when the remote is not a GitHub repository, the git-only path is first-class rather than degraded.

**Read external context first when the user names it.** An external record the user points at is read before the assessment and treated as a set of claims to verify. A decision the owner has already made is settled and is not re-argued.

**Rank the review criteria the repository declares.** Gather the criteria from the repository rather than from a fixed checklist: the standing repo rules, plus the root guardrail documents when the repository carries them, each read behind a `test -f` presence gate so a repository carrying none is reviewed unchanged and draws no missing-document finding. Rank what they say by the authority hierarchy the `guardrail` skill defines, so each finding's severity rests on a declared source rather than on the reviewer's taste. A violation of `CHARTER.md` is what puts a finding under the critical heading; a divergence from `TESTING.md` or `SECURITY.md` is reported for the user to weigh; `ARCHITECTURE.md` and its peers supply descriptive context, where code short of a declared direction is unmet work rather than a defect. Cite the governing document by name in every finding resting on one, and locate the nearest precedent in history beside it.

**Verify rather than read.** Build the gate list from two sources and reconcile them: the continuous-integration workflow definition, which names the suites, validators, linters, and commit-message checks that run and the range each covers, and the project's documented local entry points, meaning its task-runner targets and the commands the standing repo rules name. A repository with no continuous integration still yields a gate list from the second source alone. Where the two disagree on a gate or on the command that runs it, report the disagreement as its own finding, since a contributor who runs the documented command passes a check the merge then fails. Run those gates the way the repository runs them, state which of them ran locally and which only the forge's check run covered for the same commit, and when a hook runtime or a linter is missing name it skipped and continue. Reproduce a suspected bug with concrete inputs before reporting it, and label each finding verified or inferred.

**Scale the reading to the diff.** Read a small diff directly. For a large diff, read each changed file sequentially in order with the bundled question list (read the whole file, sample nothing, trust no comment or docstring). Call no change approvable while changed lines remain unread; name what was not read instead.

**Judge and report in the fixed order.** Open with the reviewed commit, the tree state, and the verdict on approvability in general with the shortest path to yes. Then use these headings in this order: What the changes do and implement; What it retires; What of the existing workflow changes; What is critical; Bugs it may introduce; What should be fixed though it is not a clear bug; Decisions the implementer must make before fixing; Can it be structurally merged as it is. On a first review, omit a findings section that has no findings, and say in one line when all of them are empty. On a delta re-review, keep all eight headings in that order as tag homes even when a heading has no remaining findings. Each finding names its location in a form the destination renders, quotes or reproduces the evidence, states the consequence, proposes the fix, and names who decides; CHARTER-boundary findings live under the critical heading per Rank the review criteria, and every other finding carries a non-blocking label. Phrase each decision as a choice between named options with a suggested default. Answer the closing question yes or no from the test merge, the counts, and the checks, with required approvals and other protection policy mentioned as context outside the answer. For the uncommitted-changes target, `Can it be structurally merged as it is` becomes `Can they be committed onto the default branch as they are`, judged by the same gates; the eight-headings-verbatim fixture applies only to branch and pull-request runs.

**Support the re-review.** When the target was reviewed before, which an anchor commit in the conversation or a prior post by the user on the pull request shows, read every comment and review body newer than the reviewer's last post first, fetch the new commits, and review the delta under the same headings: tag each prior finding as closed, open, open and not acknowledged, settled by a decision, regressed, or new; verify each claimed fix against the tree; separate code changes from prose concessions and the author's defects from the reviewer's own scope calls; leave out items the author declined or deferred with a stated reason, keep items routed to someone but unanswered open, and fold in decisions the user relays from outside the pull request; and say plainly whether the review loop can stop.

**Honour scope modifiers.** A focus area, a "no nitpicking" instruction (fold minor items into one line), and an "only what is genuinely open" instruction (actionable items and decisions only, written from the reviewer toward the author) each reshape the report without changing the evidence gathered.

**Publish only on explicit request.** Draft the body into a scratch file first. Extract a requested slice by heading range with the bundled helper, inclusive of both named headings, so the headings in the chat report and in the post stay identical and a range resolves exactly; when a posting instruction admits two readings, such as a range and a topic to drop in one sentence, ask before publishing. Apply the requested wording constraints: state what is true and the fix, use the reviewer's voice toward the author, include an attribution line only when asked, and convert file links to plain paths or to permalinks pinned to the reviewed commit. Prefix a slice with one line naming the reviewed commit and disclose any text added beyond the slice. Post as a plain pull request comment under the authenticated `gh` user by default because it stays editable, and use the formal review states (comment, request changes, approve) only when the user names one; an approval opens with the approved commit, labels the nits non-blocking, and restates deferred items. Verify the post through the API and report its URL; on a correction, edit the existing post in place rather than adding a second; correct an earlier wrong statement publicly in the same place. Resolving a review thread joins this same explicit-request class: resolve a thread only when the user asks and the re-review confirmed that thread's finding closed in the tree, and leave open every thread whose finding still stands. Offer a copy-ready fenced markdown block with plain paths when the user prefers to post by hand. Warn when a push to the branch will dismiss an existing approval. Never instruct another party's agent; frame a hypothesis about the author's environment as a check for them to run.

**Keep reviewer-side edits gated.** Fix a flagged defect on the branch only when the user asks in the current turn, after checking write permission, code ownership, and fork status; leave the tree uncommitted until the user asks to commit, and commit through `git_commit`. Push only when told, and after a push re-read the checks and the merge state, since a push can reset both. Merging the pull request stays the author's step.

**Bundled helpers.** Ship a `scripts/` helper that collects the git layer and, when available, the forge layer into a scratch directory of plain files with a manifest, so the model reads evidence rather than issuing dozens of commands, and a second helper that extracts an inclusive heading range from a markdown file. Put the per-file review question list, the report template with its fixed headings, and the manual fallback under `references/`. The question list carries four lenses beside its per-file questions, selected by what the diff touches rather than run on every change: migration safety and reversibility, drift between a definition and its consumers, abstraction weighed against the change's actual requirement, and coupling introduced across a module boundary. Only definition-versus-consumer drift is a required finding on a fixture. Every lens stays language-agnostic, so a stack-specific rule reaches the review through the repository's own declared criteria instead. Write the `description:` for both audiences per the standing rule: a compact statement of what the skill does, the trigger phrases (review this branch, assess the pull request, full assessment, can this be merged, review my uncommitted changes, re-review the delta, post the review as a comment), the explicit-request guard on publishing and on branch edits, and the boundary that keeps checkout, commit, approval, merge, and branch cleanup with their owners.

**Out of scope:**

- Putting the repository onto a branch, which `git_checkout` owns and this skill invokes.
- Creating commits, which `git_commit` owns; this skill commits nothing itself.
- Merging the pull request, which stays the author's step.
- Approving the pull request or requesting changes without an ask that names that state.
- Forge adapters other than GitHub through `gh`, since GitHub is the only forge the review rounds used; the git-only path serves every other remote.
- Pruning and deleting branches after the merge, which `git_refresh` owns.

This adds shipped content under `plugins/ai_dev/`, so registration and versioning for the landing commit follow the standing repo rules, which own the plugin version-lockstep procedure.

## Acceptance

Forge-layer scenarios put a stub `gh` on `PATH` that serves fixture JSON and records every invocation.

- A new `plugins/ai_dev/skills/git_review/SKILL.md` exists with frontmatter `name: git_review` and `version: 1.0.0`, and a both-audiences `description:` carrying the trigger phrases, the explicit-request guard on publishing and branch edits, and the boundary toward the three siblings.
- On a fixture whose feature branch is checked out and ahead of the default branch and whose diff is seeded with changes that place at least one finding under each of the seven findings headings (What the changes do and implement through Decisions the implementer must make before fixing) and none under `Can it be structurally merged as it is`, a run with no argument produces the report with all eight headings verbatim and in the documented order (branch and pull-request runs only), opens with the reviewed commit and the tree state, states the verdict on approvability in general with the shortest path to yes, and each finding names its location in a form the destination renders, quotes or reproduces the evidence, states the consequence, proposes the fix, and names who decides, with every non-critical finding carrying a non-blocking label; phrases each decision as a choice between named options with a suggested default, and closes with a yes on structural mergeability drawn from a clean `git merge-tree` result and the counts; the lead names the forge layer as unavailable because no `gh` is on `PATH`.
- On a fixture whose feature branch is ahead of the default branch by one commit that introduces no findings under any section heading, the run emits one line stating that no findings were identified, in place of any findings-section content, and still opens with the reviewed commit and closes with the structural-mergeability answer.
- On a fixture whose feature branch conflicts with the base, the closing answer is no and names the conflicting file.
- On a fixture checked out on a default branch named other than `main`, the base resolves to that branch.
- On a fixture on its default branch with staged, unstaged, and untracked changes plus one commit ahead of the upstream, the report reviews the two lanes under separate labels and closes under the heading `Can they be committed onto the default branch as they are`.
- On a fixture whose checked-out branch is behind its remote on a clean tree, the run fast-forwards and reports it; on a fixture that is behind with a dirty tree, the run reviews the remote ref in a detached scratch worktree, removes the worktree, and leaves the tree and its changes untouched, having run no stash and no reset.
- On a fixture where a hook refuses the checkout of the target branch, the run completes the review from a scratch worktree and lists the refusal as a finding.
- On a fixture whose target branch exists only on the remote, a run that asks to be put onto it invokes `git_checkout`, and a run that only asks for the review, including one given the remote-qualified form of that branch, reads the remote ref without moving `HEAD`; on that same remote-only target with a dirty worktree whose local changes would be overwritten by the switch, a run that asks to be put onto it still completes the review from the remote ref without moving `HEAD` or altering the dirty tree, after `git_checkout` surfaces the block, and the report names those blocking paths.
- With the stub `gh` serving a pull request whose merge state is blocked only by a required review, the report reads the issue comments, the review bodies, and the inline review threads, each with its count, the closing answer is yes, and the required review appears as context rather than as a blocker.
- With the stub `gh` serving a pull request whose head SHA differs from checked-out `HEAD`, the lead names the mismatch and the review uses the forge head.
- With the stub `gh` serving a pull request whose review threads span more than one page and include one resolved thread and one outdated thread, the run reads every page of threads and of the comments inside each thread, and the report accounts for the resolved and the outdated thread rather than omitting them.
- With the stub `gh` serving a pull request body whose stated version and test count differ from the branch, the report names each stale claim.
- On a fixture whose user message names a wiki page that records a settled owner decision, the report treats that decision as settled rather than listing it as open.
- On a fixture whose diff includes a defect near the end of a file several thousand lines long, the report finds it, proving the whole file was read.
- On a fixture where a named changed path cannot be read, the report names that unread remainder and does not call the change approvable.
- On a fixture whose diff adds a line matching a common credential pattern (for example a value prefixed `AKIA`) and a line containing a hardcoded absolute home path (for example `/home/alice/...`), the report lists both as findings.
- On a fixture whose diff includes at least one binary file and at least one file whose name matches a generated-file convention (for example `_generated.go` or a file under a `vendor/` subtree), the report states the size and the share of binary or generated files in the diff, independent of whether those files carry code findings.
- On a fixture whose diff contains one defect the run can reproduce with a concrete command and one defect it cannot reproduce directly (for example a race condition described only in a comment), the report labels the reproducible finding `verified` and the unreproducible one `inferred`.
- On a fixture whose tree already carries a repository-wide lint baseline hit and whose optional linter is absent from `PATH`, the report does not treat the baseline hit as a defect, names the missing linter as skipped, and completes the run.
- On a fixture whose diff changes a schema that a consumer elsewhere in the tree reads, the report carries a definition-versus-consumer drift finding naming that consumer.
- On a fixture with a test suite and a workflow definition, the report states which gates ran locally and which the workflow runs.
- On a fixture whose workflow definition and whose documented task-runner target name different commands for the same gate, the report carries the disagreement as its own finding; on a fixture with a documented task runner and no workflow definition, the run still states which gates it ran.
- On a fixture carrying a root `CHARTER.md`, `TESTING.md`, `SECURITY.md`, and `ARCHITECTURE.md` and whose history already contains a prior commit touching the same charter constraint, a change crossing a charter boundary appears under the critical heading citing `CHARTER.md` by name and locating that nearest precedent beside it, a divergence from `TESTING.md` and a divergence from `SECURITY.md` each appear as a non-blocking finding citing that document, and code short of the declared direction draws no defect finding; on a fixture carrying none of those documents, the run reviews unchanged and reports no missing-document finding.
- On a fixture whose change renames a file that a standing instruction still references and edits the source of a derived artifact without regenerating it, the report names both and flags the derived artifact for regeneration by its owner rather than editing it.
- On a fixture whose change bumps a component version without updating the manifest files the repository's standing versioning rules name, the report names the lockstep gap.
- Delta eval: given a prior review whose findings cover the full tag set (one fixed in the tree, one claimed without a code change, one acknowledged but still unfixed, one declined with a reason, one settled by a decision, one that regressed, one new, one prose-only concession beside a code change, one routed to someone and unanswered, and one outside decision the user relays) and whose pull request carries comments and review bodies newer than that reviewer's last post, the re-review reads every comment and review body newer than the reviewer's last post first, then tags closed, open, open and not acknowledged, settled by a decision, regressed, and new; leaves the declined-with-reason item out; keeps the routed-unanswered item open; folds in the relayed decision; separates the prose concession from the code change; keeps the eight headings; and states whether the loop can stop.
- Scope eval: a "no nitpicking" run folds minor items into one line; an "only what is genuinely open" run emits actionable items and decisions only, written toward the author; a focus-area run reports findings inside the named area and omits findings outside it.
- A posting run writes the report body to a scratch file first; the heading-range helper, given that file and two heading texts, returns exactly the inclusive slice; an eval whose posting instruction combines a range and a topic to drop makes the run ask before any post; a run that posts a slice prefixes it with one line naming the reviewed commit and discloses any text added beyond the slice.
- A run without a posting instruction records no `gh pr comment` or `gh pr review` call in the stub log; a run with a posting instruction and "no attribution line" posts a plain comment as the authenticated `gh` user whose body carries no attribution, converts file links to permalinks pinned to the reviewed commit, states each finding affirmatively, frames environment hypotheses as checks for the author, and does not instruct another party's agent, verifies the post through the API, and reports its URL; a run naming approval posts the approve state with the approved commit in the lead, the nits labelled non-blocking, and deferred items restated.
