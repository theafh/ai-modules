# Limit a scoped `--uninstall` to the scope it names

## Goal

`deployment.sh --uninstall --global` removes only artefacts deployed into the global scope, and `deployment.sh --uninstall --project-dir DIR` removes only artefacts deployed into that project. Entries from every other scope stay deployed and stay in the deploy log. A scopeless `--uninstall`, which `make uninstall` runs, keeps removing matching entries from every scope. This task is the point-fix for uninstall: it adds a helper that derives a logged entry's scope from its deployed path and applies it to uninstall's selection.

## Context

`uninstall_logged_artifacts` in `deployment/deployment.sh` walks every line of the deploy log and selects an entry when `logged_path_matches_active_targets` accepts its target and `logged_type_matches_filter` accepts its type. Neither check looks at where the entry was deployed, so `--global` and `--project-dir` change nothing about which entries are removed. A project uninstall therefore deletes global copies as well, without a backup, because the main flow skips backups whenever `PROJECT_DIR` is set. A global uninstall likewise deletes every project's copies. On 7 October 2026, `--project-dir <empty scratch directory> --target claude --type skill --uninstall --dry-run` listed every logged global Claude skill and every Claude skill entry of a second project for removal, while the named project had no entries at all.

The log records no scope, but each deployed path implies it under the derivation rule in **Approach**. A JSON-merge entry appends its key to the settings file's path as a `[key]` suffix. The run's own target-directory variables follow its scope flag, so under `--project-dir` they point into the project and cannot place a global entry.

The scopeless form is a deliberate maintenance mode, which the explicit-scope check marks with `NO_SCOPE_UNINSTALL`. The `style_run.sh` scenario under the comment `# --- Legacy four-field path[key] still strips ---` relies on it removing an entry whose settings file lies outside every target directory.

[The `make update` task](deployment_update-from-deploy-log.md) groups every log entry by this same derived scope and reuses the helper, which is why the helper serves any logged entry rather than only the entries of the run's own scope.

`tests/deployment/script_tests/run.sh` stages a scratch home through `HOME` and a scratch project, copies the deploy log aside and restores it on exit, and already runs project-scoped uninstalls for OpenCode, Antigravity, and Codex. Each of those runs while the log holds only that project's entries, so their assertions hold after the fix.

## Approach

Add one helper, `logged_path_scope`, to `deployment/deployment.sh` that returns the scope of any logged entry from its deployed path and target id, after stripping a `[key]` suffix from the path. For each target, compute global-form roots as the roots `backup_roots` would back up for that target in global mode, and project-form matchers as the project-relative path suffixes the `# Target directories` block appends under `--project-dir` for that target, including `.agents/skills` beside `.codex` and both VS Code project suffixes. Return the literal `global` when the path lies under one of that target's global-form roots, the recovered project directory as an absolute path — the path prefix before the matched suffix — when the path lies under `{recovered_project}/{suffix}` (or equals that directory) for any of that target's project-form suffixes, and an empty string when the path fits neither form. `logged_path_scope` returns status 0 on every path, its three outcomes being carried by the returned string alone and the empty string meaning "no derivable scope". Compute those global-form roots and project-form suffixes from the target id together with the machine's global layout — `HOME_DIR` and the OS branch that selects the VS Code prompts root — rather than from the run's scope flags. Derive those global-form roots inside the new helper from the target's base directory plus the antigravity, opencode, and VS Code special cases, rather than extracting a shared roots function, and leave the two existing `backup_roots` derivations in `clear_backups_for_active_targets` and the main backup loop as they are. Because the helper takes only the logged path and target id — and does not read scope flags, `PROJECT_DIR`, or source-prior log fields — it works on every line the log already holds, four-field and five-field alike, and the log format stays as it is.

In `uninstall_logged_artifacts`, **after the existing target and type filters**, select only entries whose derived scope is the literal `global` when `--global` is set, and only entries whose derived scope equals that project directory when `--project-dir DIR` is set, comparing against the directory in the form the script already resolves `--project-dir` to. Leave every unselected entry deployed and in the log, the way entries outside the target and type filters stay today. An entry whose derived scope is the empty string is unselected under a scope flag, and the run reports it through the script's existing `skip` label as `skip  out-of-scope for this uninstall: <logged path>`, leaving the entry in the deploy log. This message is the selection branch's own, so it appears for a scope-mismatched entry and not for the main flow's `skip  Backups are disabled in project-dir mode` line. Without a scope flag, keep today's selection, so a scopeless uninstall still reaches every scope, empty-string derived scopes included.

Rewrite each passage that describes what uninstall selects so it states that a scope flag limits removal to that scope and that a scopeless run covers every scope:

- In `deployment/README.md`, the `--uninstall` row of the **Flags** table and the sentence "`--uninstall` removes only log entries that match the active filters." in the **Deploy Log and Uninstall** section.
- In `deployment/deployment.sh`, the `--uninstall` entry of `print_usage`, which today reads "Uninstall mode; remove matching logged deployed artifacts after backup."
- In `deployment/deployment.sh`, the `--uninstall` line of the header comment's `Features:` block, which today reads "Remove previously deployed artifacts from deployed_artefacts.log".
- In `wiki/concepts/deployment-model.md`, the overview sentence "uninstall works by replaying that log" and the opening of the `### Uninstall restores the value it replaced` section, so each states that a scope flag limits removal to that scope and a scopeless run covers every scope. Make the edit through the wiki skill family, as the standing repo rules direct. Two other live tasks edit this same page. The `make update` sibling rewrites the overview sentence and the "what the script has become" sentence that names "an uninstall path", so this edit and that task's share the overview sentence alone; this task's second passage, the opening of `### Uninstall restores the value it replaced`, is untouched by that task. All three edits therefore land as one coordinated change to the shared overview sentence.

Add the scenarios that **Acceptance** lists to `tests/deployment/script_tests/run.sh`, with the shared fixture deploying the `language_humanizer` skill for the `claude` target and staged afresh before each scenario that consumes it so every scenario observes the copies and log entries it asserts on, and name the new coverage in the `script_tests/run.sh` description within the deployment entries of `tests/README.md` and `tests/CLAUDE.md`.

**Out of scope:**

- Separating, under a `--project-dir` run, a project-scoped entry whose project directory overlaps a global root from the global entries beside it, most plainly `--project-dir "$HOME"`, which writes entries at the global form's own path; no `--project-dir` run can single such an entry out, because the helper derives it as `global`, so `--global --uninstall` removes it alongside genuine global entries.

## Acceptance

Unless an item names its own fixture, each scenario runs in `run.sh` with the shared fixture's target and skill type as the `--target` and `--type` filters, after the same skill type for one target is deployed globally into the scratch home and into two scratch projects.

- `--project-dir <first project> --uninstall` removes the first project's copies and log entries, and leaves the global copies, the second project's copies, and their log entries in place.
- `--global --uninstall` removes the global copies and their log entries, and leaves both projects' copies and log entries in place.
- `--project-dir <first project> --uninstall --dry-run` lists only paths under the first project.
- With its own fixture — a `path[key]` log entry for one target under the global settings file and under each of the two projects' settings files — `--project-dir <first project> --uninstall --dry-run` lists only the first project's `path[key]` entry, and leaves the global and second-project `path[key]` entries unlisted and still in the log.
- A scopeless `--uninstall` removes the copies and log entries of all three scopes.
- Under `--global --uninstall`, a log entry for that target whose deployed path fits neither form produces an output line matching `skip  out-of-scope for this uninstall: <that logged path>`, its path stays in place, and the entry stays in the log; the check greps that message, so it passes only when the scope-selection branch runs and would fail if the entry were selected for removal.
- Under `--project-dir <first project> --uninstall`, a log entry for that target whose deployed path fits neither form produces an output line matching `skip  out-of-scope for this uninstall: <that logged path>`, its path stays in place, and the entry stays in the log; the check greps that message, so it passes only when the scope-selection branch runs and would fail if the entry were selected for removal.
- A scopeless `--uninstall` removes a log entry for that target whose deployed path fits neither global nor project form, and a `--dry-run` of that run lists that entry for removal.
- The `--uninstall` row of the **Flags** table in `deployment/README.md` and its **Deploy Log and Uninstall** section both state that a scope flag limits uninstall to that scope, and the sentence "`--uninstall` removes only log entries that match the active filters." no longer appears there as written.
- The `--uninstall` entry that `deployment.sh --help` prints and the `--uninstall` line of the header comment's `Features:` block in `deployment/deployment.sh` both state the scope limit.
- `wiki/concepts/deployment-model.md` states in its overview and in its uninstall section that a scope flag limits uninstall to that scope, and its overview sentence "uninstall works by replaying that log" no longer appears there as written.
- The deployment entries in `tests/README.md` and `tests/CLAUDE.md` name scope-limited uninstall in their `script_tests/run.sh` description.
- After sourcing `deployment/deployment.sh` with `DEPLOYMENT_SH_SKIP_MAIN=1` and `HOME` set to the scratch home, and argv that includes `--project-dir` pointing at one scratch project (the `style_run.sh` sourcing pattern), the helper returns the literal `global` for one logged deployed path under the scratch home's global form, the first project's absolute directory for one path under the first scratch project, the second project's absolute directory for one path under the second, and the empty string for one logged path for that target that fits neither global nor project form. For each target, it also returns the first project's absolute directory for one logged path under the first scratch project for every project-relative suffix the `# Target directories` block appends for that target under `--project-dir`, each such path passed with that target's id. For each target, the helper also returns the literal `global` for one logged path under that target's global form — under the scratch home's `.gemini` tree for `antigravity`, under `.config/opencode` for `opencode`, and under both the `.copilot` root and the OS-selected VS Code prompts root for `vscode`. Every one of those calls returns status 0.
- Sourcing `deployment/deployment.sh` the same way, with argv that includes `--global` in place of `--project-dir`, the helper returns the first project's absolute directory for one logged path under the first scratch project and the literal `global` for one logged path under the scratch home's global form.
