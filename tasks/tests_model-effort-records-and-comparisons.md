# Record model and effort in judge-harness run records, and refuse cross-setting comparisons

## Goal

The two judge harnesses, `natural_language` and `language_humanizer`, record the vendor, the worker model and effort, and the judge model and effort in every run record they write, so each verdict names the settings that produced it. Every comparison against a prior run that a runner makes, the wiki layer 2 benchmark compare and the `language_humanizer` re-grade's as-run comparison, refuses a prior run recorded on another vendor, model, or effort: it writes its own records without the comparison and exits non-zero with a message naming both values, the way the trigger-eval baseline check does. A deterministic test pins each new record field and each refusal.

## Context

[The finished Opus-effort task](archive/tests_claude-worker-opus-effort.md) made effort a vendor setting and carried it into every command, the verdict cache key, every Pattern A run record, and the trigger-eval baseline check. The review of that change named the three gaps below as follow-ups.

- **The precedent.** `baseline_worker_mismatch` in `tests/trigger_evals/run.py` normalizes both sides before comparing: a missing `worker_effort` reads as the empty effort, and a missing `worker_model` reads as `unknown`, which matches no run. Its caller checks the vendor first, then the worker settings, writes `results.json` without `baseline_comparison`, prints a `WARNING:` naming both values, and returns 1.
- **`natural_language`.** `tests/natural_language/evals/run.py` writes `summary.json` and `summary.md` into the run directory and copies both to `results/run-<ts>.{json,md}`; `run_pass` writes each pass's `verdict.json`. The console prints the CLI version, the run directory, and the style. None of these names a model or an effort, although `resolved` carries all four values. The harness is Claude-only.
- **`language_humanizer` run.** `tests/language_humanizer/evals/run.py` writes the worker model and effort labels into each pass's `timing.json` and prints worker and judge settings in its `Worker vendor:` console line. `summary.json`, `results/run-<ts>.json`, and each pass's `verdict.json` (written by `run_isolated_pass`) carry neither the worker nor the judge settings.
- **`language_humanizer` re-grade.** `tests/language_humanizer/evals/regrade.py` re-grades a captured run without re-running the worker, through `run_mod.summarize` and `run_mod.render`. It writes `verdict.regrade.json` per pass, `summary.regrade.{json,md}` in the run directory, and `results/<run>-regrade.{json,md}`, and it compares the re-graded rates with the original verdicts' rates through `summary["original_rates"]` and the `## As-run rates before the instrument fix` report section. Its judge settings reach only the `Judge vendor:` console line, and the comparison runs whatever judge produced the original verdicts.
- **Wiki layer 2.** `tests/wiki/layer2/run.py` passes the newest `workspace/run-*/benchmark.json` (from `latest_previous_benchmark`) to `tests/wiki/layer2/aggregate.py` as `--previous`, and `aggregate.py` runs `detect_regressions` against it with no settings check. Each pass's `timing.json` carries the worker model and effort labels but no vendor, and `benchmark.json` carries no settings. The layer 1 scenario `g2_aggregate_names_baseline_and_warns_on_narrowing` in `tests/wiki/layer1/run.sh` builds its current run and both baselines without settings.
- **Pool tasks on the same runners.** [The language_humanizer shared-pool task](tests_language-humanizer-shared-pool.md) and [the layer 2 runner dedup task](tests_wiki-layer2-runner-dedup.md) move these runners' pass loops onto `tests/lib/eval_runner.py`. They leave the records and comparisons alone, so neither orders this task, and whichever lands second carries the other's edit through the code as it then stands.
- **Docs that describe the comparisons.** `tests/CLAUDE.md` (the paragraph opening "The aggregator compares against the most recent prior"), `tests/wiki/RUNBOOK.md` and `tests/wiki/README.md` (the same claim), `tests/language_humanizer/RUNBOOK.md` (`## Re-grading versus re-running`), `TESTING.md` (the trigger-baseline sentence opening "Pass a baseline recorded on the same vendor"), and `wiki/concepts/verification-surfaces.md` (the sentence ending "a trigger-eval baseline recorded on another model or effort is refused rather than compared").

## Approach

1. **Record shape.** A judge-harness record carries top-level `vendor`, `worker_model`, `worker_effort`, `judge_model`, and `judge_effort`, holding the resolved raw values the way the trigger `results.json` does: an empty string means the flag was omitted and the CLI applied its default. A `--skip-judge` run records `null` for both judge fields, because no judge ran. Each judge runner builds this block once through a pure `run_settings(resolved, skip_judge)` function, and `summarize` takes the block and places it at the top of the summary, so `summary.json` and the copied `results/run-<ts>.json` carry it.
2. **`natural_language`.** `run_pass` writes the block into each `verdict.json`, `render` prints one settings line naming the vendor, the worker model and effort, and the judge model and effort (so `summary.md` and the results copy carry it), and `main` prints a console header line from a pure function naming the same values plus the worker command.
3. **`language_humanizer` run.** `run_isolated_pass` writes the block into each `verdict.json`, and `render` prints the same settings line. The console header stays as it is.
4. **`language_humanizer` re-grade.** `regrade.py` reads the block from the original run's `summary.json`, reading a missing file or field as absent. Its records carry the original's `vendor`, `worker_model`, and `worker_effort` (`null` when absent), because the captured responses are the original worker's. They also carry the judge that produced the re-graded judge verdicts: `judge_vendor`, `judge_model`, and `judge_effort` from the re-grade's resolved vendor and judge, or, under `--skip-judge`, the original's `vendor` and judge fields carried forward with those verdicts. `verdict.regrade.json`, `summary.regrade.json`, and the results copy carry these fields. When the judge re-runs, compare its vendor, model, and effort with the original's `vendor`, `judge_model`, and `judge_effort` under the precedent's normalization, with a missing vendor reading as `unknown` like a missing model. On a difference, leave out `original_rates` and the as-run section, record the message as `original_mismatch` in the summary and as a line in the report, print it as a `WARNING:`, and exit 1. A `--skip-judge` re-grade keeps the comparison, because its judge verdicts are the original ones.
5. **Wiki layer 2.** `run.py` writes `run_settings.json` (`vendor`, `worker_model`, `worker_effort`) into the run directory before the first pass, through a function a test can call. `aggregate.py` copies those fields to the top level of `benchmark.json`, leaving them out when the file is missing, and exposes a pure `settings_mismatch(previous, current)` under the precedent's normalization: a missing vendor or model on either side reads as `unknown` and matches nothing, and a missing effort reads as the empty effort. When `--previous` names a benchmark on other settings, `aggregate.py` skips `detect_regressions` and the baseline block, records the message as `baseline_mismatch` in `benchmark.json` and `benchmark.md`, prints it as a `WARNING:`, and exits 1. `run.py`'s automatic choice becomes the newest prior benchmark whose settings match this run's under `settings_mismatch`, and the run prints the benchmark it chose or that none matched. A run after a vendor or effort switch therefore compares against the last run on its own settings and never fails on the switch alone.
6. **Docs.** Rewrite the `tests/CLAUDE.md`, `tests/wiki/RUNBOOK.md`, and `tests/wiki/README.md` passages so the aggregator compares against the newest prior benchmark recorded on the same vendor, worker model, and worker effort, and refuses an explicit `--previous` recorded on others. Extend the re-grade passage in `tests/language_humanizer/RUNBOOK.md` with the judge-settings refusal. Rewrite the `TESTING.md` trigger sentence and the `wiki/concepts/verification-surfaces.md` sentence so they state the one rule that every comparison against a prior run refuses another vendor, model, or effort, with the trigger baseline, the layer 2 benchmark, and the re-grade as its instances; edit the wiki page through the `wiki` skill family. Where `tests/CLAUDE.md` lists what each judge harness's deterministic tests cover, add the new tests, and keep `tests/AGENTS.md` in lockstep wherever it carries the same statement.

**Out of scope:**

- Moving either runner's pool onto the shared helper, which the two pool tasks in Context own.
- Changing the trigger-eval check, which already refuses cross-setting baselines.
- Comparing worker settings in the re-grade, since the re-grade never re-runs the worker.
- Re-running any behavioral eval, since every change here is pinned by deterministic tests.

## Acceptance

- `python3 tests/natural_language/evals/test_run.py` passes new cases: `run_settings` on a default Claude resolve yields `opus`/`high`/`opus`/`xhigh` and on `--skip-judge` yields `null` judge fields; `summarize` output and the `render` text carry those values; the console header function names them; and a `run_pass` call with stage, deployment, worker, grader, and judge stubbed writes a `verdict.json` carrying all five fields.
- `tests/language_humanizer/evals/test_run.py` exists, is listed in `tests/language_humanizer/evals/covered-by-entrypoint`, runs from `tests/language_humanizer/run_all.sh`, and passes cases for:
  - `summarize` output carrying the block, and a stubbed `run_isolated_pass` writing `verdict.json` with all five fields;
  - a re-grade on the original's judge settings keeping `original_rates` and writing the settings fields into `verdict.regrade.json`, `summary.regrade.json`, and the results copy;
  - a re-grade at another judge effort, and one on another judge model, each writing no `original_rates`, recording an `original_mismatch` naming both values, and exiting 1;
  - an original summary without judge fields refusing a re-judged comparison with the missing model named `unknown`, while a `--skip-judge` re-grade of it keeps `original_rates`.
- `bash tests/wiki/layer1/run.sh` passes a new scenario in which `aggregate.py --previous` on another worker effort, on another worker model, and on a benchmark without settings each exits 1, writes no regressions, and records a `baseline_mismatch` naming both values; a matching benchmark still compares; `benchmark.json` carries the run's `run_settings.json` fields; and `run.py`'s benchmark choice, run against a temporary workspace, skips a newer benchmark on other settings for an older matching one. The existing `g2_aggregate_names_baseline_and_warns_on_narrowing` scenario still passes with matching settings on its run and baselines.
- `rg -n "most recent prior .benchmark.json." tests/CLAUDE.md tests/wiki/RUNBOOK.md tests/wiki/README.md` finds no passage that omits the same-settings condition, and each file states the `--previous` refusal.
- `tests/language_humanizer/RUNBOOK.md`, `TESTING.md`, and `wiki/concepts/verification-surfaces.md` each state the cross-setting refusal for the comparison they describe, and `rg -n "a trigger-eval baseline recorded on another model or effort is refused" wiki/concepts/verification-surfaces.md` finds nothing.
