# Enforce, reconcile, migrate, and align the raw-sidecar origin-field contract (source_url / source_path), plus a safe-fix for absolute in-repo paths across source_path and sources

## Goal

The whole wiki skill family enforces and teaches one raw-sidecar origin-field contract: `source_url:` for an externally-published source (a real remote URL), `source_path:` for a source tracked inside the repo (repo-relative), and neither field for a local file outside the repo (captured by a body excerpt plus a prose locality note). This task also anchors, once and explicitly, the operating contract the `auto_shaper_wiki` agent already works by: autonomously apply every safe, deterministic fix and report it, and surface only genuine decisions for the user — so origin-field handling is an instance of that contract, not a bespoke rule. Six gaps that currently leave the contract under-specified and unenforced close:

1. **Origin-field value forms are validated.** The linter flags a `source_url:` value that is a `file://` URL or a bare path rather than a real remote URL, and — the mirror case — a `source_path:` value that carries a remote `scheme://` (a URL misplaced where a repo-relative path belongs), each with a message redirecting the author to the correct field or the out-of-repo excerpt rule, and flags a sidecar that carries both origin fields at once. The `source_path:`-holds-a-URL check runs everywhere, including a wiki outside a git repo where `check_source_path_portable` is skipped and such a value would otherwise pass silently.
2. **The canonical contract states how a mislabeled or legacy sidecar reconciles.** One canonical rule in `template_schema.md` states the deterministic, lossless reconciliation — a value whose form fits the other field moves to it (a `file://` or path value naming an in-repo target becomes a repo-relative `source_path:` with the URL field dropped; a remote URL becomes `source_url:`), and two fields naming the same origin collapse to the one matching field — and defines the irreducible case a human decides (two fields naming *different* plausible origins, or a value that fits no field and whose removal would strand the source, such as an out-of-repo `file://` with no stand-alone excerpt).
3. **A SCHEMA customization that contradicts canonical semantics is surfaced, not silently kept.** When a wiki's own `SCHEMA.md` carries content that *contradicts* the canonical semantics rather than merely *extending* them — the motivating case being a `### raw/ Frontmatter` block that teaches the superseded `source_url: file://…` form — the agent surfaces it for the user instead of classifying it as a customization to preserve.
4. **Stale `source_url`-only prose is aligned.** `raw_taxonomy.md` and the three `source_url` or `source_path` phrasings in the agent stop implying `source_url:` is the sole or interchangeable origin field.
5. **The agent's operating contract is anchored — auto-apply every safe fix and report it, surface only the decisions.** `auto_shaper_wiki`'s remediation is stated once as one governing rule: autonomously apply every fix that is safe and deterministic (loses no meaning, invents no value, resolves no genuine ambiguity), record each in the per-file change report, and surface for human decision only genuine judgment calls — contradictions, conflicts between two real values, genuinely broken or ambiguous cases — through the existing contested-page protocol. Origin-field handling becomes an instance of this contract: the agent auto-applies the gap-2 reconciliation and surfaces only an irreducible origin case, so the `<fix_raw_source_frontmatter_missing>` block keeps its existing *never fabricate an origin field* rule but sheds the blanket *an absolute `source_path:` is surfaced… never auto-rewritten* stance that made origin the outlier.
6. **An in-repo absolute provenance path is a surfaced safe auto-fix, not a hard block — for `source_path:` and `sources:` alike.** When either field holds an absolute or `~`-prefixed path that resolves to an existing in-repo file — for `source_path:` anywhere inside the repo, for a page's `sources:` entry inside the wiki's `raw/` tree — the linter computes the equivalent repo-relative path and surfaces it as a **warn** carrying that concrete rewrite as a safe auto-fix, rather than the current blanket block; the agent applies the rewrite as a deterministic same-file normalization. A path that resolves outside its allowed root (the repo for `source_path:`, `raw/` for `sources:`), or to no file, stays blocking — it has no in-repo equivalent and routes to the existing surface path (the out-of-repo excerpt decision for `source_path:`, the migrate-or-surface handling for `sources:`).

## Context

The two-field contract itself shipped and is deliberate — the settled Option A decision in [wiki_lint-local-path-portability.md](wiki_lint-local-path-portability.md) established that `source_path:` is repo-relative only (an absolute, `~`-prefixed, or repo-escaping value is blocking; a non-repo wiki is local-only and skipped), and that an out-of-repo local file is captured by excerpt with no stored path. Read that task for the portability rationale this one extends to the `source_url:` side. The problem is that the contract is enforced and taught on only one of its two fields, and nothing covers the wikis that predate it.

- **Origin-field values are only half-checked.** In [lint.py](../plugins/knowledge_management/skills/wiki/scripts/lint.py), `check_source_paths_exist` validates the page-level `sources:` inventory, and `check_source_path_portable` validates a `source_path:` for in-repo path portability — but only in a wiki that lives in a git repo, and only against path shapes (absolute, `~`-prefixed, repo-escaping, non-resolving). No check inspects `source_url:` at all — a `file://` value, a bare path, or a both-fields sidecar passes silently — and no check gives a URL misplaced in `source_path:` a useful signal: a non-repo wiki skips `check_source_path_portable` entirely so it passes silently, while a repo wiki flags it only as a misleading "does not resolve on disk" path error rather than redirecting the author to `source_url:`. The `file://`-in-`source_url:` form that motivated this task is the primary invisible case; the URL-in-`source_path:` mistake is its mirror.
- **An in-repo absolute provenance path is hard-blocked though it is trivially fixable.** `check_source_path_portable` blocks any absolute or `~`-prefixed `source_path:` outright, and `check_source_paths_exist` blocks any absolute `sources:` entry, per the archived Option A portability rule ([wiki_lint-local-path-portability.md](wiki_lint-local-path-portability.md)). But when the path resolves to a file inside the repo (for `sources:`, inside `raw/`), its repo-relative equivalent is deterministic and lossless — the same file, portably spelled — so hard-blocking it forces a manual edit for something the tooling can settle on its own, and leaves the gap-5 operating contract with a day-one exception (a safe fix the agent applies for one provenance field but not its sibling). This task refines that sub-case, on both fields, to a surfaced safe auto-fix; the genuinely non-portable out-of-repo case stays blocking.
- **The "origin optional" posture is intentional, and this task stays consistent with it.** The [wiki_lint-blind-spots-and-false-positives.md](wiki_lint-blind-spots-and-false-positives.md) added `check_raw_frontmatter` and deliberately kept the origin field *optional* (a sidecar for an out-of-repo local source legitimately carries neither field). The new `source_url:` check validates the *form of a value that is present*; it never makes an origin field required, so the two checks sit beside each other in `lint.py` without conflict.
- **No migration story for pre-split wikis.** `init_wiki.sh` copies `template_schema.md` verbatim into a new wiki's `SCHEMA.md`, so a wiki initialized before the split froze an era-1, `source_url`-only snapshot and improvised local conventions (the downstream `source_url: file://sources/…` form). Nothing documents how those sidecars migrate onto the current contract.
- **The agent preserves contradicting SCHEMA content.** The hunk-classification rule in [auto_shaper_wiki.md](../../plugins/knowledge_management/agents/auto_shaper_wiki.md) sends any hunk where the wiki has content the canonical lacks to "customization, preserve as-is", with no carve-out for a customization that actively contradicts canonical semantics — so a local `### raw/ Frontmatter` teaching `file://` is silently kept.
- **The auto-fix mechanism already works this way — the principle is just unstated.** `wiki_fix` never edits files; it fronts `auto_shaper_wiki`, which is the actor (the labels are the reverse of how it is easy to picture them). The agent already fixes findings autonomously, reports a per-file change list, and surfaces contradictions through the contested-page protocol (`<contradictions_surfaced>`, `<fix_contested_page>`, `<report_changes>`). So "auto-apply the safe, surface the decisions, report what was done" is the agent's de facto model — but it lives scattered across per-check rules with no single governing statement, which is why each new check (origin included) re-derives it and can drift, as the origin outlier below shows.
- **The agent surfaces every origin issue and auto-fixes none.** The `<fix_raw_source_frontmatter_missing>` block in `auto_shaper_wiki.md` backfills `ingested`/`sha256` but treats every origin question as surface-only — its guardrail reads *never auto-rewrite an origin field*, so even a deterministically mislabeled value (a URL sitting in `source_path:`, an absolute path that resolves in-repo) is handed to the user rather than corrected. That posture is right against *fabrication* but too broad: reclassifying a value already present into its correct field, or dropping a duplicate that names the same origin, invents nothing and loses nothing, so it is safe to automate. Gap 5 narrows the guardrail to fabrication and conflict resolution and auto-applies the lossless reclassifications, so an LLM handles what it can settle deterministically and the user sees only true conflicts.
- **`source_url`-only prose lingers.** [raw_taxonomy.md](../../plugins/knowledge_management/skills/wiki/references/raw_taxonomy.md) predates `source_path:` and frames its bucket table's "Typical `source_url`" column and its `source_url`-keyed classification heuristics as if `source_url:` were the only origin field; the agent's three `source_url` or `source_path` phrasings imply the two fields are interchangeable: two declare the canonical `### raw/ Frontmatter` shape, letting a `source_url`-only schema read as satisfying it, and the third reports a raw file's own origin in the same either-or terms.

Full edit surface: `lint.py` and `references/lint_checks.md` (gaps 1 and 6); `references/template_schema.md` for the canonical reconciliation contract (gaps 2, 5, and 6), with `skills/wiki/SKILL.md` and `skills/wiki_import/SKILL.md` citing it; `auto_shaper_wiki.md` (gaps 3, 4, 5, and 6); `references/raw_taxonomy.md` (gap 4). Within `auto_shaper_wiki.md`, gap 5 rewrites the assess-phase **Raw-source frontmatter drift.** detection and the fix-phase `<fix_raw_source_frontmatter_missing>` block, both adjacent to the **Frontmatter field drift.** and `<fix_raw_frontmatter_subsection_missing>` blocks gap 4 rewrites, and adds the governing remediation-contract statement at the agent's `<role>`/`<objective>` altitude. Gap 6's linter changes span `check_source_path_portable` and `check_source_paths_exist`; its agent normalization rides `<fix_raw_source_frontmatter_missing>` (for `source_path:`) and `<fix_external_source_pointer>` (for `sources:`).

Co-edit coordination: [wiki_auto-shaper-internal-contradictions.md](wiki_auto-shaper-internal-contradictions.md) rewrites other blocks of the same `auto_shaper_wiki.md` (its exit criterion and the stale body-Sources anatomy); coordinate so this task's raw-frontmatter-drift, hunk-classification, reconciliation-behavior, and per-file-report edits land coherently alongside it. [wiki_raw-kind-rubric-and-out-of-repo-paths.md](wiki_raw-kind-rubric-and-out-of-repo-paths.md) introduced `source_path:` and the `raw_taxonomy.md` rubric that gap 4 realigns.

## Approach

1. **Validate origin-field value forms (gap 1).** Add a value-form check to `lint.py` over the `raw/` tree, beside `check_source_path_portable`, covering both origin fields and both mismatch directions:
   - A `source_url:` value that uses the `file://` scheme, or is path-like (carries no `scheme://` at all — a bare relative or absolute path), yields a **warn** redirecting the author to a repo-relative `source_path:` for an in-repo source or to the out-of-repo excerpt rule; a value with a genuine remote scheme passes.
   - A `source_path:` value that carries a genuine remote `scheme://` (a URL where a repo-relative path belongs) yields a **warn** redirecting the author to `source_url:`; a plain repo-relative path passes this form check and is left to `check_source_path_portable` for portability.
   - A sidecar carrying both `source_url:` and `source_path:` at once yields a **warn** (the two name mutually-exclusive origin kinds — keep one).

   All three are **warn**, not blocking, because these are overwhelmingly legacy or mis-filled sidecars to migrate (gap 2) rather than newly-authored non-portable paths: matching the sibling `raw-frontmatter` check's treatment of a mechanically-fixable legacy gap, a warn surfaces every one without hard-breaking a pre-split wiki's lint on upgrade. Unlike `check_source_path_portable`, this form check does not depend on the wiki living in a repo, so it runs everywhere — which is what closes the non-repo `source_path:` gap, where `check_source_path_portable` is skipped. To keep a repo wiki from emitting a redundant, misleadingly-messaged double finding on the same field, `check_source_path_portable` yields the URL-in-`source_path:` case to this form check: it skips a `source_path:` value carrying a remote URL scheme (a genuine repo-relative path never carries one), so the author gets the single redirecting **warn** everywhere instead of a blocking "does not resolve on disk" error inside a repo and a silent pass outside one. This harmonizes the URL-in-`source_path:` severity to **warn** in both contexts, consistent with the gap's legacy-migration posture. The repo-escaping and non-resolving path cases `check_source_path_portable` already blocks stay blocking; gap 6 separately converts its in-repo absolute-path case from blocking to a safe-auto-fix **warn**. Rewrite the affected rows of `references/lint_checks.md` in place — a new origin-field-form row (covering the `source_url:` wrong-kind, `source_path:`-holds-a-URL, and both-fields cases) and any severity-bucket line it belongs in, plus the existing `raw-source-path` row to note the URL-scheme carve-out — so the matrix keeps matching the script.
2. **Document the reconciliation contract once (gap 2).** In the `### raw/ Frontmatter` subsection of `template_schema.md` — the canonical home for the field semantics — state, beside the two-field meanings, how a mislabeled or legacy sidecar reconciles onto the contract. State the deterministic, lossless moves: a value whose form fits the other field moves to it (a `file://` or path value naming an in-repo target becomes a repo-relative `source_path:` and the `source_url:` is dropped; a remote URL becomes `source_url:`), an absolute or `~`-prefixed `source_path:` that resolves to an in-repo file normalizes to its repo-relative equivalent (the same file, portable spelling), and two fields naming the same origin collapse to the one matching field. State the irreducible cases a human decides: two fields naming *different* plausible origins, or a value that fits no field and whose removal would strand the source (an out-of-repo `file://`/absolute path with no stand-alone body excerpt, which drops to a body excerpt plus a prose locality note only once a human confirms it). State the test that separates the two — *is the corrected state deterministically recoverable from the present values without inventing or discarding provenance?* — and give the cases as illustrations, not a closed combination list. State it once there; the `skills/wiki/SKILL.md` capture bullet and the `wiki_import` capture step cite that rule rather than restating it, and gap 5's agent behavior cites it too.
3. **Surface a contradicting SCHEMA customization (gap 3).** Add a carve-out to the agent's hunk classification: a hunk where the wiki has content the canonical lacks is preserved as a customization only when it *extends* the canon; when it *contradicts* canonical semantics it is surfaced for the user instead — the same human-routes-the-conflict posture the contested-page protocol already uses. Write the carve-out at that general altitude (in agent prose it costs no more than an origin-only exception and avoids leaving the same "customization, preserve as-is" rule to be re-edited by a later task), and let the `### raw/ Frontmatter` block teaching `source_url: file://…` be its motivating illustration.
4. **Align the `source_url`-only prose (gap 4).** Rewrite `raw_taxonomy.md`'s "Typical `source_url`" bucket column and its `source_url`-keyed classification heuristics to speak of the origin field in two-field terms (a remote URL in `source_url:`, a repo-relative `source_path:`, or neither for an out-of-repo source). Rewrite the two agent phrasings that declare the canonical `### raw/ Frontmatter` shape — the space-delimited **Frontmatter field drift.** assess phrasing and its hyphenated fix mirror in the `<fix_raw_frontmatter_subsection_missing>` block — so an `or` no longer reads as "either alone satisfies the canonical shape": the canonical template declares both fields with distinct meanings, and at most one carries a value on a given sidecar. Separately rewrite the `<raw_subtree_drift>` per-file origin report, which lists each surfaced file's "`source_url` or `source_path` origin", into those same two-field terms including the out-of-repo *neither* case, so a sidecar carrying no origin field is reported correctly rather than implied to hold one of the two.
5. **Anchor the operating contract, then bring origin under it (gap 5).** First state the remediation contract once, at the agent's governing altitude (beside `<role>`/`<objective>` in `auto_shaper_wiki.md`): the agent autonomously applies every fix that is safe and deterministic — one that loses no meaning, invents no value, and resolves no genuine ambiguity — and records it in the per-file change report; it surfaces for the user only genuine judgment calls, routing them through the existing contested-page protocol. Cite the contested-page protocol and the per-file change report as the contract's surface and report mechanisms rather than restating them, and frame it as making explicit what the agent already largely does — which is what makes it safe to run unattended: nothing is fabricated, no genuine ambiguity is resolved silently, and everything done is reported. Then bring origin under the contract: extend the assess-phase **Raw-source frontmatter drift.** detection — today missing `ingested`/`sha256` and a non-portable `source_path:` — to also flag a mislabeled or redundant origin field, classifying each per the gap-2 test as deterministically reconcilable or irreducible; and rewrite the fix-phase `<fix_raw_source_frontmatter_missing>` guardrail: keep its existing *never fabricate an origin field* rule, replace its blanket *an absolute `source_path:` is surfaced… never auto-rewritten* clause with the contract's reconcile-the-safe / surface-the-conflict behavior, and add *never silently resolve a conflict*. Under it the agent applies the gap-2 lossless reclassification automatically (reclassify a present value, normalize an in-repo absolute `source_path:` per gap 6, drop a provably-redundant duplicate), records each fix in the change report, and routes an irreducible case to the user. This auto-fixes, during a shaper run, the same mismatches gap 1's linter warns on statically; the out-of-repo excerpt decision and any conflict stay with the user. Keep the reconciliation rules in the gap-2 canonical contract — the origin blocks cite both it and the operating contract rather than re-listing anything, so each rule stays stated once.
6. **Surface the in-repo absolute provenance path as a safe auto-fix, on both fields (gap 6).** In `check_source_path_portable`, stop blanket-blocking an absolute or `~`-prefixed `source_path:`: resolve it, and when it names an existing file inside the repo, emit a **warn** whose message carries the computed repo-relative rewrite (relative to the wiki root) as a safe auto-fix, since the relative form denotes the same file and loses nothing; keep the block for a value that resolves outside the repo or to no file. Apply the mirror change in `check_source_paths_exist` for a page's `sources:` entry: an absolute entry resolving to an existing file inside the wiki's `raw/` tree becomes a **warn** carrying its `raw/…`-relative rewrite, while one resolving outside `raw/` or to no file stays the blocking `broken-source` finding. Both normalizations are gap-2-style deterministic moves under the operating contract, so the agent auto-applies them during a shaper run — the `source_path:` case in `<fix_raw_source_frontmatter_missing>` (gap 5), the `sources:` case in `<fix_external_source_pointer>` — and these linter findings are their static, human-facing mirror. Update the `raw-source-path` and `broken-source` rows of `references/lint_checks.md` to record the in-repo-absolute warn-with-suggestion beside the still-blocking out-of-repo case, and rewrite that file's `## Severity buckets` section in place to match: its **blocking** line today lists raw-sidecar `source_path:` and `sources:` non-portability wholesale, so move the in-repo absolute `source_path:` and in-`raw/` absolute `sources:` cases down to the **warn** line and qualify the remaining **blocking** entries to the out-of-repo / outside-`raw/` cases — otherwise the buckets keep calling blocking what the reclassified rows now warn on.

**Out of scope:**

- **Enforcing origin presence.** This task validates the *form* of a value that is present; requiring an origin field, or changing the pre-existing `check_raw_frontmatter` "origin optional" posture, is separate work it does not take on.
- **Retrofitting the agent's other checks to the operating contract.** The governing statement anchored in gap 5 already binds every check; giving each one an explicit citation is optional polish across the whole agent and stays a candidate follow-up, not work this task does.

The Layer 2 scenarios are graded out-of-band per the harness's standing Layer 2 grading, so the default Layer 1 `run_all.sh` gate in item 8 does not exercise them.
