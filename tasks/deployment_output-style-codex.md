# Deploy the output style to Codex

## Goal

Codex receives the repository's output style as a synthesized style-layer replacement rather than an appended rule, so the style displaces Codex's own personality and formatting guidance instead of arguing with it. The deploy re-derives Codex's current base instructions from the installed build on every run, substitutes the style sections, writes the result to a file, and points the instructions-file configuration key at it. Re-deriving on every run is what keeps the generated file from going stale as Codex updates.

## Context

This builds on [the Claude groundwork task](archive/deployment_output-style-claude-groundwork.md), which shipped the repo-root source directory, the `style` artefact type, and the deploy-log restore behaviour. This task adds one target, and the configuration key it sets needs the prior-value capture and restore that the groundwork task delivers. The groundwork's Claude arm serves both scopes; this task rejects project scope for Codex for the reasons in **Out of scope**.

The wiki records the mechanism on its [OpenAI Codex](../wiki/entities/openai-codex.md) page and in [system prompt substitution across harnesses](../wiki/comparisons/system-prompt-substitution-across-harnesses.md). The essentials: Codex carries exactly one instructions slot whose provenance is either generated from the model's template or explicitly configured, nothing composes the two, and there is no keep-the-original flag. Setting the key therefore replaces the whole slot, and the configured value is documented as surviving model changes unchanged. Tool schemas travel separately and are not lost. Three facts make the synthesis viable. The wiki's OpenAI Codex page still carries the superseded account of the cache, and the wiki rewrite in **Approach** is what brings that page into line. The installed Codex renders its model catalog as JSON through `codex debug models`, including each model's resolved `base_instructions` string beside the `instructions_template` it was rendered from, so the current text needs no committed copy. The resolved text is ordinary Markdown under named headings that vary by model and build: a style-owned set, which `## Approach` enumerates, plus operating headings such as `# Rules for getting work done`, `# Using skills`, and, on some models only, `# Destructive actions`. The on-disk model cache carries each model's instructions text as `model_messages.instructions_template`, a snapshot stamped with the client version that fetched it, so the deploy reads the installed binary's catalog as the authoritative source rather than trusting a possibly older snapshot.

Two constraints follow from the same block. The text differs per model and so does its size, so the generator reads the configured model rather than assuming one. And the section names are undocumented internal structure, so a generator that cannot find an expected heading fails loudly instead of appending and hoping.

## Approach

Locate the Codex binary by feature detection rather than assuming it is on the executable search path, since it can ship inside an application bundle. Probe the sources in this fixed order and use the first that exists: a `CODEX_BIN` environment variable naming an explicit binary, then the bundle's `Contents/Resources/codex-cli/bin/codex` under the active home directory's `Applications`, then the same bundle path under `/Applications`. `CODEX_BIN` ranks first so an explicit binary from a staged test or an unusual install is honoured rather than silently outranked, and the home-directory bundle ranks ahead of the system one so a scratch `HOME` stays isolated from a Codex installed for the whole machine. When it is absent, skip the Codex target with a clear message rather than failing the whole deploy.

The Codex arm acts only on the style named by `style:<name>` under `#codex` in the machine's `~/.ai_asset_deploy/config`, resolved through the same `STYLE_MAP` lookup the Claude arm already uses, because the style type runs once per `styles/*.md` file and a second style file would otherwise write a second generated file and merge the key twice, last one winning. A style file that is not the active one is skipped with a message and writes no file and no key. Add `style:natural-language` under `#codex` in the machine's `~/.ai_asset_deploy/config`, and leave the committed template free of any `style:` line, since a style activation is a machine's own choice; then refresh the passages that call the directive Claude-only: the `style:<name>` doc comment at the head of `deployment/deployment.sh`, the matching comment in `deployment/ai_asset_deploy.conf.template`, and the `style:<name>` row plus its following paragraph in `deployment/README.md`'s Per-Tool Configuration section, so each names both the Claude and Codex arms.

Read the configured model from the Codex user configuration file, render the model catalog as JSON through `codex debug models`, and take that model's `base_instructions` string as the derived text, not its `instructions_template`; any `{{…}}` template variable the resolved string still carries survives into the generated file byte-for-byte, because the derived text is reproduced as the binary rendered it and dropping a variable the deploy cannot resolve would trade a placeholder for silently missing text. When the user configuration sets no `model` key, skip the Codex style with a warning and write no file and no key, matching how the style arm already treats an absent active-style line rather than deriving from an arbitrary catalog entry.

Substitute the three style-owned headings — `# Personality`, `## Writing style`, and `## Final answer` — by rewriting each one in place with the style prose the enumeration below assigns to it. Each replacement covers only the named heading's own span, wherever that heading sits in the derived text: the heading line plus the body it currently holds, ending at the next heading of any level, in the set or not. `## Technical communication` and its `### Writing PR descriptions` subsection, where the derived text carries them, are removed with their bodies rather than filled, because the first sets plain language over jargon — `Use plain language over jargon` on some models and `You prefer using plain language over jargon` on others — the opposite of the style's `<precise_terms>`, and the second sets pull-request prose the style's scope already covers; both are listed in the header's replaced-heading list. Every other heading — one outside both the set and the removal list — is never replaced, so its own heading line and own body survive byte-for-byte while a heading nested beneath it is handled by its own rule, including `# Working with the user`, `## Intermediate commentary`, `### Visualizations`, `### Formatting rules`, an operating heading such as `# Rules for getting work done` or `# Using skills`, a heading with no style-owned counterpart, and a heading the model omits. `### Formatting rules` stays because its body carries rendering mechanics — that the answer is rendered by an application for the user, GitHub-flavored Markdown, clickable file links, angle brackets around paths holding spaces, no `file://` URIs, and CommonMark blank-line rules — and no style element reproduces them, so replacing it would trade working rendering instructions for prose checks. The heading set varies by model and build, so the generator matches these style-owned headings by their text and level in the derived text and never assumes a fixed set beyond them; only a missing style-owned heading takes the fail-loudly path below, naming the heading it looked for and the Codex version it was looked for in, and writing nothing.

Fill each style-owned heading from the style body by element, in the style file's own order. `# Personality` takes `<objective>`, the `<prose>` and `<verbatim_content>` elements of `<scope>`, `<focus>`, `<goal_statements>`, `<keep_the_meaning>`, and `<policy>`. `## Writing style` takes `<sentence_style>`, `<paragraphs>`, `<technical_vocabulary>`, and `<worn_phrasing>`. `## Final answer` takes the `<format>` element of `<output_contract>` followed by that element's `<validations>` list, one paragraph per `<validation>`. `<engineering_behavior>` is not carried: the clause stated below replaces it. Drop the `# Natural Language` H1 and the `<natural_language>` wrapper, render one paragraph per leaf element with every tag removed, render a branch element's own lead-in text as its own paragraph, and keep every carried element's text unchanged. A leaf element is one with no child element, so `<objective>`, each `<focus>` child, each `<rule>`, and `<lists>` each become one paragraph, and `<paragraphs>`'s lead-in sentence becomes one paragraph ahead of its seven children.

Resolve the Codex tree once for the whole Codex target rather than per artefact: in the global branch beside the other target roots, set `CODEX_DIR="${CODEX_HOME:-${HOME_DIR}/.codex}"`, so `CODEX_HOME` when set relocates every artefact the run deploys to Codex and the default stays `~/.codex`. The deploy log's `global_roots` array inside `logged_path_scope()` keeps its `HOME_DIR`-derived `${HOME_DIR}/.codex` entry and gains `${CODEX_HOME}` as a second `codex` entry, only when `CODEX_HOME` is non-empty, rather than substituting for the literal: that array is rebuilt from `HOME_DIR` on every call so the helper reads a logged line whichever scope wrote it, and it never inherits the project branch's `${PROJECT_DIR}/.codex` reassignment. The array's block comment gains the `CODEX_HOME` case beside the rule it already states, so a path under a `CODEX_HOME` tree derives its scope when the log is read. An uninstall or update that reads entries a `CODEX_HOME` deploy logged exports the same `CODEX_HOME`, so that second entry is present when the log is read. Under `--project-dir` the tree stays `${PROJECT_DIR}/.codex` and the style actions are skipped, as **Out of scope** states. Write the result into that one tree as a generated instructions file. Then set `model_instructions_file` in the Codex user configuration (`config.toml` in that same tree) with a TOML-aware top-level edit rather than a JSON merge or a line append: read the file with a TOML parser, replace the key when it already exists and otherwise insert it above the first table header, leave every other key, table, and comment in place, and reject the result without writing when it does not parse as TOML.

Generate the file from the style body rather than from the style file: strip the Claude frontmatter, which Codex does not read, and replace the `<engineering_behavior>` element, whose text names Claude's `keep-coding-instructions` mechanism, with a clause stating that the wording rules govern prose while coding, tool-use, and verification behaviour come from the Codex operating sections kept from the derived text.

Record the prior `model_instructions_file` value, or `@absent` when the key is missing, in the deploy log's existing fifth field, and teach both readers of a logged prior the TOML branch: `remove_logged_path` restores the value from a TOML-aware branch beside its JSON branch, and `json_key_uninstall_succeeded`, which the uninstall loop calls immediately after it, verifies the restored value through that same branch and the same file-identity discriminator, so uninstall returns the original value, strips only a key this deploy created, and reports the entry removed rather than failed.

Fail loudly when a style-owned heading is missing from the derived text, naming the heading that was not found and the Codex version it was looked for in, and write nothing. A silent fallback to appending would produce the weak behaviour this whole target exists to avoid. `personality` leaves the derived text alone: the catalog render returns the same `base_instructions` for `personality` absent, `"none"`, and `"friendly"`, and the setting's reference entry scopes `none` to the built-in section it would otherwise compose while leaving explicit instruction overrides unchanged, which is what `model_instructions_file` sets, so a `personality = "none"` configuration leaves `# Personality` in place for substitution and produces the same generated file as a run with the setting absent. Scope every derivation failure to the Codex style alone: a catalog read that fails — the render exiting non-zero, or the configured model absent from the catalog — skips the Codex style with a warning naming the cause, while a missing style-owned heading fails the Codex style with its named-heading message. Either way every other target and artefact still deploys.

Record in the generated file's own header which model and which Codex version it was derived from, which headings the substitution replaced, and which derived headings were left untouched, so a stale or drifted file is diagnosable by reading it. Re-running the deploy after a model change or a Codex update re-derives and overwrites it, which is the intended way to heal drift.

Refresh the wiki's account through the wiki skill family, rewriting three passages in its [OpenAI Codex](../wiki/entities/openai-codex.md) page in place. In `### The single instructions slot`, the paragraph stating that the on-disk `~/.codex/models_cache.json` "carries no base instructions" and that the binary output is "the only route" becomes the verified account: the cache carries each model's instructions text as `model_messages.instructions_template`, stamped with the client version that fetched it, while `codex debug models` renders the installed build's catalog as the authoritative source. In that same section, the heading inventory drops `destructive actions` as a universal member and records `# Destructive actions` as a heading some models carry. In `### Personality, verbosity, and profiles`, the sentence calling `personality` a closed enum switchable inside a running session becomes the deprecated compatibility setting the **Out of scope** block describes, written from the `personality` entry in the configuration reference the page already lists in `## Derived from` — `learn.chatgpt.com/docs/config-file/config-reference`. Stamp each rewritten passage with the verification date; the `personality` passage carries 2026-11-25.

**Out of scope:**

- Project-scoped deployment under `--project-dir`, which this task rejects outright rather than defers. A project `.codex/config.toml` can set the instructions-file key, so the rejection is a judgement rather than a limitation: a committed whole-slot replacement changes the operating instructions for everyone who works in that repository, not only the person who deployed it, and the generated text is pinned to one model and one Codex version so it is wrong for every contributor on a different one. Codex also loads project layers only for a trusted project, so the placement would silently do nothing until trust is granted. Skip the Codex style actions with a warning under `--project-dir`.
- The additive alternative of writing a marked block into the Codex global rules file, which reaches a weaker outcome and is not what this task delivers.
- The personality setting and the profile layer, neither of which can carry repository prose: the first is a deprecated compatibility setting whose `friendly` and `pragmatic` values no longer select a style, and the second needs a launch flag rather than a persisted key.

## Acceptance

- A dry run restricted to the style type and the Codex target reports one generated-file write and one configuration key merge, and reports a clean skip with a message when no Codex binary is found.
- With `PATH` stripped of any `codex` and `CODEX_BIN` naming a stub executable staged at an application-bundle-shaped path inside the scratch tree, the deploy finds and uses that stub: the stub answers `--version` and the model-catalog debug call with fixture text, the generated file's header names the version the stub reported, and the run reports the generated-file write and the configuration merge instead of the no-binary skip.
- With `PATH` stripped of any `codex` and `CODEX_BIN` unset, the deploy finds and uses a stub staged at `$HOME/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex` inside a scratch `HOME` that also carries a Codex `config.toml` setting `model = "<slug>"`: the stub answers `--version` and the model-catalog debug call with fixture text, the generated file's header names the version the stub reported, and the run reports the generated-file write and the configuration merge instead of the no-binary skip.
- A real deploy produces a generated instructions file in which each style-owned heading `## Approach` names carries the style prose `## Approach` assigns to it in place of the body it held, each heading `## Approach` leaves untouched survives byte-for-byte across its own span — its own heading line and own body, with any heading nested beneath it excluded — including `# Working with the user`, `## Intermediate commentary`, and `### Visualizations`, and the header lists the substituted headings and the untouched ones.
- The generated file carries no style-body tag and follows the stated rendering unit: a search of it for `<focus>`, `<sentence_style>`, `<paragraphs>`, `<rule>`, `<lists>`, `<validation>`, and `<natural_language>` finds none, `<paragraphs>`'s lead-in `These rules govern documents and other multi-paragraph text.` appears once as a paragraph of its own, the `<answer_first>` and `<answer_what_was_asked>` texts sit in two separate paragraphs, and the `<one_theme>` text beginning `Give each paragraph one theme` and the `<section_lead>` text beginning `Lead a section with the conclusion` each sit in a paragraph of its own rather than sharing one, and the `<short_sentences>` text beginning `A plain fact can take ten words` and the `<one_idea>` text beginning `Give each sentence one claim` each sit in a paragraph of its own rather than sharing one.
- A deploy against a staged derived text whose `base_instructions` carries `{{connector_id}}` and `{{plugin_id}}` tokens produces a generated file in which both appear byte-for-byte and a search of it for `{{` finds those two tokens and no other, proving the generator consumes the resolved string and edits no variable the deploy cannot resolve.
- A deploy against a derived text shaped like the configured model's — carrying `## Technical communication` with its `Use plain language over jargon` clause and a `### Writing PR descriptions` subsection beneath it — produces a generated file that carries neither heading and no `plain language over jargon` clause, keeps `## Intermediate commentary` and `### Visualizations` byte-for-byte, and lists both removed headings in the header among the replaced headings.
- A deploy against a staged derived text shaped like the `gpt-6.2-astra` model, where `## Final answer` sits under `# Personality` rather than under `# Working with the user`, substitutes each style-owned heading `## Approach` names and leaves every other heading byte-for-byte. Prove this by sourcing the deploy script with `DEPLOYMENT_SH_SKIP_MAIN=1` and calling the substitution with that derived text.
- The generated file's header names the model, the Codex version it was derived from, the headings the substitution replaced, and the derived headings left untouched.
- A deploy against a scratch configuration whose `config.toml` sets `model = "<slug>"` produces a header naming that slug, and one whose `config.toml` sets no `model` key skips the Codex style with a warning and writes no file and no key.
- A deploy over an existing generated file replaces it: under a scratch `HOME`, after one run, overwrite the generated file with sentinel text and a header naming a different model and Codex version, run the deploy again, and confirm the file's content is the freshly derived text and its header names the current model and Codex version.
- The Codex user configuration parses as valid TOML after the merge and points `model_instructions_file` at the generated file, and a scratch configuration seeded with another top-level key, a `[table]` section, and a comment still carries all three after the merge.
- Running the deploy against a scratch configuration that already sets the instructions-file key, then uninstalling, restores the original value rather than deleting the key, reports the logged entry removed rather than failed, and leaves the deploy log with no line for it.
- A deploy run against a derived text with a renamed or missing expected section fails with a message naming the missing heading and the Codex version, and writes no file and no key. The same run still reports its other targets' deploys. Prove this on a staged fixture holding a derived text with one expected heading removed.
- A deploy run against a scratch Codex configuration whose catalog read fails — a catalog render that exits non-zero, or a catalog that omits the configured model — skips only the Codex style with a warning naming the cause, and the same run still reports the other targets' deploys. Prove this by sourcing the deploy script with `DEPLOYMENT_SH_SKIP_MAIN=1`, as `tests/deployment/script_tests/style_run.sh` does, and calling the derivation function with the failing catalog path.
- The generated file carries no Claude output-style keys and no reference to Claude's flag mechanism: a search of the generated file for `keep-coding-instructions` and `force-for-plugin` finds neither, and its `<engineering_behavior>` clause states that the wording rules govern prose while coding and tool-use behaviour come from the Codex operating sections kept from the derived text.
- `deployment/README.md` gains a Codex row in the Generated Formats style section naming the derivation source, the substituted sections, the fail-loudly behaviour, and the fact that the configured value does not re-derive on a model change without a redeploy, and its existing Target Layout Styles cell for Codex no longer reads `not yet`.
- A deploy restricted to the style type and the Codex target against a scratch copy of the tree whose `styles/` holds a second, non-active style file reports exactly one generated-file write and one configuration key merge, for the style named by `style:<name>` under `#codex`, and a skip message for the other file.
- The `style:<name>` documentation no longer calls the directive Claude-only: the head comment in `deployment/deployment.sh`, the comment in `deployment/ai_asset_deploy.conf.template`, and the `style:<name>` row and its following paragraph in `deployment/README.md` name both the Claude and Codex arms, and `#codex` in the machine's `~/.ai_asset_deploy/config` carries `style:natural-language` while the committed template carries none.
- A deploy against a staged derived text whose `### Formatting rules` body carries the rendering line `Your answer is being rendered by an application for the user` produces a generated file carrying that line and the whole `### Formatting rules` span byte-for-byte, and the header does not list `### Formatting rules` among the replaced headings, while the style's `<validations>` paragraphs appear under `## Final answer`.
- A deploy against a scratch configuration setting `personality = "none"` writes the generated file and merges the configuration key exactly as a run with `personality` absent does, and the generated file carries the style's `# Personality` prose, proving the setting does not reach the derived text.
- A deploy with `CODEX_HOME` naming a scratch configuration tree writes every artefact that run deploys to Codex into that tree, the generated instructions file and the merged `config.toml` included, and leaves `~/.codex` untouched; an uninstall run with the same `CODEX_HOME` exported, over the resulting deploy log, resolves those artefacts to the codex target and removes them from that same tree.
- Under a scratch `HOME` with `CODEX_HOME` naming another tree, sourcing the deploy script with `DEPLOYMENT_SH_SKIP_MAIN=1` and calling `logged_path_scope()` with target id `codex` derives `global` for a logged path under `$HOME/.codex` and `global` for one under the `CODEX_HOME` tree.
- With `CODEX_HOME` set to a tree other than `<project>/.codex` and `<project>` a scratch directory that is not `$HOME`, `logged_path_scope()` derives `<project>` for a `codex` path under `<project>/.codex` and for one under `<project>/.agents/skills`.
- The `wiki/entities/openai-codex.md` page records `model_messages.instructions_template` as the cache field carrying each model's instructions text while `codex debug models` remains the authoritative source, records `# Destructive actions` as a heading some models carry rather than a universal one, and records `personality` as a deprecated compatibility setting sourced from the `personality` entry in `learn.chatgpt.com/docs/config-file/config-reference`, each rewritten passage carrying its verification date.
