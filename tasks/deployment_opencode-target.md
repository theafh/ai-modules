# Add an OpenCode deploy target for skills, agents, and commands

## Goal

Extend `deployment/deployment.sh` with a new `opencode` deploy target so the repo's file artefacts — skills, agents, and commands — copy into OpenCode's own configuration directories, the same way the script already serves Claude, Cursor, Codex, Gemini, and Antigravity. After the change, `./deployment/deployment.sh --target opencode` (global or `--project-dir`) lands each skill as a real directory and each agent as a file whose frontmatter is transformed into OpenCode's agent schema, and routes any command to OpenCode's `commands/<name>.md`.

The user-visible outcome is that OpenCode gains the repo's curated agents as first-class OpenCode artefacts and a ready command route: commands stay a supported artefact class this target installs into OpenCode's `commands/` directory, and — treating a standalone command as the legacy, deployer-installed mechanism the standing repo rules describe — the repo ships none of its own today, so the target readies the route rather than delivering a populated command set. This matters because of how OpenCode discovers artefacts: it reads **skills** from foreign directories (`~/.claude/skills/`, `~/.agents/skills/`) as well as its own, but it reads **agents** and **commands** only from its own directories — never from `.claude/agents` or `.claude/commands`. So the repo's skills already surface in OpenCode today through the existing Claude deploy, whereas its agents, plus the command route this target opens, are the genuinely new capability it unlocks. A dedicated OpenCode **skills** copy becomes load-bearing only once an operator isolates OpenCode from the Claude directories (the `OPENCODE_DISABLE_CLAUDE_CODE=1` environment variable, operator-set, stops OpenCode reading `~/.claude` and `~/.agents`), at which point OpenCode shows only the curated set deployed here.

## Context

OpenCode's config lives in a global directory `~/.config/opencode/` and a per-project directory `.opencode/`, each holding plural subdirectories `skills/`, `agents/`, `commands/`, and `plugins/` (singular names are accepted for back-compat; deploy to the plural, canonical form). Skills are `skills/<name>/SKILL.md` directory trees, commands are `commands/<name>.md`, and agents are `agents/<name>.md`. This is confirmed by OpenCode's official docs (opencode.ai/docs/config, /skills, /agents, /commands); the `harness_portability` skill also carries the general OpenCode-compatibility knowledge as background.

The deploy mechanism to extend is `install_for_app()` in `deployment/deployment.sh`, which switches on `app_id` inside each artifact-type case (`command`, `skill`, `agent`, `hook`). Deployment is copy-based today — the symlink mode was removed and audited in [deployment_copy-not-symlink.md](deployment_copy-not-symlink.md) — so a new target copies like the existing `claude`/`cursor` branches rather than linking.

Concrete wiring points, all in `deployment/deployment.sh`:

- **`VALID_TARGETS`** — the comma-separated allowlist that gates `--target`. Adding `opencode` here also enables a `#opencode` section in `deployment.conf` and lights up `OPENCODE_`-prefixed agent frontmatter for free, because `rewrite_agent_frontmatter` derives its known vendor prefixes from `VALID_TARGETS`.
- **The target-directories block** — the `if [[ -n "$PROJECT_DIR" ]]` … `else` block that assigns `CLAUDE_DIR="${HOME_DIR}/.claude"` and its siblings. OpenCode breaks the `~/.<tool>` pattern every other target follows: its global dir is `${HOME_DIR}/.config/opencode`, and its project dir is `${PROJECT_DIR}/.opencode`. Set `OPENCODE_DIR` in **both** branches (unlike Gemini/Antigravity, OpenCode has a real project convention, so project-dir mode must not skip it).
- **`ALL_APP_TARGETS`** — the `id|label|base_dir` list; add `opencode|OpenCode|${OPENCODE_DIR}`.
- **`install_for_app()` cases** — only the `agent` case needs a new `opencode` arm. The `command` case's `*)` default arm already copies any unrecognized `app_id`'s `.md` to `${app_dir}/commands/<name>.md`, and the `skill` case is an if/else (not an `app_id` switch) whose `else` branch already copies the directory to `${app_dir}/skills/<name>` for every non-codex target — so `opencode` commands and skills deploy with no new arm (an explicit `opencode` command arm is optional, for readability only). The `agent` case, by contrast, is a `case "$app_id"` switch with no `*)` default, so an unmatched `opencode` silently deploys nothing; add an `opencode` arm there that calls a new generator (below) rather than a straight copy, since the agent needs a transform.
- **Backup handling** — `backup_app_dir` names a backup from `basename(app_dir)`, and `is_managed_backup_path` requires the backup to sit directly in `$HOME`. For `~/.config/opencode` the basename is `opencode`, producing `~/opencode_<timestamp>`, which reads as unrelated to OpenCode. Apply a backup-name override (the same mechanism the VS Code prompts dir uses via the `path|name` `backup_roots` entries in the main backup loop and in `clear_backups_for_active_targets`) so the backup lands at a self-describing name such as `~/.opencode-config_<timestamp>`.
- **Human-facing target-set enumerations** — three hand-maintained restatements of the allowlist that do not derive from `VALID_TARGETS`, so each is rewritten in place to add `opencode`: the file-header option comment `--target TARGETS Filter by deploy target (vscode,claude,cursor,codex,gemini,antigravity)` and the `print_usage` line `--target TARGETS  Comma-separated deploy targets: vscode,claude,cursor,codex,gemini,antigravity` both become `…,gemini,antigravity,opencode`, and the file-header tool-list comment naming "VS Code GitHub Copilot, Cursor, Claude Code, OpenAI Codex, Gemini CLI, and Google Antigravity" gains OpenCode in its tool prose. Left unedited, `deployment.sh --help` keeps advertising the old six-target list while `--target opencode` already works.

The agent transform is the one non-mechanical piece. The repo's agents are Claude-style markdown with frontmatter (`name`, `description`, `model`, sometimes `tools`, and a `readonly`/vendor-prefixed convention), and the script already generates target-specific agent variants twice — `generate_toml_agent` for Codex and `generate_gemini_agent` for Gemini — each of which first runs `rewrite_agent_frontmatter` to resolve vendor prefixes, then emits the target's schema. A new `generate_opencode_agent` follows that same shape, and — like both existing generators, which each emit only a known key set (`generate_gemini_agent` via its explicit allowed-keys list, `generate_toml_agent` via field extraction) — it whitelists to OpenCode's own schema: it emits only OpenCode's frontmatter keys (`mode`, `description`, `model` when not inherited, `temperature`, and a `permission` object — OpenCode's `tools` boolean map is deprecated as of v1.1.1 in favour of `permission`, verified against opencode.ai/docs/agents and /permissions in July 2026, so the transform emits `permission` and never a `tools` object — with the agent body carried through as the prompt) and drops every other source key, including `version`, `background`, `effort`, `model_reasoning_effort`, the vendor-prefixed conventions `rewrite_agent_frontmatter` resolves, and `name` — OpenCode derives the agent name from the filename, so no `name:` key is emitted. Whitelisting is deliberate: OpenCode passes any unrecognized frontmatter option straight through to the provider as a model option (documented in OpenCode's agents docs, opencode.ai/docs/agents, confirmed July 2026), so emitting a repo-maintenance key such as `version`, `background`, `effort`, or `model_reasoning_effort` would inject it as a bogus provider model parameter; whitelisting to OpenCode's own schema keys keeps those keys out of the provider call. OpenCode's agent frontmatter differs from Claude's in three ways that the transform must bridge:

- **`mode`** — OpenCode registers a subagent only when frontmatter carries `mode: subagent`. The repo's `auto_*` agents are subagents, so the transform emits `mode: subagent`.
- **`model`** — OpenCode expects `provider/model-id` and inherits the session model when the key is absent. Every repo agent sets `model: inherit`, so the transform maps that `inherit` sentinel to key omission (as the Codex generator already does for its own inheritance).
- **read-only via `permission`** — Every read-only repo agent carries `readonly: true` and an explicit `tools:` allowlist together (`auto_drift_task`: `readonly: true` + `tools: Read, Grep, Glob, Bash`; `auto_reviewer_task`/`auto_verifier_task`: `readonly: true` + `tools: Read, Grep, Glob`), and no agent carries one without the other, so the transform reads both keys together. OpenCode expresses tool restrictions through its `permission` object (`allow`/`ask`/`deny` per key), where `edit` gates all file modification — the `write`, `edit`, and `patch` tools — so there is no separate `write` permission key. The transform maps the read-only role to `permission` denies: `readonly: true` emits `permission: { edit: deny }` (the file-write deny), plus `bash: deny` unless the source allowlist lists `Bash`. So `auto_reviewer_task`/`auto_verifier_task` (no `Bash`) get `permission: { edit: deny, bash: deny }`, while `auto_drift_task` — which needs `bash` for its `git log` intent reconstruction — gets `permission: { edit: deny }` and keeps shell access; the read tools it grants (`read`, `grep`, `glob`) default to allowed and need no entry. An agent whose source carries neither key — the full-capability writer agents such as `auto_shaper_task`, `auto_gate_task`, and `auto_shaper_wiki` — emits no `permission` restriction at all, leaving OpenCode's default full access intact.

Documentation to refresh in the same change, all in `deployment/README.md`: the **Target Layout** and **Generated Formats** tables gain OpenCode rows (its `~/.config/opencode` global path, `.opencode/` project path, and the agent-generation entry); the intro sentence ending "…OpenAI Codex, Gemini CLI, and Google Antigravity" is rewritten to end "…Google Antigravity, and OpenCode"; the `--target TARGETS` flags-table row that lists the six targets appends `opencode` in place; the **Per-Tool Configuration** `#tool` line (`Section heading: vscode, cursor, claude, codex, gemini, antigravity`) appends `opencode` to its identifier list; and the **Backups** section gains an `opencode` per-target bullet and rewrites its single-override sentence — which today frames the VS Code user-prompts dir as the current sole override — to name both override cases, the VS Code prompts dir and the OpenCode config dir (`~/.config/opencode` → `~/.opencode-config_<timestamp>`). Root `README.md` enumerates the deploy targets in two places, both rewritten in place to add OpenCode: the **Why You Should Install This** sentence that today ends "…Copilot, Gemini, and Antigravity" becomes "…Copilot, Gemini, Antigravity, and OpenCode", and the **Installing and deploying** `make deploy` parenthetical that today ends "…Gemini CLI, Google Antigravity" appends OpenCode.

Companion, not a prerequisite: [deployment_relocate-state-to-home.md](deployment_relocate-state-to-home.md) co-edits `deployment.sh` and `deployment.conf`/its template; whichever lands second reconciles the shared surface, and neither blocks the other. [deployment_antigravity-target-gemini-retire.md](deployment_antigravity-target-gemini-retire.md) is a larger-overlap companion on the same target set — it co-edits `VALID_TARGETS`, `ALL_APP_TARGETS`, the target-directories block, and the `install_for_app()` cases, and it strikes `gemini` from those enumerations; if it lands first, this task's `gemini`-bearing enumeration rewrites and its `vscode,claude,cursor,codex,gemini,antigravity` greps go stale, so whichever of the two lands second reconciles that shared target-set surface, and neither blocks the other. ## Approach

Add `opencode` to `VALID_TARGETS` and rewrite in place the three human-facing target-set enumerations that restate it — the two file-header comments and the `print_usage --target` line — to the `…,gemini,antigravity,opencode` / "…and OpenCode" form so `--help` and the header stop advertising six targets; define `OPENCODE_DIR` in both branches of the target-directories block (`${HOME_DIR}/.config/opencode` global, `${PROJECT_DIR}/.opencode` project), and append `opencode|OpenCode|${OPENCODE_DIR}` to `ALL_APP_TARGETS`. Give the backup path a self-describing name override so activating `opencode` backs up `~/.config/opencode` to `~/.opencode-config_<timestamp>` rather than `~/opencode_<timestamp>`.

In `install_for_app()`, rely on the existing branches for commands and skills: the `command` case's `*)` default arm already lands `${app_dir}/commands/<name>.md` and the `skill` case's `else` branch already lands `${app_dir}/skills/<name>/` for `opencode` via `copy_path_with_replacements`, so neither needs a new arm (add an explicit `opencode` command arm only if it aids readability). Add the one required arm to the `agent` case — a `case "$app_id"` switch with no `*)` default, so `opencode` otherwise no-ops — calling a new `generate_opencode_agent` built on the `generate_toml_agent`/`generate_gemini_agent` template: run `rewrite_agent_frontmatter` first to resolve `OPENCODE_`/other vendor prefixes, then emit OpenCode frontmatter with `mode: subagent`, `model` mapped inherit→omit, and the read-only role mapped to OpenCode's `permission` denies as described in Context (no deprecated `tools` object), writing the agent body through unchanged.

Add an `#opencode` section with `disallow:*legacy*` to `deployment.conf` for parity with the other tool sections, and rewrite in place its file-header `#tool` comment enumeration `tool identifier (vscode, cursor, claude, codex, gemini, antigravity)` to append `opencode`. Rewrite in place the `deployment/README.md` Target Layout and Generated Formats tables to add the OpenCode rows, the intro sentence to end "…Google Antigravity, and OpenCode", the `--target TARGETS` flags-table row to append `opencode` to its target filter, the **Per-Tool Configuration** `#tool` enumeration line to append `opencode`, and the **Backups** section to add an `opencode` per-target bullet and rewrite its single-override sentence to name both the VS Code prompts dir and the OpenCode config dir as override cases. Rewrite in place, too, the two root `README.md` deploy-target enumerations: the **Why You Should Install This** sentence to end "…Copilot, Gemini, Antigravity, and OpenCode" and the **Installing and deploying** `make deploy` parenthetical to append OpenCode.

**Out of scope:**

- Hook deployment for OpenCode is owned by [deployment_opencode-hook-bridge.md](deployment_opencode-hook-bridge.md); OpenCode has no declarative hook config to merge into, so it needs a different mechanism than the JSON-merge used for Claude/Codex/Cursor.
- This task sets no environment variables and does not configure OpenCode's Claude-directory isolation; `OPENCODE_DISABLE_CLAUDE_CODE=1` is operator guidance noted in the docs, not a deploy action.
- Relocating the deploy conf and log into `$HOME` stays owned by [deployment_relocate-state-to-home.md](deployment_relocate-state-to-home.md).

- A deploy into a throwaway `--project-dir` scratch directory with `--target opencode` produces `<scratch>/.opencode/skills/<skill>/SKILL.md` as a real directory tree (`test -d` true, `test -L` false) and `<scratch>/.opencode/agents/<agent>.md` as a real file; and, because the repo ships no command artefacts of its own, a fixture command staged for the run — placed in the `commands/` directory of a throwaway, uncommitted plugin created beneath `plugins/` (so artefact discovery finds it) with a non-`*legacy*` name so no `disallow` rule skips it, removed after the run — lands at `<scratch>/.opencode/commands/<command>.md` as a real file, proving the generic `command`-case `*)` default arm routes an `opencode` command.
- The generated `<scratch>/.opencode/agents/<agent>.md` carries `mode: subagent`, and an agent whose source expresses `model: inherit` has no `model` key in the output — verified by reading the generated file.
- Deploying the repo's read-only agents (`auto_reviewer_task`/`auto_verifier_task` with `readonly: true` + `tools: Read, Grep, Glob`; `auto_drift_task` with `readonly: true` + `tools: Read, Grep, Glob, Bash`) produces a `permission` object that enforces read-only through OpenCode's current schema: `auto_reviewer_task`/`auto_verifier_task` (no `Bash`) carry `permission: { edit: deny, bash: deny }`, while `auto_drift_task` carries `permission: { edit: deny }` and keeps shell access for its `git log` use — with no deprecated `tools` object and no `write` key (file writes are denied by `edit`) — verified by reading each generated file.
