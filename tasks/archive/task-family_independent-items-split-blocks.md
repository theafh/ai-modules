# Block ready on a bundle of independent items

## Goal

The base `task` skill's **Blocking bar** names a **Scope sizing** or **Focus** finding about independent items bundled in one task among the classes that block `ready` by definition. `task_check` then never stamps `ready` on a bundle the sizing rule says to split, it judges such a bundle the same way on every vendor, and the `scope_split_stuck` eval of `tests/task_auto_check` reaches `task_auto_check`'s `<structural_split_boundary>` on every run.

## Context

- **What happened.** In Claude's 2026-11-15 run of `scope_split_stuck`, the dry run's finding dr5 said the auth work and the billing work "share no rationale, no edit surface, and no acceptance story". The gate still recorded `scope sizing: clean` and `focus: clean`. Its reasons were that bundling the two causes no wrong result and that the frozen Goal's "in one pass" makes a split the user's call. The loop repaired three other blocking issues, stamped `ready`, and raised the split only as a question in its report. Cursor's run of the same fixture recorded both lenses as issues and passed.
- **Two base passages pull apart.** The sizing paragraph of the base skill's `<body>` ends "Split independent items, expandable tangents, and tasks that grow past **300 lines** into siblings before continuing". The `<readiness_checklist>` **Blocking bar** makes every finding outside its by-definition classes a note unless the literal implementer would produce a nameable wrong result. Neither passage names the other, so a gate can follow either one.
- **The fixture predates the bar.** `scope_split_stuck` has been tracked since commit 58f3bd1 (2026-08-30), and the **Blocking bar** arrived in commit af74b47 (2026-10-27). The fixture's task bundles two small edits, so a gate that follows the bar finds no wrong result to name.
- **What the split boundary needs.** `<structural_split_boundary>` in `task_auto_check`'s SKILL.md acts only on a scope-sizing, focus, or complexity defect the gate raises, so a bundle cleared as a note never reaches it.
- **The pinned sentence.** Scenario s15 of `tests/task_auto_check/script_tests/run.sh` pins the bar's by-definition sentence word for word, in the assertion labelled "charter, structure, invalidated premise, and frozen counts block by definition".

**Decision (user, 2026-11-15).** An independent-items finding blocks `ready`, because the sizing rule already says to split such items before continuing, and a `ready` stamp would hand `task_implement` a bundle that rule forbids. The rejected alternative kept the finding a note and redesigned the fixture so its bundle gives the literal implementer a nameable wrong result or passes the 300-line ceiling. The change moves which findings block `ready` in `task_check`, `task_auto_check`, and `task_fix` alike.

## Approach

1. In the base `task` SKILL.md, rewrite the **Blocking bar**'s by-definition sentence in place so it adds a **Scope sizing** or **Focus** finding that names independent items under the sizing rule. The sentence's opening ordinal changes from `Four classes block by definition:` to `Five classes block by definition:`, so the count matches the five classes it then enumerates. Only a finding that names independent items joins the by-definition classes; a too-small finding and a size finding at any length, one at or past the 300-line ceiling included, stay under the ordinary bar.
2. In `plugins/ai_dev/skills/task_check/SKILL.md`, delete the `<assessment>` sentence that restates the bar's test — "Class by the bar's test alone: a finding whose literal reading produces one of the bar's four wrong results blocks however small its fix, and a finding with no nameable wrong result is a note however easy its fix." — so the sentence before it, which already classes every verified finding with the checklist's **Blocking bar** and routes a blocking finding to `## Issues` and a note to `## Notes`, stands as the only classification statement and the front end reads the bar from the base skill.
3. In `plugins/ai_dev/agents/auto_gate_task.md`'s dry-run rule and `plugins/ai_dev/agents/auto_dryrun_task.md`'s `<rule>Class and verdict.</rule>`, rewrite the classing sentence in place so each takes the base `<readiness_checklist>` **Blocking bar** as the one statement of which findings block: a finding in a by-definition class stays blocking whether or not the dry run named a wrong result, and a finding outside those classes that names no wrong result becomes a note. In `auto_dryrun_task.md`, delete the rule's next sentence, `Name the concrete wrong result in every blocking finding.`, because the rewritten classing sentence already carries that demand for a finding outside a by-definition class and the `<rule>Findings, numbered dr<k>` requires every finding to say what would go wrong for the implementer, so the surviving sentence would state a second, contradicting rule. Then qualify the wrong-result demand in the three report shapes that still require it of every blocking entry, rewriting each clause in place so it demands a wrong result only of a finding outside a by-definition class: `auto_dryrun_task.md`'s `## Findings` shape clause `naming the wrong result for a blocking finding` reads `naming the wrong result for a blocking finding outside a by-definition class`; `auto_gate_task.md`'s `## Issues` shape clause `every verified blocking issue with its location, wrong result, and minimum fix` reads `every verified blocking issue with its location and minimum fix, and the wrong result for a blocking issue outside a by-definition class`; and `task_check/SKILL.md`'s `<output_contract>` `## Issues` entry clause `the wrong result a literal implementer would produce` reads `the wrong result a literal implementer would produce for a blocking issue outside a by-definition class`.

   The same clause has a second verbatim copy in `tests/task/evals/evals.json`'s `check` eval expectation 4, which quotes the shape as `'**[short title]**: where it sits, what is wrong, the wrong result a literal implementer would produce, and the minimum fix' shape`; rewrite that copy in place so the quoted clause reads `the wrong result a literal implementer would produce for a blocking issue outside a by-definition class`, leaving the expectation's surrounding text unchanged.

4. In scenario s15, update the pinned sentence and its assertion label to the new text.
5. In the `scope_split_stuck` fixture's `setup.sh`, rewrite the comment above the staged files so it names the rule its bundle meets.
