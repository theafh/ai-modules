# Task provenance and lifecycle status across the task_* family

## Goal

Give every task file two provenance fields and a richer lifecycle status, all enforced by the linter and backfillable onto existing tasks from git history:

- **`reported-by`** — the user who created the task, resolved by the user-name chain (Context) and written by the create path at creation time.
- **`implemented-by`** — the user who built the work, resolved by the same user-name chain and written by `task_implement` when the implementation lands.
- **A seven-state `status` lifecycle** — `open → checked → ready → implemented → audited → finished`, with `deferred` as an alternate terminal — replacing today's three-value `open`/`implemented`/`deferred` set. Each stage of the `task_*` chain stamps its own status as it acts, so the frontmatter records how far a task has travelled. A shared **backward-move guard** keeps an earlier stage from silently regressing a status that a later stage already set.

The linter makes the fields and the status mandatory, validates `status` against the enum, and enforces the status↔location boundary. Its default run judges the live backlog in `tasks/` and does not perform per-file maintenance checks on `tasks/archive/`, so everyday skills can invoke plain `lint.py --quiet` without remembering a defensive archive flag. `task_fix` alone passes `--include-archive` and owns the one-time legacy work — reading git history to backfill a missing `reported-by`/`implemented-by` and migrating a legacy archived status to its new terminal. That whole legacy backfill is one-time bookkeeping that leaves `updated` untouched; forward-going stage transitions on a live task bump `updated` as usual.

## Context

**Why.** A task file today records *what* and *when* but not *who*, and its status collapses the whole create→check→implement→audit→finish journey into a single open/closed bit. Recording the reporter and the implementer, plus the stage reached, makes the backlog auditable across people and across time without reading git by hand — and lets a glance at the frontmatter tell open-but-unchecked from checked-and-ready from built-but-unaudited.

**The lifecycle, and the status each stage stamps.** One node per stage owns its outbound transition, stamping its status when it finishes its job. Where a stage has both a clean and a had-issues outcome, each is named:

- `open` — created, not yet checked. Stamped by the create path (`task_create` / base `<create>`).
- `checked` — `task_check` ran and the verdict is *not* clean: blocking issues remain, and neither a clean verdict nor a user declaration has marked the task ready. Stamped by `task_check` on the had-issues outcome.
- `ready` — the task is implementation-ready, by **either** path: `task_check` ran and reported no blocking issue (the clean outcome, stamped by `task_check`), **or** the user declares it ready over remaining findings (stamped through the base skill's apply-findings update flow).
- `implemented` — the work is built. Stamped by `task_implement` when the work lands, together with `implemented-by`.
- `audited` — `task_audit` confirmed **every** body item, acceptance check, and test as genuinely implemented. Running the audit is not enough on its own: only a clean, complete verdict over a current `implemented` flips it to `audited` (a clean re-check of an archived `finished` task leaves it `finished`); any gap leaves the status at `implemented` and routes the gaps to `task_implement`.
- `finished` — closed out and archived. Set on a done task through the archive close-out — `task_finish`, or the base skill's `<archive>` flow that task_finish fronts.
- `deferred` — parked or dropped without implementation; archived. Set through that same archive close-out (`task_finish` or the base `<archive>` flow), and always available from any stage: parking a task is never gated behind reaching a particular point in the lifecycle, and is not the sole job of a single skill.

**Backward-move guard (`task_check`, `task_implement`).** The lifecycle has a forward order — `open(0) → checked(1) → ready(2) → implemented(3) → audited(4) → finished(5)`, with `deferred` an off-line terminal. Before a stage writes its status it first reads the task's current status: overwriting a current `implemented`, `audited`, or `finished` with a lower status is a regression — an earlier stage silently undoing the work a later stage recorded. Exactly two stampers can land below one of those work states, and they are the ones that carry the guard: `task_check` (stamps `checked`/`ready`, e.g. re-run on a task already at `implemented`) and `task_implement` (stamps `implemented`, over an `audited` or `finished` task). On a regression the stage does not silently overwrite: it warns, names the current→target move, and asks the user to confirm the move is intended — **unless** the session context already makes the intent clear (for example a deliberate re-implementation after a re-audit found drift) — and only then proceeds. Everything else proceeds without a prompt: forward moves (including skipping an intermediate stage), re-stamping the same status (a no-op), a re-check revising `ready` back to `checked` (`task_check` correcting its own verdict, not a later stage's), and the deliberate `deferred` park from any stage. `task_create` (only ever `open`, on a fresh file), `task_finish` (only ever the terminal `finished`/`deferred`), and `task_audit` (stamps `audited` only over a current `implemented` — a forward move, since a clean re-check of a `finished` task leaves it `finished`) can never land below a work state, so none carries the guard. The base skill's apply-findings update flow also writes `ready` (when the user declares a task ready over remaining findings), but it runs only in the pre-implementation readiness band — never on a built task — so its `ready` stamp cannot overwrite a work state and it needs no guard either, which keeps the two guard-carriers exhaustive among writers that can regress. This is shared skill behaviour: the base skill documents it once and the two stampers reference it, realised as a rule each runs at the top of its status write — not a Claude Code hook — keeping the toolchain to skills plus the linter. It is a soft, confirmable guard, distinct from linter-enforced ordering (see **Non-goals**).

**Status ↔ location, and the two regimes.** The forward-going invariant: `open`, `checked`, `ready`, `implemented`, and `audited` live in `tasks/`; only `finished` and `deferred` live in `tasks/archive/`. This moves the archive boundary — `implemented` and `audited` become *working* states that stay in `tasks/`, and the archive move happens only at `task_finish`. The base skill today equates "done" with `implemented`-in-archive (`<when_to_activate>` and `<archive>`); both shift to `finished`. Two regimes touch the frontmatter, and they differ on `updated`:

- **Forward transitions** on a live task, once the skills run the new workflow — each stage stamps its status as it acts and bumps `updated`, a real state change.
- **One-time legacy backfill/migration** of tasks that predate this work — adding a missing `reported-by`/`implemented-by`, and migrating a legacy archived status to its new terminal — is bookkeeping, not work, and leaves `updated` as it was (see the no-bump exception below).

**Read-only refinement for the gates.** `task_check` and `task_audit` are read-only today ("it judges, it does not edit" / "it makes no state change"). Each gains exactly one allowed mutation: stamping the `status` it just established (`checked`/`ready` for check — subject to the backward-move guard; `audited` for audit — only over a current `implemented`) and bumping `updated`. They still change no task body, no other frontmatter, no code, and move no file — the status stamp is the recorded outcome of their assessment. Every absolute read-only claim in each gate — not only `<role>` and `description:` — restates this one-stamp refinement so the claim stays accurate: in `task_check`, also `<authority>` ("do not edit it"), `<assessment>` ("change nothing"), and `<output_contract>` ("Make no edit and move no file"); in `task_audit`, also `<workflow>` ("make no edit to the task or the code") and `<output_contract>` ("Make no state change"). None of these is left asserting an unqualified read-only stance after the refinement.

**Resolving the user name.** Both provenance fields take their value from one resolution chain, applied wherever a name is recorded:

1. `git config user.name`.
2. If that is empty or the project is not a git repo, ask the user which name to record — the creation user for `reported-by`, the implementation user for `implemented-by`.
3. If the ask goes unanswered, write the literal string `default_user` as the field value (e.g. `reported-by: default_user`).

The everyday writers run this chain directly — `task_create` for `reported-by` on a new task, `task_implement` for `implemented-by` when the work lands (a new or an already-open task). The one-time legacy backfill puts a git-history step in front of the chain (see below): recover the original author from history, falling back to this same chain when history yields nothing. The linter never asks or writes — it reports a missing field and, on its archive-inclusive run, enriches the finding with the git-history value (or the `git config user.name` head of the chain when history is empty); the writer that heals the file completes the chain.

**Git-history retrofit — `--include-archive` only (mechanics verified against this repo on 2026-06-12).** This is part of the archive-inclusive run only — the one `task_fix` makes with `--include-archive` — so the git-history archaeology never runs in an everyday skill invocation. On that run, a missing provenance field is recovered per file from history; the linter reports the value and never auto-edits, and `task_fix` applies it:

- `reported-by` for any tracked task missing it — the author of the commit that first added the file:
  `git log --diff-filter=A --follow --format='%an' -- <file> | tail -1`
- `implemented-by` for an archived `finished` task missing it — the author of the commit that moved the file into `archive/`:
  `git log --diff-filter=R --follow --format='%an' -- <archive-file> | head -1`

When a query yields nothing — or the missing field has no applicable history query at all (a live `implemented`/`audited` task, an untracked file) — the field falls back to the **user-name chain** above. The archived-task `implemented-by` is the archive-mover (the `task_finish` author) — a best-effort proxy for the builder, correct in this single-author repo and offered only as a one-time hint, never authoritative. (Confirmed e.g. against `tasks/archive/task-skill_acceptance-contract.md`, whose archive-move author resolves from the family-overhaul commit.)

**Legacy backfill does not bump `updated`.** Backfilling `reported-by`/`implemented-by` or migrating a legacy status onto a pre-existing task is one-time bookkeeping, not work: it leaves `updated` as it was, because `updated` records when the task's content last changed. The exception is scoped to backfill or migration being the *only* change to the file: when one pass also makes a real content fix — a re-pointed link, a normalised datetime — that content change bumps `updated` as usual and the backfill rides along. This is the single exception to `<bump_updated>`; every forward transition on a live task bumps `updated` as usual. The linter's retrofit hints state the no-bump rule inline.

**Linter location vs. migration — one owner per case.** With `ARCHIVE_STATUS = {finished, deferred}`, exactly one check fires for each misplacement, so no file ever receives two conflicting fixes:

- A **terminal** status (`finished`/`deferred`) found under `tasks/` is a location error → hint: move to `archive/`. This is `check_location`'s only direction.
- A **non-terminal** status (anything not in `ARCHIVE_STATUS`) found under `archive/` is a legacy artifact → hint: migrate `status` to `finished`, no `updated` bump. The migration check owns this, replacing the old `open`-in-archive location branch. Decision: any non-terminal archived status migrates to `finished` — in practice the only legacy case is `implemented`→`finished`, since the old model archived only `implemented`/`deferred` and `checked`/`ready`/`audited` did not yet exist; `deferred` stays `deferred`.

So `check_location` no longer emits a "move to `tasks/`" hint for an archived non-terminal status; the migration hint is the single response there — and, being archive-side, it surfaces only on the `task_fix` `--include-archive` run, while the terminal-in-`tasks/` direction stays an everyday check.

**Severity and the deferred case.** `reported-by` (every task) and `implemented-by` (status `implemented`/`audited`/`finished`) are mandatory: absent → blocking, like the existing required fields, and the finding carries the resolved value (per the user-name chain and git-history rules above) plus the exact frontmatter line so the fix is mechanical. A `deferred` task was never implemented, so the linter does not require `implemented-by` for it. On a default run these checks see only live tasks; an archived task's provenance — and its git-history enrichment — is reached only when `task_fix` runs with `--include-archive`.

**Two linter modes — live by default, archive-inclusive only in `task_fix`.** `lint.py` defaults to live-backlog mode: it iterates `tasks/*.md` for per-file checks and skips archived files as maintenance targets. That default still resolves live-task links into `archive/` and keeps filename collisions checked across open and archived tasks, preserving the existing uniqueness rule without running legacy archive retrofits during everyday work. The everyday front-ends — `task_create`, `task_check`, `task_implement`, `task_audit`, and `task_finish` — invoke the linter normally, so no legacy archive finding ever surfaces in their output; `task_finish` trusts its own archive write and leaves archive validation to `task_fix` (which heals any field a skipped `task_implement` left unstamped). `task_fix` is the sole skill that passes `--include-archive`: it is where the migration and archived-provenance findings surface and where the git-history retrofit fires, healed in one pass per the retrofit and no-bump rules above. This is also the cross-repo migration path — when the plugin lands in a repo whose backlog predates this work, the everyday skills stay quiet and the first `task_fix` run heals the legacy archive, so migrating the host repo's own backlog is out of scope here.

**Non-goals.** The **linter** enforces no transition order — it validates enum membership and status↔location only, so a task may skip `checked` or `audited`. Accidental *backward* moves are caught at the skill level by the soft, confirmable backward-move guard above, which is distinct from linter-enforced ordering. No field beyond the two named. The `git log` archaeology lives in `lint.py` and fires only on `task_fix`'s `--include-archive` run — no everyday skill invocation triggers it; the only other git use is the user-name chain's first step, `git config user.name`, read by the create/implement writers and as the retrofit's fallback. The current-repo retrofit sweep is implementation out of scope: after the new skills are working and deployed, a separate later session will run the new retrofit path over this repo's existing backlog.
