# Ground CLAUDE.md / AGENTS.md / GEMINI.md as harness standing rules the family follows, and gate restating them at readiness

## Goal

Both kinds of root standing doc are UPPERCASE.md files: the harness rule files the agent harness loads (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md`, carrying authoring and build conventions) and the task-family guardrail docs the family consults through its own presence-gated reads (`CHARTER.md` / `ARCHITECTURE.md` / `FEATURES.md` / `TESTING.md`). The family's file-grounded standing-doc machinery — `<standing_doc_consumption>` — builds its model over only the second set; the harness rule files appear in the family solely as `<discover>` root markers, never named as standing instructions to follow. Two consequences follow, both observed in a project whose root carries `CLAUDE.md` / `AGENTS.md` but none of the family guardrail docs: the create path copies repo rules into task bodies again instead of following them, and the readiness gate passes the result clean.

This task closes both at the general-behavior altitude, not as a point-fix for one task file. It delivers two coupled changes to the base `task` skill, which the front-end siblings inherit:

- **Ground and baseline.** Name `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` as the concrete referents of "the project's standing instructions" at the base skill's definition sites, recognized as harness-loaded root standing docs alongside the family guardrail docs rather than mere root markers, and state that this harness-rule baseline is followed at every touchpoint whenever present, independent of whether any family guardrail doc exists. The guardrail docs are an additive layer the family consults on top of that baseline, never a replacement — so the standing-doc machinery cannot be read as "no guardrail doc present, therefore no standing rules to follow."
- **Readiness gate.** Add a *restated standing rules* content-lens item to the shared `<readiness_checklist>` so the readiness gate (`task_check`, and `task_create`'s own pre-write self-check) catches a body that copies a baseline rule instead of citing it.

The motivating episode — repo rules copied into tasks again, `task_check` not catching them — rides along as the illustration; the deliverable is the general standing-rule model and its readiness gate.

## Context

The cite-don't-restate corollary already exists in the base skill's `<body>`: "content a standing project instruction already mandates is cited from the task, with the rule's text staying in its source document." It is worded abstractly and names no file. This corollary, and the history that motivated it — repo rules copied into bodies until mass-stripped — were established by [the self-sufficiency-concept task](archive/task-skill_self-sufficiency-concept.md); the recurrence this task addresses is that same failure returning.

The standing-doc framework being extended — the `<standing_doc_consumption>` presence-gate model, the graduated drift-prevention spectrum in `<family>`, and the author-once-in-base-skill approach — was built by [the optional-standing-doc-conventions task](archive/task-family_optional-standing-doc-conventions.md). Read it before extending the model: the harness-rule baseline this task adds is a recognized category beside that framework's guardrail docs, not a rewrite of it. The harness rule files need no presence-gated `test -f` read of their own — the harness already loads them — so the work is to place them in the standing-instruction *model* and the gate, not to add a read mechanism.

Current state, by anchor:

- The base `<body>` corollary and `task_create`'s gather step say "the project's standing instructions" with no file anchor. Only `task_check` (its bar prose, "flagging the absence of content a standing instruction already owns is a false positive") and `task_fix` (its *restated standing rules* assess check) ground the phrase onto `CLAUDE.md` / `AGENTS.md`.
- `<standing_doc_consumption>` builds its presence-gate model over the family guardrail docs and is silent on the harness rule files; `<architecture>` likewise lists only `CHARTER.md` / `ARCHITECTURE.md` / `FEATURES.md` / `TESTING.md` as its root UPPERCASE.md examples, and `<discover>` lists `CLAUDE.md` / `AGENTS.md` only among root-detection markers — so nothing in the family names the harness rule files as standing docs to follow.
- The shared `<readiness_checklist>` content lens has no item for a body that restates a standing rule. `task_check` assesses purely by reference to that checklist, so it cannot catch the restatement; its bar prose guards only the opposite direction (do not demand restatement). The asymmetry is the bug: `task_fix`'s *restated standing rules* advisory already detects and proposes the fix for copied rules over the whole tree, but the per-task readiness gate that runs before implementation does not.
- `CHARTER.md`'s Key Invariants rank the charter above the softer family guardrail docs (`ARCHITECTURE.md` / `FEATURES.md` / `TESTING.md`) but likewise never mention the harness rule files — the same omission this task fixes in the skill. A separate charter invariant ("Skill-family rules live in the family base skill … front-end skills inherit") is the authority for landing this once in the base skill.

This task pairs with [the title/description coverage task](task-skill_title-body-coverage-check.md): both add one content-lens item to the same shared `<readiness_checklist>`, and that task settles the pattern this one follows — a shared-checklist item that `task_check` inherits by reference with no separate copy, model-applied rather than added to `lint.py`. Reconcile the two items as co-edits of the same block.

## Approach

Land every change in the base `task` skill's `SKILL.md`; let `task_create` and `task_check` inherit through their existing `<authority>` / assess-by-reference design, adding no divergent copy to either.

**1. Ground the abstract phrase.** Rewrite the `<body>` cite-don't-restate corollary in place so it names the harness rule files as the concrete referents — "a standing project instruction (`CLAUDE.md` / `AGENTS.md` / `GEMINI.md` and equivalents)" — keeping one canonical statement of the corollary rather than adding a second. Carry the same concrete anchor into the `<role>` / `<single_shot_ready>` mentions of "standing instructions" only where the prose would otherwise read as silent on what the phrase points at; point the rest at the grounded statement per **State once**.

**2. Recognize the harness baseline in the model.** Extend `<standing_doc_consumption>` (and the `<architecture>` root-docs framing it builds on) to place the harness rule files in the model explicitly: `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` are harness-loaded root standing docs — the baseline of the project's standing instructions, followed at every task-family touchpoint whenever present and independent of any family guardrail doc — while the guardrail docs (`CHARTER.md` / `ARCHITECTURE.md` / `FEATURES.md` / `TESTING.md`) are the additive layer the family consults on top of that baseline, not a replacement. Make explicit that both kinds are root UPPERCASE.md files distinguished by role — harness-loaded rule files versus family-consulted guardrail docs — rather than by name. State the precedence decided: `CHARTER.md` is the highest-order guardrail (already its own invariant) and overrides the rest; the harness baseline governs wherever the guardrail docs are silent; a genuine conflict between a harness rule and a softer guardrail doc is surfaced for human review rather than auto-resolved, matching the family's surface-don't-auto-resolve pattern. Reflect the baseline in the `<family>` drift-prevention spectrum so it is discoverable beside the guardrail tiers.

**3. Add the readiness gate.** Add one content-lens item — *Restated standing rules* — to the shared `<readiness_checklist>`: flag a body passage that instructs the implementer with a copy of a rule the baseline standing instructions already own, framing the fix as replacing the copy with a citation (or dropping it when the surrounding text carries nothing else), and pointing at the `<body>` corollary as the rule source. Keep it distinct from **Over-specification** (which narrows an implementation choice) and from the **Acceptance** contract's task-specific-gates clause (a generic project-gate item is such a restatement; a task-specific executable check is not), pointing at those rather than restating them per **State once**. Mirror `task_fix`'s existing *restated standing rules* check so the readiness gate and the tree sweep share one grounded rule source. Leave `task_check`'s existing false-positive guard intact: do-not-demand-restatement and do-not-allow-restatement are distinct directions and both belong.

Non-goals: making any standing doc mandatory; adding a presence-gated `test -f` read of the harness rule files (the harness already loads them); adding a mechanical `lint.py` rule for the restatement check (the judgment is semantic and lives in the checklist lens); changing `discover_tasks.sh`; editing `task_fix`'s check beyond confirming it cites the same grounded corollary; and re-ranking the softer guardrail docs among themselves. This edits shipped skill content under `plugins/ai_dev/`, so the standing plugin-version-bump and validation gates apply at commit time.

## Acceptance

- The base `<body>` corollary is rewritten in place to name `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` and equivalents as the concrete referents of "a standing project instruction," and a grep finds one such grounded corollary, not a second competing copy of the cite-don't-restate rule.
- `<standing_doc_consumption>` (with the `<architecture>` root-docs framing) recognizes the harness rule files as harness-loaded root standing docs that form the baseline followed at every touchpoint whenever present and independent of any family guardrail doc, names the guardrail docs as the additive family-consulted layer over that baseline, and makes explicit that both kinds are root UPPERCASE.md files distinguished by role rather than by name.
- The recognized precedence is stated and decided: charter highest and overriding; the harness baseline governing wherever the guardrail docs are silent; a harness-versus-softer-guardrail conflict surfaced for human review. The `<family>` spectrum reflects the baseline tier.
- The shared `<readiness_checklist>` carries a new *Restated standing rules* content-lens item that points at the `<body>` corollary as its rule source and reads as distinct from **Over-specification** and the task-specific-gates acceptance clause, pointing at them rather than restating them; grepping the checklist finds it.
- `task_check` and `task_create` gain no separate copy of either the grounding or the new item; a grep confirms `task_check` still assesses by reference to the base `<readiness_checklist>` and `task_create` self-checks against it.
- On a staged fixture project whose root holds only `CLAUDE.md` (carrying a named convention, e.g. a toolchain or versioning rule) and `AGENTS.md`, with `tasks/` and none of the family guardrail docs: a `task_create` request whose natural implementation touches that convention produces a body that cites the rule rather than copying its text, and the create-time self-check does not pass a planted draft that copies it.
- On the same fixture, `task_check` over a planted task whose body copies a `CLAUDE.md` rule verbatim raises the *Restated standing rules* finding and withholds `ready`; over a control task that correctly cites the same rule it raises no restated-rule finding, preserving the existing don't-demand-restatement guard (no false positive).
- `task_fix`'s existing *restated standing rules* check and the new readiness item cite the same grounded `<body>` corollary as their rule source; a grep confirms the two name one shared rule source rather than divergent definitions.
