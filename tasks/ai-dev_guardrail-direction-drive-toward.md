# Declared direction is a target the code drives toward, not a build ledger

## Goal

The guardrail family gains a third enforcement register beside guarding and describing: **declared direction**. A `## Direction` statement in `ARCHITECTURE.md` names a target shape the project is deliberately steered toward, and it holds as a standing commitment whether or not the code has reached it — code short of the target is unmet work the next task drives toward, exactly as a guarding rule's shortfall is unmet work, not a doc to soften. The user-visible outcome is twofold. First, `references/architecture.md` stops permitting a `## Direction` section to read as a progress ledger ("the write side shipped", "two thirds of the read side has now shipped", "what remains is…"): the section states the target, and built-versus-intended is told apart at the section boundary rather than by per-item shipped markers. Second, `guardrail_audit` stops treating an unreached direction target as a describing falsehood: it neither flags a `## Direction` component the code has not built yet as a "names a technology the code does not use" finding, nor offers to soften or delete the target to match today's code, and instead reads it as drive-toward work.

This closes the gap the predecessor [guardrail-target-state task](archive/ai-dev_guardrail-target-state-and-audit-findings.md) left open. That work made *rules* normative and, in the same pass, scoped `references/architecture.md`'s direction rules as binding *descriptive* content — leaving `## Direction` sitting inside the describing register with no drive-toward pull of its own. A real `ARCHITECTURE.md` `## Direction` section that labeled each item as shipped or remaining satisfied "built and intended told apart" yet degenerated into exactly the ledger this family should forbid, and an audit run over it would offer to bring the doc "back to the code" by deleting the not-yet-built target. Direction needs its own register.

## Context

- The family lives at `plugins/ai_dev/skills/guardrail/SKILL.md` with its four bundled `references/`, and `plugins/ai_dev/skills/guardrail_audit/SKILL.md`. The standing repo rule on authoring a family rule once in the base skill applies: the shared register lands in the hub or its references, and the audit sibling cites it through its `<authority>` block rather than carrying a copy.
- The hub's `<role>` preamble carries the rules-are-normative spine — "A guardrail doc carries rules, and a rule holds whether or not the code satisfies it yet" and the three paths by which a rule becomes true, touch-it-and-fix-it among them. It says nothing about direction being pulled toward in the same way; "A guardrail bounds work; it never freezes it" is the nearest line and is about the docs evolving, not about the code being steered toward a target.
- The hub's `<hierarchy>` enforcement spectrum has exactly two registers below the charter's hard fence: **Verified rule** and **Descriptive context**. Its "**Descriptive context.**" bullet covers `ARCHITECTURE.md` and `FEATURES.md` whole, so a `## Direction` target falls under "their guard value is truthfulness" and "a passage that no longer matches the project … misleads every future agent" — which reads an unbuilt target as a truthfulness defect. There is no register that says a declared target is a commitment the code moves toward.
- The hub's `<format_contract>` bullet "**Falsifiable where it guards, truthful where it describes.**" draws the guard/describe line and folds direction into the describing half: "an account of the system's shape may still label an intended component or a migration underway as direction." That keeps direction inside describing, where truthfulness is measured against the current tree — the framing this task splits out.
- The hub's `<consumption>` guard behaviours end with "**Bring touched code to the rule.**", the operational form of touch-it-and-fix-it for rules. No behaviour states the direction counterpart: that work shaped in a doc's domain moves toward the declared direction, and work that would move away from it is surfaced before it is built. The user's framing is exactly this — an agent drives development toward the architecture with each task filled, shaped, or implemented, so the design does not silently degenerate.
- `references/architecture.md` carries the rules "**Present and direction, told apart.**" and "**Refreshed as the project evolves.**", plus an optional `## Direction` template section. The predecessor task set both to bind descriptive content. "Present and direction, told apart" requires built and intended to be "clearly told apart" and keeps `## Direction` "legitimate for intended structure" — but permits telling them apart by per-item shipped/remaining markers, which is the ledger form. "Refreshed as the project evolves" states "landed direction moves from intended to built" as a close-out duty, which is precisely the bookkeeping that turns `## Direction` into a progress tracker.
- `guardrail_audit`'s `<finding_classes>` second class, "**A descriptive statement naming a technology, component, or convention the code does not use.**", already carves out rules: "a rule the code has not reached draws no such finding." Direction has no such carve-out, so a `## Direction` target naming an unbuilt component trips this describing-half finding. Its `<normative_reading>` and `<workflow>` "Doc-vs-code" step present both reconcile directions for a descriptive statement, one of which is bringing the doc back to the code — applied to direction, that is deleting the target. Its `<output_contract>` closing question offers which-direction for descriptive findings.
- The local `tests/guardrail_audit` harness grades five behavioral scenarios (`presence_gate`, `doc_vs_doc`, `doc_vs_code`, `missing_testing`, `nature_mismatch`) through `evals/evals.json` (`expected_output` per scenario), `evals/grade.sh` (a per-scenario branch), and `evals/fixtures/<id>/setup.sh`. None exercises an unreached `## Direction` target. The predecessor task named "a new descriptive-both-directions harness scenario" as out of scope; the direction scenario is the deferred follow-up, not a duplicate.
- The `tests/guardrail_audit/script_tests/run.sh` mechanical checks pin the `guardrail_audit` frontmatter `version`, the `ai_dev` plugin `version` in both `plugins/ai_dev/.claude-plugin/plugin.json` and `plugins/ai_dev/.codex-plugin/plugin.json`, and the marketplace `version` in both `.agents/plugins/marketplace.json` and `.claude-plugin/marketplace.json`. Editing these skills ships new versions, so every pin that tracks an edited artifact moves with the bump, the same way the predecessor task moved them.

## Approach

Add the declared-direction register to the hub and its architecture reference, teach `guardrail_audit` to read a direction target with that register, and prove the audit behaviour with one new harness scenario. Rewrite each affected passage in place so one statement of each rule remains.

**1. Hub: name the register.** In `plugins/ai_dev/skills/guardrail/SKILL.md`:

- Extend the `<hierarchy>` enforcement spectrum with a third register beside **Verified rule** and **Descriptive context**: a **declared direction** statement (the `## Direction` section of `ARCHITECTURE.md`) names a target the project is steered toward, and code short of that target is unmet work the next change drives toward, not a truthfulness defect. Rewrite the "**Descriptive context.**" bullet in place so its truthfulness measure applies to present-tense description, and a declared target is handed to the new register rather than read as a stale description.
- Rewrite the `<format_contract>` bullet "**Falsifiable where it guards, truthful where it describes.**" in place so it names three registers: a guarding rule (falsifiable against a change, code short of it is unmet work), a describing statement (factual, true to the current tree), and a declared direction (a target the code is driven toward, stated as direction, not softened to match the current tree and carrying no per-item shipped/remaining ledger).
- Add a fourth-analogue `<consumption>` guard behaviour beside "**Bring touched code to the rule.**": work shaped in a doc's domain moves the design toward the declared direction, and work that would move the design away from a declared direction is surfaced before it is built rather than silently redefining the target. State its relationship to the touch-it-and-fix-it behaviour: that one moves code up to a rule, this one steers work toward a target.

**2. Architecture reference: forbid the ledger.** In `plugins/ai_dev/skills/guardrail/references/architecture.md`:

- Rewrite "**Present and direction, told apart.**" in place so the `## Direction` section states the target shape as a standing commitment, built and intended are told apart at the section boundary — the descriptive sections carry what stands, `## Direction` carries the target — and per-item build-status narration inside `## Direction` (shipped, landed, remains, "N of M done", "the write side shipped") is named as the drift this rule prevents.
- Rewrite "**Refreshed as the project evolves.**" in place so a reached direction is absorbed into `## Components` or `## Design Decisions` as what now stands, while the `## Direction` statement is refreshed when the target itself changes, not when a piece of it ships. Refresh tracks design change, not build progress.
- Update the optional `## Direction` template-section note so it states the section carries the target, not its completion state.

**3. Audit: read direction with the register.** In `plugins/ai_dev/skills/guardrail_audit/SKILL.md`:

- Add a direction carve-out to the `<finding_classes>` second class, mirroring the existing rule carve-out: a `## Direction` target the code has not reached draws no "names a technology the code does not use" finding.
- Extend `<normative_reading>` and the `<workflow>` "Doc-vs-code" step so a declared direction target short of the code is reported as drive-toward work (how to move the code toward the target, or revise the target deliberately), with the both-directions presentation kept only for present-tense descriptive statements. Softening or deleting the target to match today's code is not offered.
- Rewrite the `<output_contract>` closing question in place so a direction finding asks how to move the code toward the target or revise the target deliberately, never offering to soften the target to the code.

**4. Harness: prove it.** Add one `direction_target` scenario to `tests/guardrail_audit`: a fixture (`evals/fixtures/direction_target/setup.sh`) whose `ARCHITECTURE.md` `## Direction` names a component the fixture code has not built, a matching `evals/evals.json` entry whose `expected_output` requires the audit to leave that target unflagged as a describing falsehood and to offer no doc-softening, and the `evals/grade.sh` branch that grades it. Move every `script_tests/run.sh` version pin that tracks an edited artifact to the versions this change ships, and bump the two edited skill versions and the `ai_dev` plugin and marketplace versions per the repo's versioning convention.

**Out of scope:**

- Editing the guardrail docs of any repository, including the `ARCHITECTURE.md` this task's motivating episode already fixed in the aurora repo. The family states the register; each repository's own adoption carries the change.
- Reworking the rules-are-normative spine, the three finding classes, or the guard/describe treatment the [guardrail-target-state task](archive/ai-dev_guardrail-target-state-and-audit-findings.md) shipped; this task adds the direction register beside them and leaves that work intact.
- A new guardrail doc type, or any change to the four recognized types and their peers.
- Giving `guardrail_audit` a write path or an auto-repair mode; it stays read-only and ends by asking how to proceed.
- Widening the audit's `<audit_bound>` beyond obvious, high-confidence findings.
